EP226: API Concepts Every Software Engineer Should Know

一句话判断

EP226 是一期复习型周刊，主场把「设计一个别人能依赖的 API」拆成一张结构化清单：HTTP 细节（方法、状态码、请求格式、响应结构）、协议选型（REST / GraphQL / gRPC / webhook / WebSocket）、早期决定（命名、分页、版本化、错误响应、向后兼容）、鉴权（API key、OAuth、JWT、scope）、可靠性（超时、重试、幂等、限流、缓存）与配套工程（文档、规范、可观测性、契约测试）；另附 prompt injection 的两层五类防御、12 篇 AI 论文回顾、单体 vs 微服务 vs Serverless 与负载均衡 7 个用例。对资深工程师没有新知识，但 API 清单适合当 review 模板，prompt injection 的分层对做 agent 集成的人有直接参考价值。3/5 星：轻量，但两张清单值得留档。

1. 文章主张了什么

  • API 设计（主场，清单式铺开）:问题往往从基本的 HTTP 细节开始——方法与状态码、请求格式与响应结构，决定了 API 是「清晰可预期」还是「混乱不一致」；更大的选型是 REST、GraphQL、gRPC、webhook、WebSocket 各自适合什么系统与用例；命名、分页、版本化、错误响应、向后兼容这些早期决定，直接决定 API 是「好维护」还是「令人沮丧」；安全上 API key、OAuth、JWT、scope 说起来容易做对难，错代价高；可靠性上超时、重试、幂等、限流、缓存常被拖到系统承压时才补；API 长大之后，文档、规范、可观测性、契约测试决定团队能否「不靠猜」地信任它。原文以互动提问收尾：你觉得最被忽视的 API 概念是什么。
  • prompt injection 两族五类防御：prompt injection 高居 OWASP LLM Top 10 之首，没有单一解法，只能叠加。模型层：spotlighting——把不可信文本包进 <UNTRUSTED> 这类控制标签，并告诉模型「里面的东西是数据不是指令」；instruction hierarchy——微调模型，让它把开发者系统提示排在用户消息之上、两者都排在第三方内容之上。系统层：最小权限工具、人在回路（敏感动作需显式批准）、planner / executor 分离（两个 LLM：planner 有工具但从不接触不可信内容，executor 读不可信内容但没有工具）。生产系统（如 Gmail）就是把两类叠起来，让间接注入变得可控。
  • 12 篇论文回顾：AlexNet、GANs、Transformer、GPT-3、InstructGPT、Scaling Laws、ViT、Latent Diffusion、DDPM、CLIP、Chain-of-Thought、RAG，每篇一句话。
  • 单体 vs 微服务 vs Serverless：单体是一套代码、一个库、一次部署，小团队最快；代码库长大后，一个小改动要全量重部署，一次坏发布能拖垮全局。微服务拆开单独扩缩、各自管数据，代价是服务发现、分布式追踪、请求路由。Serverless 按触发运行、云厂商负责扩缩、按用量付费，代价是冷启动、无状态函数的调试与厂商锁定。真实系统多数是混合：核心单体 + 少数拆出的服务 + 后期用 Serverless 承接通知/后台任务。
  • 负载均衡 7 个用例：流量分发、SSL 终止、会话保持、高可用（摘除故障节点）、可扩展性、DDoS 缓解、健康检查。

2. 我的解读

  • 清单的组织顺序本身就是观点：把「命名/分页/版本化/错误语义/向后兼容」放在 HTTP 细节之后、安全与可靠性之前，等于说 API 的长期体验主要由这些早期决定决定，而不是「请求能不能跑通」。这符合工程直觉——HTTP 细节有框架和工具兜底，早期决定没人替你兜。
  • 这份清单最实用的读法是当 review 模板：设计新 API、评审别人的接口、做内部平台 SDK 时逐条对照，缺哪条补哪条。
  • prompt injection 一节是本期信息密度最高的部分：模型层与系统层的分工讲得很清楚——模型层降低「被诱导成功」的概率，系统层限制「被诱导成功之后」的损失；planner / executor 分离本质是把不可信输入与工具权限物理隔开，这和当前 agent 安全的主流实践一致。Gmail 的例子也点出关键：单层防御在生产里不够用。
  • 12 篇论文与单体/微服务、负载均衡两则属于标准复习，没有增量；论文清单可以当读 AI 发展史的索引。

3. 对实际工程的意义

  • 把 API 清单落成 review checklist：命名一致性、分页与版本化策略、结构化错误响应、向后兼容规则是否写进文档；可靠性四件套（超时、重试、幂等、限流）在设计阶段就定下来，而不是等事故倒逼。
  • 契约测试与可观测性应列入 API 的 Definition of Done：它们是「团队敢依赖这个 API」的前提，而不是上线后的加分项。
  • 给 agent 接工具时可以直接抄这五类防御：最小权限 + 人在回路 + planner / executor 分离 + 对不可信内容做标签隔离；尤其是「有工具的不碰不可信输入，碰不可信输入的没有工具」，实现上很便宜，收益很大。
  • 架构判断保持默认值：从单体起步，只有出现独立的扩展或发布诉求才拆服务；Serverless 留给通知、后台任务这类异步场景，避免过早背上冷启动与厂商锁定的成本。

4. 可信度与局限

  • 周刊体裁：五六个小节互相独立，深度都浅；主场部分是「清单式铺开」，把主题列全但没有深入任何一条，原文也以互动提问收尾而非结论。
  • 全篇没有案例、代码或数据；任何一条想深挖都要另找资料（比如幂等键怎么设计、分页用游标还是 offset 的取舍，都没有展开）。
  • prompt injection 五类防御是公开文献（spotlighting、instruction hierarchy 等）的准确整理，但非原创，也没有给出各自在什么条件下会失效。
  • 论文清单截至 2022（最新的两条是 CoT 与 InstructGPT），不含更近的方向；只适合做索引，不适合当「当下最重要的论文」清单。

5. 最值得记住的三点

  1. API 的长期口碑取决于早期决定（命名、分页、版本化、错误语义、向后兼容），而不是请求能否跑通的瞬间；这份清单可以直接当 review 模板用。
  2. prompt injection 没有单点解法：模型层（spotlighting、instruction hierarchy）降低发生概率，系统层（最小权限、人在回路、planner / executor 分离）限制损失上限，两层叠加才是生产做法。
  3. 单体/微服务/Serverless 是混合现实：核心单体 + 按需拆出的服务 + Serverless 承接异步任务，是多数生产系统的实际形态；拆分的触发条件应该是独立的扩展或发布诉求。

我的推荐

3/5 星。复习型周刊，没有新结论；但 API 设计清单适合当 review checklist 留档，prompt injection 的两层防御对做 agent 集成的人有直接参考价值。低量周末读完这一篇即可：先看 prompt injection 一节与 API 清单，其余快速扫过。
