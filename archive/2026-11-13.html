本周最该动手自查的 CI 供应链事件 · ★★★★★ · TLDR InfoSec

wfx-loot：被盗 GitHub 凭证把 CI 密钥窃取脚本推进 6 万个仓库

为什么值得看：文章把攻击者的分支名、PR 标题和提交信息都列成了可直接搜索的字符串，今晚就能在自己仓库里搜一遍；它还讲清了载荷如何在 60 秒内伪造状态检查绕过分支保护，这一点比"密钥被偷"更值得警惕。

展开完整精读

一句话判断：这不是又一篇"供应链投毒"通报，而是一份可以直接照着排查的事故报告——它把攻击者的可搜索特征、载荷的四个阶段和"为什么删日志后你查不出来"都写明白了。

  1. 攻击面比想象的大。攻击者拿着 4,837 个被盗 GitHub 账号，向 61,764 个仓库开了标题为 docs: dependency audit notes 的探测 PR，来源分支统一叫 wfx-docs。其中 10,431 个 PR 落在账号本身并不拥有的仓库里，是靠 collaborator 或组织权限写进去的——也就是说，被入侵的不一定是仓库主人，而是任何一个有写权限的协作者。92% 的探测 PR 到文章发布时仍然开着，说明绝大多数仓库主根本没注意到。

  2. 三个阶段，每一步都在绕过你现有的防护假设。探测 PR 只确认写权限；真正的载荷有三种投递方式：往已有 workflow 里塞约 1,500 行（提交信息 ci: refresh build cache）、在 package.json 加 postinstall 钩子（chore: add ci helper）、或者在一次性分支上新建 workflow（chore: add dependency audit workflow）。三条路都绕过了"我不改 workflow 就安全"的直觉，因为改 workflow 的人看起来有合法写权限。

  3. 最狠的一步是持久化，而不是窃取。脚本在收集任何东西之前，先用仓库自己 required checks 的 context 名字伪造 success 状态——分支保护只匹配 context 名，不校验是哪个 App 发的，所以合并闸门在载荷还在跑的时候就被打开了。接着它把链式角色的信任策略改成 Principal: {"AWS": "*"}，等于把这个角色开放给任何 AWS 账号；再用 Graph token 给 Azure AD 应用加 wfx-ci-… 联合身份凭证，指向被入侵的仓库。后两条的可怕之处在于：你把所有 token 轮换一遍也没用，信任关系已经写进了云侧配置。

  4. 取证上的反直觉结论。脚本收集的不只是 Actions secrets，还有 runner 上所有能找到凭据的文件、shell 历史、运行中进程的内存（优先 Runner.Worker），以及 OpenAI、Anthropic、Gemini、Hugging Face、Cursor、Copilot 这些 AI 工具的 key。它把数据打包后用 HTTP POST 发到两个固定 IP，其余通道（Actions Cache、step summary、artifact、加密提交、Telegram）在本轮被关掉了。关键细节：命中仓库的 run 记录和日志都被删了，所以"没有 wfx-loot artifact、没有 wfx- 缓存、没有 WFX-BEGIN 标记"都不能作为没被偷的证据；一个缺失的 run 编号反而更可靠。作者还提醒，脚本里专门留了私有仓库的配置分支，说明公开仓库之外可能还有看不见的一批。

  5. 该做什么。今晚就能做的三件事：在全组织搜 docs: dependency audit notes 的 PR、搜 wfx-docs 分支和 chore/[a-z0-9]{8} 分支命名；对 11 月 10 日 12:45 UTC 之后跑过 workflow 的仓库，假设其 workflow 可见的所有 secret 与云角色都已泄露；重点不是轮换 token，而是检查 AWS 角色信任策略里有没有 Principal: *、Azure AD 应用里有没有 wfx-ci- 开头的联合身份凭证。文章还指出这批账号与 10 月的 GhostAction 活动高度重叠，但工具链和基础设施不同，判断是不同团伙在复用同一批泄露凭证。

我的推荐：凡是自己维护 CI 的人都该读，并且读完立刻去搜。它给出的不是"要注意供应链安全"这种废话，而是一组能直接粘进 GitHub 搜索框的字符串，和一句真正的教训——分支保护的 context 名可以被伪造，删掉 run 日志比删掉代码更容易。

方法本身比结论更值得读 · ★★★★★ · TLDR AI

从模型权重里读出芯片型号：六个中国前沿模型带着 Blackwell 的指纹

为什么值得看：它没有依赖线人，只用公开权重反推出训练用了哪一代 GPU，并且在真机 H100、B300、GB200 上做了双向验证；49σ 到 1,385σ 的证据强度也把"巧合"这条退路堵死了。

展开完整精读

一句话判断：一篇罕见的、可以自己跑代码验证的硬件取证报告——结论涉及出口管制，但真正稀缺的是它把"权重是证据"这件事讲透了。

  1. 方法的起点很朴素。训练开始前权重要有初始值，PyTorch 用 Philox 这个确定性伪随机算法生成，输入是一个 seed；为了快速填满几十亿个参数，它把生成任务切成很多线程并行跑，每个线程按固定步长在权重数组里落位。线程总数由 GPU 的 SM 数量决定：Hopper 的 H100/H200/H800 是 132 SM、270,336 线程，B200/B300 是 148 SM、303,104 线程，GB200/GB300 是 152 SM、311,296 线程。seed 对了但线程数错了，数字本身对、位置全错——作者用一个 6 SM、8 线程的玩具例子把这件事画得很清楚：从 48 线程换成 40 线程，只有 6% 的数值还在原位。

  2. 训练会冲掉大部分痕迹，但不会冲掉全部。一部分权重（例如训练语料里从未出现的符号对应的行）几乎原封不动，可以直接比对；被训练改过的权重则保留一种弱相关——初值大的，终值仍倾向于大。用几百上千个这样的弱信号做统计检验，就能把 seed 和布局反解出来。作者还做了留出集验证：用一批权重选出组合，再拿另一批没参与搜索的权重去预测，这一步把"拟合出来的假象"排除掉了。

  3. 验证做到了物理层面。DeepSeek 的 seed 是 953049583，V3 和 V4-Flash 都用它。在真机 H100 上用未改动的 PyTorch 能逐位复现 V3 的 57,344 个保留值，复现不了 V4-Flash；在 B300 上反过来，复现了 V4-Flash 的 445 整行，复现不了 V3；seed 加一，两台机器都复现不出任何一行。Kimi K3 在租来的 GB200 上用 seed 20256586 复现了全部 13 行。这一步是整篇文章可信度的来源：不是统计推断，是同一个软件在两种硬件上跑出的两个互斥结果。

  4. 排除了 AMD 这条退路。MI300X 常规是 304 个计算单元，但可以被切成两组 152 或者只用 148 个，随机数软件也能产生同样的底层序列，所以在布局层面它和 Blackwell 不可区分。作者转而在数值细节上找差异：AMD 和 NVIDIA 在生成过程里有一处计算不同，DeepSeek-V4-Flash 的保留值在 377 个有差异的位置上，363 个命中 NVIDIA、0 个命中 AMD。其余五个模型做不了这个测试，但认为 AMD 解释"非常不可能"——需要有人刻意把整集群配成和 Blackwell 一样的单元数。

  5. 文章自己划的边界比结论更值得学。方法只能看到"初始化权重时用的是哪块卡"，不能证明后续训练没换硬件、不能说明芯片在哪、是谁的、是否通过走私获得；混合集群、先用 NVIDIA 初始化再上华为训练，都不会被这套方法发现。闭源模型无法检查；用 PaddlePaddle 初始化的 ERNIE 查不出布局；CPU 初始化的 Qwen 部分模型没有 GPU 指纹；Meituan 的 LongCat-2.0 明确说跑在 ASIC 超节点上，也确实没有 NVIDIA 指纹。附录里还有一条反例支持：NVIDIA 自家 Nemotron-3 Ultra 的技术报告写了 GB200，方法读出 152 SM，一致。

我的推荐：如果你关心"公开权重还能泄露什么"，这是今年最好的案例。代码和保留行都开源了，笔记本上几秒就能跑完一遍。读的时候建议把附录 1 的表格对着看——DeepSeek 跨代复用同一个 seed、Moonshot 用一条规则派生 seed，正是这种工程习惯让跨代追踪成为可能。

把"AI 写的代码变好了吗"这个问题拆成了三层来回答 · ★★★★☆ · TLDR

代码级 slop 在消失，设计级 slop 在长出来

为什么值得看：作者用三个基准分别测行级质量、库设计和库复用，结论是：单行代码确实干净了，但代价转移到了错误处理和抽象设计上，而且每个模型都在 73% 以上的解答里重写了库已有的功能。

展开完整精读

一句话判断：这是一份少见的、用同一套基准跨十几个模型版本追踪"代码质量"的报告，结论不讨喜——模型学会了怎么写干净的单行代码，没学会怎么设计一个能被别人用下去的东西。

  1. 测什么。三个基准各管一层：SlopCodeBench 给 36 道题、196 个 checkpoint，每个 checkpoint 在上一个规格上追加需求，考的是模型维护自己代码的能力；LibraryDesignBench 让被测模型写一个库，再让固定的三个实现者用它解题，用"减少多少代码"给库打分；LibraryUseBench 则给人写好的库和极简提示，看模型会不会去用。滑点（slop）用 137 条 AST-grep 规则按千行命中数计，另有一个"侵蚀度"指标衡量复杂度有多集中在超长函数里。

  2. 好消息是真的。只看 Anthropic 和 OpenAI 两家的时间线：规则总命中率降了 25%，return None, error 元组降 59%，len(x) == 0 降 70%，sys.exit 从 187 次降到 3 次，超 200 行函数从 50 个降到 1 个，最长函数从 1,099 行降到 294 行。进程类错误几乎消失，模型不再忘记 import、不再写空模块、不再硬编码会在后面 checkpoint 崩掉的测试值。这一层确实在进步。

  3. 坏消息是滑点换了楼层。同样的对比表里，type(x) == T 涨了 19 倍，内联的 if not isinstance(x): raise 涨 5 倍，# pragma: no cover 涨 16 倍，宽 except（4 种以上异常，且包含 KeyError/TypeError 这类编程错误）从 8 处涨到 29 处。作者的解释很有说服力：原来那些 except Exception: pass 并没有被修好，只是被换成了更窄的写法——except OSError: return None、手写字段校验梯队。规则过了，行为没变，只是从"规则能抓到"变成了"规则抓不到"。

  4. 最刺眼的一段是 Python 2 借尸还魂。Claude 系列开始在 Python 3.12 的代码里用 % 格式化作为主风格（Opus 5.5 在 20/36 个题目里），class X(object) 出现 126 次，而 Opus 4.6/4.7 分别是 0 和 3。作者也承认这很奇怪，没有给出确定解释——但这提醒一件事：训练数据的分布变化会以这种莫名其妙的方式回流到生成结果里，而这类退化在单元测试里完全看不出来。

  5. "Ugly"那一节是全文最有价值的部分。LibraryUseBench 上，所有模型都会在 73%–100% 的解答里手写库已提供的功能：8/12 个模型自己实现了 SimPy 的调度队列，读完 bs4 的 dammit.py 之后自己重写 find_declared_encoding。LDB 的数字好一些（40% 重写），但作者诚实地指出那是因为提示词极其具体，同样条件下人类写的库只有 17% 被绕过。更微妙的一处：Opus 5.5 和 Fable 写的库有约 30% 复用了生产库的公开命名，GPT-6 SOL 只有 13%——照抄接口、自己写实现。还有一个设计师把自家 HTML 解析库的主类别名成 BeautifulSoup，赌实现者会因为训练语料而伸手去拿这个名字。

我的推荐：读这篇的时候不要只看那张下降的表。真正值得记住的是三个判断：单点质量可以被训练修好，错误处理的习惯没有；模型会绕开规则而不是改正行为；当产物主要被别的 agent 消费时，重写库的代价会复利放大。如果你在给团队定 AI 编码规范，第 2 和第 3 条几乎可以直接写进 review checklist。

今日判断

今日判断：三条主线都指向"AI 已经进入工程与硬件的现实约束"。安全侧，wfx-loot 用一次大规模凭证复用证明 CI 的信任边界比想象中松——分支保护的 context 名可伪造、run 日志可删除，检测要往云侧配置里找；硬件侧，权重指纹把"谁在用受管制的芯片"变成了可复现的技术问题，方法本身（seed 加 SM 布局）也说明公开模型会泄露训练环境；工程侧，slop 基准显示代码级质量在改善，但设计判断和错误处理习惯没有跟上，规则一改就露馅。值得留意的方向是：agent 互相消费产物之后，"重写库已有功能"这类浪费会被放大成系统性问题，而不是单次代码质量问题。
