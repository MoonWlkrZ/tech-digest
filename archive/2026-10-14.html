第一份公开的「AI 代码产量压垮人类尺度基础设施」的完整工程记录，值得逐段细读。 · ★★★★★ · TLDR

Redesigning source control at Anthropic

为什么值得看：Anthropic 用 7 人、5 个月自研版本控制系统 Scion 并完成 monorepo 迁移；文中数字（30k merges/day、镜像体系缩小 200 倍、CI 检出从分钟到秒）与「工程师给 agent 说不」的组织观察都是第一手材料。

展开完整精读

一句话判断：这是第一份公开的「AI 代码产量压垮人类尺度的开发者基础设施」的完整工程记录——Anthropic 用 7 个人、5 个月自研并替换掉了 git。

  1. 先看规模：2026 年 5 月每天约 2,500 次合并，到 9 月已超 30,000 次/天，且增速没有放缓迹象；主分支历史近 100GB，压缩后的工作副本超 25GB，每天约 2,500 万次代码检出（不含开发者环境、agent 沙箱与研究任务）。所有为人类规模设计的工具链——源码控制、构建、CI——成了新瓶颈。

  2. 为什么 git 输了：git 的基本假设是客户端离线、每个克隆都是可独立运算的完整仓库；而 Anthropic 的「客户端」几乎全是常年在线、按需取数的 agent 与 CI 作业。峰值时他们运营着数百个内部 git 镜像，随着合并率上升，seed 刷新赶不上主分支推进、部分克隆上的 diff/blame 越来越难维持。

  3. Scion 的六个设计原则：客户端永远在线（服务端始终可达，按需取数）；客户端-服务端不对称（blame、合并、rebase 全在服务端，客户端只维护有界对象缓存）；源码控制查询全部暴露为 API（自动化 bisect/revert 流水线因此可行，作业不再需要本地仓库）；一切组件水平扩展（没有任何完整副本，也没有 packfile 与仓库维护）；提交廉价、增量、无锁（changeset 是写前日志条目，只记录相对父提交的变更文件与内容寻址的 blob 指针）；工作副本可选、稀疏、按需虚拟化。工程上采用三层缓存（scion-daemon / scion-cache / scion-server），每层命中率 >99%，按区域与故障域严格隔离。

  4. 效果与代价：新基础设施的 CPU/内存占用比旧 git 镜像体系小 200 倍；CI 与研究任务检出从分钟级降到秒级，仅 CI 就收回 25% CPU 容量。迁移期间合并量还涨了 10 倍。一个细节：手写的 git-to-Scion 摄取流水线被 Claude Mythos 重写后，内存少用 20 倍、速度快 4 倍，且保留了所有隐式不变量。

  5. 组织观察：工程师坦承 Claude 写代码比自己强，但他们的价值转向高层组件理解、设计取舍，以及在系统约束上说「不」——agent 常为满足模式而违反约束，或对假想风险过度设防（一次对抗评审让 Claude 加了过多校验）。评审从逐行读码变成看变更意图。运维上每个组件配一个「superfan」Claude 盯日志与 telemetry，能发现传统告警发现不了的细微问题。他们还重新思考了 merge queue：agent 规模下全局锁不再可行，转向 post-merge 与 pre-deploy 测试。

我的推荐：如果你想理解「当写代码不再是瓶颈，瓶颈会出现在哪」，这是目前最好的第一手材料——数字、架构、组织变化都在，且作者坦承 Scion 不打算开源、只分享思路，诚意很足。

Are Harnesses Worth the Cost?

为什么值得看：同一任务、双条件、178 项外部验收测试的对照实验，给出了模型分层的一个具体结论：harness 的价值取决于模型能力，sensors 该不该常开、什么时候开。

展开完整精读

一句话判断：用 20 次配对实验回答「行为 harness 值不值」——结论不是笼统的「值」或「不值」，而是「取决于模型能力：前沿模型上它是纯开销，便宜模型上它是把 3/10 成功率变成 10/10 的关键」。

  1. 实验设计：任务是一个商品发现 BFF 服务（HTTP 语义、超时降级、Kafka 发布、精确错误码），外部评测用 178 项验收测试，开发与评测分离。harness 由 guides（OpenAPI/AsyncAPI 规格、请求响应示例、实现技能）与 sensors（契约检查、API 测试、副作用断言）组成，在开发过程中持续给 agent 反馈；其期望来源独立于实现者。

  2. 前沿模型的结果：GPT-6 Sol 在低推理档位下，有没有 harness 都是 10/10 全过。但 harness 让 token 用量涨到 10.5 倍、时间近 3 倍、成本约 7 倍（平均 $2.679 vs $0.406）。作者原本的预期被直接推翻。

  3. 便宜模型的结果：GPT-6 Luna 裸跑 10 次只成功 3 次（平均 $0.086/次）；加上 harness 后 10/10 全过，平均每次 $0.273。harness 平均多加 1,700 万 token 与 19 分钟自主运行时间，但即便如此，harnessed Luna 每次仍比裸跑 Sol 便宜约 33%，可靠性持平。

  4. 失败点分析：裸跑的失败不是语法错误或误解需求——每个失败应用都至少通过 144/178 项检查，卡在协议边界与集成缝上：超时后该回 202 却回了 503/400/429、缺 monitor link、Kafka 消息带 Spring 的 TypeId 头或 categories 为 null、该 400 的回了 415、配置变量名 ORDER_API_KEY 与 ORDER_API_API_KEY 对不上。作者把这叫「注意力滑落」：需求写清楚了，但在实现中失去了影响力；harness 是「可执行的注意力」，sensor 一红就把丢掉的细节拉回焦点。

  5. 边界条件：单服务、greenfield、每个模型 10 次配对、brief 异常详细——样本不足以断言长期可靠性；guides 与 sensors 的贡献没有分离；harness 的前期编写与维护成本没有计入。作者下一步要测「只在最终 gate 跑一次」的前沿模型条件与更模糊的 brief。

我的推荐：如果你在给团队制定模型分层策略，这是少有的「有数字、有对照、有失败案例拆解」的一手实验。它把「什么时候该给 agent 加验证反馈」从直觉变成了可以按模型能力分档的工程决策。

Uber 的 AI 开发工具不是一年长出来的，是十年平台工程加一个 Model Gateway 决策的复利——Distinguished Engineer 复盘 11 条内部实践。 · ★★★★☆ · The Pragmatic Engineer

Uber's AI infra, from the inside

为什么值得看：与 Gergely Orosz 对谈的 Uber 工具链全景：Model Gateway、AIFX、Code Review、CI 的 code red 与 PR 分类法，都是可对照的组织级实践。

展开完整精读

一句话判断：Uber 的 AI 开发工具看似一年建成，实际是十年平台工程的复利——Distinguished Engineer Uday Kiran Medisetty 复盘了内部工具链如何承接 agent 时代。

  1. 先有平台，后有 agent：DevPods（2017）承载了 2025 年的 Minion；MCP Gateway 借已有的 Thrift/Protobuf 注册表快速建成；Jaeger 让 Slate 路由与 context graph 变简单。Uday 的原话：「为工程师做的工具，对 agent 同样有效」。历史包袱也有价值——服务数从 2015 年的 2 个涨到 2019 年的数千个，2026 年大致回到 2019 数量级而业务规模是 10 倍；M3DB、Cadence、Morpheus 都是因为市面没有而自建。

  2. 关键决策是 2023 年的 Model Gateway：所有 AI 功能模型与 harness 无关，一个网关支持在 Anthropic、OpenAI、自托管开源模型间切换，并扩展出 AI Guard（安全中间件，检查请求/响应与延迟）、按用户计费追踪、审计日志与 session trace。

  3. 多 harness 共存：Uber 同时支持 Claude Code、Codex、OpenCode；AIFX 是上面的一层包装，工程师换 harness 时设置、skills、插件随人走。花费采用分级制：超出额度需经理签字，但对合理工作不设上限；CostCheck 插件跨会话给成本建议。

  4. 评审与 CI：所有 PR 仍由人评审，但先跑 AI 评审、加功能录屏与风险分，帮人决定这份变更要花多少时间。CI 今年早些时候宣布过 code red——作业量 12 个月翻倍——应对方式是把 lint、build 这类简单作业移到 inner loop，让 agent 用 afx validate 在开 PR 前跑掉。度量上不再看「PR 速度」，而是给 PR 打类型标签（feature/bugfix/maintenance/testing/docs），观察到 feature 占比升、maintenance 占比降。

  5. 角色变化：Uday 说工程师的工作是「为 agent 构建正确的 context」，context engineering、多任务并行、验证输出成为核心技能——因为可并行的东西多了，把关的人和方式也要变。

我的推荐：如果你想对照「别人家的内部平台怎么演进到 agent 时代」，这份对谈的 11 条 takeaway 几乎是提纲式的清单；尤其适合关注模型网关、多 harness 并存与 CI 承压的团队。
