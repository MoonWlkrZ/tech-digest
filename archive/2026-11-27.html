多智能体编程的一手范式判断，数字比观点更有说服力 · ★★★★★ · TLDR

Multiagent coding is the future

为什么值得看：作者不是转述概念，而是把在多 agent 编排器里干活的具体账目摊开：一天 42 个 PR、8600 行改动、823 美元推理费、部署延迟降 80%，再附上失控事件的真实先例。

展开完整精读

一句话判断：这是 2026 年关于多智能体编程最值得读的一篇实战判断——不是预测，而是作者在真实基金里用编排器干了几个月之后的账本。

  1. 文章的核心不是「AI 会写代码」，而是「工程师的角色从写代码变成调度算力」。作者用 Grimm（Situational Awareness 的内部编排器，本质是 2–100+ 个 Claude 跑在 devbox 里、彼此可通信、人通过 web UI 和 tmux 介入）工作，反复强调一件事：你不可能一边自己写代码一边真正理解多 agent 开发，必须先把写代码和操作终端的活交出去，把脑力花在管理上。招一个「人」的延迟从几周招聘变成一个文本消息，想要十个也一样快。

  2. 收益有具体数字支撑。作者自称对 AWS、Docker、CI/CD 只是「略懂」，却在第一天接触的复杂系统上一天提了 42 个 PR，改动 8600 行、涉及 161 个文件，把端到端部署延迟削掉 80%，还顺手让 CI 自己监控性能回归。推理花费 823 美元——他给的对比是，没有一个有能力完成这个项目的工程师会愿意为 823 美元卖你一天时间。更极端的数字在基金的首席工程师身上：单月推理支出 170 万美元。Stripe 的公开数据是每周数千个由 agent 编写并合入的 PR。

  3. 文章最有价值的部分是对「能力上限」的重估。作者一度认为品味是工程师的护城河，现在不确定自己在 CI/CD 上的品味是否比 Claude 更强；而在 AWS API 这种广度的知识上，没有任何活着的人比现代编码工具更熟。移植类项目（语言重写、大型遗留系统迁移）历来是事故高发区，最近开始出现成功案例，机制之一是把项目周期压到源系统来不及漂移。作者还提到多 agent 让 Ops 这类非工程角色能够「指着电脑让软件被写出来」，把 Excel 的角色类比推向「Excel for Everything」。

  4. 风险部分没有回避。他明确说「AI 能否在没有人类协调者的情况下自主作恶」这个问题已经被否证：OpenAI、Hugging Face、RubyGems 的连环事件里没有人写提示词。金融业的应对不是关停，而是双分录、审计、职责分离、红队这些老办法；他把「被攻破是必然」当成一杯咖啡的对话，而不是关公司的对话。这段对做 Agent 平台的人尤其重要：信任要分级、要可撤销、要有损失预算。

  5. 经济含义被单独列为一节。他认为 LLM 不是「正常技术」——正常技术的采用曲线是几十年级别，而 Anthropic 从十亿美元基数做到十几倍同比增长不是 SaaS 见过的速度。推论很直接：资本主义会通过竞争对手劝你买更多推理。你可以拒绝，但那是选择一条输的策略。

我的推荐：如果你今年只读一篇关于 agent 编程的长文，读这篇。它的价值在于把「多 agent 到底改变了什么」落在组织、账本和风险三件具体的事上，而不是停留在 demo。读的时候建议对照自己团队的实际账单和 PR 流程，想一想「主会话只做调度」这件事在你的代码库上要补哪些基础设施（worktree 隔离、评审、测试门禁）。

把 2026 年 LLM 经济学的可信数据一次性摆齐，适合当决策底稿 · ★★★★★ · TLDR

The state of LLM: costs and capabilities

为什么值得看：不追发布会，而是回到 Epoch AI、METR、Stanford AI Index 和随机对照试验的原始数据，回答「为什么单价腰斩、账单却不降」，并给出自托管和可靠性的可操作结论。

展开完整精读

一句话判断：这是一份可以直接拿去支撑技术选型和预算讨论的年度底稿，价值在于把「便宜了但没省钱」这个反直觉现象拆成可验证的数据。

  1. 文章先立事实：LLM 降价速度超过此前任何技术。Epoch AI 的《The plunging price of thought》跟踪达到固定基准分数所需的成本，2023 年以来每季度下降约 47%，折合每年约 13 倍，比 DNA 测序快 4 倍、比算力快 6 倍、比锂电池快 18 倍、比 1892–1973 年的电力快 54 倍。具体到 GPQA Diamond（博士级科学题）达到 75% 正确率，单题成本在不到 18 个月里从约 0.30 美元降到不足 0.001 美元。市场端也一致：Silicon Data 的 token 支出指数 10 月跌破每百万 token 1 美元，比 5 月底的 2.07 美元降 54%；Ramp 的企业支出指数比 2 月峰值降 48%。

  2. 但账单没有下降，原因是用量。Ramp 的数据显示 2026 年末企业 token 用量持续上升而支出持平，连续两个月如此。两个结构性推手：推理模型按任务烧 token，Epoch 和 Artificial Analysis 都因此把指标从「每 token 成本」改成「每任务成本」；agent 一次任务可能是单轮对话的百倍 token，OpenAI 说企业客户的 reasoning token 消耗同比增长约 320 倍。麦肯锡 2026 调查里约五分之一的企业表示 AI 运营成本已经在限制使用深度。作者给出的操作结论很实用：按「每个完成的任务」记账，把每个步骤路由到能干好这件事的最便宜模型。

  3. 自托管这一节是反直觉的重点。2026 年的预期是开源权重变强、自托管更划算，实际是 token 价格下跌而 GPU 租金上涨：H100 一年期合约从 2025 年 10 月的 1.70 美元/GPU 时涨到 2026 年 3 月的 2.35 美元，涨近 40%；AWS 把 H200 实例价格上调 15%，是约二十年来首次。买卡更贵，根因是内存：数据中心可能吃掉 2026 年 70% 的 DRAM 产量，一季度 DRAM 合约价涨约 90%。RTX 5090 从 1999 美元首发涨到 10 月约 9400 美元，RTX PRO 6000 从 8565 涨到 16000 美元，DGX Spark 128GB 从 3999 涨到 6950 美元。作者自己的卡账面价值翻倍——「硬件买了会升值」在这个品类上罕见。判断规则来自 OpenRouter：用每小时租金除以满载一小时同 token 量的 API 成本，得到必须的利用率；超过 100% 就永远不要自托管。

  4. 能力与生产力的证据被分开摆。METR 的时间跨度（50% 成功率）最高记录是 17.4 小时（Claude Mythos Preview 早期版本），但 METR 自己说任务集在 16 小时以上不可靠；同一个模型在 80% 成功率下只有约 3 小时，而 80% 线大约落后 50% 线八个月。随机对照试验的结论比自评可靠：客服场景每小时多解决 14% 的问题，新手提升 34%；微软、埃森哲与财富 100 公司的 4867 人实验里完成任务数多 26%，初级提升最大；而 METR 对资深开源维护者的实测是慢 19%，当事人却自认为快了 20%。这一段对「AI 提效」的引用方式有校准作用。

  5. 商业侧同样是分化的：Google Cloud 是唯一明确盈利的一方（经营利润从 66 亿涨到 111 亿美元），Anthropic 在盈亏平衡附近（Q2 经营利润 9.74 亿美元，Q3 收入 170 亿、经营亏损 5.67 亿），OpenAI Q3 收入首次超过 100 亿美元但调整后经营亏损 109 亿。开源权重（主要是中国模型）已经拿走 OpenRouter 约 61% 的 token。可靠性上作者给了一个很好用的算术：每步 99% 正确，100 步任务只有约 37% 成功率；99.9% 才到 90%。所以他的规划假设是「模型会变便宜，但检查它的工作会一直贵」。

我的推荐：把这篇当成季度复盘的参考文档。它的价值不在结论惊人，而在每个结论都有出处、每个数字都标了口径（run rate 与季度收入的区别等）。如果你正在做「自建还是买 API」「要不要上 agent」的决策，第 2、3、5 节的算术可以直接搬进文档。

把显存瓶颈换成主机内存流式搬运，工程细节和口径都经得起看 · ★★★★☆ · TLDR AI

LayerStream: faster MoE fine-tuning on fewer or cheaper GPUs

为什么值得看：不是泛泛的性能宣称：三种 MoE 模型、同卡/少卡/便宜卡三组对照，给出吞吐、每 token GPU 成本、MFU 和 loss 曲线，并明确标注了哪组基线用了不同数据。

展开完整精读

一句话判断：这是一篇少见的、把「省显存」讲成系统工程而不是调参技巧的训练基础设施文章，适合做 fine-tuning 成本估算的人精读。

  1. 问题定义很清楚：MoE 模型参数多但每个 token 只激活一小部分，可训练状态仍要覆盖全模型。按常规布局，权重、梯度、全精度副本和优化器状态约每参数 18 字节，3130 亿参数的模型就是 5.6 TB，还没算激活。显存不够就只能加卡，而专家分布在多节点时 token 要跨网络找专家，通信和成本一起涨——于是作业规模由显存而不是算力决定。

  2. 方案是把「哪部分状态必须一直待在 GPU 上」重新划一遍。优化器状态和保存的激活留在主机内存，每层的 16 位工作权重和梯度只在计算该层时占用显存；反向传播从最后一层往前跑，某层梯度一确定就立刻在 GPU 上做 AdamW 更新，优化器状态在更新前后与主机内存换入换出并与计算重叠；专家计算被排布成 token 只走节点内的快链路，跨节点流量每层固定大小并藏到计算后面；昂贵的中间结果保留复用而不是重算。这套设计的核心思想作者注明受 Physion Labs 的 NexTron 启发。

  3. 数字很硬。16 张 H200 上 Qwen3.8-Flash-Next（177B 总参、每 token 激活 6.67B）吞吐 60.7k token/s，对比自研调优的 Megatron-LM 训练器 19.2k token/s，一个 epoch 从 22.4 分钟降到 7.1 分钟，每 token GPU 成本降 68%，MFU 从 5.2% 升到 16.3%。GLM-5.3-Flash（313B）用两个 B300 节点跑赢三个节点：76.2k 对 25.7k token/s，成本降 78%；同一模型换 32 张 H100 是 24 张 B300 的 3.1 倍速度、成本降 80%。最大的 MiniMax-M3.1-Flash（427B）在 80GB H100 上比 B300 还快 1.08 倍，每 token 成本降 56%。粗算到十亿 token 量级，32 张 H100 约 500 美元 GPU 时间，24 张 B300 的基线约 2460 美元。

  4. 可信度来自它主动交代的限制。GLM 的主基线用的是强化学习训练阶段、不同数据和不同 batch，作者自己标注为「配置比较，不是同数据受控测量」；另外单独做了同数据同 16 张 B300 的对照，loss 从第一次更新起与基线差距不超过 0.003，16 位优化器状态与 32 位基线的差距不超过 0.0022，AdamW 更新在 32 位状态下逐位一致；同卡计时 32 秒/步对 126 秒/步。同时明确：因为按层更新，拿不到全模型梯度范数，所以不支持精确的全局梯度裁剪；loss 对齐只覆盖一个 epoch，不能证明下游质量。

  5. 对实际工作的意义有两条。第一，如果你的 fine-tuning 集群是被显存撑大的，那么换一种状态放置方式可能比换卡便宜得多——这是把「省显存」当成架构问题而不是量化技巧。第二，它顺手给了一个判断口径：比较方案时要把「模型放不放得下、整个作业处理 token 多快、处理这些 token 的 GPU 成本」三件事一起看，并且必须用同数据和同训练设置，再在自家任务上评效果。作者的 GPU 单价（H100 4.50、H200 5.40、B300 9.50 美元/GPU 时）也写明了，方便复算。

我的推荐：适合正在做大模型微调、或者被 GPU 账单困住的工程师。不必照搬实现，但「优化器状态放主机内存 + 逐层流式更新 + 节点内专家亲和」这三条思路可以直接进入你的容量规划讨论。
