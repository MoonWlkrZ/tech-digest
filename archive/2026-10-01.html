把递归信息流装回 Transformer 的一个务实做法，预训练仍可全并行。 · ★★★★☆ · TLDR AI

A New Transformer Passes Its Hidden State to the Next Token Instead of Recomputing It

为什么值得看：arXiv 新论文提出 LIFT：把每个 token 与一个信息稠密状态配对做教师强制式预训练，让模型学会把深层状态回传给后续生成步。135M–1B 上 token-matched 预算全面领先，状态跟踪对照中小模型胜过 8 倍数据的同尺寸模型。

展开完整精读

一句话判断：LIFT 点出了 Transformer 一个常被忽略的结构约束——深层表示只能靠「下一个 token」这条窄通道向后传递；论文给出的修法（预计算状态 + 教师强制）保留全并行预训练，又在 135M–1B 规模上领先，是「机制清楚、代价可算」的架构改进。

  1. 问题：现有模型是单向的。深层表示不回流到浅层，跨生成步的信息通道只剩「已解码的 token」。代价有两个：中间结果被反复重算；除选中 token 之外的所有备选续写被直接丢弃。长链推理、状态跟踪这类任务，一直在为这条窄通道买单。

  2. 方法：LIFT 把「递归地保持状态」改写成教师强制式的监督问题。每个输入 token 配一个信息稠密的状态，状态取自一个现成预训练模型的 next-token 分布——不用新训一个老师，直接复用已有模型。模型只加少量参数，同时预测下一个 token 和下一个状态。

  3. 为什么还能全并行：教师状态离线预计算好，每个位置的状态在输入侧就绪、不依赖上一步输出，预训练保持位置间全并行——这正是传统循环式回传做不到的。推理时则把模型自己预测的状态喂回去，额外开销可控，且论文称开销随模型规模下降。

  4. 实验：135M 到 1B、token-matched 预算下，LIFT 在语言建模、下游推理与程序性任务上稳定优于标准 Transformer 与基线；compute-matched 下持平或领先。最有说服力的是状态跟踪的对照实验：小 LIFT 打败用 8 倍数据训练的同等大小 Transformer——哪怕教师状态来自一个在该任务上失败的模型，学生仍能学到可用的反馈机制。

  5. 边界与疑问：规模只到 1B，「开销随规模下降」恰好需要更大模型来证实；摘要里没给出状态维度、回传位置等设计细节对收敛的影响。作为方向性结果值得跟踪，离生产级替代还有距离。

我的推荐：如果你关心「Transformer 之后」的架构演化，这是本周最值得花时间的一篇。不必读全文，先把摘要和状态跟踪实验设定过一遍——它解释了一个被主流叙事忽略的瓶颈，也给「用便宜的老师教结构」提供了一个可复制的套路。

一个缺失的签名校验能走多远——当晚最值得读的安全复盘。 · ★★★★★ · TLDR Dev

How I Could've Accessed 17 Trillion Microsoft Records

为什么值得看：16 岁研究者的完整漏洞复盘：微软内部 Titan 分析服务不校验 JWT 签名，无签名令牌穿过四层校验、以 admin 身份执行 SQL，可触及 17.3 万亿行的环境。攻防细节、处置时间线与教训俱全。

展开完整精读

一句话判断：一篇教科书级的「只看内容、不验签名」漏洞复盘——一个免鉴权的 SQL 接口，被 AI 猎手加人类直觉打到 17.3 万亿行的门内；攻防细节与「AI 做不到什么」的反思都值得读。

  1. 入口：微软内部服务 Titan 的前端有 VPN 限制，但它的 API 有一个公开的 Swagger 文件，列出四条路由——三条要求 Azure AD 认证，唯独接受原生 SQL 的 /v2/Query 不需要。作者用 Wayback Machine 里 2023 年的页面快照恢复出 56 个表路由值（含 TestData），随后开始逐层试探。

  2. 破门：接口对匿名请求返回 401 后，AI 猎手 Antares 逐一挖出 JWT 校验逻辑的层级——换 tenant、换 audience、换 appid，最后进入用户查找。关键线索是：payload 一直变、签名一直没变，接口仍然接受——签名根本没有被验证。于是直接构造 alg:none 的无签名 token，三段结构的第三段留空。

  3. 致命一跳：无签名 token 已通过全部校验层级，却卡在「用户不存在」。Antares 按邮箱格式的 UPN 猜了十天；作者凌晨换了个角度——upn 在后端可能只是本地用户名。把值改成 admin，命中本地用户 ID 1（Admin 角色），SQL 开始执行。这是「AI 勤奋加人类换视角」最直观的示例：模型记住了字段名，人想到了字段背后的实现。

  4. 范围：56 个路由值中 30 个仍存活，穿过 24 个配置映射到 17 个 ClickHouse 分析库、9,863 张表；元数据里能看到约 2.5 万条账号记录、1.8 万条员工邮箱等。作者只做有界验证：Bing 分析分区取了两行样本，全程未触碰客户数据或 PII。总量估算 17,333,335,124,315 行（含副本与历史数据）。

  5. 余波与教训：MSRC case 144051，9 月 9 日端点被封停，随后拿到 5,000 美元奖励；微软对文稿有编辑控制权，部分影响描述被改写，这本身也是披露流程的一环。技术教训一句话：验证签名优先于验证声明——所有访问控制逻辑都做对了，漏掉这一条，等于没做。

我的推荐：这是当晚最佳安全写作。开发者可以把它当成「JWT 校验清单」的反面教材；关注 AI 工程的人能看到一个 agent 主导的真实挖洞工作流，以及它在哪里必须停下来等人类。9 分钟，值。

把执行层收回自己手里的完整架构课，数字和细节都实在。 · ★★★★☆ · TLDR Dev

5x Faster Edge Functions: How We Replaced V8 Isolates with Firecracker MicroVMs

为什么值得看：Netlify 把 Edge Functions 从第三方托管的 V8 isolate 迁到自家网络内的 Firecracker MicroVM：p50 从 25–40ms 降到 5–6ms，p99 改善 47.4%。请求全链路、隔离模型、快照恢复与运维经验都写得细。

展开完整精读

一句话判断：一次把「边缘函数执行层」整个换掉的一手复盘——从第三方托管的 V8 isolate 迁到自家网络内的 Firecracker MicroVM，每天约 10 亿次调用的底座，warm 调用 p50 从 25–40ms 降到了 5–6ms。

  1. 成绩单：warm 调用 p50 5–6ms（旧设施 25–40ms），p99 快了 47.4%，可用性 99.998%，日志投递快 5 倍；冷启动只占 1.2% 的调用，平均约 9ms。对「每个请求都压在用户等待路径上」的场景，这是实打实的量级改善。

  2. 请求链路：edge 节点终结 TLS 后写一份 machine spec（runtime、平台、用户代码三份镜像，加 CPU/内存/连接限制）；spec 的哈希加站点信息构成 service ID——不同 deploy、不同环境变量就是不同 service，永不共享 MicroVM。选节点用 rendezvous hashing 保持粘性（同一 service 总落在同一节点，换来热缓存与本地镜像），超过阈值再放宽，以吸收单租户流量尖峰、防止热点。

  3. 隔离升级：这是从 isolate 迁到 MicroVM 最本质的收益——即使某个 deploy 逃逸出运行时，也无法污染其他客户或计算层本身。文中直接写明「V8 isolate 提供不了这个级别的隔离」。对多租户平台，这一条比延迟数字更重要。

  4. VM 生命周期：Firecracker MicroVM 亚毫秒创建、p99 约 2ms 启动；代码以未压缩 EROFS 镜像挂载并内存映射，只读用到的部分；用户 JS 服务开始监听后对 VM 做快照，闲置时缩容到零，下次调用从快照恢复、内存映射直接执行。boot、快照、恢复、缩容到零这整套生命周期由 Unikraft 的产品支撑。

  5. 运维与后续：本地 DNS 解析器、分段指标（boot 时间、首次端口打开、用户代码启动）、熔断与渐进发布（新 fleet 健康后才接管流量）。能力上：npm 支持走出 beta、isolate 时代的三项限制（50ms CPU、512MB 内存、20MB 压缩包）具备重新审视的条件、计算留在自家网络内——「执行层的天花板归自己抬」。

我的推荐：如果你的系统里也有「把第三方执行层换成自建」的选项，这篇是难得的一手对照材料：什么时候值得换（隔离、延迟、控制权），换的时候会踩什么（DNS、端口、热点、发布），全部用数字说话。
