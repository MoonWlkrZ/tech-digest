今年最值得读的一份推理栈事故复盘：一次 200 响应里混进了别人的 prompt，根因是配置错配与引擎缺陷叠加，两层都修才算真修。 · ★★★★★ · TLDR Dev

Cross-request KV cache exposure in the GLM-5.3 Workers AI model, and our remediation with SGLang

为什么值得看：完整时间线、逐跳解剖 KV 页去向，还给出五条可直接照抄的运维检查项；把「用状态码推断引擎行为」这个坏习惯钉在了墙上。

展开完整精读

一句话判断：这是今年最值得读的一份推理栈事故复盘——一条 200 响应里混进了别人的 prompt，根因是配置与引擎缺陷叠加，两个都修了才算真修。

  1. 事故是什么
    8 月 27 日 GLM-5.3 在 Workers AI 上线时，prefill GPU 的 KV 池只有 681,280 token，而模型声明的上下文长度是 1,048,576 token。9 月 8 日安全研究员 Gadi Evron 通过 HackerOne 报告：发给该模型的超长 prompt 偶尔会返回其他用户会话的内容。9 月 9 日声明安全事件，40 分钟内把模型下线，当日 19:40 恢复。共 155 条响应受影响，全部来自超过 681,280 token 的 prompt；Cloudflare 核对时间与请求量后认为与正常长上下文使用一致，没有发现有人反复利用这个 bug。

  2. 为什么状态码是 200 却泄露了
    Cloudflare 用 SGLang 的 disaggregated 模式服务：prefill GPU 算 prompt 的 KV cache，经 Mooncake 用 RDMA 交给 decode GPU 生成。SGLang 调度器遇到超池长度的请求会拒绝，但拒绝信息记在 to_finish 里，finished() 仍旧返回 False；两个准入队列只查 finished()，于是这个已被拒绝的请求照样走完 bootstrap、prefill、KV 传输。prefill 上跑的其实是被替换成单 token 的占位 prompt，只写了一页 KV，却告诉 decode「传输完成」。decode 按预留的 8 页做 attention：P0 是本请求写的，P1 到 P7 还留着上几位用户的数据。结果是 HTTP 200、prompt_tokens 对得上、文字通顺，内容却是别人的。

  3. 修法分两层
    配置层把池扩到约 204 万 token，约为上下文两倍，合法请求从此进不了拒绝路径。引擎层让带拒绝标记的请求在 disaggregation 准入队列就带着原始错误退出，不做 bootstrap、不做分配、不做传输，并让 decode 校验收到的 token 数与预留一致。Cloudflare 的补丁 upstream 成 #38704，SGLang 在 v0.5.20、v0.5.21、v0.5.22 陆续合并相关修复，作者建议所有 disaggregated 部署升到 v0.5.22 或更新。

  4. 真正值得抄的那条测试教训
    上线前他们只验证了 HTTP 状态码和长上下文下的性能，没有验证模型输出本身是否连贯——这个 bug 正好从这条缝里过去。文中的原话是：不要从响应码去推断引擎行为，池大小与上下文长度要在每台 prefill 和 decode 节点上直接量、每次改权重量化并行度后重量。

  5. 长期方向
    页级 tag 的原型是：每个物理 KV 页带一个重分配时变化的 tag，请求记录自己期望的 tag，decode 读之前校验。实测吞吐与尾延迟损失不到 1%，但八月在 GLM-5.2 上试用后因可靠性问题先下线。per-transfer checksum 已经进 #39500，作者认为页级 tag 更进一步，因为它校验每一次读而不只是交接。他们还准备把形式化方法（Topaz、Meerkat 的经验）用到 RDMA KV 传输协议上，目标是从数学上排除这类 bug。

我的推荐：如果你在跑任何 disaggregated 推理（SGLang、vLLM 同类），把文末五条建议逐条对照自己集群，特别是第一条和第二条——量池子、升引擎。即使不跑推理，这篇对「两台机器对同一份状态看法不一致」的逐步还原，也是很好的故障推理教材。

AI SRE: what is it, how could it change on-call – and does it work?

为什么值得看：采访 Rootly、incident.io、ResolveAI 三家加四家自建团队，把「多代理排查」从流行词拆成具体角色和已知失效模式。

展开完整精读

一句话判断：AI SRE 眼下不是替你值班，而是在你打开八个标签页之前把排查做完，并且把结论先挑战一遍。

  1. 为什么突然热起来
    驱动不是模型变强，是部署变多。AI agent 写代码让多数公司的 PR 频率一年内翻倍，事故率按 i = c × p 拆开：变更量 c 上去了，单次变更出错概率 p 没降，事故与 page 自然跟着涨。Rootly 的数据显示 page 总量比一年前上升，非工作时间的 page 几乎翻倍。也就是说，不是可靠性变差了，是同样的可靠性水平被更高的变更频率放大成了更多事故。

  2. 它到底做什么
    三家最一致的能力是排查：alert 触发后拉 telemetry、近期部署、feature flag，并行 fan out 子代理，再互相挑战结论，最后把摘要发到 Slack，工程师在频道里随时 steer。写代码这块三家分歧明显：incident.io 把事故上下文交给工程师自己的 coding agent，ResolveAI 简单 PR 自己写、大改交给客户的 agent，Rootly 的愿景是 agent 起草 PR、另一个 agent 判断能否合，目前所有 PR 都还在人批准之后。

  3. ResolveAI 的三代架构是最好的样本
    2024 年是脚本流水线：分类 alert、收集日志指标、提取洞察、给假设排序。常见事故处理得不错，但凡不按剧本走的就崩。2025 年单 agent 加知识图谱，准确率上去了，三个新问题冒出来：context rot，长事故里上下文饱和，agent 开始要它已经有的数据、并自相矛盾；self-confirmation，让它给自己提出的假设打分，它几乎总是确认第一猜；没有记忆，上次的教训带不到下次。2026 年拆成 Investigator、Verifier、Communicator 三个角色，Verifier 在结构上独立于 Investigator，就是为了绕开自我确认。这是目前最可靠的一版。

  4. 自建还是买
    agent 要有效就得看 telemetry、日志、代码库，甚至只读的生产库快照，信任门槛很高，中大型公司因此自建：OpenAI 的 Sevbot 只收集细节和给建议，从不执行，工程师下指令才动手；Stripe 的排查 agent 简单跑平均 3 分钟，深度排查平均 14 分钟；Google 的 ProdAgent 只通过 MCP 调工具、不生成代码，带策略执行和审计；Monzo 把它做成通用工程 agent Project Chip 的事故模式。作者的判断相反于直觉：vendor 长期更强，因为自建容易变成「新鲜感过了就没人管」的副项目。

  5. 记忆与自主性的边界
    Rootly 把记忆分成激活与隔离两类：某条笔记在某次事故里起了作用才升级，被推翻就隔离，免得把陈旧结论喂给 agent。它还允许客户 opt-in 汇聚事故数据，想做「AI SRE 的 Stack Overflow」，前提是脱敏，而脱敏代码目前还没开。自主性方面，舞台上全自动的演示还不是现实，真正在变多的是 triage 与静音噪音 page；代价是技能退化，作者建议用事故演练补上，并提醒会出现一类新的 AI 相关故障。

我的推荐：把第 3 节当设计模板读——它把「多代理」从流行词变成了具体角色分工。做 agent 系统的人可以直接抄走两条：Verifier 必须与 Investigator 结构独立；记忆要有失效机制，否则它会拿三个月前的结论解释今天的事故。

把分析型数据库的向量化执行搬进搜索引擎，赌的是「多做可预测的工作」胜过「少做不可预测的工作」。 · ★★★★★ · TLDR

The first search engine with fully vectorized query execution

为什么值得看：从 Volcano 模型的逐行开销讲到 block-max WAND 的数据依赖，解释了为什么搜索一直躲开了这道税、又为什么现在躲不掉。

展开完整精读

一句话判断：一个搜索引擎把分析型数据库的向量化执行搬了进来，赌的是多做可预测的工作胜过少做不可预测的工作。

  1. 背景：Volcano 模型的税
    传统执行器按行 pull，每个算子每处理一行都要付函数调用、动态分派、解释的开销，CPU 大半时间在决定下一步干什么而不是干活。分析型数据库早就用两条路绕开：编译执行（Hyper 为代表）和向量化执行（DuckDB 为代表）。向量化保留 Volcano 的通用算子，但一次处理一批行，把分派开销摊薄。

  2. 搜索引擎为什么一直没这个问题
    搜索的典型形状是「按相似度取 top-k」，可以写成一个专用循环，不需要异构算子拼流水线，所以从来不用付那道税。更麻烦的是算法本身：block-max WAND 和 HNSW 都是先算相似度才知道下一个该看哪，天然带数据依赖，CPU 既没法预取也没法批量向量化。

  3. 变化来自查询形状
    客户开始在一个请求里叠过滤、时间衰减加权、自定义打分，再加上聚合、group by、order by。turbopuffer 现在支持十几个算子，平均一条文本查询要评估近 17 个算子，而且还在涨。异构算子一多，逐行分派的成本就回来了——这正是向量化能吃掉的部分。

  4. 两个硬件友好的替换
    向量索引不用 HNSW 而用 SPFresh，它的聚类分区设计让候选向量可以按批扫描；文本检索不用 block-max WAND，而用 block-max MAXSCORE 的向量化变体，作者说在他们测过的方案里表现最好，尤其是对 LLM 生成的那种长查询。v3 的关键改动不是某个算子变快，而是批次成了算子之间交换数据的默认单位：新算子只要接这个接口，就自动参与向量化，不用再写一份专用实现。

  5. 结论与规模
    作者的表述是 dumb and serial 胜过 smart and random：宁可多扫一些数据，也要分支可预测。用他们的话说，多做可预测的工作比少做不可预测的工作更快。规模数据是 1T+ 文档、10M+ 写每秒、100k+ 查询每秒，v3 今年晚些上线，届时每条查询都走端到端向量化管线。

我的推荐：这篇的价值不在 turbopuffer 本身，而在「查询形状变了、执行引擎就得重做」这条判断链。如果你的检索服务开始在一个请求里拼过滤加权重加聚合，先成为瓶颈的会是逐行循环，而不是模型延迟；这时候该看的是执行层，不是再加一层缓存。

今日判断

今日判断：三条主线说的是同一件事——AI 进生产之后，瓶颈从模型能力移到了工程可靠性。AI 把 PR 频率推高，事故和 page 跟着涨，AI SRE 这条赛道因此成立，但它现在解决的是排查而不是值班；推理栈的租户隔离仍然取决于 KV 页生命周期这种底层细节，一处配置错配就能让 155 条响应串数据；而服务 AI 检索负载的查询引擎，绕了一圈又回到数据库几十年前的老问题，重做执行层。值得留意的方向：Anthropic 递交 S-1 之后的估值叙事、agent 直接拿到生产权限后的实测数据，以及 SGLang 升到 v0.5.22 这条运维动作。
