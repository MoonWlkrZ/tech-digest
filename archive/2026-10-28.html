01
一次跨租户数据泄露的完整根因复盘，把推理引擎的调度语义讲透了 · ★★★★★ · TLDR InfoSec

Cross-request KV cache exposure in GLM-5.3 Workers AI, and our remediation with SGLang

为什么值得看：罕见地把事故追到「配置不一致 + 状态机语义不一致」的叠加，并给出可直接抄走的部署闸门；对任何自建或多租户使用推理服务的人都是必读。

展开完整精读

一句话判断：这不是一篇普通的租户隔离事故公告，而是一份把根因一路追到推理引擎调度器状态机的一手工程复盘，附带可执行的部署闸门。

  1. 事故的形状比「缓存没清干净」精细得多。Cloudflare 给 GLM-5.3 配了 1,048,576 token 的上下文窗口，但 prefill GPU 上的 KV cache pool 按启动时剩余显存只算出 681,280 token。作者明确承认他们在上线前就知道这个不匹配，并假定引擎会对装不下的请求报错——而长上下文测试返回的都是成功状态码，于是这件事被判定为「不是问题」。

  2. 真正的放大器在 SGLang 的拒绝路径与 disaggregated 模式的交互。超长请求被 scheduler 拒掉后，错误被写进 to_finish，prompt 被替换成一 token 占位符以便排空批次。单机部署下这条路是对的：占位符跑完，客户端收到错误。但在 prefill/decode 分离部署里，两端的 admission 队列检查的是请求是否 finished()，而被拒绝的请求此时仍自称存活，于是它被正常 admit：prefill 只做一次一 token 的前向，把一页 KV 通过 Mooncake/RDMA 传给 decode，并发出「传输完成」。decode 按路由给的 8 页预留内存，只写了 P0，P1 到 P7 还留着前一个请求的用户提示与半截生成结果，然后在这些陈旧页上做注意力、返回 HTTP 200。响应里的 prompt_tokens 与真实长度一致、文字连贯、还比正常 prefill 快——除了内容掺了别人的数据，一切指标都像成功。

  3. 修复刻意做成两层，理由比补丁本身更值得记。配置层把 prefill pool 调到约 204 万 token（约为上下文的两倍），让合法请求永远进不了拒绝路径；引擎层让携带待处理拒绝的请求在 disaggregation admission queue 就以原错误退休，不再经历 bootstrap、分配与 KV 传输，并让 decode 校验实际传输的 token 数与它预留的数量一致。作者说得很直白：只靠 pool 大小是脆弱的，量化、张量并行度、CUDA graph 尺寸、模型版本任何一个变化都会悄悄改变 pool 大小，所以必须有一个与 pool 无关的兜底。

  4. 最该被记住的其实是测试盲区。他们上线前验证的是 HTTP 状态码与吞吐，没有验证模型输出内容与连贯性——这正是「状态码绿了、数据漏了」的经典形态。事后他们把「从运行中的引擎直接读取 KV pool 大小并与 context length 比对」写成任何 disaggregated 部署变更的前置检查，而不是从响应码反推。

  5. 长期方向有两条。其一是页级 tag 校验：每个物理 KV 页带一个在重分配时变化的标签，请求记录自己期望的标签，decode 读缓存前比对，原型代价不到 1% 吞吐与尾延迟，但因为可靠性问题在 GLM 5.2 上试过又下线了；per-transfer checksum 是这条路的过渡形态。其二是形式化方法：他们打算把基于 Mooncake 的生产 KV 传输协议建模并证明其安全性质——此前在 Topaz 策略引擎与 Meerkat 的 QuePaxa 实现上做过同类工作。

我的推荐：逐段读，尤其是「Issue two」那七步和「What we recommend to other operators」五条。哪怕你只是调 API 而不自建集群，这篇也给出了一套判断多租户推理服务是否可信的提问清单：pool 与 context 如何比对、拒绝路径是否在跨节点前生效、decode 有没有校验传输量。自建 SGLang 的直接动作是升到 v0.5.22 或以上，并把 pool/context 比对做成部署闸门——这一条抄走就够了。

02
把「人类在环上」从口号落成五件套基建的一手工程说明 · ★★★★★ · TLDR Dev

How Meta Built Forum With AI-Native Engineering

为什么值得看：不是又一篇代理写代码的感想，而是讲清楚为了让循环自转，代码库、构建产物、测试信号各自要改成什么样；八周做到功能对等的结果背后是基础设施而不是提示词。

展开完整精读

一句话判断：这篇文章的价值不在「用 AI 八周做完一个 App」，而在于它讲清楚了把「人类在环内」换成「人类在环上」时，代码库、构建产物与验证信号各自要付出什么改造。

  1. 先把成功的定义换掉。他们不用代码量衡量，只用「verified, production-ready outcomes」——能构建、过测试、活过评审的改动。编译不算终点，任务只有在自动化测试与视觉检查都通过后才算完成，代理要先自检再把结果交给工程师，于是到达评审的是数量更少、置信度更高的一批改动，而不是一堆需要筛的产出。这一点看似只是流程措辞，实际决定了整个系统的优化方向：如果没有可信的验证，AI 生成的代码只是把约束从写代码挪到了「读那些看起来完成了其实没有的代码」。

  2. 让循环自转需要四种能力。其一，把规划写成技术规格——人能靠直觉补掉的歧义，对代理就是直接失败，所以他们在上游做严格拆解与机器可读的上下文。其二，把构建状态、单测、UI 规格匹配这些自动判定直接接进循环，让异步开发产出「自带测试计划与验证录像」的可评审 PR；他们明确说，能把多少环节安全交给循环，取决于验证器有多可信。其三，用导航代理做模拟用户测试：像真人一样操作、读屏、报回归，路径可以反复跑。其四，上线后的代理化运维：用户反馈进来，代理去定位疑似回归并把分析交给工程师判断。

  3. 运行模型是五个组件，命名朴素但分工清楚：rules 是永久项目指令，同一个错误被代理犯两次以上就编码一次给所有人用；skills 把团队约定变成可按需加载的步骤；agents 把原本需要人工过一遍的检查自动化；commands 把 skills 和 agents 串成「评估复杂度 → 复现 bug → 规划并实施 → 建 PR → 多阶段评审」的工作流；hooks 是自动触发器，比如每轮之后跑 linter、安装前检查模拟器连通性、建 PR 前校验测试。这套东西的本质是把「资深工程师的习惯」变成可执行、可复用的对象。

  4. 全文最硬的一句是「最大的收益来自改我们的代码和工具，而不是改提示词」。具体三条：架构可读性优先于继承复杂度，必要时宁可重写也不背着遗留结构走，因为代理从它读到的代码里学模式，修掉一个坏模式，之后每个会话都继承这个改进；给代理工具而不是描述——他们最主要的失败模式是代理搞不清自己在 App 的哪个位置，于是给它可以读实时视图层级、列出屏幕上真实元素、查目标视图路径的工具，改错地方的比率骤降；用独立 build flavor 做安全原型，通过 plugin/socket 架构把原型代码从生产构建里编译出去，于是原型既能自由跑，又不可能让生产包崩掉。

  5. 结果与缺口要一起读。八周达到 Facebook Groups 的核心功能对等；常规的压力场景（暴力滚动、随机浏览分组、快速导航、反复加载媒体）跑出稳定信号后，代理自己 triage 异常、缩小触发序列、定位根因，抓到的那次内存问题让设备端内存增长与 page fault 大约减半，而且是在开发期而不是上线后。但要留意原文的「What Worked, and What Did Not」这一节是空的——标题承诺了失败清单却没有正文，所以这篇目前只呈现了成功侧的证据，失败与他们踩过的坑仍然缺失。

我的推荐：把它当成一份可直接借鉴的改造清单来读，而不是励志故事。最可复制的三条是：把验证信号真正接进循环（而不是让人当人肉 CI）、给代理「能查状态的工具」而不是更长的说明、把「错两次就写成规则」当成制度。如果你在带团队推进代理化开发，这三条今天就能落地。

03
结论惊人，但真正值得学的是它交付证据链的方式 · ★★★★☆ · TLDR AI

Anthropic's Claude Refutes the Exponential Time Hypothesis, With a Lean Proof

为什么值得看：一个 AI 模型独立给出 3-SAT 的次指数算法并完成 Lean 形式化，本身就是大事；仓库还示范了「声明层可人读、证明可一键重跑、双内核复核」这套交付形态，对任何要让 AI 产出高强度结论的人都适用。

展开完整精读

一句话判断：结论本身是数学界的炸弹——3-SAT 有 2^o(n) 算法就等于证伪指数时间假设——但这个仓库真正值得工程读者看的是它的验证工程，而不是那条渐近界。

  1. 声明是什么。仓库首页第一段说：一个确定性算法在 2^o(n) 时间内解决 n 变量的 3-SAT，从而证伪 ETH；更强的是它解的是计数问题 #3-SAT，在 2^O(n log log n / √log n) 时间内统计可满足赋值数。作者紧接着补了一句关键限定：结果是纯渐近的，对实际求解公式没有任何意义。这句话很重要，它把「理论地震」和「你今天写代码会受影响」彻底分开。

  2. 交付形态是分层的。MainResults.lean 只有一个文件、只 import Mathlib、不含任何证明，作用是声明到底证了什么：ETHIsFalse 和论文主定理 MainTheorem，都建立在 Mathlib 的图灵机模型上。论文本身是 paper.pdf，配套的 proof/PaperIndex.lean 逐条列出论文里每个编号陈述对应的 Lean 版本，并说明形式化版本与印刷版本的差异。这个设计意图很清楚：让「证明对不对」交给机器，让「证明的是不是论文说的那件事」交给人快速读一个短文件。作者自己承认，没有机器检查这个文件是否忠实表述了论文。

  3. 复现成本是可以算的。装 elan 后在 eth 目录里 lake exe cache get 拉预编译好的 Mathlib，lake build 在 24 个虚拟 CPU 上约 8 分钟、最大进程占用约 7GB 内存；构建会打印两条 sorry 警告，都来自 Challenge.lean——那是为更强检查准备的、只声明定理不给证明的文件。最后 lake env lean scripts/PrintAxioms.lean 应打印出两个定理只依赖 propext、Classical.choice、Quot.sound 三条标准公理。Lean 与 Mathlib 都钉在 v4.33.1。对一个「AI 证伪了复杂性理论基本假设」的声明来说，这些数字的意义是把验证从「相信作者」变成「跑一条命令」。

  4. 还有一层更硬的检查在 CI 里：comparator-check.sh 调用 Comparator，把定理陈述与 Challenge.lean 对比，并用一个独立编写的第二内核 nanoda 重新校验证明。双内核的意义在于，单个内核的实现漏洞不会同时骗过两个独立实现。这条工程实践比结果本身更值得抄：当结论的利害足够大时，验证链要有冗余，而且冗余要在实现层面独立。

  5. 最反直觉的细节是那段落款式的「压缩描述」。README 说 Claude Opus 5.5 在高 effort 下，可以仅凭一段关于张量网络收缩、SWAP 分解成单重态、按单重态数分组、行列合并的简短描述，重新推导出 ETH 被证伪——但只能得到对任意 δ>0 的 O(2^δn)，拿不到页面顶部更紧的界。这把「可复现」推进到了新层次：复现的不只是构建，而是推理路径本身。当然，这也意味着这段描述本身成了一个待检验的声明。

我的推荐：值得读，但要带着怀疑读。这个仓库最诚实的地方恰恰是它自己划出的边界——没有机器检查声明与论文的对应关系，所以「证伪 ETH」的可信度目前建立在「人读一个足够短的声明文件」加「两个独立内核复核」之上。对工程读者更实用的启示是：当 AI 给出高强度结论时，交付物应该包含一个能被人快速核对的声明层、一条能一键重跑的证据链、以及一份明确写出来的「机器没有检查什么」。
