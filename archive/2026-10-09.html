强烈推荐——想理解 GPT-6 智能界面的实现细节，这是目前最完整的一篇逆向解析 · ★★★★★ · TLDR Dev

How ChatGPT Intelligent UI works

为什么值得看：从模型写出的 DIL 到服务端编译、沙箱执行、流式重新编译，把一个已上线产品的完整技术链路逐层拆开，粗糙面也如实列出。

展开完整精读

一句话判断：目前对 GPT-6 智能界面（Intelligent UI）最完整的公开逆向解析，把「模型写界面」从产品宣传拆成了可以逐层验证的工程链路。

  1. 模型先写一种叫 DIL 的格式：Markdown 负责文字，JSX 式标签负责组件，JavaScript 负责状态与事件。它被刻意设计成「半写状态也可用」：语句按行独立、未闭合的元素可以自动补全，服务端因此能随时在最后一个完整结构处截断并编译。

  2. 服务端把 DIL 编译成一段 JavaScript 程序加一份 JSON 数据：静态文本进常量表（流式过程中文字增长只改数据、不改程序），每份状态带固定 key（重新编译后用户已经拖过的滑块不会重置），表达式包在 __dilSafe 里做错误隔离，属性按组件目录校验、不合法的直接摘除并记录诊断。

  3. 编译产物不在页面里执行，而是进隐藏 iframe 加 Web Worker 的沙箱：执行前先清掉网络、定时器、消息与动态求值并冻结剩余全局对象，再用 new Function 求值；超时无响应的程序会被隔离、worker 重启。渲染只在页面侧发生——运行时把新旧组件树的差异编码成操作序列，交给 ChatGPT 自己的原生组件系统（注册约 70 个组件，实测响应里出现 39 个）。

  4. 流式更新以整份重新编译为主：每几百毫秒把模型已写出的全部内容重新编译一遍再发送。实测一次 6.3KB 的回复共产生 275KB 补丁，其中 83% 是重复发送的编译产物；文字逐词出现，而每个组件要等标签闭合才出现。

  5. 粗糙面也完整列出：刷新丢状态、模型看不到用户改过的界面值、图表逻辑错误静默（一个示例把 $6,930 的数值切成了 $256,410）、无效属性的诊断似乎没有回传给模型、Markdown 降级版本会丢计算内容。这份问题清单本身就是做生成式 UI 的参照物。

我的推荐：如果你在做生成式界面、代理前端，或任何「让模型产出可交互界面」的系统，这是现成的架构参考；作者用「重新实现编译器并做逐字节对齐」来验证理解的测试方法，也值得借走。

强烈推荐——供应链攻击升级样本：修复顺序和直觉相反，先别吊销令牌 · ★★★★★ · TLDR InfoSec

Tensorlake npm Package Compromised: A Worm With a Hostage Token

为什么值得看：恶意版本从项目主干构建并通过 npm 溯源认证，「吊销被盗令牌」这个常识反应反而触发本机擦除，修复步骤有严格顺序。

展开完整精读

一句话判断：一次把「先偷令牌」升级成「拿令牌当人质」的 npm 供应链攻击——吊销被盗令牌这个常识动作，反而会触发本机擦除。

  1. 恶意代码是被直接推送到项目主干的（冒用维护者身份，八次提交、全程没有任何 PR），随后从同一仓库发布了 tensorlake@0.5.144。因为构建来源是真的，npm 上挂着有效的 provenance 溯源证明——这份证明只能说明包在哪里构建，完全不代表代码安全。

  2. preinstall 钩子在安装时动手，而且会识别并跳过 CI 环境——目标明确是开发者机器。它下载 Bun 运行一个混淆过的 856KB 载荷，收集 GitHub 与 npm 令牌、云密钥、Kubernetes 与 Vault 凭据、SSH 私钥、浏览器保存的登录信息，以及 Claude、Cursor、Windsurf 等 AI 工具的配置，加密后发到受害账号下新建的公开仓库或外部域名。

  3. 传播靠偷来的令牌自我复制：用 npm 令牌给受害者名下的其他包加上自己、升版本再发布；用 GitHub 令牌以「chore: update dependencies」的提交信息把 .claude 和 .vscode 文件写进受害者的仓库，让恶意代码在别人打开 Claude Code 或 VS Code 时再次执行。

  4. 最狠的部分是它留下的 gh-token-monitor 服务：每 60 秒对照 GitHub API 检查一次被盗令牌，最长持续 24 小时；一旦令牌失效，就执行 rm -rf ~/（Windows 上是删除用户目录）。也就是说，发现入侵后如果按直觉先吊销令牌，会直接触发破坏。

  5. 修复顺序因此和直觉相反：先确认是否装过 0.5.144，固定到 0.5.143、清掉 node_modules 与 npm 缓存、设置 ignore-scripts=true；然后找到并停用 gh-token-monitor 服务；之后才轮换全部凭据；最后检查是否出现可疑的新仓库与提交。作者明确说：无法确认干净时，直接重装系统。

我的推荐：每个在开发机上跑 npm install 的人都该读一遍，尤其是修复步骤的顺序——「先拔掉监视服务，再换令牌」不是可以事后补救的细节。它也是供应链攻击转向对抗性的又一个实证：恶意代码开始惩罚你的响应动作。

03
推荐——自建云代理运行时的一手经验：沙箱会死，任务不能死 · ★★★★★ · TLDR Dev

We built our own cloud agents runtime. Here's what we learned

为什么值得看：四个产品共用一个代理运行时的复盘，覆盖持久化工作流、消息队列、网络层阻断与自定义镜像，全是能直接对标的决策细节。

展开完整精读

一句话判断：把四个产品塞进同一套云代理运行时的复盘——「沙箱可以死，任务必须活下来」，这篇把这句话落成了具体设计。

  1. 所有运行挂在 Temporal 工作流上：状态存在 worker 进程之外，部署杀不死正在跑的任务；快照在克隆与安装完成后打一次，后续运行不用重复这些步骤。任务记录、对话、工作树分别落在 Postgres、运行日志和快照里，凭据每次现发——沙箱消失后就地重建、恢复工作树、重放日志，任务接着跑。

  2. Slack 场景暴露了三个必须解决的问题：回复要能进入一个正在忙的运行（消息按到达顺序排队，一次一条交给代理，另有可插入进行中回合的插队消息）；要能送达虚拟机已经休眠的运行（从快照拉起新沙箱再投递）；还不能重复送达（Slack 会重发它认为失败的 webhook，每条消息带 id 做去重）。

  3. 无人值守的「自驾驶」场景把安全要求抬高了一档：信号是产品里流出来的不可信文本，现在直接摆在有仓库权限的代理面前。他们用 LLM 评委过滤可疑信号（一周拦下 1,374 条），但清醒地指出这类非确定性检查会有约 2% 的漏网；所以底下必须有机器层的确定性阻断：域名白名单在网络栈上执行，模型再怎么请求也走不出去。

  4. 沙箱最终从 gVisor 容器换成真 VM（跑在 Modal 上）：因为用户的技术栈要能跑 Docker，而 gVisor 里跑不了。网络规则最多允许 100 个域名、通配符只允许最左一段、禁止裸 IP；另外预热池让虚拟机在用户还在打字时就先启动，首 token 到达时间因此接近模型本体速度。

  5. 镜像构建把仓库当不可信输入处理：先让扫描评委按未受信输入检查镜像规格，克隆用只在该步骤生效的构建密钥完成、并在任何用户命令执行前移除远端；构建器代理本身在一个独立沙箱里读仓库、试装依赖，把结果写成简短的 YAML 规格，还安排定时任务检查基础镜像漂移并自动重建。

我的推荐：想自建代理运行时、或正在被沙箱生命周期折磨的团队，这篇从「为什么换 Temporal」到「网络层为什么必须是确定性的」都可以直接拿去对标；收尾一句就是设计原则：按沙箱一定会死来设计，任务才不会死。
