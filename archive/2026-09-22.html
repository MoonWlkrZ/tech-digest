Jev's Architecture Unmasked

为什么值得看：用上万次 API 探测把 Jev「只输出概率、不生成文本」的机制还原成可检验的假设，并给出评估这类决策接口时需要的方法纪律：排列不变性、校准曲线、别把 confidence 当正确率。凡是让模型输出分数再由软件按阈值动作的系统都用得上。

展开完整精读

一句话判断

这是目前对 Jev 最认真的一篇外部拆解：用上万次 API 探测把「只输出概率、不生成文本」从营销话术还原成可检验的架构假设，也顺手给出了评估这类决策接口时该怀疑什么。

1. 文章主张了什么

作者（Archer Hume）用约一万次 API 调用（含 1029 条带埋点的探测记录、6800 条基准记录）反推 Jev 的实现：一个因果 transformer 在 prefill 之后直接读出概率，而不是逐 token 生成；共享的 state 只编码一次，每个问题是一个独立分支（共享 KV 前缀、彼此不可见，作者推测是稀疏 MoE 底座）。证据链里最硬的一条是 output_tokens 字段：它恰好等于「4 个共享 token + 每个答案 15 个 token + 问题标识符长度」，与延迟无关（255 个选项的响应报 2714 output tokens，返回速度和两选项请求一样快），而文档明确说问题标识符不参与推理——所以它是计费口径，不是解码记录。行为实验同样清楚：把密文放进兄弟问题里，被问到时可见性是 0.00；放进共享 state 里则是 0.90–0.92。服务端耗时在约 100 个问题以内几乎不变，之后才随问题数增长，每 token 的问题文本开销约为 state 的两倍，符合「state 算一次、问题批处理」。

2. 我的解读

这篇文章的价值在于拆掉了「并行输出」这个说法里的含糊：并行指的是问题之间没有答案依赖、可以批处理，不是一张卡一个问题。作者做了一个很漂亮的反驳实验：往四选一里加一个无关的第五选项，如果模型对每个选项独立打分再归一化，两个既有选项之间的几率不该改变；实测对数几率从 +0.38 掉到 +0.11，10 个随机区组全部下降（均值变化 −0.28，95% 配对区间约 [−0.36, −0.19]），说明选项之间会互相影响——这也意味着选项顺序会改变答案：把选项顺序反过来，一个技术支持分类的概率从 0.84–0.89 变成 0.93–0.96。校准部分同样值得看：作者测出 1200 题 MMLU 样本上十桶 ECE 为 0.0313，而且难题上模型会主动降低置信（三位数乘法准确率 86.7%、平均最高概率 0.83；两步应用题掉到 32%、0.30）。

3. 对实际工程的意义

  • 评测这类「决策模型」必须加排列不变性测试：同一组选项换顺序跑一遍，看结论是否翻转；阈值卡在 0.9 附近的动作最容易因此改变。
  • 不要把接口里的 confidence 字段当成「答对的概率」：按官方适配器它等于 (pmax − 1/K)/(1 − 1/K)，只是分布相对均匀分布的集中程度（三个选项、最大概率 0.8 时显示 0.7），真正的正确性要看校准曲线。
  • 架构上可抄的是省算力的方式：共享上下文只编码一次、把每个待判问题做成独立分支、最后统一读概率——凡是有大量共享 prefix 的分类或评测任务（例如一次跑几十条规则的批量评测），这个结构都值得借鉴。
  • 用它做策略动作时要显式建模代价不对称：文中给的例子是升级一条不紧急工单算 1 个单位、漏掉一条紧急工单算 9 个单位，那么 p(urgent) > 0.1 就该升级——这个算术只有在概率经过校准的前提下才成立。

4. 可信度与局限

作者把证据分了级：直接读概率是官方说法，问题隔离与选项顺序效应是行为观测，KV 共享、指针式读头、稀疏专家是推断。局限也摆在明面上：基座模型与 tokenizer 未知（415 条探针匹配不上 192 个公开 tokenizer，最接近的 Qwen 也只中 348 条）；延迟数据取自上游服务响应头，不含排队；稀疏专家「无法从外部观测」，只能从「约 3 万 token / 约 160ms」这类量级倒推；部分实验（比如换掉第五个选项描述文本）结论不显著。它是一篇高质量的逆向工程，不是官方文档。另外该文引用的 TypeSafe 官方文档与基准页面本身也需要保留怀疑。

5. 最值得记住的三点

  • Jev 不生成文本，只读概率；output_tokens 是计费字段，和推理方式无关。
  • 选项是整体读取的：加一个无关选项就能改变旧选项之间的相对几率，顺序也会影响结果。
  • confidence 是算出来的集中度，不是概率正确性；要谈可信度就拿校准数据说话。

我的推荐

如果你在做任何「模型输出一个分数、软件按阈值动作」的东西，这篇值得精读——它给的是评估方法，比结论更耐用。28 分钟的阅读量主要花在实验细节上，时间紧的话可以先读第 4、5 节（选项交互与校准），再回头看前两节的证据链。

Swarm Scaling

为什么值得看：从 OpenAI 公开图表里估出 swarm 的缩放指数 λ≈0.5，把「多代理到底买到了什么」从感觉变成可算的数字：买的是速度，不是省钱；并给出 10 倍 agent ≈ 3–5 倍单 agent token 这类可直接引用的量级。

展开完整精读

一句话判断

多代理 swarm 不是「更省钱的推理扩展」：按 OpenAI 自己放出的数据反推，把 agent 数量扩大 N 倍，效果只相当于把单 agent 的 token 扩大 N^λ 倍（实测 λ≈0.48–0.68），多代理买到的是速度，不是省钱。

1. 文章主张了什么

Toby Ord 从 OpenAI 发布 GPT 5.6 Sol 时的评测图里反推 swarm 的缩放规律：扩大 agent 数量，得到的性能提升相当于把单 agent 的 token 数扩大 N^λ 倍。他用回归估出三个基准的 λ——BrowseComp 0.68（90% 置信区间 0.63–0.76）、SEC-Bench Pro 0.57（0.52–0.61）、Terminal-Bench 0.48（0.40–0.57）。换算下来：swarm 扩大 10 倍只相当于单 agent 多用 3–5 倍 token；要追上单 agent 100 倍 token 的收益，需要把 swarm 扩大 900–15000 倍。另一面是速度：4 个 agent 用约一半时间完成任务但多花约一倍 token，16 个 agent 是约 1/4 时间和 4 倍成本。文中还引 Noam Brown 在 Dwarkesh 播客上的说法——Navier-Stokes 那个一万 agent 的成果里「多代理的功劳不到 10%」，主要是模型本身变强了；按 λ=0.5 粗算，同样的结果用 100 个 agent 花 10 倍时间可以做到约 1/10 的成本。

2. 我的解读

λ 借自经济学里研究「人多手杂」的并行效率：N 个人一起干，相当于 1 个人干 N^λ 倍的时间，λ 越接近 1 任务越可并行。把它套到 agent swarm 上，妙处在于从公开图表就能估出来，不需要内部的 token 账单。值得注意的是测量的 λ 与之前递归自我改进研究里的默认假设（AI Futures Model 用 0.5、Forethought 的中位数 0.6）几乎重合，作者本来希望 agent 场景下 λ 更低、让智能爆炸更难发生，结果没有。对做多代理编排的人，结论要拆成两句：任务本身可切分时，并行编排能缩短挂钟时间；但它不是「同等效果更省算力」的免费午餐，甚至经常更贵，因为并行还额外增加了协调、重复读取上下文与合并的开销。

3. 对实际工程的意义

  • 决定要不要 fan-out 之前先问两件事：任务的可并行度（λ）和你实际想买的东西——要缩短时间、且愿意多付 token，多代理值；只想省钱，单 agent 加长推理或用更强模型通常更划算。
  • 量级可以当经验值用：10 倍 agent ≈ 3–5 倍单 agent token；跨量级差距放大（100 倍 token 的收益 ≈ 900–15000 倍 agent）。
  • λ 应该当成测量项而不是常数：三个基准分别是 0.48 / 0.57 / 0.68 说明任务类型影响很大（Terminal-Bench 这种步骤耦合紧的基准并行收益最差），做内部评测时按任务类型分别估，比统一拍一个系数有用。
  • 图中另一条更值得注意的曲线是模型换代的效率跳变：内部模型达到 GPT-6 Astra 同等水平只需约 1/100 的 token，比 swarm 规模带来的收益大得多——先把模型换对，再谈编排。

4. 可信度与局限

数据是二手推断：图表取自 OpenAI 的发布页，作者从对数坐标的直线上插值取点、并用 Claude Opus 5 跑回归得到 λ 与置信区间。曲线在 log 轴上确实很直，插值比较可靠，但样本只有 1/4/16 三档、三个基准，外推到 1 万 agent 只是粗略假设（作者自己写了 heroically assume 这样的措辞）。Navier-Stokes 那部分的成本口径用的是 API 价格估算（一万 agent 约 2000 万美元），量级参考意义大于精确值；他也提示 λ 在更大规模或新编排方法下可能变化。

5. 最值得记住的三点

  • 扩大 agent 数量 N 倍 ≈ 单 agent token 扩大 N^λ 倍，实测 λ 在 0.48–0.68。
  • 10 倍 agent 只值 3–5 倍单 agent 的 token；多代理买的是速度，不是成本。
  • 同一份数据里模型换代带来的效率跳变（约 1/100 的 token 达到同等水平）远大于 swarm 规模的收益。

我的推荐

如果你手上有「要不要把任务拆给多个 agent」的具体决策，这篇 13 分钟就能给出量化判据；配合队列里 Jev 相关的几条一起看，正好是同一个问题的两面：一次决策该花多少算力，以及算力该花在几个 agent 上。

How will AI change operating systems? Part 2: Windows

为什么值得看：微软 Windows 团队的一手路线图：agent 身份、系统级 MCP 注册与分级沙箱被做成操作系统原语，加上本地模型（Windows ML + 内置 SLM）。对在 Windows 上跑带工具 agent 的人，这份材料决定了下一代沙箱会是什么样子。

展开完整精读

一句话判断

微软正在把「agent 是一等公民」写进 Windows：agent 有独立身份、有系统级注册的 MCP 工具、有分级隔离的沙箱，同时用 WSL 与本地小模型试图把开发者拉回来——这是一份路线图，不是现状。

1. 文章主张了什么

Pragmatic Engineer 采访了 Windows 团队的三位负责人（Pavan Davuluri、Scott Hanselman、Logan Iyer），拿到的是微软对「AI 时代的操作系统」的完整规划。原文列了八条，抓取到的部分覆盖前五条：一、开发者份额——Windows 在普通用户中仍有约 63% 份额，但在开发者中持续流失（作者自己做的一次近万人调查里 Windows 排第三，落后于 Linux）；二、agent 身份与发现——Entra ID 给 agent 发本地身份，任务管理器里 agent 像另一个用户一样列出来，所有针对人类用户的可观测性对它同样成立，Defender 开始「能看见 agent」并扫描本地 agent 活动；ODR（On Device Agent Registry）是系统级的 MCP 服务器注册与发现中心，自带 File Explorer、System Settings 等连接器，有第三方研究显示 ODR 会把自己插在 MCP 客户端与服务器之间做代理（微软未确认）；三、隔离——MXC（Microsoft Execution Containers）用 JSON 策略文件描述网络、文件系统、UI 与执行限制，按敏感度在「进程 → 会话 → WSL 容器 → 轻量 Hyper-V → 完整虚拟机」之间选隔离级别，已能在 Windows/Linux/macOS 上跑，企业侧用 Intune 统一下发策略；四、本地模型——Windows ML 是 ONNX Runtime 之上的硬件抽象层（覆盖 GPU/NPU/CPU，厂商以 execution provider 方式接入，不再被驱动更新周期卡住），系统打算内置 SLM（Edge 的 Aion 模型已可通过 Prompt API 调用，几行 JS 就能做情感分析这类任务），现场演示的预发布 Surface + NVIDIA 跑 Qwen 约 40 token/s 并接上 GitHub Copilot；五、建 agent 的工具链。后面关于「更友好的 Windows」「WSL」「硬件与 ARM」三节只在开头目录里出现，正文被付费墙截断。

2. 我的解读

这篇的信息量不在「Windows 支持 AI」这种说法上，而在三件具体的事：一是 agent 身份被做成了系统原语——行为可审计、可归因，反过来「假装是人的 agent」就变成了异常行为，这是把 agent 治理放进操作系统层；二是 ODR 如果真把自己做成 MCP 代理，Windows 就成了本地工具调用的检查点，安全团队会很喜欢，但 agent 框架直连 MCP 的假设要重新考虑；三是 MXC 把隔离级别的选择变成配置项而不是架构决策，正好对应我们平时手工在「快」和「安全」之间做的取舍（进程最轻但共享用户文件系统，容器与虚拟机更安全但更慢）。本地模型这条线也和「按能力分层路由」的趋势对上了：简单推理放本地，复杂推理留给云端。

3. 对实际工程的意义

  • 在 Windows 上跑编码 agent（要执行 shell 的那些）时，MXC 式的分级隔离值得关注：策略是 JSON，可以按命令敏感度分档，而不是所有工具都丢进同一个沙箱。
  • 本地模型路线的可行性在变：Windows ML 抹平硬件差异、系统内置 SLM 让应用不必为简单推理付 token 费，混合「本地跑简单任务、云端跑难题」的成本结构可以提前试。
  • 如果 ODR 的代理行为坐实，本地 MCP 的调用链会多一层检查点，「agent 直连服务器」的部署方式需要重新评估。

4. 可信度与局限

来源是微软方的直接访谈，路线图成分大于既成事实：ODR 还在 beta、MXC「尚未被广泛采用」、SLM 内置没有时间表。抓取到的正文在第五节被付费墙截断，关于 WSL 与 ARM/NVIDIA 的部分只有目录摘要可用，这也是我给 3 分的原因之一。另外作者自己的读者调查有选择性偏差，他也承认了这一点；开发者份额的数字来自多次外部调查，口径不一致。

5. 最值得记住的三点

  • agent 在系统里有了自己的身份（Entra ID）与完整可观测性，Defender 会扫描本地 agent 活动。
  • ODR 想当 MCP 工具的系统级注册与代理，MXC 用 JSON 策略把隔离级别做成配置项。
  • 微软在赌本地模型与 WSL：前者抹平 GPU/NPU/CPU 差异，后者是留住开发者的底牌。

我的推荐

值得扫一遍第 2–4 节（agent 身份与发现、隔离、本地模型），把 MXC 的策略格式与隔离级别记下来；如果你在 Windows 上跑带工具的 agent，这可能就是下一代的沙箱方式。篇幅不长，适合在通勤时读完。

Jev introduces a new shape of LLM—System One, aka Decision Models (5 minute read)

这是一份公开的构思文档，讨论「为什么还要再做一个编码代理」，切入问题很刁：如果 LLM 没有 KV cache，你会怎么设计编码代理？作者认为编码代理本身意外地简单（大多是有少量工具的 while 循环），真正的约束来自 KV cache 带来的几个后果——一是路由失效：先路由到便宜模型再切回大模型反而更贵，因为大模型要把上下文重新处理一遍，他按 opus 5/25 与 sonnet 3/15 的价目算过一笔账，在长会话下纯 opus 只有「opus→sonnet→opus」方案约三分之二的成本；二是工具调用是别扭的取舍，工具必须在系统消息里一次性声明、吃掉大量上下文，而模型对高基数、off-policy 的工具调用并不擅长；三是压缩（compaction）之所以存在，是默认了后续所有轮次共享同一份状态，而按查询做感知压缩本来会容易得多；四是子代理表现平平，作者怀疑卡点在「该传哪些状态进去、子代理的状态怎么合并回来」；五是重启与上下文腐化。由此推出的设计方向包括：权限与审批可编程化、由代理自己充当工具调用的路由器，以及「元注意力」式的动态上下文——对每个上下文块（工具输入输出、内部推理、甚至用户往返）用 noul 判断该隐藏、给短摘要、给长摘要还是全文，从而让路由与子代理变成一等公民；再往上一层是把 skills/MCP 重做成「小片段描述可用动作 + 需要时再拉完整 schema 且不污染上下文」的形态。附录里还有一组可参考的数字与模式：后台只读任务（跨模型互审等）适合做成后台处理，以及据微软 fastcontext 的分析，读取与搜索占编码代理工具调用轮次的 56.2%、主代理总 token 的 46.5%——这解释了为什么压缩工具输出、结构化检索的收益这么大。
