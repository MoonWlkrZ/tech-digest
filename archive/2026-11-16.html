币安热钱包被盗复盘：50 个有效签名，1 个生效，授权持续了 3 小时 49 分

为什么值得看：它不是在讲「交易所被黑了」，而是给出一个可复用的失效模型：签名有效 ≠ 签名生效，而「生效」的授权可以落在组织所有应急开关的射程之外。凡是做钱包、托管、签名服务或 agent 凭证的人都该读。

展开完整精读

一句话判断：这是本周最值得花时间的一篇安全取证——它把「签名有效」和「签名生效」拆成两件独立的事，再用链上数据证明，一件生效的授权可以活得比组织的应急开关更久。

  1. 攻击的形状。2026-10-29 20:20:59 UTC，区块 26,300,753 第 138 位的一笔 type-4 交易里塞了 50 个 EIP-7702 授权，nonce 覆盖 18,914,775 到 18,914,824，链 id 全是 1，全部指向同一个 1,674 字节的 sweeper 合约。50 个签名用 EIP-7702 的消息格式都能恢复出 Binance 14 这个热钱包——也就是说，它们全部是密码学意义上有效的。

  2. 为什么只有一个生效。EIP-7702 执行时拿每个授权的 nonce 和签名者当下的 nonce 比对，不等就跳过，跳过不影响列表继续往下走，而签名消息里根本没有时间字段。交易执行时 Binance 14 的 nonce 正好是 18,914,809，于是那一个匹配、nonce 加一、账户代码从空变成 0xef0100 加上 sweeper 地址。更巧的是：同区块第 133 位，Binance 14 自己发了一笔经「钱包 34」转出 5 USDC 的普通交易，把 nonce 推到 18,914,809。没有这 5 USDC，生效的会是 18,914,808 那个授权，装的是同一份代码——换张票，同一结果。

  3. 3 小时 49 分里发生了什么。首次扫掠在 20:24:23（委派后 3 分 24 秒），取走 167,464.2479 ETH 和 63 笔代币转账（含 1,615,409,498.97 USDT）。之后 6 次调用继续取，5 次扫 Binance 14 合计 172,624.4046 ETH，每次恰好留 1 ETH；关联钱包 34 被取走 823,000,000 USDC，靠的是 Binance 14 本来就有的调用权限（selector 0x043ff9d2）。最刺眼的一段是补血：半小时一次的归集任务和一笔 200,000,000 USDT 的储备补款一直在往这个已被控制的钱包里打钱，后者到账 72 秒就被扫走。Tether 在首扫后 37 分 12 秒冻结收款地址时，已有 7 亿 USDT 转出。直到 00:10:35 币安自己发了一笔指向零地址的 type-4 交易，委派才被清掉。

  4. 最反直觉的一段：剩下的签名。50 个里还有 15 个指向钱包尚未到达的 nonce，而 EIP-7702 不会把跳过的授权标记为已用——它们一直有效，直到钱包自己的 nonce 越过它们。作者算出一个反事实：委派后的头三分钟左右，如果币安用自发的撤销交易，撤销本身还可能被一个剩余签名再翻回去；把撤销清干净的其实不是防守方，而是钱包自己的日常出金流量——20:24:23 用掉 18,914,824 之后，50 个签名全部过期。

  5. 方法论值得单独学。全文没有折算一个美元数字（「看到美元符号，那不是我们的」），用两个公共 RPC 端交叉核对 53 个区块指纹，并明确承认「两个 provider 不构成两个独立节点」；它把「实际损失 / 可触及敞口 / 处置有效性」分成三个量，指出「报警后还被拿走多少」只回答最窄的那个问题；文章末尾逐条列出未解问题（sweeper 代码没读、签名何时产生、出金何时暂停）以及每条论断的推翻条件。顺带一个值得注意的元信息：这篇是 AI 研究流水线产出、三个不同实验室的模型交叉核查、人做裁决——它本身就是「agent 做取证、人做判断」的一个可检验样本。

我的推荐：把它当三份材料读。做钱包/托管的读第 2、4 节（授权是独立签名类别、撤销要演练到「剩余签名」这一层）；做检测的读第 3 节（账户「获得代码」这个告警太晚，一笔交易可以既安装又使用）；做运维的读补血那一段（被控制的钱包要从所有补血路径里摘出去，不只是停普通出金）。

低精度训练从论文配方走到生产运行的完整工程记录，取舍写得比结论更有价值 · ★★★★★ · TLDR AI

端到端 4-bit 训练：把 NVFP4 前向放进生产训练配方

为什么值得看：文章没有停在「我们省了内存」，而是把每个阶段的误差敏感度分开算：前向用 4-bit、反向用 8-bit、通信再单独量化，最后给出 2% 计算效率损失换来的墙钟收益。这是少见的、能照着抄的训练栈细节。

展开完整精读

一句话判断：这是把「端到端 4-bit 训练」从论文配方推到生产运行的一份工程记录，价值在于它写清了每一步为什么这么选，而不是只报一个加速比。

  1. 起点是一个简单算术。NVFP4 每值 4.5 bit（(4×16+8)÷16），在 GB300 上是 15 PFLOPS；MXFP8 是 8.25 bit / 5 PFLOPS；BF16 是 16 bit / 2.5 PFLOPS。位宽少 3.6 倍，吞吐高 6 倍——这个缺口足够大到值得忍受量化误差。但作者一开始直接全 NVFP4 训练，计算效率（CE）掉得无法接受，于是改为按阶段拆：前向最能容忍误差、反向最不能容忍偏差（bias）。

  2. 真正的卡点不是精度，是转置。前向里 NVFP4 按 1×16 的块算 scale，反向要把张量转置，块就变成按列取 16 个值，分组全变、scale 全变，大量值直接被舍成零。NVIDIA 的解法是用 16×16 的 tile 算单一 scale，转置前后一致；作者试过，太粗，CE 还是不可接受。他们的做法是：把前向张量反量化到高精度、转置、再用随机舍入重新量化到 MXFP8。随机舍入按距离概率上取或下取，保证期望值不变——只需要前向反向张量「在期望上相等」，不需要逐位相等。这一步是整个配方的支点。

  3. 加速之后瓶颈换了位置。MoE 的前向 GEMM 理论上快了三倍，结果卡在专家并行的通信上：在 GB300 NVL72 上 NVLink 每向 900 GB/s，而 NVFP4 GEMM 能跑 15 PFLOPS，折算下来每收到 1 字节就得配 16,000 次浮点运算，否则 Tensor Core 就在空等。dispatch 阶段直接传 NVFP4 就够了；combine 阶段输出必须保持较高精度，他们先试 MXFP8，被离群值坑了，最后用 32 维随机 Hadamard 变换把数据「转平滑」，再量化到 block-scaled S2F6（2 位整数 + 6 位小数），把传输量从 16 bit 压到 8.25 bit，精度无损。

  4. 配方细节与代价。最后 16.6% 的层留在 MXFP8（NVIDIA 的配方是 15%，他们按 6 倍层数阶梯取 1/6）；激活量化用 Four Over Six 在两个 scale 之间选，权重不用；权重按专家、激活按 token 取外层 scale，借了 Composer 2 的做法。代价写得很直白：预训练 CE 损失约 2%，换 NVFP4 的速度；最大规模任务上预训练墙钟快 8%、RL 快 20%，RL 的 reward 无可测差异。Inkling 2 Small 是他们所知最大的、前向原生 4-bit 端到端训练模型，68 小时预训练完成。

  5. 值得记住的两句。一是「十六年前没人相信能用少于 32 bit 训练」，今天 BF16 已经被称为高精度；二是他们的 BBBK kernel 同时压满 NVLink、ALU 和 Tensor Core——低精度训练的瓶颈往往是 ALU 侧的 scale 计算、随机舍入、数据合并，而不是矩阵乘本身。

我的推荐：如果你在做训练或推理的成本优化，第 2、3 节（转置错配、随机舍入、通信量化）是可以直接搬的工程结论；如果只是想知道趋势，记住一句话就够：4-bit 不是推理的专利，它已经在预训练配方里，代价被量化成 2% 的计算效率。

把「agent 提交速度 > CI 检查速度」这个新瓶颈讲清楚的一份可执行清单 · ★★★★☆ · TLDR Dev

AI 写代码的时代，怎么把 CI 提速

为什么值得看：五个动作都有具体做法和踩坑点（缓存 key 别带时间戳、必需检查不能用 path filter、部署流水线不要用 cancel-in-progress），适合直接对照自家 workflow 改。

展开完整精读

一句话判断：它把「agent 写码比 CI 检查快」这件事从体感变成了数字，然后给出五条按性价比排序的动作。

  1. 先给瓶颈定量。2026 年 4 月 GitHub COO Kyle Daigle 说平台一周处理 2.75 亿次提交、按年化 140 亿（2025 年约 10 亿）；同一周 GitHub Actions 跑了 21 亿分钟，2023 年是 5 亿。也就是说 agent 的产出全部堆进了 CI：15 分钟的流水线，一个人一天推几次还能忍，一个 agent 一下午开十个 PR，它就变成了队列。

  2. 先测量，别猜。多数团队对最慢步骤的判断是错的——感觉是测试慢，实际可能是 90 秒装依赖 + 30 秒跑测试。做法很朴素：看最近十次运行的逐步耗时，取中位数而不是最差值，并把排队时间、环境准备时间、执行时间分开看，因为三者的解法完全不同。

  3. 缓存与分层。actions/cache 的关键全在 key：用 lockfile 哈希，依赖不变 key 就不变；restore-keys 是常被漏掉的一半——精确 key 不命中时能退到较旧的缓存，只补装新增的包。反过来，key 里塞时间戳或 commit SHA 就是永不命中、每次都存一份新缓存。Docker 同理：先拷 lockfile 装依赖、再拷源码，代码改动就不会重建安装层；跨运行复用层用 BuildKit 的 type=gha 后端。

  4. 硬件与并行。私有仓库默认 runner 只有 2 vCPU / 7 GB，这是很多「CI 慢」的真实原因。作者引用的第三方基准（RunsOn 的公开测试，关掉缓存，Rust 测试 + TypeScript 类型检查 + PostHog 生产 Docker 构建）里，4 vCPU 档的 Avrea 约 7 分钟对 GitHub 4 核 runner 约 18.5 分钟。分片则要认清边际收益：四个 shard 能把 12 分钟压到 3 分钟，但每个 shard 都要付一遍启动成本，超过临界点只增加花费；少数特别重的文件要单独拆，否则会有一个 shard 拖尾。

  5. 最便宜的一条：少跑。path filter 能把文档改动挡在全量构建之外，但必需检查不能用它——检查永远不跑，PR 会卡在 pending，正确做法是让 workflow 跑起来、用 if 条件跳掉 job（跳过的 job 算通过）。monorepo 用 Nx/Turborepo/Bazel 的 affected 只测受影响的包，注意 checkout 默认只取一个 commit，比较 main 需要足够历史。最后，连续两次推送时先跑的那次已经过期，用 concurrency 组取消；但部署流水线不要这么做，中途取消会留下坏状态，应该排队。

我的推荐：照着做第一、五条就能拿到大部分收益——先量出真正最慢的三步，再砍掉不必跑的工作。它引用的 runner 数据来自厂商自己的基准（作者也标了 Avrea 是文中的服务商），选型时用自家 workflow 复测一遍比看榜单可靠。
