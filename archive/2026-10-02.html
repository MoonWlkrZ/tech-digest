01
长时运行智能体的持久化设计范本：把每一步都变成带检查点的任务 · ★★★★★ · TLDR

Pi Durable

为什么值得看：与 Pi 1.0 同日出货的实验包，完整展示耐久智能体的存储、任务、压缩与多人协作设计，对自建 agent 基础设施的团队是一手材料。

展开完整精读

一句话判断：这是目前把智能体耐久性讲得最具体的一份工程说明——不是概念文，而是一套可以直接照着实现的设计：任务化、检查点、重放语义、所有权树。对做 agent 基础设施的人，这是今晚最值得读的一篇。

  1. 定位与背景：Pi 1.0 面向「一个用户在终端里跑编码代理」的场景；同日发布的 Pi Durable 是实验包，目标是任何地方运行、多种客户端接入、无限长会话、熬过崩溃、多人协作。它不替代编码代理，而是构建任意智能体应用的框架，与 Pi 共享 pi-ai 等代码，全部源码不含测试约 1.5 万行——刻意控制在模型能通读的规模，方便让代理自己改自己。

  2. 核心机制是任务与检查点：模型请求、工具调用、压缩各是一个任务，每个任务每步先把意图和进度写进存储再继续。进程死掉后，新进程打开同一份存储、找到未完成任务、从最后检查点续跑；被截断的模型请求重发，部分回答标记为 aborted 留在转录里。工具按声明的 replay 语义处理：只读工具可安全重跑；有副作用的（如 deploy）绝不自动重跑，而是把中断事实告诉模型让它决定。requestId 保证一次提交恰好一次，客户端崩溃后重试拿到的是同一个结果。

  3. 会话模型：一个 harness 并发跑任意多会话；任何会话可以从转录任意位置 fork，父历史不复制（文章用 Slack 频道与线程举例）。压缩作为后台任务提前进行，摘要放在下一个回合边界，老消息永不删除；reset/handoff 从一条交接笔记开新上下文后，旧历史仍可搜索——交接即失忆的问题被正面解决。

  4. 可扩展与可变更：扩展是系统提示片段、工具、钩子、任务的命名包；会话只存名字不存代码，重启后自动拾到新版本；同名 install 可在运行中替换实现，运行中的调用按启动时的代码跑完。所有权树让中止自底向上级联，每个任务负责清理自己的副作用。

  5. 对自建 agent 的借鉴点：SQLite 存储只把工作集放内存（活跃转录、运行中任务、待处理提交），几万条消息的会话也装得下；系统提示每次请求重建、变更记录进转录，支持中途修改的模型只接收到增量以保住 prompt cache；多客户端先给当前视图、之后只送增量，支持迟到加入与实时 steer。对照我们自己的运行时（会话持久化、cron、子代理恢复），这套组合是目前最完整的公开参考。

我的推荐：值得精读。重点关注任务与检查点一节、工具重放语义、压缩与 handoff 的设计；如果你在给任何长时运行的代理补崩溃恢复，直接照这份设计列自己的缺口清单。

02
写 MCP 工具的人必读：实测出两大客户端在「模型实际看到什么」上的大量未文档化差异 · ★★★★☆ · TLDR InfoSec

MCP Beyond the Spec: Inside Codex and Claude Code

为什么值得看：基于源码分析与抓包实测，覆盖审批注解矩阵、工具搜索排名、Schema 静默改写与输出截断，很多调试不出来的问题根源都在这里。

展开完整精读

一句话判断：写 MCP 工具的人必读——它实测出 Codex 与 Claude Code 在「模型实际看到什么」上的大量未文档化差异，很多调试不出来的问题根源都在这里。

  1. 视角：MCP 规范只定义客户端与服务器的通信，把「给模型看什么」留给客户端。Codex 开源，文章基于其仓库分析（版本 0.157.1）；Claude Code 闭源，作者用替换模型 API 做动态分析（2.1.283）。结论是快照式的，客户端演进后可能变化。

  2. 审批与注解行为：Codex 默认对 destructiveHint=true 或缺少注解的工具要求审批；只读工具是唯一默认并行调用的一类。Claude Code 的 readOnlyHint 只在计划模式与并行决策中使用，且 _meta 里的 requiresUserInteraction 会强制每次调用都问（dontAsk 模式直接拒绝）。文章给出五个权限模式乘五种注解的完整实测矩阵，并实测了并行行为（只读三个并行、无注解三个串行）。

  3. 工具发现被改写：两家都默认延迟加载 MCP 工具。Codex 走 code mode——模型初始看不到任何工具名和定义，要用 JavaScript 过滤工具列表；Claude Code 始终看到服务器说明与工具名、但不给定义，用一个关键词搜索工具来取，文章完整复盘了它的排名规则（名字整词最高、再是 searchHint、最后描述，词形处理有坑，如 invoice 搜不到 invoices）。

  4. 静默截断与改写：Codex 对插件方式安装的服务器截断 1000 字节以上的描述；把输入 Schema 规范化为 TypeScript 时直接丢掉 default/minimum/maximum/pattern/format 等关键字（实测例子：integer 变 number、边界与默认值全消失、无 type 的嵌套字段连描述都被清空）。Claude Code 默认截 2048 字符，可用环境变量调整。输出侧：Codex 按 4 字节每 token 估算截 40KB 且从中间截断；Claude Code 超 50k 字符转存文件、只给 2000 字符预览。写 MCP 工具时把这些限制记在心上，很多「模型漏看约束」其实是被客户端剪掉的。

  5. 为什么要读：这不是理论文章——每个结论都有版本号、源码行号和抓包实测。它还给出可操作建议：先用 MCP Inspector 验证，再用本地代理抓真实请求；并提醒 code mode 是趋势（Hex-Rays 的 IDA MCP 也跟进，Anthropic 自己的案例报告 token 降 98%）。对每天用 Codex/Claude Code 的人，这是一份「为什么工具不听话」的问题地图。

我的推荐：值得精读。优先看审批矩阵、工具搜索排名、Schema 改写三节；如果你在写或维护 MCP 服务器，按文末清单过一遍兼容性再发版。

03
生产规模的智能体身份方案：每一步一个短期 JWT，把完整授权链带进每一次调用 · ★★★★☆ · TLDR InfoSec

Solving the Identity Crisis for AI Agents

为什么值得看：公开了可审计的多代理授权架构：SPIRE 工作负载身份、自定义 STS 单跳令牌、Agent Registry 防冒充、MCP Gateway 策略执行，附低于 40ms 一跳的开销数据。

展开完整精读

一句话判断：一份少见的、生产规模的智能体身份方案公开说明——核心是「每一步一个短期 JWT，把完整授权链带进每一次调用」，值得任何要让代理安全访问内部系统的团队参考。

  1. 问题定义：现有身份模型围绕人类与工作负载（服务账号/API key）构建，描述不了「代理」这种代他人行事的实体；更麻烦的是执行上下文在代理间跳跃时丢失——文章开场的例子很典型：值班工程师触发 Oncall 代理，经 Investigation 代理最终由 Monitoring 代理提交了 PR，但 PR 上看不到工程师是谁。审计断链导致事件响应只能靠人肉拼接各系统日志。

  2. 身份发放：工作负载先从 SPIRE 拿 SPIFFE 身份（证明运行环境合法），SDK 再带本地元数据、入站 JWT 和目标受众去自定义 STS 换令牌；STS 与 Agent Registry 核对该 agent_id 是否被允许跑在这个工作负载上，防止冒充。每个 JWT 单跳、短 TTL（分钟级）、带明确受众，无法被拿去重放到另一个服务。

  3. 溯源传播：STS 在每次交换时把完整 actor chain 写进令牌——下游（如 MCP Gateway）看到的是 user1 到 oncall-agent 再到 investigation-agent 的全链路，而不是只有最后一个调用者。这样策略引擎可以同时按「人类发起者」和「代理身份」评估授权。机制借鉴 OAuth 2.0 Token Exchange（RFC 8693）但按内部审计与性能需求定制。

  4. 落地与治理：MCP Gateway 是策略执行点，做工具级授权与敏感数据脱敏；为消化历史上先建的代理，他们做了 secure-by-default 的标准 A2A 客户端，把令牌交换与链路传播自动化——安全路径同时是最省事的路径。可观测性覆盖从用户到每个下游工具调用的每一跳，新增一跳延迟低于 40 毫秒。

  5. 行业位置：文章明确说在跟踪 IETF WIMSE 工作组和 AI Agent 认证授权草案（draft-klrc-aiagent-auth），说明这块标准还没定，Uber 这套是当下最完整的生产实践之一。对要跨多个自研代理做权限与审计的系统，这套架构（Agent Registry + STS + Mesh + MCP Gateway）可以当参照基线。

我的推荐：值得一读。重点看身份发放四步与 actor chain 传播两节；如果要设计内部代理的权限体系，先确定「谁授权、令牌受众、链路如何携带」三个问题的答案。
