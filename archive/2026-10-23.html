里程碑级：形式化验证第一次跑到了真实开源库的机器码层面，而不是玩具证明。 · ★★★★★ · TLDR

LLMs are making formal software verification feasible at a much larger scale

为什么值得看：Anthropic 与 Theorem 合作，让 Claude 在 123 个 OSS-Fuzz 库里对编译后的 RISC-V 机器码写证明，顺手挖出人类测试几年没发现的 bug。这是「AI 找 bug」之后必须补上的一环：证明没有 bug。

展开完整精读

一句话判断：这是「AI 让找 bug 变便宜」之后的另一半拼图——让证明「没有这类 bug」也变便宜，而且第一次落在生产软件的编译产物上。

  1. 做法很聪明：不追求给整个程序写规格说明，而是把已有的 fuzz 测试改写成规格。「这个 fuzz 入口在 RISC-V 上跑，任何小于 64MB 的输入都不会崩」——于是原本靠暴力变异碰运气的模糊测试，变成了一条可以被证明的定理。Claude 证明了 239 个入口、横跨 123 个 OSS-Fuzz 库，产出约 1.8 亿行 Rocq；典型证明 60 万行，对应中位数只有 1.8 万条 RISC-V 指令的二进制。

  2. 证明过程本身就是漏洞挖掘器，而且挖的是 fuzzer 结构上碰不到的角落：一个解压器里的计数器下溢导致越界写，只在约 20MB、特定布局的输入上触发；一个图像解码器需要 64MB 输入加 2GB 内存才暴露越界读；还有需要跨两个文件句柄的特定调用序列才出现的读越界，以及 libexpat 的 CVE-2026-56132 被重新发现。逻辑类 bug 也能抓：某库「限制可加载文件」的功能并非在所有路径上生效。对照点是 fuzzer 通常把输入压到 1MB 级。

  3. 可信基（trusted base）被压到很小，这是工程上最值钱的部分：1.8 亿行证明几乎不需要人读，因为 Rocq 检查器会验；开发者真正要信的是 RISC-V 与 Linux 进程语义模型、被证明的那几条定理陈述、以及检查器本身。换句话说，审计面从「几十万行 C 代码」缩成「几个形式语义模型」，而且这个面不随被验证项目数量增长。

  4. 局限写得比宣传诚实：形式化验证不等于无 bug，规格与真实机器不一致时证明就失效（当前是单线程静态 musl 二进制，线上多是 x86/ARM + glibc 动态链接）；ASan 也覆盖不了全部内存安全问题；即便每个入口都证了，库里的死代码与调用方的误用仍在射程之外。这几条决定了短期内它是「补强」而非「替代」测试。

  5. 经济性正在快速变好：Opus 5.5 在 36 个小验证任务上比 Opus 5 少用约 40% token 就证完一半；让 agent 共享已完成的证明可再省 17%，部分单干失败的 agent 靠抄同伴的证明过关——这和 Mathlib 靠复用长到 30 万条定理是同一个机制，而依赖是幂律分布的：先证 glibc、OpenSSL、cURL 这类少数关键库，覆盖面就上去了。

我的推荐：值得完整读一遍，尤其是「怎么把测试改写成规格」和「可信基只剩三样」这两节。它给出一条现实路径：不用重写代码、不用换语言，先在二进制层面把最关键的依赖证掉。如果你在做安全、编译器、或者任何「测试跑了几万亿次还是不放心」的系统，这是今年最该读的一篇。

一个 3500 人公司被迫自研源码控制系统的完整现场记录，附赠一场开源抄袭争议。 · ★★★★★ · TLDR

The Pulse: Anthropic builds its own source control system

为什么值得看：四个月里每天合并量从 2500 涨到 3 万，25GB 的 monorepo 每天 2500 万次 checkout，git 的镜像方案直接撞墙。想看清 agent 规模化之后工程基础设施会先在哪断掉，这篇给的是第一手数字。

展开完整精读

一句话判断：当 agent 把代码产出放大一个数量级，最先崩的不是模型也不是人，而是 git 这类「为人类节奏设计」的基础设施。

  1. 数字本身就是结论：2026 年 5 月 Anthropic 日均合并约 2500 次代码变更，9 月超过 3 万次，四个月 12 倍；约 3000 名员工，每人常态开 10–15 个 Claude agent；光是 CI 每天就要 2500 万次 checkout；monorepo 工作副本 25GB。作者 Gergely Orosz 的判断是：3500 人的公司，产出对标 3.5 万到 7 万人的组织。

  2. 为什么 git 撑不住，文章讲得很具体，不是「git 慢」这种废话：其一，git 的设计假设客户端会离线，回到线上要追平分支，而 Anthropic 的客户端始终在线，为离线付出的代价变成低效 checkout 与多余数据传输；其二，git 的横向扩展靠镜像——主节点收写、推给上百个镜像、客户端分散拉取，一旦仓库超过镜像磁盘容量就没法再加；其三，3 万个 PR/天带来的评审与合并队列压力，GitHub 的评审体验也接不住。

  3. 替代品的工程细节值得抄作业：Scion 服务端与客户端都用 Rust，changeset 放 Google Spanner、大文件放 GCS，数据内容寻址且写入后不变，所以缓存层承担了大部分负载——合并量涨了 10 倍以上也没触发自动扩容。可用性上把默认的三副本加到更多、改成多地域复制，再加全量备份与 Spanner 的按时间点恢复。评审平台 Antique 是 Go 后端 + React 前端。整套东西 7 个人维护（4 人核心、3 人做代码搜索与合并队列）。迁移 100% 完成，Claude 在迁移里出了大力，作者形容为「自愈式」：覆盖到 99% 就强切，剩下由 Claude 补。

  4. 争议不该被略过：Mononoke（Meta 开源的 Mercurial 服务端）作者公开指控 Scion 抄袭其数据模型与 Bonsai 序列化结构，并称存在人员重叠；Anthropic 最初的文章没有致谢，投诉后才补了一条小注脚，并以「带宽不够、代码变动太快」为由拒绝开源。对照 Meta 当年照样开源了 Sapling 与 Mononoke，这个解释站不住。读这篇时把技术部分和这件事分开看：架构经验可用，致谢与开源态度是另一个问题。

  5. 对大多数团队的现实意义：作者判断极少公司会真的自研 VCS，但「agent 把合并量推高 10 倍后 git 会不会坏」已经从假设变成可观测的问题。市场上出现了一批主打 AI 规模的 git 兼容方案（Entire、Cursor Origin、Code Storage），GitHub 也在补可靠性与扩展性。真正该带走的不是「去写个 Scion」，而是：先量一下自己的 checkout、CI、评审队列在什么量级开始非线性劣化。

我的推荐：当作一份「agent 规模化后的基础设施故障报告」读。前半段的数字与 git 失效机制值得逐条对照自己团队；后半段关于 Mononoke 的争议，是判断一家实验室工程文化的重要旁证。

03
少见的把「成本怎么降下来」拆到每一段的实测报告，方法和结论都能直接搬。 · ★★★★☆ · TLDR Dev

How we cut GitLab Duo Code Review's cost by 98%

为什么值得看：同一个 agent、同一批 50 个 PR，单 PR 成本从 0.589 美元降到 0.0135 美元，F1 还略升。关键不是换了便宜模型，而是先量出钱花在哪一段，再逐段改、改完回头重测。

展开完整精读

一句话判断：这是一篇可以直接照抄方法的成本工程案例——先按阶段归因，再一次只改一个变量，改完回头重测之前的所有结论。

  1. 先把钱花在哪说清楚。GitLab Duo Code Review 是四段式流水线（探索仓库树、抓取相关文件、分析、评审），默认全段 Claude Sonnet 5，基线 0.589 美元/PR、F1 46.4%。账单集中在评审段：65%，其中光输出就占三分之一——Sonnet 5 每次评审写约 1.86 万输出 token，几乎全是推理；探索与抓取合计 27%，分析 9%。这种归因比「换个便宜模型试试」有用得多，因为它告诉你哪一段值得动。

  2. 第一个发现反直觉：压缩上下文省的钱比算术预期少。用规则（不做摘要）把变更文件的上下文窗口化成「每个 hunk 前后各 25 行」，并把带双重行号标签的逐行 diff 改写成标准 unified diff，中位提示从 59K 降到 32K token，评审段上下文花费降 62%。但总成本只降了 19.4%——因为 Sonnet 5 在压缩后反而写了更多推理（1.86 万涨到 2.38 万输出 token）。这条对做 agent 成本优化的人很关键：输入省下来的钱，可能被模型「想得更多」吃掉。

  3. 第二个发现是「换模型要看阶段」。Haiku 4.5 放在探索和抓取两段，选中的文件和 Sonnet 5 一样，成本降 15.4%（叠加压缩 34.6%）；一旦放到分析和评审段，质量立刻掉，评审段掉得最狠。真正的大头在评审的推理，只能换出 Claude 家族：DeepSeek V4 Flash（自建 vLLM on H100）按 Together 公开价，输入便宜 14 倍、输出便宜 36 倍，全段替换后 0.086 美元/PR，降 85.3%，F1 48.4%，延迟 0.37 倍。

  4. 为什么停在 85%：自建部署只接 256K 以内的提示，更长的留给 Sonnet 5 兜底；不做压缩时部分评审提示到了 480K，50 个 PR 里有 3 个越界、产生 11 次回退调用——6% 的 PR 吃掉了剩余成本的 77%，典型的尾部分布。把压缩重新加回来，最大提示从 480K 降到 109K，全部装进窗口，成本到 0.0135 美元/PR（−97.7%），F1 47.2%，延迟 0.35 倍。注意同一项改动的价值变了：在 Sonnet 5 前面它是 19.4% 的成本优化，在 256K 部署前面它是「能不能用这个模型」的开关。

  5. 边界条件写得诚实，读的时候要一起读：配置是在用于评分的那 50 个 PR 上选的，属于样本内调参；F1 只是单一公开基准、两个裁判模型；换新代码库是否成立未验证；具体设置已过时（GitLab 之后把 Duo 换到了 Sonnet 5.5）。能带走的只有方法：按阶段量成本、一次改一个变量、每改一项就回头重测旧结论。另外质量结构也变了——终版更准（精确率 46.8% 对 41.9%）但召回略低（47.6% 对 52.0%），输出约 9000 token 而不是 1.86 万。

我的推荐：如果你在任何地方跑 LLM 代码评审或长上下文 agent，这篇是本周最实用的一篇。重点读「钱花在哪」「为什么停在 85%」和「没用的招」三节——尤其最后一个表，它帮你省掉三次注定无效的尝试。
