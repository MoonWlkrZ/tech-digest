深度案例 · ★★★★★ · ByteByteGo

GitHub 如何用 AI 把 Copilot 从 TypeScript 迁到 Rust

为什么值得看：一篇少见的完整迁移复盘：80 万行代码、单人主导、几个月完成，而且把 token 成本、性能前后对比、以及迁移中真实踩到的回归都摆了出来。想在自己仓库里试 agent 大规模改写的团队，可以把它当成一份带数字的风险清单。

展开完整精读

一句话判断：这是目前公开材料里最扎实的一次「AI 主导的大型语言迁移」复盘，价值不在结论多震撼，而在于它把方法、成本和翻车点都写清楚了。

  1. 问题从哪来：Copilot 的运行时要被嵌进 Python、Java、C# 等宿主应用，但原实现是 TypeScript 跑在 Node 与 V8 上，每个客户端光启动就要背约 100MB 内存，还要多起一个进程、多监控一个可能崩掉的 Node 进程。改成可被宿主进程直接加载的 Rust 库，动机是资源与可嵌入性，不是追新技术。

  2. 迁移怎么切：没有推倒重写后一次性切换，而是在原仓库里逐组件替换。一个组件的 TypeScript 实现和对应的 Rust 实现在同一个 PR 里完成，中间用一层薄包装桥接，旧实现当场删掉，逼着团队只维护一份活代码。顺序按依赖排：先动有强测试、不共享状态的小工具函数，用它们把构建、打包、跨语言调用这条路走通；状态管理、模型客户端、集成依次跟进；最复杂、需要多轮返工的会话编排留到最后。整程目标只有一条：保持原有行为与算法，重构一律推迟到迁移之后。

  3. agent 怎么组织：协调 agent 先把大组件读透再拆任务。最典型的是 3 万行的 session.ts，协调 agent 花一小时读代码，然后拆给 15 个子会话，每个子会话有自己的分支和工作副本，最后把改动合回自己的分支。15 个会话同时构建测试直接把开发机压垮，后来改成子会话不做重构建、只在父会话跑，并另开一个会话做构建闸门，一次只放一个构建通过。

  4. 代码怎么审：仓库一直在变，所以每一步都要先 rebase 到最新主干，再检查新进来的 TypeScript 改动有没有同步到 Rust——删掉旧文件本身就是一种提示机制，别人再改那个文件就会撞冲突。审查由多个不同模型的 agent 逐行对比新旧实现，重点看行为差异、Rust 实现是否够高效、旧代码与临时包装有没有清干净，以及端到端测试有没有被改动。人只看架构、接口契约和 agent 标出来的风险点。

  5. 真实代价：整项工作的 token 费用约 12 万美元（原文为 $120K，约 1360 亿 token，大头是缓存输入），外加其他开发者在集成、打包、构建和评审上的投入。回归也很具体：整数被译成浮点导致某些 SDK 出错，空字符串、时区、替换库的错误处理语义不一致；取消操作没有真正停掉子任务，资源释放过早导致会话卡死；Rust 代码跑到 Node 主线程上把界面冻住；Windows 上缺进程启动参数弹出多余控制台窗口。

我的推荐：值得精读，尤其是准备让 agent 动大仓库的人。三条可以直接抄走：先迁移有测试覆盖的小件来验证整条链路；行为不变优先，别把迁移和重构混在一起；把端到端测试当成唯一的期望行为来源，并且要有机制防止 agent 为了让测试过而改弱测试。

一线实验 · ★★★★★ · TLDR Dev

1000 个 agent、28.7 小时：多智能体团队重做费马大定理形式化证明

为什么值得看：Anthropic 把多 agent 协作的工程量摊开讲：1000 个沙箱、一张共享 SQL 数据库、Git 主干验收，以及过程中 agent 如何自己建表分工、如何低估难题又被提醒拉回来。对正在设计多 agent 编排的人，这是一份有具体数字的参考架构。

展开完整精读

一句话判断：这篇不是「AI 会做数学」的宣传，而是多 agent 系统的工程记录——它把协调机制、失败阈值和安全边界都写到了可复现的程度。

  1. 实验设置：60 条命题（最终定理加 59 个中间里程碑）、47 条 9 月形式化时已证明的引理，外加一句古典路线的提示。没有 Prove2Me 那样的专用平台，没有研究员随时纠偏，只有 1 个 lead 加 999 个 helper 的层级，以及每个 agent 一台无网络的轻量虚拟机。

  2. 协调靠自己长出来：开头十分钟，lead 在共享数据库里建了五张表——分工、任务、笔记、公告、结果；写 999 行把每个 helper 指派到一条命题，每组 16 到 17 人，各组指定一个 captain 出计划、拆任务。27 分钟时三条命题已证完，lead 读完成员的难度判断，把 47 条被判「预算内做不完」的命题先放到一边，把人力压到剩下 10 条上，小组从 17 人扩到 46 至 139 人。70 分钟内这 10 条全部完成，lead 随即说「没有理由闲着」，把人调回难题。到第 5.6 小时，73 个 helper 写了 756 个任务，其中只有 16 个是 captain——分工权从 lead 下沉到了执行层。

  3. 最硬的一块：Langlands–Tunnell 的 captain 早先估计至少要 70 万到 100 万行 Lean、按时完成概率不到 1%，lead 也承认「胜算不高」，但在第 18 小时把约 750 个 helper 压了上去。任务被组织成树，一块太大就往下拆，最终 2418 个任务、最深 10 层，子任务可以假设下层已成立，于是几百个 agent 能并行推进。第 28.4 小时该命题通过，第 28.7 小时主定理进了主干，Lean 官方检查器验过。

  4. 规模化的真实瓶颈与安全：一台共享机器在约 100 个 agent 时就撑不住，100 个 agent 的试跑里超过一半因内存、磁盘或 CPU 耗尽被中止或重启，所以改成一人一台沙箱。安全上是三层：无网络沙箱、逐条工具调用过 LLM 分类器（命中即全队暂停等人复核，防止另一个 agent 接着做被拦的动作）、离线监控复查全队行为。这次实际只启用了基于动作的监控，整场一百万次以上工具调用没有一次达到拦截线，事后用带思维链的监控重放，只有一次检查 root 权限的动作接近边界。

  5. 局限：agent 会系统性低估难题——60 条里有 47 条一开始被判做不完，最后大多做出来了；也会提前放弃，需要人或其他机制在关键时刻推一把。作者自己也说，这不能替代领域专用平台，Prove2Me 那类工具在编译与复用人类结果上仍有优势。

我的推荐：做多 agent 编排的人值得精读。最该记住的不是 1000 这个数字，而是三件事：共享数据库加 Git 主干就够撑起千级协作；瓶颈会先出现在单机资源而不是模型能力；监控要能一键停全队，否则拦得住一个动作拦不住下一个 agent。

方法论文 · ★★★★☆ · TLDR AI

AutoCompress：按目标硬件实测约束来压缩大模型

为什么值得看：把剪枝的目标从「参数量」换成「目标机器上的实测延迟、吞吐与显存」，并在 vLLM 里校准代价模型。三个部署场景都有对照实验，其中 RTX 5070 那条 4GiB 显存、750ms 延迟的设定，对本地跑模型的人直接可参考。

展开完整精读

一句话判断：这是一篇工程取向很明确的压缩论文——它不追求在固定参数量下刷分，而是先问「这台机器、这个负载、这个引擎，能装下什么」，再让搜索去满足约束。

  1. 动机：现有剪枝流程大多给人一个参数预算，再由人去猜这个预算能不能满足延迟和显存。但参数量并不预测延迟：同样的参数，层结构不同、专家数不同、批大小不同，跑在 vLLM 里的时间可以差很远；只按权重加 KV 缓存估显存，还会漏掉执行工作区与运行时缓冲。结果是工程师要反复试错，才能把部署指标翻译成剪枝目标。

  2. 方法：把硬件约束直接写进可微架构搜索。搜索空间同时包含全局维度（隐藏层宽度、Mamba 头数）和逐层维度（每层专家数、路由与前馈宽度，宽度可以取零来删层），因此允许不同层保留不同容量，而 Minitron 那类方法要求各层统一。代价模型在目标引擎里测：用约十种层配置拼一个短模型跑一遍，按层边界用 Nsight 分别量 prefill 与 decode 的 GPU 时间，再相加估算整模型延迟；显存则按权重、请求缓存、prefill 工作区和运行时缓冲逐项算，另加一个实测残差项兜底。路由器用 Gumbel-softmax 采样软架构，蒸馏损失加一个只在超出预算 98% 到 100% 区间时才生效的惩罚项。

  3. 三个场景：RTX 5070 上的游戏 NPC，4GiB 显存、750ms 端到端、2048 输入 256 输出；RTX 5080 上的本地编码 agent，26 万缓存加 1.6 万输入、11.5 秒、13.96GiB；8 张 H100 的数据中心批推理，每卡 batch 128、8192 输入 65536 输出，目标比父模型吞吐高 50%。

  4. 结果：八个基准平均分相对按同样约束改造过的 Minitron++ 分别高 6.57、2.35、0.57 个百分点，蒸馏损失低 19.3%、4.3%、0.6%，而架构搜索用的 token 只有对方的二分之一到三分之一。两个消费级卡上的学生模型实测达标：739.7 毫秒、3.93GiB，以及 11.1 秒、13.61GiB。放大到 Nemotron 3.5 Super，120B 压到 74B（减 38.3%），在单张 B200 上以 BF16 跑 128K 上下文、batch 16 占 178GB，九项基准均值 54.74，父模型 57.58，保住约 95%，比同规模参考模型 Nemotron 3 Super 高 9.30 分。整个搜索加恢复训练用 32 个 GB200 节点跑约 64 小时。

  5. 值得挑刺的地方：单层耗时相加仍是近似，层结构变化会改变 kernel 选择与缓存行为，作者只用留出模型验证了误差；H100 那一档收益只有 0.57 个百分点，说明结构统一的场景下逐层异构的空间有限；大模型案例没有跑 Minitron++ 对照，省下的对比只能靠小模型那三组外推。

我的推荐：做端侧或私有部署的人值得读。最实用的一点是方法本身——先量清楚目标引擎在你的负载下的延迟与显存，再把这组数当成搜索约束，比盯着参数量挑模型靠谱得多。
