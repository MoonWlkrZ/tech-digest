01
agent 时代把 Git 的本地独立假设变成负担，Scion 用服务端集中 + 客户端薄缓存重构源码控制 · ★★★★★ · ByteByteGo

How Anthropic Redesigned Source Control

为什么值得看：不是又一篇架构综述，而是把 2500 到 30000 次日合并、每天 2500 万次 checkout 这些数字摊开，再逐条解释为什么 Git 的既有优化手段在这里失效；对任何被 CI 检出和 agent 沙箱拖慢的团队都能直接对照。

展开完整精读

一句话判断

Git 假设每个客户端都值得拥有一份自包含的仓库，这个假设在人类开发者身上成立，在每天几千万个自动化 job 身上不成立；Scion 把仓库操作收回服务端，客户端只做缓存和文件落盘，用责任划分而不是更聪明的传输解决规模问题。

1. 问题有多大

Anthropic 的代码主要在一个 monorepo 里。合并变更从 2026 年 5 月的约 2500 次/天，涨到 9 月的 30000 次/天以上；主分支历史接近 100GB，即使压缩后的工作副本也超过 25GB。CI 每天大约做 2500 万次 checkout，这还没算开发者环境、agent 沙箱和研究任务。一次变更可以派生许多 job，每个 job 都要准备环境，所以基础设施负载远大于变更数。按最朴素的方式，每次 checkout 传一份压缩工作副本，一天就是 600PB 以上的流量。问题因此有两面：既要快速接收新变更，又要把代码分发给海量消费者，只优化一面，另一面立刻成为瓶颈。

2. 为什么 Git 顶不住

Git 的价值在于本地独立：完整克隆之后，看历史、比版本、建提交都不需要中心服务。但 Anthropic 的客户端绝大多数是自动化 job 和 agent，本来就依赖网络服务，这种独立性用不上，反而要为每份数据付重复传输、存储和维护成本。他们并没有少用 Git 的优化手段：shallow clone、sparse checkout、partial clone、内部镜像、repository seeds 都上了。第一版架构就是 job 从 seed 起步、通过缓存补数据、外面套多层镜像，峰值时运行几百个内部镜像。问题是镜像之间要同步，仓库变化一快 seed 就过期，而客户端只持有部分历史后，任何需要历史的操作都变得难做。

3. Scion 怎么改

Scion 的核心是 client-server 不对称：服务端负责历史查询、计算 diff、创建提交、合并与 rebase；客户端 scn 只维护有限缓存、在磁盘上准备文件、监听本地改动，并给开发者和 job 提供接口。一个工具想知道某行代码的来龙去脉，直接问服务要答案，不必先攒够本地历史；创建提交也是服务端操作，没有单独的 push 步骤。服务端本身不是单机：数据分散在多台机器上，没有任何一台持有完整仓库，代价是对可用性和连通性的强依赖。

4. 变更怎么表示

Scion 用 changeset 作为变更的持久记录。它只记录相对第一父提交改了哪些文件以及内容引用，元数据放在 Spanner，压缩后的文件内容放对象存储，root tree 由服务端按需派生而不是塞进 changeset。这样记录一次变更只需要处理改动到的数据，不用碰整个仓库；合并提交可以有多个父提交，第一父提交充当基线。

5. 缓存与扩展

对象按内容寻址，ID 由内容哈希得到，因此对象不可变：同一个 ID 永远指向同一份数据，缓存不需要因为仓库别处有开发活动而做新鲜度检查。扩展靠四件事叠加：仓库操作变成 API，客户端直接问结果，服务端把派生数据算好存进 Spanner；不可变对象让共享缓存变得简单；客户端按 tree 和 blob 精确请求缺失对象，服务端不需要定制传输；缓存分三层，节点上的 scion-daemon 在 job 之间共享对象，缺失时找区域级 scion-cache，再缺才回权威服务。三层实现同一套对象请求接口，区域缓存故障时不会把权威层打穿。

我的推荐

值得读的不是某个具体组件，而是那句判断：当客户端几乎全是在线自动化任务时，把能力放在客户端是浪费。文中还给了两个反直觉的细节：Scion 和代码评审工具 Antique 一共只有七个人做；团队里所有人都认为 Claude 写代码比自己强，而人的价值在于理解系统间的高层关系和阻止 Claude 走某条路。如果你的 CI 正在被 checkout 拖慢，这篇值得当成设计对照表来读，而不是当成可以直接照搬的方案。

02
把「你用的到底是不是那个模型」变成可验证的密码学命题，FlashProve 把 400B MoE 的证明成本压到单卡 110 token/s · ★★★★★ · TLDR AI

Progress on provable inference for large language models

为什么值得看：这是少见的、把研究动机、系统实现、实测数字和局限一次讲完的进展报告，还开源了代码和 Lean 证明；做模型路由、审计或 agent 供应链的人都该知道现在的能力边界在哪里。

展开完整精读

一句话判断

当模型变成按 token 计费的服务，用户其实无法确认响应来自自己选的模型——路由服务可能为省钱换模型，攻击者可能篡改 token 流。Anthropic 给出的答案是用 zkSNARK 做可验证推理：证明不小，但已经小到可以在 CPU 上几秒验完，成本也从「不可能」降到「两个数量级的开销」。

1. 要解决的问题

今天用户查模型，几乎没有握手的凭据：看不到、听不到、也摸不到。仅凭输出质量判断并不可靠。三类场景最需要证明：独立评测机构要确认评的就是被服务的那个模型；通过第三方路由的客户要确认 token 来自自己付费的模型；攻击者篡改 token 流时，用户无法从输出察觉。还有监管场景：要求服务商只用获批模型，或要求硬件确实在做推理而不是偷偷拿去训练。

2. 方案长什么样

FlashProve 分两段。离线阶段，服务商发布对权重的承诺——一个很短的指纹，钉死某一组权重，同时不暴露权重本身。在线阶段，对每个请求生成一份证明，声明「被承诺的模型在这个 prompt 上会产生这些 token」。任何拿到承诺、prompt 和回复的人都能验证，不需要权重，也不需要大机器。协议要同时满足四条：诚实的证明一定被接受；伪造在密码学上不可行；证明不泄露权重、中间值或每一层激活了哪些专家；证明足够小、验证足够快。

3. 实测数字

测试模型是 Llama 4 Maverick，400B 参数的 MoE，每个 token 约用 17B 参数，使用公开的 4-bit 权重。离线承诺每模型一次，约 39 分钟，之后可用于约 1600 万次请求。在线阶段 24 个请求一批，在单张 H100 加 24 核 CPU 上耗时 223 秒，折合 110 token/s，每条证明 18.78MB。验证端不需要 GPU：下载约 6.5MB 的承诺，再对每个请求验证，24 线程 17 秒、单线程 21 秒。与 vLLM 跑同一个模型相比，每 GPU 的证明时间约为纯推理的 72 倍，高负载下约 94 倍。作为参照，此前开源系统在同一个 400B 模型上是 0.02 token/s 量级，证明接近 94GB、验证要一天。

4. 工程上做对了什么

证明工作量与实际激活的专家成正比，而不是与 400B 全部参数成正比，MoE 的结构被用来省算力，同时证明仍然不暴露选了哪些专家。请求不逐条在线证明，而是成批、事后证明：一次并行读完已生成的文本，每批只打开一次权重承诺。系统按层切分权重、流式载入，所以一张 80GB GPU 加约 290GB 主机内存就能跑，不必把 232GB 的量化权重全塞进显存。他们还用 Lean 形式化了完整性与可靠性、零知识这三条顶层性质，并提供一个可执行的慢速 Lean 验证器，与日常使用的 C++ 验证器在测试中结论一致。

5. 别忽略的局限

这是研究原型。证明针对的是整数版本模型加贪心解码，浮点实现或采样解码可能在某个位置偏离，就不再与所证明的计算一致；上下文只支持到 1,024 token，离真实对话窗口很远；只隐藏权重、不隐藏架构；证明耗时这类侧信道没有纳入威胁模型；快速 C++ 验证器没有形式化保证，Lean、论文、代码三者一致靠人工审计。所以它证明的是「方向可行、成本可测」，不是「明天就能上线」。

我的推荐

如果你的产品要回答「这条回复真的来自这个模型吗」，这篇文章值得完整读完，尤其是第 6 节的横向对比——它把 zkML 过去几年从 0.001 token/s 到 110 token/s 的曲线摊开了。读完再判断：你要的是可验证推理，还是更便宜的 TEE 方案；两者的信任假设完全不同，文中也明确说它们是互补而非替代。

两个人、一次 2.1 万美元的训练，从零做出可用的 2B 文生图模型，关键取舍是丢掉 VAE 在像素空间压缩 · ★★★★☆ · TLDR AI

Training a Text-to-Image Model for $21K

为什么值得看：少见地把训练设置表原样公开：样本数、步数、学习率、EMA、硬件全给了；对想估算「小团队自研模型到底要多少钱」的人，这比任何榜单都有用。

展开完整精读

一句话判断

2.1 万美元听起来像个营销数字，但这篇的价值在于它把架构动机和训练设置都摊开了：为了降低注意力的 O(n²) 成本，他们不用 VAE，直接在像素空间做扩散并自己学压缩，结果 token 数减少 4 倍、收敛快 11 倍，代价是模型只有 2B、复杂场景明显吃力。

1. 为什么去掉 VAE

视频和图像生成的瓶颈都在注意力，成本随 token 数平方增长，压缩得越狠越便宜。业界通常用单独的 VAE 做压缩，但作者认为 VAE 的压缩率有经验上限，更麻烦的是重建质量和下游生成质量不是一回事：把 VAE 调得重建更准，扩散模型生成反而可能更差。既然扩散模型比 VAE 更强，就让它一边压缩一边生成，学一个为自己的用途定制的潜空间。

2. 架构细节

文本和图像各经过两个单模态 refiner DiT block，然后并成 22 个相同的 DiT block。文本表示取自冻结的 Qwen3.5-4B，读第 7、15、27 层——它的三个全注意力层——拼接后投影进文本 refiner。图像切成 32×32 patch 压到 1024 维，再投影进图像 refiner。第 5 个 block 后接一个两层 PixelREPA 读出，把潜空间对齐到 DINOv3-L；主干第 10、16 个 block 后各有一个线性读出头，分别预测四分之一和一半分辨率的干净图像，用低分辨率预测给出更早的梯度信号。总损失是各读出头的 MSE、PixelREPA 余弦距离、最终输出头的 MSE，加上全分辨率上的 LPIPS 与 P-DINO 感知损失。

3. 训练账本

512² 阶段跑了 6.1027 亿样本、297,985 步；切换到 1024² 后再跑 4,997 万样本、24,400 步。全局 batch 都是 2048，硬件是 8 个节点共 64 张 H100，bf16 加 FSDP2。优化器混用：二维矩阵块用 Muon，其余用 AdamW，并把 Muon 的更新做 RMS 匹配；峰值学习率 2e-4，先线性预热 100 万样本，平到 5.5 亿样本，最后 6000 万样本按 1 减根号衰减到 2.5e-5。噪声课程是前 8000 万样本集中在高噪声学结构，之后放宽学细节；EMA 从 1 亿样本开始，半衰期 1954 步，还对梯度尖峰做了保护——梯度范数超过滚动中位数 10 倍时暂停 EMA 更新 250 步。

4. 结果与短板

作者给出的总训练开销是 2.1 万美元，但文章没有拆解这笔钱的构成（算力单价、数据准备、失败的实验都没单列），所以别把它当成可复现的通用价签。能力上，这个 2B DiT 加 4B 文本编码器的组合在全身、多实体（六辆车、人群）、多人交互和世界知识上明显吃力；更关键的是训练数据里过滤掉了渲染文字，所以它不会写字、做不了海报和信息图。作者说这是刻意的：这些数据对他们的动画工具目标没用。

5. 值得记下的方法论

他们没有把「小模型效果好」当结论，而是当成通往更大视频模型的压力测试：先在小规模上验证像素空间压缩这条路，再往上堆。后训练部分也很坦白——扩散模型的后训练还很年轻，DPO 容易过拟合审美，Flow-GRPO、Diffusion NFT、FDFO 都才出现不久，根本原因是扩散模型拿不到自回归模型那样的强似然估计。

我的推荐

把它当一份工程账本读，而不是当教程：附录的训练设置表可以直接对照自己的实验；也是少见的、愿意把失败案例和局限写清楚的团队。如果你在评估「自研小模型」的可行性，这篇能帮你把预算和预期都校准一遍。
