强烈推荐——今晚最该读的一篇 · ★★★★★ · TLDR Dev

The Agent Said It Was Done. The Database Disagreed.

为什么值得看：把「代理是否可信」拆成可复现的度量：507 个业务流程 × 20 次重复、只看数据库终态——67% 的失败没有任何报错，这个数字会改变你验收代理的方式。

展开完整精读

一句话判断

代理评测的范式应当从「模型说了什么」转向「系统留下了什么」：这份微软 × Hugging Face 的联合研究用 507 个有状态业务流程、每任务重复 20 次，把代理的可靠性与成本第一次放到了可执行的数据库终态上。

1. 方法：轨迹是声明，数据库状态才是证据

每个任务给定初始后端状态、用户目标、MCP 工具集与领域策略，由确定性检查核对最终状态（477/507 纯状态判定，30 个附带答复评分）；同一任务的两次尝试永远不共享数据库行。评分不看工具调用是否工整、不看模型的自述。总计 121,680 次有效试验、12 个模型、507 × 20 次重复。开篇例子很典型：客服代理九次工具调用全部合法，却把工单标成 resolved，而承运商异常未解、要求的终态应为 on hold——「一个只查工具调用的评分器会看到九个漂亮的调用；数据库不同意。」

2. 最扎心的发现：67% 的失败是「静默失败」

79,853 次失败里有 67.24% 终止得干干净净：没用错工具、没报工具错误、模型自信收尾。可执行检查却发现字段值错误 77.61%、多余副作用 43.30%、漏做必备动作 25.36%（有重叠）。也就是说，只看轨迹或只看有没有报错的验收方式，会漏掉三分之二的问题。

3. 能力 ≠ 可靠性：pass@20 与「20/20」是两回事

Kimi-K3 是全场覆盖面最广的模型（93.89% 的任务至少解出一次，477/507），但在全部 20 次都通过的任务上只有 13.41%（68/507）；Claude Opus 5 一次解出的任务更少（79.09%），却把 47.53% 的任务做到 20/20 全过。更刺痛的是：Opus 5.5 每个维度比 Opus 5 涨了半分（67.16% vs 66.50%），而 20/20 的任务数一模一样（241）——半分头名精度没有换来任何可靠性。单次成功只说明模型能做，重复 20 次才回答它是否总会做对。

4. 可靠性的价格

成本要分两档看：每次成功尝试的成本（GPT-5.6 Sol 最低 $0.127）与每个「可靠任务」的成本（20 次全过）。后者前排：GPT-5.4 $6.80（128 个可靠任务）、GPT-6 Astra $7.45（231）、Claude Opus 5.5 $7.80（241）。「拿到正确答案最便宜的方式，不是拿到可靠答案最便宜的方式。」单次能力能保住多少：只有 Astra 保留 78%、Opus 5.5/5 保留 71%，而 GLM-5.1、Kimi-K2.6、DeepSeek-V4-Pro 只剩约 8%。

5. 失败签名与落地动作

约八成失败是工具处理问题：79.9% 工具使用、10.3% 状态更新错误、7.0% 未完成用户诉求、2.9% 没有状态变更。多数代理是「走得够远、但翻不过工具错误与空查询」——这是重试与错误恢复问题，其次才是模型问题。作者建议：提交前检查终态而不是相信模型的总结；给工具面做减法；不可廉价回滚的变更强制人工批准。评测环境（数据集 + 评测器）已在 Hugging Face / OpenEnv 开源，可以拿自己的模型复现单任务。

我的推荐

如果你在给公司搭代理或验收别人的代理系统，这是今晚最该读的一篇：它把「代理到底可不可信」拆成可复现的度量（终态、20 次重复、每个可靠任务的成本），并附送一整套能直接跑的评测环境。和下面 Unit 42 那篇一起读，是「如何验证」与「如何被攻破」的完整一课。

强烈推荐——跑代理的必修课 · ★★★★☆ · TLDR InfoSec

A Vault with a Heap-View: The Uncomfortable Space Between AgentCore Harness and Identity

为什么值得看：把「提示注入能造成什么」从抽象恐惧变成一条从工单注释到客户 PII 的完整、可重放的攻击链，并给出三条可直接进 checklist 的加固项。

展开完整精读

一句话判断

一篇把「托管代理运行时最窄的那个缺口」演示到字节级的安全研究：默认配置下 shell 工具以 root 跑在与解析凭据相同的进程空间里，一条间接注入就能把身份保险库里的 JWT 掏出来——而 AWS 把报告关成了 informative，把缓解责任留给了使用者。

1. 背景：保险库保护静态与传输，不保护「使用中」

AgentCore Identity 把凭据加密存储（KMS + IAM 管控），引用时用 ARN；但运行时要把 ARN 解析成明文才能拿去调下游服务——解析结果就躺在 harness 进程（PID 1，python3.10 -m loopy.server）的堆里。而 harness 默认自带 shell 与 file_operations 两个内置工具，与 PID 1 同 UID，shell 直接以 root 运行——「不需要任何配置错误，这就是开箱状态」。

2. 攻击链：从工单里的一行注入到全网可重放的 JWT

研究者先直接提示模型执行侦察命令，被拒两次；于是换上更顺从的模型 + 间接提示注入，把载荷藏进支持工单的 HTML 注释，指令只有一行「curl 我们的脚本 | python3」——不需要精确语法，一次到位。随后在环境内 whoami/id 发现 root，读 /proc/1/maps 拿到内存布局、再扫 /proc/1/mem 的堆，从进程内存里揪出 1,034 字节的 JWT 与 MCP 服务器 URL，一并 POST 到攻击者 webhook，再从自己的笔记本（无任何 AWS 凭据）重放：列出 MCP 工具、调用 lookup_customer 拿到客户 PII、创建工单。

3. 被偷的是谁的凭据：操作者的服务账号，不是终端用户的

这是全文最值得记住的边界：调用者只有 bedrock-agentcore:InvokeHarness 权限；harness 的执行角色却能触达操作者接入的每一个下游服务。保险库里那份跨所有用户会话复用的 mcp-service 凭据，才是落进堆、被带走的那一份——终端用户自己的会话 JWT 反而干不了这事（短命、不可预注册）。用户从未拥有、也本不该拥有的权限，被一次注入拿走了。

4. AWS 的立场与 allowedTools 的坑

AWS 以共享责任模型关闭报告（informative），把 allowedTools 收窄与出站过滤列为客户侧控制。研究者提醒一个细节：allowedTools 在 InvokeHarness 时生效而不是 CreateHarness——参数灵活，但不知道就会漏；内置 shell 与 file_operations 对每个会话默认开启，不需要你显式同意。

5. 给运维者的三条与给平台作者的一条

运维三条：按会话把 allowedTools 收到最小（不需要的会话就不给 shell）；把保险库服务账号按最小权限绑定下游集成（泄露的凭据只值它作用域内的东西）；盯紧 harness 容器的出站流量——出现清单外的端点就是「注入正在发生」的证据，而不是配置漂移。给平台作者一条：把 harness 给模型的每个能力当成攻击面原语；任何运行时解析的凭据，要么放在 shell 读不到的地方，要么把 shell 与凭据解析进程隔离——「保险库只防静态与传输，使用中的明文是另一个问题。」

我的推荐

如果你在自己的基础设施上跑带 shell 的代理，或正在评估任意托管代理运行时，这篇是今晚的必修课：它把「提示注入能造成什么」从抽象恐惧变成一条从工单注释到客户 PII 的完整、可重放的攻击链，还给出三条可以直接进 checklist 的加固项。

推荐——基础设施升级的方法论范本 · ★★★★☆ · TLDR Dev

Beyond synthetic testing: Capturing and replaying real database workloads at Airbnb

为什么值得看：捕捉、重建、回放、比对每一步的取舍都摊开了，包括 last_insert_id 重写、同起跑线调度这些魔鬼细节；5.7→8.0 升级零重大事故就是它的成绩单。

展开完整精读

一句话判断

Airbnb 把「用真实生产流量给数据库做测试」工程化到底的一篇：在 ProxySQL 上建无侵入的捕获点，把事务重建成可回放数据集，用几千个 worker 按原始节奏重放——5.7→8.0 升级零重大事故，容量规划先在离线环境里把天花板撞出来。

1. 动机：合成基准测的是你想象的负载

sysbench 之类的合成负载盖不住生产的查询光谱；performance_schema 的 digest 只是摘要，无法复现问题。他们要三个能力：真实流量压测（按 1x/2x/3x 或目标 QPS 回放，为峰值季节做容量规划）、升级与迁移的兼容性验证（同一流量打到两个目标比对结果）、以及把事故工作负载离线重放来定位与验证修复。

2. 架构：三个组件，一个无侵入捕获点

捕获点在 ProxySQL——理解 MySQL 协议、本来就站在应用与数据库之间，客户端无关、无需应用改动。Log Mover 边车把查询日志送进对象存储；Log Processor 离线把多集群混在一起的二进制日志按集群分区、按原始顺序重组每个事务、以 5 分钟窗口分桶，并做一件不起眼但关键的事：把 INSERT 重写为显式携带 last_insert_id（不同引擎/版本的自增分配方式不同，否则后续依赖自增 ID 的读会漂移、制造假阳性）。代价是不再顺带测试目标库的原生自增，作者明确接受这个取舍。

3. 回放器：把「同一起跑线」做成了工程

API Server + 任务调度器 + 可横向扩展至数千实例的 worker。调度器按日志文件切任务、给同批任务同一个「预期开始时间」，worker 各自等待该信号后同时开跑——这样复现的是原始并发与节奏，而不是各自孤立地回放五分钟文件。两种模式：Replay only（负载测试，追踪错误、分位延迟、资源利用率）与 Replay and compare（同一查询打两个库、diff 结果，用于升级验证）。

4. 战果：把「回归」在离线阶段撞出来

5.7→8.0 升级中抓到的实例：某查询模式延迟从 0.03s 飙到 2.6s（每 join 读 273MB 而非 5MB，定位到 8.0.20+ 排序时读行的变化）；先对 5.7 带/不带 query cache 回放做二分、再与 8.0 对比，暴露出应用重复发送可缓存查询的问题。可靠性上也拦下两类经典坑：innodb_autoinc_lock_mode 默认变更带来的交错自增 ID；没有 ORDER BY 或排序键不唯一 + LIMIT 的查询在新引擎上悄悄返回不同行——提前和业务团队补上显式排序。容量侧：某大集群写流量 +80% 时平均提交延迟从约 6ms 涨到 34ms，远在真实流量撞墙前标出天花板。

5. 合规姿态与边界

查询日志只对测试集群、测试窗口开启；传输与静态全程加密；访问限数据库基础设施团队；回放只在生产等价环境里跑，绝不落到低阶环境、也不复制到开发层。这套约束不是装饰——它是这套系统能存在的前提，也提醒读者：回放生产流量的能力必须配套同等强度的治理。

我的推荐

给所有「改了数据库心里没底」的团队：这篇把捕捉、重建、回放、比对每一步的取舍都摊开了，包括 last_insert_id 重写、同起跑线调度这些魔鬼细节，并用 5.7→8.0 的实战成绩证明值得建。哪怕你不做数据库，这套「用真实负载给变更上保险」的方法论也适用于任何关键基础设施的升级决策。

Everyone into the Pool (14 minute read)

PostgreSQL’s connection model is the one it has always had: one client connection, one operating system process. Each backend is a `fork()` of the postmaster, with its own catalog caches, its own memory contexts, and its own opinions about `work_mem`. This is simple and it is expensive. Connection setup costs a fork, an authentication exchange and (these days) a TLS handshake. Every connection that exists costs memory whether it is doing anything or not. And every connection that *is* doing something wants a CPU core, of which the database server has far fewer than the application tier has threads.

PostgreSQL 连接池横评：对比 Pgpool-II、PgBouncer、RDS Proxy、PgCat、PgDog 的进程模型、事务池化下会话状态处理与坑点；只做池化选 PgBouncer，读写分离或分片用 PgDog。
