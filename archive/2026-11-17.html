01
把「验证层」当成一套独立系统来建，是从同时跑一两个 agent 走到跑上百个的唯一分水岭。 · ★★★★★ · TLDR AI

How the Claude Code team thinks about verification

为什么值得看：文章不只讲该写哪几种测试，而是给出 Anthropic 内部的完整机制：E2E/property/differential 的分工、39 项可靠性清单、提交门禁的三档模式，以及怎么评估评审器本身。

展开完整精读

一句话判断：这篇文章的价值不在「要多写测试」这种常识，而在于它把 agent 的验证能力当成一套需要设计、需要被审计的系统，并且给出了 Anthropic 自己在 90% 代码由模型产出的规模下跑通的机制。

  1. 为什么验证决定了并行度。没有验证回路，你只能同时跑一两个 Claude，因为每个改动都得自己看。有了它，几十上百个并行才有意义。作者引用内部实验：给 agent 配一个独立的 grader 按 rubric 打分，任务成功率最多提升 10 个点，且难题上收益最大。这个数字比任何「agent 很强」的宣传都更有说服力——提升来自反馈，而不是模型本身。

  2. 三类测试的分工。E2E 是唯一「难以被糊弄」的层次：功能要么通了要么没通，而且能具体说出坏在哪；单测更快更稳，却可能全绿而功能已坏，因为 agent 和测试都没理解完整任务。property test 补的是「人没想到的边界」——先写一句你认为不可能失败的性质，再用库生成上千输入去证伪，这类输入不带写代码那个 agent 的偏见，重写场景尤其有用。differential test 针对大规模迁移：新旧系统同输入对比，差异就是 bug 或破坏性变更，关键是输入要随机化或用生产流量抽样，并对空白这类无关差异做归一化。

  3. 落地方式。真正跑起来的一步是 verify skill：放在仓库里、离相关代码尽量近，让 agent 知道提交前要跑它，然后反复让 Claude 自己迭代、压测这个 skill，把它当冒烟测试底座。文章反复强调「跑起来比测试更重要」——web 用 Chrome 扩展，移动端用 iOS/Android MCP，桌面用 computer use，后端就在本地起服务。

  4. 制度比技巧更关键。39 项可靠性清单，每项带一个能从 diff 读出的触发条件、一条检查、以及它背后的线上事故；Claude 只读触发命中的 3 到 10 项，没人需要背事故史。评审不靠叠加更多 reviewer，而是维护 REVIEW.md 告诉评审者该看什么，并让每一轮评审接上前几轮的上下文，而不是每轮从零重查。最锋利的一条：如果一个变更能改动评判它的检查，这个检查就是坏的——所以 Code Review 只从 base 分支读规则。加上三道门：便宜检查先跑，commit 盖验证标记，commit gate 分 off / observe / enforce 三档渐进启用，被拦两次后放行一次以免 agent 卡死。

  5. 谁来评审评审者。团队跟踪合并后被回滚的比例、维护者在合并前拒掉的比例，以及规模匹配、至今干净的样本。做正式评估时，把仓库恢复到当时状态、每题给一句话答案，只有准确描述该 bug 的发现才得分，并用已合并且稳定的改动做对照来抑制过度报警。召回率分三段独立统计，这样才看得出系统有没有丢掉自己已经找到的 bug。规则也不是越堆越好：测试、验证步骤和 md 文件只会膨胀，要定期清理。

我的推荐：如果你在团队里推 agent，先抄三件事——一个能真跑起来的 verify skill、一份从 diff 能读出触发条件的清单、一个 observe 模式的提交门禁。这三样不需要模型升级就能立刻降低返工。

Inference engineering for software engineers

为什么值得看：把「什么时候该离开 frontier API、怎么选模型和供应商、多租户与专用 GPU 怎么取舍」讲成了一条可执行的路线，并给出 Uber 每 token 成本降 50%、Pinterest 90%、AT&T 56% 这类真实参照。

展开完整精读

一句话判断：这是一篇少见的、把 LLM 推理当成运维问题而不是模型问题来写的文章，适合任何要为自己的产品定 AI 成本结构的人。

  1. 推理服务商是什么。它们不预训练基础模型——一次 frontier 级预训练要花数百万美元，只有超大厂和 frontier 实验室付得起——而是托管开源权重模型，靠后训练、效率优化和专用硬件竞争。Modal 强调可编程与代码可见，Fireworks 主打专用部署加微调与延迟保证，Baseten 往上叠沙箱、治理和 agent 构建层。一个细节值得记住：Fireworks 的 Ember-1 在 Kimi K3 基础上后训练，质量接近但推理 token 少 40%——同样的答案用更少的 token，成本优势比单价比价更真实。

  2. 另一个被低估的动机是可用性。文章引用各家状态页：Anthropic 自报 99.5%，OpenAI API 99.97%、ChatGPT 99.2%，都低于云厂商常见的四个九。更要命的是「性能退化时段不算宕机」，而多租户意味着退化会随机落到某些租户头上，你既看不见也做不了什么。所以只要关键路径要承诺 99.99%，就不能只挂一家 frontier API，LLM gateway 加 fallback 是必然产物。

  3. 迁移的三个理由：成本、延迟可控、可定制。成本这条最普遍——很多请求根本不需要 frontier 模型的能力，路由到便宜模型没人会察觉；Uber 的每 token 成本降一半主要靠 prompt 感知的 smart router。选模型的正道是私有 eval：Satya Nadella 在播客里说私有 eval 会成为公司 IP 的一部分，先拿 trace 找确定性工作流，再换模型、用 trace 微调。只有公开榜单时，退一步做 A/B，让一部分工程师先用新模型并反馈。

  4. 多租户阶段的三个坑。TTFT 的分布有长右尾，p95/p99 才是用户抱怨的来源；服务端 instrumented 的推理时间和 client 端看到的实感延迟要分开量，后者还包含网络和 TLS 握手，连接池这类常规优化仍然有效。缓存这条最容易被忽略：无状态 REST 接口让应用层看起来很干净，代价是服务商要在分布式环境里保证 prefix/KV cache 命中，命中率直接决定成本和首字延迟，而且它从 API 响应的 usage 字段就能读出来。

  5. 什么时候该上专用 GPU。信号是三条：频繁撞限流、性能一致性无法接受、为实际用量付了过多钱。上了专用节点，工程细节才真正开始——模型大小、交互还是吞吐优先、KV cache 留多少、故障怎么切——文章在这一段进入订阅区，只留了标题结构：专用 GPU 配置与 speculative decoding（用闲置算力加一个 draft 模型加速解码）。所以这篇免费部分覆盖了决策与多租户阶段，落地的参数细节要看全文。

我的推荐：先做两件不需要采购的事——把各模型的每任务成本用自己的 eval 集量一遍，再把 prompt cache 命中率接进监控。等这两条给出数字，要不要谈专用 GPU 自然有答案。

03
把「on-policy」从调度层承诺变成数值层事实：采样器和训练器对同一个 token 必须给出逐位相同的 logprob。 · ★★★★☆ · TLDR AI

Unlocking Stable On-Policy RL on TPU with Bitwise-Zero Train–Inference Mismatch

为什么值得看：根因分析干净——浮点加法不满足结合律，不同的规约顺序就会产生不同的 logprob——并给出四条可复用的实现规则和三路对账方法，不是只报一个结果。

展开完整精读

一句话判断：这是把「数值一致性」从工程迷信变成可验证合同的一篇短文，凡是自己跑 RL 或要复现别人 RL 结果的人都该读。

  1. 问题是什么。LLM 的 RL 里模型就是策略，真正的 on-policy 要求每个动作都由同一份策略生成并评估。同步循环保证了「同一批权重」，但没保证「同一套算术」。生产环境里采样和训练走两条专门化的执行路径：采样器在增量解码时记录行为 logprob，训练器在整批前向反向里重新算同一个 token 的 logprob。权重相同，两个实现仍可能给出不同的数值。

  2. 根因很朴素：矩阵乘要累加部分和，归一化要统计量，张量并行要把分片结果合起来，而浮点加法不满足结合律。改变相加的树，就改变了舍入发生的位置，bfloat16 下尤其明显。JAX 又会按输入形状特化计算，训练前向还跑在带自动微分的程序里——这两条路径的规约顺序和中间精度从来没对齐过。所以模型方程没变，算术变了。

  3. 合同怎么定。对每个被采样的动作，在相同 rollout 权重、相同 token 历史、相同采样设置下，解码、服务端 prefill、训练器前向三条路径必须给出逐位相同的 logprob，比较的是原始浮点字节，没有容差。三路而非两路是设计上的巧思：直接比采样器和训练器只能说明「有差距」，加了 prefill 这个中间检查点，就能区分是服务引擎自身不自洽，还是跨编译/微分边界出的问题。这对任何 RL 栈都可照搬。

  4. 四条实现规则。其一，分片内用 batch-invariant 的 Pallas kernel 控制累加顺序与中间精度：按固定分块顺序遍历、以 float32 累加、显式转回输出类型，累加器跨 tile 延续而不是从转换后的输出续算，覆盖注意力和 MLP 投影以及 LM 头。其二，行并行投影的跨分片合并要把通信和相加分开，用 ppermute 搬运部分和，再由每个 rank 按源 rank 顺序相加，让规约顺序写在程序里而不是交给集合通信实现去选。其三，对齐必须延伸到最后那个被采样动作的概率：三条路径用同一套采样变换和同一份 Pallas log-softmax，且沿用 rollout 时产生的 token id，不重新选动作。其四，训练侧用 custom_vjp 包住服务端 kernel，前向值来自服务 kernel，反向由一份镜像其累加与类型转换的可微副本提供，另外用 xla_allow_excess_precision=false 压住 kernel 周围的额外精度。

  5. 结果与位置。64 颗 TPU v5p（DP8×TP8）多机验证，200 步 FrozenLake 用公开的 Qwen3-8B，GSPO-token loss 配 leave-one-out 优势。Zero-TIM 在每个记录步上采样器与训练器的 logprob 平均绝对差都是 0，solve rate 同步上升；标准配置与 token 级截断重要性采样（TIS）都仍有非零差——TIS 只是调整更新权重，没有消掉底层不匹配。同期 vLLM+TorchTitan、LMSys Miles 也在做 batch-invariant kernel 这条路，可见这已经是稳定大规模 RL 收敛的事实标准。对自建 RL 的团队来说，三路对账合同比任何单个 kernel 优化都更值得先落地。

我的推荐：不必上 TPU 也能借鉴——先在自己的训练/推理栈上加一条「同权重下 logprob 逐位相等」的断言，你会发现误差来源比你预想的多。
