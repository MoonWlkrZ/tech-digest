把「验证」从口号拆成可落地清单的 agent 工程文，值得逐节细读。 · ★★★★★ · TLDR

Agentic Verification

为什么值得看：为什么值得看：模型写代码已经很便宜，文章给出「瓶颈已移到验证」的完整解法——E2E 做 oracle、property-based 描述「永不发生」、差分测试把旧系统当基准，以及回路必须快且确定的原因。

展开完整精读

一句话判断：AI 工程的瓶颈已经从「写代码」移到「确认代码是对的」——谁给 agent 搭好可自我验证的回路，谁的产出质量就上一个台阶。

  1. 论点与背景：模型已经足够好，真正贵的是验证。agent 无法自验时其实是在猜，错的猜测最后由你的测试套件来「验证」，反馈回路又回到最慢、最贵、无法扩展的那条：人工读 diff、跑测试、找 bug、回报。

  2. E2E 测试是首选 oracle：模拟真实用户流程（注册、加购、结账、确认），忽略内部结构、只看用户可见行为——mock 单测可能「通过但功能坏了」，E2E 很难被骗过。它同时定义了 done：「让这条 E2E 测试通过」是 agent 能自己追逐的目标；配套建议是维护一份用户视角的 feature map，给 agent 装上眼睛和手。

  3. Property-based testing：用「永不发生」的约束（round-trip 编解码、不变式、幂等、等价性）让工具生成成百上千输入去攻破。关键点：agent 会自造「按自身逻辑必然通过」的示例，property 强制它面对任意输入；fast-check/Hypothesis/proptest 还会把失败输入最小化。

  4. 差分测试与迁移：新旧系统并跑同一批输入比对输出，旧系统即 oracle；用随机生成或回放线上流量样本，并归一化无意义差异、维护「已批准变更」清单。适合 agent 主导的大规模重构——不必对 agent 解释每条边界条件。

  5. 回路要快且确定：慢或 flaky 的测试会教坏 agent——它学会「重跑而不是修复」，或攒一大批改动失去归因能力。样板：每轮可跑、亚秒级、确定性（种子随机、冻结时钟、隔离状态）、输出简短；flaky 测试隔离并立刻移除。另附实践：让 agent 复述成功标准、用独立 reviewer agent、把生成的测试本身也当作需要审查的产物。

我的推荐：如果只读一篇 agent 工程文，读这篇——它把「验证」从口号拆成了可落地清单：先写检查再写代码，把测试基建当产品投资，让 agent 在快回路里自己迭代，人只审决策与证据。

LLM 时代第一个被奖励的 Chrome 全链攻防复盘，进攻成本被改写的第一手记录。 · ★★★★★ · TLDR InfoSec

Zero to Calc in Six Days: Inside XBOW's Chrome Full Chain

为什么值得看：为什么值得看：不是一篇「AI 很强」的观点文，而是三段真实漏洞的完整技术复盘（Maglev 反优化、动画 WebP 的 TOCTOU、Crashpad 重试读），加上 6 天、约 4 万美元的工程账本与撞车报废后救链的编排细节。

展开完整精读

一句话判断：LLM 时代的第一个被奖励的 Chrome 完整利用链——6 天、约 4 万美元 API 成本，进攻方的成本结构被彻底改写，防守方要按这个成本线做打算。

  1. 三段式链条：Maglev 反优化 bug 把可变 HeapNumber 当不可变常量复用，在 V8 的 4 GiB 指针压缩笼内拿到任意读写；动画 WebP 的 TOCTOU（缓存的帧几何 + 被换掉的像素字节）换来一次受控的笼外原生写；Crashpad 对「已冻结」渲染进程的重试读假设被击穿，跨出进程沙箱执行代码。

  2. 第一段细节：Maglev 的 BuildHeapNumber 把可变数字对象写入 deopt literal 数组，通用 materializer 又直接拷贝其身份，嵌套激活下多个对象共享同一个可变 HeapNumber；利用 Array.prototype.at() 的两处观察分歧，重写 Uint8Array 元数据获得全笼访问。修复：每次反优化新建 box、显式禁止去重。

  3. 第二段细节：V8 沙箱威胁模型下，transfer 后的 ArrayBuffer 并不承诺对笼内攻击者不可变——攻击者切断 Uint8Array 的 detach 通知链视图，Blink 却以为独占了字节；WebP A 的缓存矩形配 WebP B 的当前数据 = 越界写。生产利用借 PartitionAlloc 同桶相邻布局，把像素写变成「一个自选 64 位值写到自选地址」。

  4. 第三段细节：Crashpad 的 ReadUpTo 在 ERROR_PARTIAL_COPY 时按页边界重试，假设进程地址空间在两次读之间不变；利用 THREAD_CREATE_FLAGS_BYPASS_PROCESS_FREEZE（0x42）线程在快照间隙反复翻转页保护，把 0xb8 字节请求放大成 0x168 重试、溢出相邻的 SnapshotMinidumpMemoryWriter；改写其 vtable 指向 CFG 合法路径，最终弹出计算器。

  5. 结论与代价：预 LLM 时代同规模链条要 4 人团队 6-9 个月，XBOW 首链 2 个月，这次 6 天（8 月 2 日至 7 日）、约 4 万美元 API 费，修复与 Chromium 补丁均已公开。作者提醒：不是谁都能用这个成本拿链，人类的选题与判断仍关键，但门槛显著降低。三段漏洞共享同一主题——被假设不可变之物实为可变，作者认为这正是 LLM 的强项。

我的推荐：安全团队必读的进攻侧基准；所有工程读者值得看「并行战役拆解 + 模块化接口 + 备份路线」的编排方法——尤其首链因与 Google 内部已报 bug 撞车而报废、数小时内用 WebP 段救活的细节，是对与 LLM 撞车现实最诚实的记录。
