本周最值得读的系统分析：不靠跑分，靠外部观测把 Apple 端侧模型的设计逆推出来。 · ★★★★★ · TLDR AI

Exploring Apple's On-Device Model: Twenty Billion Parameters in Flash

为什么值得看：作者守住 Apple 的反向工程禁令，只用 fs_usage、footprint、powermetrics 和统一日志从外部观测，却给出了「4.95GB 闪存文件、636MiB 常驻、每 32 个 token 重选 expert、约 2bit 权重」这样可复核的结论，还配了同机开源模型的对照实验。

展开完整精读

一句话判断

这是一篇罕见的、把「端侧大模型到底怎么塞进笔记本」讲到可复核程度的文章：作者不碰权重、不反汇编，靠系统自带的观测工具把 Apple Core Advanced 的架构、内存、能耗与能力边界一条条测出来，并用同机的开源模型做对照。

1. 它到底是个什么东西

macOS 27 在每台支持 Apple Intelligence 的 Mac 上放了一个可直接调用的模型：终端里 fm respond 就能问答。Core Advanced 是 Apple 两个端侧模型里较大的那个，200 亿参数，每次只激活 10–40 亿，官方说法是「与 Google 合作定制」。作者做了一份 Apple 自己没发布的 model card：模型主体是一个 4.95GB 的文件躺在闪存里，常驻 Neural Engine 的模型页只有 636MiB；另有一个独立进程跑两个 3 亿参数的安全模型（分类器 + 图像护栏），占 2.0GiB 里的 0.7GiB。

2. 关键设计：按 prompt 路由 expert，而不是按 token

标准 MoE 每个 token 都换 expert，所以每个 expert 都必须待在内存里。Apple 的官方说法很直白：NAND 到 DRAM 的带宽不足以支撑逐 token 换权重。于是它改成读入 prompt 时选一组 expert，生成过程中每隔一段时间重选。作者从文件读取轨迹里量出了节奏：一次读 294912 字节（正好是 2bit 下一个 expert 的大小），代码回答里每 32 个 token 读一次，散文里也是每 32 个——节奏按 token 计，不按秒计。对照实验很有说服力：同机 4bit 的 Gemma 4 26B A4B（每 token 跑 38 亿参数）在同样长请求后占约 15GiB，Apple 两个进程 2.0GiB，差 7.5 倍，其中约一半来自 2bit 对 4bit，另一半来自「按 token 路由就必须把所有 expert 留在内存」。

3. 代价写得很诚实

100 道小学数学题，Apple 对 78 道，三个开源 4B 模型 89–94 道；200 道知识题它居中。Apple 自己的开发者文档就把 basic math、code、logical reasoning 列进「应避免的能力」，并说早期端侧模型「不是为通用世界知识的聊天机器人设计的」。控制权也没了：没有 pin 版本或取回旧模型的 API，OS 27 砍掉了给开发者的 adapter（保留给自己按功能微调），一位开发者实测同一批 227 条消息里有 11 条判定在更新后翻转。换句话说，这个模型适合摘要、抽取、分类、标签、改写这类「短、固定形状、内存和电池敏感」的活，不适合推理与需要版本稳定的场景。

4. 与 Google 的分工，以及能耗这笔账

训练侧能测到的 Google 痕迹：tokenizer 在 429 条字符串上与 Gemma 3 计数完全一致（其他实验室的 tokenizer 命中率不到一半），Google 自己的计数端点也返回同一个数；再叠加 TPU 与「用 Gemini 前沿模型输出精调」的公开说法，作者的推断是——Apple 拿 Google 的 dense 底座与词表，再 pruning 成自己的 flash-expert 结构，因为 Apple 十月论文里明说这类模型「只能 upcycle，不能预训练」。能耗是他测出的另一个变量：同样 20 道题，Apple 464.6J，最好的开源 build 1272.9J，约为三分之一，期间 Neural Engine 4.2W、GPU 保持空闲频率。

5. 为什么这套设计会长期存在

因为它同时满足三个约束：内存要能和各家的浏览器、编辑器共存；功耗要能撑一整天的语音与听写；延迟要能接受。这三个约束决定了「小窗口 + 少激活参数 + 权重放闪存」的组合不会因为模型变大而消失——Apple 唯一欠的是一份技术报告和可商用的开放权重。作者的最后一条建议也值得听：如果权重就在每台合格 Mac 上，开放出来让人 pin 版本、做微调、验证 Google 的成分，比继续禁止拆解更能建立信任。

我的推荐

如果你在做端侧推理、MoE 部署或者任何「内存比算力更贵」的系统，这篇是本周唯一必读：它给的不是结论，是一套可复用的外部观测方法（读轨迹、量 footprint、采功耗），以及一个明确的取舍表格——用 2GB 内存和三分之一能耗，换掉数学、代码和版本可控性。

把「上下文工程」从热词整理成一门有失效模式、有工具箱、有下一步的工程学科。 · ★★★★★ · TLDR

The State of Context Engineering

为什么值得看：作者是《The Context Engineering Handbook》的作者，这篇 AGNTCon 演讲逐条复盘了四种经典上下文失效、六种固定工具（含企业一次加载 600 个 skill 导致 agent 崩掉的实例），并给出 2026 年两个新失效模式的可验证证据。

展开完整精读

一句话判断

这不是又一篇讲 prompt 技巧的文章，而是一次真正的阶段性总结：上下文工程为什么难、难在哪几种具体形态、手里有哪些工具，以及 2026 年新出现的两个坑。

1. 起点：长上下文不是银弹

2024 年底的主流想法是「窗口够大就把一切都塞进去，RAG 已死」。窗口确实从 12.8 万涨到百万级，但作者当时归纳的四种失效模式今天依然成立：poisoning（错误的、不该在上下文里的东西进来后模型绕不过去）、distraction（上下文太长，模型开始更相信上下文而不是自身知识）、confusion（无关事实悄悄影响判断）、clash（工具、skill、指令互相打架）。最生动的例子来自 Gemini 2.5 打宝可梦：FireRed 里守卫要冰茶、红版里要柠檬水，模型把「找茶」写进待办后，在旧版游戏里耗了几个小时——这就是 poisoning 的教科书样本。

2. distraction 有实验支撑

《Do as I Say, Not as I Do》那篇论文的做法很干净：先指令「所有回答翻成俄语」，再在历史里塞一堆法语问答的例子，最后看模型听指令还是学例子。结论是所有模型都会崩，只是崩得早晚不同：Gemma 3 12B 几个反例就掉到一半以下，Opus 4.6 能扛更多，但同样会掉。映射到日常：你和模型来回改 CSS 的那几十轮，本身就是一堆「坏例子」。Gemini 2.5 的技术报告附录也写了同一件事——上下文超过 10 万 token 后，agent 开始重复历史动作而不是重新规划。

3. 工具箱其实很小，而且稳定

六件工具：上下文增强（RAG、skill）、工具装载（只暴露相关工具）、上下文隔离（子 agent 从空白历史开始）、裁剪（删掉不再需要的工具结果）、卸载（写进文件或数据库）、压缩（summary）。作者用 DSPy 演示：一个 while 循环加四个函数（loadout、quarantine、prune、compact）大约 16 行改动就齐了。他提到的企业案例很典型：某公司给每个工程师的 agent 在启动时加载 600 个 skill，性能突然崩掉，加一个 loadout 过滤就好了。压缩那一段有个值得抄的细节：压缩之前先用小模型判断哪些历史真的相关，只对相关子集做摘要，摘要质量明显更好。

4. 2026 年的两个新失效模式

第一个是 fighting the weights：模型被训练环境里的工具形状带偏，遇到不一样的 MCP server 就先调错再纠正；Claude Code 的系统提示里反复七次、四次地强调「独立调用请并行」，本质是在对抗训练时形成的串行偏置——看到提示里全大写和重复，就该怀疑你在跟权重较劲。第二个是 context inertia：模型钉死在一个假设或子目标上不肯停。Anthropic 的 Memento harness 发现跑久了会执念于一个方案，修法朴素到可笑——每 90 分钟写一张便条、清空上下文、保留环境；微软的 Fork-and-Flush 与 Berkeley 的 Scaling Discovery Requires Forgetting 独立得出同一结论：定期遗忘反而让指标阶跃上升。

5. 明天的坑：记忆会腐烂

作者对 2027 的预测值得认真对待：个人 agent（他点名 Hermes、OpenClaw 等）很少有跑满半年的经验，而 skill 和 memory 会不断累积互相冲突的补丁——同一件事用不同办法解决两次，两条记忆就打架。今天大家在拼命加记忆，明天缺的是「策略性遗忘」。他给的操作建议很直接：模型表现怪，先问上下文多大；到 20 万 token 就清，别急着说模型被削弱了。

我的推荐

做 agent、写 harness、维护长期运行的个人助手，都该读这一篇。它最大的价值不是新概念，而是把「上下文」这件事拆成了可以逐项检查的失效模式与对应工具——你几乎可以拿这六项做一个自查清单，今晚就能用上。

一份完整的沙箱逃逸复盘：两层防护如何被一个语言特性绕过，以及为什么「更安全的 builtin」反而成了缺口。 · ★★★★☆ · TLDR InfoSec

Breaking the AWS MCP Python Sandbox

为什么值得看：作者从 AST 校验器和运行时代理的实际行为出发，用 match/case 的隐式属性读取绕过了所有显式检查，最终在 Lambda 里执行了系统命令；披露时间线、影响边界与失败的环节都写清楚了，可以直接当沙箱设计的反例教材。

展开完整精读

一句话判断

一篇结构清楚、可复现的沙箱逃逸报告：它不只是「我绕过了」，而是把两层防护的设计意图、各自的盲区和最终拼起来的链条都交代了，适合任何要给 agent 提供代码执行能力的人当反面教材。

1. 目标：让 agent 在 AWS 里跑一段 Python

AWS 的托管 MCP Server 提供一个 aws___run_script 工具，接受一段短 Python，在服务端沙箱里执行，目的是让 agent 把多次 API 调用、结果过滤和处理合并成一次请求。代码跑在 Lambda 里，沙箱限制 import、builtin、属性访问和文件操作。作者为了避免在 Cursor 里反复调 payload，自己写了一个 MCP 客户端 CLI，用受限权限的测试 IAM 用户连上去。

2. 两层防护各自做了什么

第一层是静态校验：把提交的脚本解析成 AST，在结构层面拒绝可疑节点，比如 obj.__class__ 这种属性读取，或者对 getattr 这类被禁用内建的调用。第二层是运行时替换：type() 换成 _safe_type()，返回受限的代理类；open() 被收窄；getattr() 直接不可用；连 operator.attrgetter 这条绕路也堵了。设计上覆盖了「显式点号」和「用字符串取属性」两种常见写法。

3. 缺口：match/case 的属性读取在 AST 里是隐形的

Python 3.10 的结构化模式匹配里，类模式 case Coordinate(a, b) 会先检查类型，再按 __match_args__ 里列的名字去读属性。关键在于：属性名不在代码里出现，读的动作发生在 CPython 内部，AST 里只有一个 ast.MatchClass 节点。而 __match_args__ 的写入没有被拦——黑名单只列了少数 dunder 名。于是只要能把 __match_args__ 改成 ("__class__",)，就能读到校验器本来禁止的属性。剩下的障碍是校验器也拒绝字符串形式的 dunder，作者用 chr(95)*2 + "class" + chr(95)*2 在运行时拼出来绕过去。

4. 从读一个属性到执行命令

链条拼得很巧：沙箱去掉了 __build_class__，没法正常定义类，但 collections.namedtuple() 还在，它内部用 type() 造类，产出的类可以改 __match_args__。把 __match_args__ 指向 __reduce_ex__ 后，pickle 的配方函数返回 copyreg.__newobj__——一个真实的 Python 函数，而不是代理。真实函数的 __globals__ 里就有原始 __builtins__。问题是怎么读 __globals__：需要给 function 类型设 __match_args__，而 function 是不可变类型。这里第二层防护反而帮了忙——_safe_type() 尝试给真实类型做子类失败后，会从零创建一个普通的代理类，于是作者拿到一个「能通过 isinstance 检查、又可以改属性」的类，用它读到了 __globals__，再拿到 __import__，导入 subprocess，执行 id，返回 uid=993(sbx_user1051)。

5. 影响边界与真正的教训

拿到的执行角色凭据除 sts:GetCallerIdentity 外对所有 AWS API 都是显式拒绝，容器按会话隔离、无外网、根文件系统只读，作者没有找到跨会话或客户数据的路径——这是 AWS 其他控制兜住的部分，也是为什么它只是一次沙箱逃逸而不是更大事故。真正的教训有两层：一是 Python 里同一件事往往有多种写法，堵住最显眼的几种不等于堵住全部；二是把内建替换成「更安全版本」时必须保证语义一致，一旦行为不同，替换本身就成了新的攻击面。披露节奏也值得一提：7 月 26 日报告，10 月 23 日标记修复，10 月 24 日公开。

我的推荐

如果你在给 agent 写代码执行、插件或工具调用沙箱，这篇要读，而且要读它的链条而不是结论：AST 校验加运行时代理这套组合拳看起来很稳，但一个语言特性（match 类模式）加上一次「好心」的类型替换就穿透了。它同时提醒你，纵深防御里那些看起来无关的约束——只读文件系统、最小权限角色、按会话隔离——才是把一次逃逸压成「仅容器内」的原因。
