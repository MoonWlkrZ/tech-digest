How the Claude Code team does code review

为什么值得看：给出了代理写代码之后评审流程的完整可抄作业版本：从持续评审、多代理投票到风险分级与「回滚率不升」的验收口径，全是一线数据。

展开完整精读

一句话判断：这是目前公开材料里最完整的一份「代理生成代码如何评审」的工程方案，价值不在理念而在那些具体阈值和失败案例。

  1. 规模前提。Claude Code 约 90% 的代码由 Claude 自己写；Anthropic 单体仓库每天落地的变更从 5 月的约 2500 涨到 9 月的 3 万以上。在这个量级上逐行人工评审已经不可能，团队把目标改写成一个可测量的约束：大多数 PR 最多一个人工审批（可以是作者本人），且回滚率和事故率不上升。人工时间同时统计审批数、评论数和等人时长，回滚与事故是护栏指标——如果它们涨了，人工时间只是被搬到了修故障那一端。

  2. 评审提前到 PR 之前。给 Claude 一个能运行的东西（测试、构建、与设计稿对比的截图），要它拿输出说话而不是声称完成；再用一个全新上下文的子代理审 diff。作者在开 PR 前还会跑几个内部 skill：找 bug、简化 diff、端到端验证行为。同一类问题被反复标记时，修的是源头——skill、lint 规则或 CLAUDE.md。CLAUDE.md 只写项目是什么、约定、目标与非目标，保持很短；REVIEW.md 由代码 owner 写这块地方什么算失败（文档是「它在撒谎」、配置是「它路由错了」），限制 nit 数量、列出可跳过路径，并要求给文件名和行号作证据。

  3. 发现要经过验证才给人看。多个代理同时找 bug，再由另一组代理对每条发现投票，票数不够就不发；只涉及风格、诊断、清理的发现被丢弃，这些过滤器在上线前用自家 PR 做过 A/B。留下的按严重度排序，并标注 Important、Nit 或 Pre-existing，避免把历史问题算在本次作者头上。每条发现必须被回应：修掉，或写理由关掉线程。安全评审独立一路，有未关闭发现就不能合并。

  4. 分级与责任。风险等级由分类器读变更决定，第二个分类器判断这一条是否还需要额外的人；敏感路径和 CI 工作流永远要人。只有仓库信任名单上的作者走轻通道，其他人一律需要第二个人；代理的批准不能占人工名额；发起这次变更的人视为作者之一，出了问题由他负责。批准只对具体 commit 有效，代理推新提交或手工解决合并后必须重新批准。

  5. 噪声与收敛。团队按作者对评论的反应给每条评论归类（改了、说它错了、说这是有意行为、认为不重要），并拿已知干净的 PR 跑评审器，统计它会诱导人做出有害修改的比例。优先级写死为：先抓真 bug，再减少评审轮次。噪声对代理作者更贵——人会一秒挥掉一个 nit，代理会去改，于是又多一个 commit 和一轮评审。最刺眼的失败案例是一个 CLI PR 一夜跑了五十多轮才被作者叫停；git blame 显示约 59% 被标记的代码在评审器第一轮就已存在，它并没有不断发现新 bug，只是每轮多翻出几个旧的。团队现在同时跟踪 recall 和 rounds-to-pass，并改了重审策略（原文此处列表在抓取中缺失）。

我的推荐：如果你所在团队已经让代理开 PR，这篇可以直接当流程模板。先做三件事：给代理一个可运行的验证手段、把评审按变更风险分级、把「回滚率不升」写成验收口径。别急着追零人工合并——作者自己也说，他们还没有在指标恶化时自动收紧审批的熔断器。

Frozen Privilege: Remote Code Execution in Snowflake-Managed PostgreSQL

为什么值得看：五个都有文档、单独看都合法的 PostgreSQL 特性被串成从普通角色到系统级 RCE 的完整链条，且逐条绕过了厂商已发布的所有缓解措施，攻防两侧的细节都值得读。

展开完整精读

一句话判断：这不是一个数据库漏洞的故事，而是一堂关于「托管服务的安全边界到底在哪」的课，链条里没有任何一步是未文档化的利用。

  1. 起点低得吓人。Snowflake 托管 PostgreSQL 实例里，snowflake_admin 是非超级用户，唯一显眼的属性是 CREATEROLE。PostgreSQL 14 之后，光有这个属性就足以自授预定义系统角色，包括 pg_read_all_data 和 pg_write_all_data——这组角色没有「创建者」，也不需要超级用户授予。于是第一步就是给自己开全库读写，连 pg_authid 里的口令校验值都能读。

  2. 用调度器换身份。拿到写权限后，研究者直接改 pg_cron 的任务表：这是一个普通表，但调度器无条件信任它，而且任务通过本地 socket 以任意指定用户、无密码执行。把任务的用户名改成 postgres，等调度器触发，就以超级用户身份执行了 SQL，并创建一个 SECURITY DEFINER 函数当后门——函数以创建者的权限运行，之后任何低权限角色调用它都等于以超级用户执行。全程没有调用被禁止的 ALTER ROLE ... SUPERUSER。

  3. 被封的名字不等于被封的能力。超级用户只是到了厂商防守的边界：COPY ... TO PROGRAM、ALTER SYSTEM、pg_read_file 与 pg_read_server_files 全被挡住。研究者的转折点是问「这些函数是怎么造出来的」——用 CREATE FUNCTION ... LANGUAGE internal 重新绑定二进制里仍然存在的 C 符号，被按 SQL 名字封掉的原语立刻以新名字复活，且没有任何库内权限检查。pg_read_file、pg_ls_dir、pg_stat_file、lo_export 都是这样拿回来的。

  4. 从读文件到执行命令。先用重绑定的读函数确认 postgres 是 uid 26，读到租户的 mTLS 私钥与证书，以及明文存放的租户 AWS STS 凭证。然后用 lo_export 把 payload 直接写到 postgresql.auto.conf——PostgreSQL 重载时读取的配置文件——把 archive_command 改成自己的命令。这个 GUC 在每完成一个 WAL 段时由 /bin/sh -c 以 postgres 用户执行，是最干净的服务器端命令汇聚点，正常需要 ALTER SYSTEM 才能改，而那条路已被封。另一条等价路径是直接写并编译一个 C 扩展，用 LANGUAGE c 加载。

  5. 为什么这比一个 CVE 更麻烦。攻击落成后是一个数据库对象，不随创建它的凭证失效而消失，改密码没用；它以 postgres 身份运行，而 postgres 拥有整个数据目录，于是可以绕过数据库直接改堆文件——约束、触发器、行级安全、库内审计全部失效，也没有 SQL 语句可以记录；还能删改 WAL 破坏时间点恢复与备库复制，损坏 pg_control，或就地加密数据文件；本机日志也能改（集中外送的日志不受影响）。从防守方看，大部分动作发生在托管客户看不见的那一层。

我的推荐：Snowflake 客户无需动作，厂商 5 月 31 日收到报告、6 月 9 日确认并在发布前完成服务端修复。但如果你自己跑 PostgreSQL，这篇列出的加固清单值得逐条对照：把 CREATEROLE 当准超级用户对待、限制 pg_cron 只能以会话用户运行、禁止非平台角色创建 LANGUAGE internal 或 c 函数、保护 postgresql.auto.conf、用 SELinux 约束引擎。最重要的心智模型是：隐藏函数名只是把门把手拆了，能力还在二进制里。

推荐 · ★★★★☆ · ByteByteGo

How Uber Built a Genie to Answer Questions Correctly

为什么值得看：把内部知识问答系统从 ETL、向量索引、服务链路到评估与转人工讲成一整条工程流水线，还有上线一年后的真实使用数据，适合当 RAG 系统的架构参考。

展开完整精读

一句话判断：这是一份少见地把「知识怎么进来、问题怎么答、答错怎么发现」三件事都讲清楚的内部 RAG 系统拆解，亮点在评估和逃生通道，而不是模型本身。

  1. 问题定义得很窄。Genie 服务的不是生产事故，而是平台团队在 Slack 里日复一日的技术支持问答：配置怎么改、报错什么意思、某个不熟的功能怎么用。Uber 内部支持频道每月约 4.5 万个问题，信息其实都在 Engwiki 和内部 Stack Overflow 里，只是散到让人宁愿开口问人。

  2. 选 RAG 的理由是交付节奏。微调需要大量高质量、多样的样本和持续的算力，文档一变就得重来；RAG 可以先拿现有文档上线，知识更新只改索引。代价是知识准备本身并不便宜——抽取、切块、生成嵌入、建索引都要做对。

  3. 知识准备是离线流水线。Spark 从各来源接口抽取内容，放进 DataFrame，每行保留源 URL、正文和元数据——源 URL 从这一刻起就跟着数据走，后面才能做引用。切块用 LangChain，嵌入用 OpenAI 模型、以自定义 Python 函数在 Spark 里并行生成。索引由 bootstrap 任务灌入向量库 Sia，Spark 任务构建并合并索引，成品放 Terrablob；服务机（leaves）下载基础索引并同步快照，从而把「建知识」和「答单个问题」彻底分开。

  4. 在线链路与防幻觉。Slack 里的提问进 Knowledge Service，先转成嵌入、在向量库里找相近片段，再把每个片段作为独立子上下文连同源 URL 一起塞进提示词，要求模型只用这些材料回答并给引用。还有一条容易被忽略的约束：知识源是预先筛选过的，只纳入适合经模型处理和 Slack 回复的文档。引用能降低无依据回答的概率，但不能保证每条陈述都对——检索到的段落要相关、原文档要准确、模型要忠实转述，所以评估是架构的一部分而不是附属品。

  5. 逃生通道与反馈。回答下面有继续追问、标记已解决、联系人工三个按钮；信息不足时 Genie 明说并指向平台 on-call，人工接手后 Genie 保持沉默。反馈分四类：Resolved、Helpful、Not Helpful、Not Relevant，区分了「部分有用」与「完全解决」、「答错」与「本就不该由文档助手处理」。反馈经 Slack 插件进 Kafka、落 Hive、进看板。评估用 LLM as judge，对回答查幻觉与相关性，也对源文档打分并给改进建议——文档不好，检索再准也答不好。

结果与成本：2023 年 9 月上线，一年内 154 个频道、7 万多问题、有用率 48.9%、约 1.3 万工程小时。成本可见性靠一个 UUID 贯穿请求链路传到 Michelangelo Gateway，可进审计日志并按调用归账。

我的推荐：适合要自建内部知识助手的团队照着拆解。最值得抄的是三处：源 URL 从一开始就与文本绑定、回答必须带引用、以及「答不了就转人工且机器人闭嘴」。48.9% 的有用率也提醒我们，这类系统的价值不在于替代 on-call，而在于把重复问题挡在前面。

今日判断

今日判断：AI 生成的代码与答案已经是主流生产路径，工程侧的应对正从「更仔细地读」转向「可验证的检查 + 按风险分级放行」。Claude Code 团队用自动评审、多代理投票与风险分层把人工审批压到每 PR 最多一人，同时盯住回滚率而不是读了多少行；Uber 的 Genie 则把内部问答做成检索、引用、评估、转人工的闭环。另一条线是边界：Snowflake 托管 PostgreSQL 用五个「本来合法」的特性串到系统级 RCE，说明托管与沙箱都不是安全边界，值得留意的是代理身份与权限治理、以及评审轮次这类收敛指标。
