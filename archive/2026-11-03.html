Agent 产能把 Git 逼到极限后，OpenAI 重写了后端而不是改工作流 · ★★★★★ · TLDR

Scaling Git at OpenAI

为什么值得看：少见地把一致性模型的取舍、packfile 复用和线上数字全摊开讲，还交代了这支后端本身是怎么用 agent 在 10 周内建起来的。

展开完整精读

一句话判断

这是今年最值得读的一篇基础设施复盘：它说明 AI 带来的不只是写代码变快，而是把源码托管这类最底层的系统直接压到设计上限，逼着团队重做架构。

1. 问题不是流量，是并发写法

OpenAI 的单体仓库在 Codex 普及后出现质变：一个工程师同时挂多个待 CI 的分支，每次 push 又带出若干 job 去 fetch 同一个 commit。去年底开始，fetch/push 变慢、merge 失败，可靠性一度跌破 90%。原来的 Git 服务把「仓库级一致性」当成前提，所有 ref 更新排一个全局顺序，于是互不相关的分支也要互相等待。Cloudflare、GitHub 这类大规模 Git 托管都绕不开这个矛盾，区别只在于是加机器还是改模型。

2. Pando 的核心取舍

Pando 做了两个反直觉的决定。第一，放弃仓库级时间点快照，只保留因果一致性：读一个 ref 时，能看到产生它的那条写路径，但同时读多个分支可能看到不同时刻的状态。单 ref 内部仍然串行化，所以同一分支的并发 push 依旧会冲突。第二，放弃「每个客户端一份定制 packfile」：push 时把 packfile 原样存进 blob store，记录一个 ref version（新 tip、这份 pack、以及它依赖的早期版本），fetch 时直接挑出需要的几份 pack 让客户端下载，服务端几乎不做打包计算。为此他们只向客户端 advertise trunk 这一个基线 ref，让 push 产出的 pack 天然可复用——代价是连续往同一分支 push 时包会变大，但他们仓库里中位 packfile 不到 20 KiB，p99 不到 3 MiB，这个代价可以接受。

3. 读路径与压缩

Git 协议一次 HTTP 响应只能带一个 pack，Pando 用 packfile-uri 返回外链，内联一个空 pack，再靠自建的 Express 服务做区域缓存，缓存命中率 99% 以上，普通云主机就能跑满 10 Gbps 网卡。后台压缩借了 LSM-tree 的思路：每次 push 产生一个 L0 pack，后台按几何级数合并成覆盖一段 ref 版本的 cover，目前用到 L4。cover 既是压缩单位，也是 fetch 规划的跳表，让「客户端落后多少」只以对数代价影响选包。

4. 数字与建设方式

生产上中位 push 延迟降了近 5 倍（文中另一处说降低近 80%），每天分发近 1 PB，单小时峰值 57 TB，其中 99% 的字节来自本地缓存。更值得记的是建设方式：10 周从 kickoff 到生产，核心由一名工程师设计、agent 团队实现，用 GPT-6 Astra 写 Lean 和 TLA+ 形式化「Pando 理论」来找 bug，还有连续跑数百小时的 agent 会话在补边界情况。

5. 对其它团队的启示

不必人人都去写 Git 后端，但可以借鉴两点：一是先问「哪条一致性保证其实没人依赖」，砍掉它往往比加机器有效；二是把「可证明等价」当成上线门槛——Pando 先做只读/只写代理与旧系统并行，再逐步切流量，这种迁移方式对任何替换核心存储的项目都适用。

我的推荐

如果你在做平台或存储层，这篇值得逐段读，尤其是三种一致性模型的模拟对比和 packfile 复用的推理链。它也是「AI 写的基础设施能不能上生产」的一个正面样本：关键不在 agent 写得多快，而在形式化、一致性测试和灰度路径给足了。

一次把「AI 大规模重构」讲透的复盘：写代码是便宜的，证明没改坏才是成本 · ★★★★★ · TLDR Dev

Porting 287,000 lines of React in 3 days. The hard part was proving nothing changed.

为什么值得看：给了 parity harness 的完整设计：像素、结构、请求日志、可访问性四路对比，还老实交代了 harness 漏掉的 180 多个缺陷。

展开完整精读

一句话判断

这是目前把「AI 重构」讲得最实的一篇：真正的工作量不在让模型写新代码，而在造一台能判定「新旧行为一致」的机器。

1. 为什么要离开 React

Maple 的 React 前端有约 520 个 atom hook 调用散在 208 个文件里，每个都有自己的缓存键和生命周期。要回答「切换 org 时还有查询在跑会发生什么」，得把整页组件读完再脑内推演渲染顺序。八月一次 React #301 崩溃就是这类隐式依赖的产物：每次渲染新建 wrapper atom，hook 按引用比较并在渲染中 setState，两边互相触发。修起来一天，但没有任何机制阻止下一次。

2. Foldkit 换来了什么

Foldkit 是跑在 Effect 上的 Elm Architecture：全部状态在一个 Model 里，只有 update 能改它；点击、响应、定时器都变成过去式的 Message；副作用只能通过 Command 发出，结果再以 Message 回来。于是「切 org 时在途查询」只有一个 case 要读，还能在不带 DOM 的 Node 里直接测。附带好处是可观测性：每个 Command 自动落在一个 Effect span 里，前端用 OpenTelemetry 和后端同构，HTTP 客户端带 traceparent，一次点击可以一路追到仓库查询。代价很明确：Foldkit 不能按路由拆包，启动体积从 703 KB 涨到估计 1.43–1.58 MB gzip。

3. 先定义「完成」，再动手

团队在移植前先写下验收标准：一条路由的所有场景都报 identical（或 pass 且感知像素差为 0）、行为差异为 0、无 console 错误、无未 mock 的请求，才算移植完成。然后造了 @maple/ui-parity：两个生产构建同源部署、共用一个 fixture 后端，这个后端不是 JSON mock，而是实现真实的 domain API，warehouse 查询走真实查询引擎进 chDB，所以查询写错连图表带请求日志都会露馅。截图前冻结时间、固定随机种子、UTC、DPR 1、动画停在末态；parity selfcheck 先让旧应用和自己比，必须零差异，再故意改一个 class 验证能抓到。

4. 对比的四个维度

像素做严格与感知两种 diff；结构对比把每段文字和控件连同位置、计算样式一起记录，按文本或无障碍角色配对，同类问题合并报告（九个按钮错一个 class 只报一条）；请求日志按 endpoint 比对，忽略顺序但多请求一次也算失败；ARIA 快照做可访问性对比。50 多个场景文件覆盖所有路由的明暗主题与移动端，一次跑 2,600 多个变体。加载与错误态也是场景：可以让某个 endpoint 延迟 60 秒或返回 502，从而稳定截到 spinner。

5. 过程与漏网之鱼

八个 spike 先回答会不会翻车，最重要的是「agent 绝不能改基线、场景或容差来让 diff 消失」，基线钉死在某个 commit。最多四个 agent 并行，各自 git worktree 和端口，一个 integrator 负责合并并重跑 parity。harness 抓到了人眼看不到的东西（一个 toast 标签在 Foldkit 是一个文本节点、React 是三个，差了 13 像素），也漏掉了没写场景的命令面板——第二晚才发现它根本没被移植。截图之间的状态迁移问题，第一轮人工复审找出约 40 个，六个 agent 的最终复审又找出约 140 个，其中 4 个严重。上线前双应用对真实后端跑了一遍：Foldkit 389 个请求，React 393 个。

我的推荐

准备用 agent 做大迁移的团队应该先读这篇，重点看「验收标准 + 确定性夹具 + 基线与容差不可改」这三条约束。它同时是一份诚实的成本清单：三天的移植之外，还有复审、修缺陷、处理 fixture 覆盖不到的真实依赖，以及对包体变大的取舍。

把「能增量就增量」做成可证明的最小构建，而不是凭感觉猜影响面 · ★★★★☆ · TLDR Dev

How we halved DNS build delay and cut memory use by 85%

为什么值得看：讲清了增量构建最难的一步：如何从含糊的事件里推出「最小但一定安全」的工作集，以及怎么用镜像流量证明等价。

展开完整精读

一句话判断

一篇教科书级的增量计算复盘：难点从来不是「少做点事」，而是证明少做的那部分真的可以不做。

1. 规模与旧设计的死结

Cloudflare 的 Zone Builder 现在每秒接收约 700 条 DNS 记录变更，另有约 100 条 zone 设置类事件；单 zone 记录数已超过 2000 万，还在往亿级走。旧设计有一个优点：不需要知道事件为什么发生，只要 zone 变了就按数据库当前状态全量重建，最后只写有差异的 key。但全量构建要把整个 zone 读进内存、编码、逐条比较，大 zone 根本装不下，一条慢构建还会卡住整个 Kafka 分区，拖累无关客户。

2. 最小可证明安全的构建

OpenAI 那种靠放松一致性换取并行的做法在这里不适用：DNS 数据是可枚举、可逐 key 比较的，安全边界必须精确到 key。Cloudflare 的做法是把构建分成五类：只重建指定名字的记录、记录加共享 metadata、apex 加 metadata、purge、全量。判定规则只有一条——目标构建写出的每个 key，必须与全量构建逐字节相同；证不出来就走全量。这条规则让「不确定」永远落在更贵但更安全的一侧。

3. 三个隐蔽的坑

第一，事件本身常常不说改了什么：有些数据库函数只更新时间戳，从事件看和无害的簿记完全一样，这类一律全量。第二，一个域名可能对应多个内部 zone（onboarding/offboarding 期间并存），而 metadata key 是所有同名 zone 共享的，写它必须按最新候选集整体重建，且要先写记录再写引用它们的 metadata。第三，事件描述的是过去，构建可能排队等到数据库已经变了，所以规划要做两遍：事件到达时出保守工作集，执行前再读一次发布快照，允许升级为全量、降级为 purge 或直接跳过。

4. 调度与 Kafka 语义

原来记录构建和全量构建各有一个调度器，互相不能合并工作，现在统一成一个：同一个 zone 的多个事件在构建开始前合并，合并只会加工作不会减，任一事件要求全量就整体全量，purge 覆盖一切。提交用 soft commit：构建可以乱序完成并在内存里标记，但 Kafka 的 committed offset 必须等更早的消息也完成才前进，重启就重放，宁可重复也不丢变更。再加每 zone 的重建间隔和 zone 锁，避免单个热点 zone 吃满 worker。

5. 验证与收益

等价性测试对新旧两种构建做逐 key 的字节比较，时间相关值钉死；灰度期间每个目标构建旁边跑一次全量构建对照，之后换成镜像 Zone Builder：消费生产 Kafka、读生产数据库、写一个不服务客户流量的 Quicksilver 环境，比对 20% 采样 zone 的缺失 key、多余 key 和值差异，并区分「暂时不一致」与「新类型的差异」。24 小时统计：86.81% 只重建资源，2.54% 资源加 metadata，2.30% apex 加 metadata，1.30% purge，全量只剩 7.04%。聚合工作集内存从 49 GiB 降到 7 GiB，峰值 79 GiB 到 12 GiB；中位构建完成延迟 7.7 秒到 3.3 秒，p99 尖峰从 14.6 分钟降到 1.21 分钟。省下的余量又反过来允许缩短重建间隔和 Kafka 缓冲，形成第二段收益。

我的推荐

做配置分发、缓存失效、CI 增量构建的人都该读。最有价值的不是那几个百分比，而是「五类工作 + 证不出就全量 + 双次规划 + 镜像比对」这套可复用的方法论；它也坦率承认全量构建不会消失，首次发布和全局性变更仍然需要它。
