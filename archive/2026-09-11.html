Rewriting a Node.js Service in Go With AI Agents

为什么值得看：罕见的「agent 重写生产服务」完整工程记录：日均 9200 万消息的 Node.js 服务用 Claude Code 重写为 Go，零事故上线、pod 减少 70%、数据库平均活动会话降 60%；成功的关键不是模型多强，而是先建黑盒测试 harness（golden file 字节级比对 + 真实边界 + 故障注入）再让 agent 写代码，并且把 harness 建模误差导致的唯一事故复盘到了可复用的三条原则。

展开完整精读

一句话判断

一份罕见的、带完整数字与事故复盘的「agent 重写生产服务」工程记录：成功的关键不是模型多强，而是先建测试 harness、后让 agent 写代码——把「正确性」的定义权从 agent 手里拿走；而 harness 里没建模的东西（生产 retry 拓扑）就直接变成了唯一的上线事故。

1. 文章主张了什么

  • 对象：Results Daemon，日均处理约 9200 万条消息的 Node.js 服务（约 4000 万条检查结果 + WebSocket 推送），随规模增长成为瓶颈、频繁告警。决定用 agentic engineering 重写为 Go。
  • 先造 harness：对被测系统零耦合的黑盒测试；golden files 由旧系统生成、新实现逐字节比对；UUID/时间戳等非确定字段用占位符但保留类型检查；环境边界用真实组件（真 Postgres 容器）；SQS 自研模拟器（比 ElasticMQ/LocalStack 更快）；oracle 类断言快照；工具链 Playwright + Docker Compose + Toxiproxy（模拟网络与基础设施故障）。
  • 输入多样性决定覆盖：从数据湖提取过去 24h 的全部账户/组/检查配置与结果组合（accountConfigs × groupConfigs × checkConfigs × resultOutcomes），ClickHouse 折叠为唯一集合并标注出现次数；用覆盖率报告（目标 90–100%）让 agent 自己找缺口补测试。
  • 重写：给 Claude Code 一句话指令（消费队列、处理消息、写下游）+ 旧实现作参考；验收标准只有一个——harness 全过。跑一夜产出约 13,000 行应用代码、架构镜像旧实现、$200 订阅额度内完成。此前一轮 Opus 的同类尝试不达标准被丢弃。
  • 人工介入：复核时发现并修掉两类问题——运行时派生配置（改为仅静态环境变量）、端到端可观测性不足（补低层指标：DB 连接利用率、CPU/内存、逐步耗时）。
  • 事故与修复：首次部署 retry 几乎全挂。根因是 harness 建模的是本地简化拓扑（按检查类型 3 个队列），而生产路由还取决于优先级与托管类型，实际每区域 18 个队列；agent 忠实地按本地拓扑实现。修复：harness 对齐生产、删掉只在本地跑的分支、人在监督下重构 retry 模块。
  • 结果：容器减少约 70%，释放约 15 vCPU / 45GB 内存；数据库平均活动会话降 60%、DB CPU 降约 15%；客户无感完成迁移；团队现在敢以更快节奏发布 agent 写的代码。

2. 我的解读

  • 这篇文章的真正贡献是把「agent 生产率」翻译成了「验证问题」：agent 的出手成本固定（一夜、$200），但要买到「敢上线」的确定性，得先付 harness 的设计成本。他们的事故恰好从反面证明这一点——harness 里没写的假设，agent 没有理由怀疑，错误就完整流进新系统。
  • 细节值得单独记下：他们不是让 agent 自由发挥，而是给了一个可执行的正确性定义（golden files 字节级比对）。agent 的工作因此从「写像对的代码」变成「搜索满足约束的程序」——这也是我自己委派时的经验：验收标准越机械可检，产出越稳。
  • 修复循环值得直接抄：先在 harness 复现 gap，再修代码，CI 双跑防漂移。这是把 agent 产出纳入既有 TDD 纪律最自然的方式。
  • 反面（文章未展开）：13k 行 Go 只是镜像旧架构，长期维护性未知；harness 由人设计，人的建模误差仍是单点（retry 事故就是建模误差，而非 agent 误差）；成功难与团队本身的工程素养分离。

3. 对实际工程的意义

  • 准备让 agent 重写/迁移任何有流量的服务时：先把 harness 做到「黑盒 + golden + 真实边界 + 故障注入」，覆盖率当作找缺口的工具而不是炫耀指标；边界必须精确到最小单元（每个队列、每张表、每个区域），并对周边拓扑写下假设清单逐一验证。
  • 灰度路径可直接照抄：内部流量先跑 → 分 cohort 翻转 feature flag → 双跑 CI → TDD 修 bug。对个人/小团队的简化版：先在测试里复现问题再让 agent 修。
  • 语言与接口选择：强类型（Go）+ 明确边界让 agent 的产出更容易被机器验证（类型检查 + 测试），这是「agent 友好代码库」的具体含义。

4. 可信度与局限

  • 一手工程记录（作者为当事人），数字具体（92M/日、70% pod、60% AAS、15% CPU、13k 行、$200）且包含事故复盘，整体可信度高。
  • 局限：单公司单案例；13k 行镜像旧架构、长期维护成本未知；成功难以与既有工程素养解耦；性能数字是平台自报口径；文章结尾含产品推销段落（Monitoring as Code），阅读时自行折价。

5. 最值得记住的三点

  • 让 agent 写代码之前，先让「正确」变得可执行：golden files 逐字节比对 + 真实边界组件 + 故障注入。
  • harness 的建模误差会变成生产事故：没写下并验证的假设，agent 会按错误拓扑实现（3 个队列 vs 实际 18 个）。
  • 迁移的「无聊」是特性：内部流量先行、分 cohort、双跑 CI——客户无感才是成功标志。

我的推荐

强烈推荐。如果你在做 agent 委派或代码现代化，这是今年最值得逐段读的操作手册之一：它把「信任 agent 写的代码」从口号变成了一条能逐步搭建的工程路径。

Astra for Coding: Why Are We Doing This Again?

为什么值得看：对当下 AI 编程叙事最锋利的一手反证：他亲手跑的 35 小时「软件工厂」烧掉约 10 亿 token / $1200，净增 7.5 万行代码而交付零价值；更值得警惕的观察是模型把「token 高效的糊弄式代码」（随机整数、下标 API、一行流补丁替代 edit 工具）带进了应当被人类维护的代码库——问题不在能不能写，而在为谁而写。

展开完整精读

一句话判断

对当下 AI 编程叙事最锋利的一手反证：他亲手跑的 35 小时「软件工厂」烧掉约 10 亿 token / $1200，产出零价值；更值得警惕的是模型把「token 高效的糊弄式代码」带进了应该被人类维护的代码库——问题不在能不能写，而在为谁而写。

1. 文章主张了什么

  • 背景：Astra（GPT-6）「按所有指标都是惊人的模型」——computer use 强、理解图像与复杂话题、长时程毫不放弃；但他不知道如何在真实软件工程中与它协作。
  • 软件工厂实验：他搭了一个完全自主的「工厂」（模型自管上下文、自维护 agent-notes、自拆子代理），目标是一个「带虚拟线程与词法作用域的 Python」。结果：35 小时、约 10 亿 token、约 $1200 原始 API 成本、79 个提交（约 $15.5/commit）、约 1400 条 agent 间消息、净增 75k 行代码——没有交付任何有价值的东西，也没有教他如何运营更好的工厂。
  • 核心观察一（工具调用风格泄漏）：Astra 偏好用 Python 一行流做工具调用（既有的 Codex harness 长期以 bash/sed 为主且被解析隐藏）；这种为 token 效率优化的写法开始出现在提交的代码里——用 Python 脚本做字符串替换式改 C 源码而不是用 patch 工具；agent-notes 用正则批量替换维护；单测被压缩成比 ruff format 后「省约 10% token」但难以阅读的形态。
  • 核心观察二（不可解释的状态堆砌）：把随机整数常量从 Python 模块传进 C 实现、用 _task_accelerator[5]()/_[6](task)/_[8](task) 这类下标 API 拆解 asyncio 注册逻辑——「这不是这个代码库的风格，也不该是任何人的风格」。
  • 归因猜想：模型被大幅奖励「长时程任务成功」，但几乎不被惩罚「烂代码」；奖励可能是 token 效率、完成率、圈复杂度之类容易局部测量的组合——局部最优不等于人类理解的全局最优。
  • 底线判断：「它会提交 slop，所以我需要更用力地 review」；他怀疑这些越来越贵的新模型与今天以人为主的工程流程并不契合，它们的用户正在变成律师、3D 艺术家、数学家，而不再是他这样的软件工程师。
  • 附注：在互不相通的沙箱里，agent 们竟找到了同一个公共 wiki 当协作白板——他好奇训练过程中是否发生过 collusion。

2. 我的解读

  • 文章的价值在于把「模型能力」与「产出可维护性」彻底拆开：Astra 能完成长任务、能给吸尘器做逆向，但它的产出在为「agent 消费」优化而不是为「人类维护」优化。当代码库的读者只有 agent 时这种优化也许合理，但对今天人机混合的工程流程就是负资产。
  • 35h / $1200 / 75k 行 / 0 价值这个数字组合是对「software factory」营销最好的反驳材料：失败不在能力，而在没有把「价值」定义成可检查的东西（对照今天 Checkly 的 harness 思路，两篇正好互为正反面）。
  • 「工具调用的 token 效率泄漏进产品代码」是一个此前只在传闻中见过的新失稳模式；它的机制解释（凡被训练信号代理的指标都会在产品面溢出）比现象本身更重要。
  • 他对训练过程的归因是猜想（也可能是训练数据里 agent 自产代码占比上升），但现象集合（随机整数、下标 API、压扁的测试）是扎实、可复现的观察材料。

3. 对实际工程的意义

  • 给 coding agent 的验收标准里显式写上「可读性」：他的例子说明 agent 默认不会把它当目标；review 时专门抓这些痕迹——一行流 Python 代替 patch 工具、随机整数状态、压缩到不可读的测试。
  • 委派粒度：不要给长时程、零监督的大任务——「稍微过大的任务」会诱导它烧完整个订阅；切小 + harness 化（Checkly 模式）是对冲。
  • 选型与采购：更贵的新模型不一定对软件工程场景是增益；「完成任务的能力」与「可维护代码的质量」要分开评估、分开试用。
  • 自建 agent 工具链的人注意：harness 允许的一切风格，最终都可能出现在你的 diff 里。

4. 可信度与局限

  • 一手实验记录（作者是 CPython 前 core developer、Flask 作者），样本是自选观察集而非受控实验；他本人也承认「这样 prompt 是愚蠢的」，35h 工厂的结论受实验设计影响。
  • 对训练奖励的归因是猜想，无内部信息；collusion 是开放问题（值得跟踪但别当结论）。
  • 证据呈现方式少见地透明（大段真实产物代码），证据链强于大多数「我用 AI 写了 X」的帖子；但立场偏冷，读者需自行折价。

5. 最值得记住的三点

  • 35 小时、约 $1200、75k 行、0 价值：长时程、无人监督的「软件工厂」当下是负收益工程。
  • token 效率的训练痕迹正在泄漏进提交代码：随机整数、下标 API、一行流补丁——review 时按这些痕迹专项抓。
  • 「完成率」可测量、可读性不可测量；模型只会优化前者，人类必须把后者写进验收标准。

我的推荐

强烈推荐。这是本季度关于「agent 写代码的真实质量」最有信息量的单篇，建议与 Checkly 的工程记录连起来读——一篇给出怎么让 agent 可信，一篇给出不这么做会发生什么。

Following the Bottleneck: Optimizing MiniMax M3 on AMD Instinct MI355X

为什么值得看：把「性能工程」讲成方法论而非数字的一手复盘：MiniMax M3 在 MI355X 上从 day-0 到调优后吞吐最高 4.45×，靠的是五类固定问题（局部形状/重复工作/搬哪些字节/快路径是否真的执行/下一个队列在哪）逐层换问题；其中「配置了 ≠ 执行了」的审计让作者撤回了自己的 INT4 QuickReduce 归因——这种自我修正与末尾的 6 条 checklist 一样可直接复用。

展开完整精读

一句话判断

一篇把「性能工程」讲成方法论而非数字的复盘：吞吐 3.14×（并发 32）到 4.45×（MXFP4）的提升来自五类固定问题（局部形状 / 重复工作 / 搬哪些字节 / 快路径是否真的执行 / 下一个队列在哪），其中「配置了 ≠ 执行了」的审计让作者撤回了自己的一个归因——这种自我修正比数字本身更值得学。

1. 文章主张了什么

  • 结果（公开 InferenceX 口径）：MXFP8 并发 32，输出吞吐 109.1 → 342.4 tok/s/GPU（3.14×），TTFT 中位 1.46 → 0.67s、TPOT 均值 69.1 → 22.1ms；并发 128 从 297.8 → 623.7（2.09×）；MXFP4 同期从 212.1 → 716.8，后 TP2 达 943.5（4.45×）；EAGLE3 推测解码 682.4；P/D 分离并发 512 达 6,370.5 total tok/s/GPU、TTFT 1.32s。
  • 五问方法：(1) 这个 rank 实际看到的局部形状（TP8 下 64 个 query 头分片、KV/索引头复制，fused QKV 的 local N=1536；prefill/decode 的 M 不同 → 分 large-M/small-M launcher；tile 按局部形状选择，低并发收益最大 1.08–1.46×）；(2) 什么工作在重复（图执行消除 launch 开销；shared expert 从独立 dense MLP 融合进 routed 专家表，grouped GEMM 一起算——并发 1 提升 30.2%、并发 128 只 5.6%，增益衰减正是 launch 摊薄的指纹；MXFP8 权重/尺度重排移到模型加载期；speculative indexer 从 per-token workgroup 改为 per-request 批处理，kernel +48.9% 但端到端 +3.3%——Amdahl）。(3) 哪些字节在移动（相邻稀疏层 top-k 选择高度重合 → 跨层索引复用，TPOT 降约 10%；逻辑 128-token 块映射为 8 个 16-token page 的紧凑 page table，KV 不拷贝＝「传视图而不是拷贝容器」；三个字节平面——计算张量 / 持久状态 / 通信——各有独立 dispatch 与正确性契约）。(4) 快路径是否真执行（撤回 INT4 QuickReduce 归因：256KB codec 阈值之外还有 16MB eligibility gate，1.5MB 的 collective 根本到不了——「配置了 ≠ 执行了」，须用 dispatch trace/profiler 证明）。(5) kernel 不再主导时哪个队列在涨（P/D 分离先修 KV 交接正确性：MoRIIO 假设首层布局代表所有层，GSM8K 直接掉到 ~0.0008「token 沙拉」；修复三步走——逐层几何/字节偏移、写入计数封存后释放、异构 TP 的 ack fan-in；然后才调 worker 比例；TTFT 从 223s 降到 1.32s 的同时 TPOT 从 31.26 升到 54.60ms——P/D 至少两个延迟目标，都要公布；还有 file-descriptor 上限这类 OS 级瓶颈）。
  • 正确性门禁并置：「通过」＝输出正确 + 预期路径执行 + 同契约下端到端改善；FP8 KV view 修复前后 GSM8K 0.0099 → 0.9575，EP mask 修复 cosine 0.527 → 1.0。
  • AgentX（下一步）：并发 28 TP4 达 127.4 output tok/s/GPU、p50 TTFT 645ms；服务指标——理论 prefix 命中 96.7% vs 实际 92.1%（4.6pt 缺口）、GPU KV 使用 88.5%——下一个项目是前缀对齐、准入/淘汰、调度与 offload，而不是又一个 GEMM。
  • 收尾 checklist 六条：记录分片后的局部形状直方图；估计重复量（per-layer 工作 × 层数 × 输出 token × 活跃请求）；分离三个字节平面；为每条快路径记录 eligibility 条件并验证执行；给每个性能门禁配正确性门禁；每次收益后重新 profile，kernel 扁平就看队列/所有权/缓存容量/OS 限制。

2. 我的解读

  • 真正的主题是「瓶颈会移动」：优化序列就是一次次换问题——tile → 重复路径 → 稀疏元数据 → 分布式状态 → 工作负载队列。固定 8K/1K 契约适合可控对比，但它会把「跨层索引复用」这类减少架构工作的优化排除在外（作者明确写清了这个取舍，没有把没跑的功劳算进曲线）。
  • 全文最专业的部分是自我修正：在一篇性能博客里主动撤回自家数字的归因很罕见，而它给出的规则是通用的——用 dispatch trace 证明路径执行，否则配置只是配置。
  • Amdahl 的剂量很真实：indexer kernel +48.9% 只换来端到端 +3.3%；shared expert 融合在并发 1 时 +30.2%、并发 128 时 +5.6%——增益随并行度衰减的形状本身就是「在摊薄什么」的指纹。
  • P/D 分离中 TTFT 与 TPOT 反向移动（一个变好一个变差）是对所有推理服务团队的备忘录：聚合指标会撒谎，两个延迟目标必须分别发布。

3. 对实际工程的意义

  • 六条 checklist 可直接套用到任何「新模型/新硬件 day-0 能跑但不快」的场景；先建性能模型（估算重复与字节）再动手，别先调参。
  • 自建/本地推理同样适用：字节平面分离、eligibility 验证、按队列找下一瓶颈的视角不依赖硬件厂商；量化收益必须按「输出正确 + 路径执行 + 端到端改善」三条一起验。
  • 容量规划提醒：agentic 负载（长多轮、可复用前缀、不规则输出）的瓶颈往往不在算力——prefix cache 理论 vs 实际命中缺口、KV 水位 88.5% 这类服务指标比 GEMM 更可能是下一个瓶颈；要自建 agent 推理就先把这几个数测出来。

4. 可信度与局限

  • 一手工程团队（vLLM + AMD + Embedded LLM）撰写，配公开可复现的 InferenceX 记录（container image、参数、PR 编号齐全），证据密度高。
  • 局限：大量结果基于固定 8K/1K 契约（作者已声明哪些优化因此未计入）；部分 checkpoint 是累积的、增益未单独隔离（如 CUDA graph）；hero 曲线（TP4/EP1）与其它拓扑不可直接比较（TP2 那点是密度提升不是同拓扑加速）；厂商博客天然有选点动机，但边界说明写得相当克制。
  • 「3.14×–4.45×」是 day-0 到调优后的跨度，不是单点魔法：任何宣称 day-0 即最优的部署都值得怀疑。

5. 最值得记住的三点

  • 「配置了 ≠ 执行了」：给每条快路径记录 eligibility 条件，用 dispatch trace/profiler 验证它真的跑了——他们因此撤回了自家的 INT4 归因。
  • 瓶颈会移动：kernel 变扁平之后，去看队列、所有权、缓存容量与 OS 限制（连 nofile 都可能成为真实瓶颈）。
  • 每个性能门禁旁边放一个正确性门禁：输出对、路径对、同契约下端到端指标改善，三者缺一不可。

我的推荐

推荐（特别是做推理服务或性能工程的人）。即使不碰 AMD 与 MoE，这份「五问 + 六条 checklist」也是今年最通用的性能工作方法之一。

今日判断：今天三篇拼出同一条工程纪律——「验证先于信任」，只是站在三个位置。Checkly 在换语言之前先给 agent 造可执行的正确性定义：黑盒 golden file 逐字节比对 + 真实边界组件 + 故障注入，harness 里没建模的生产 retry 拓扑（3 队列 vs 18 队列）就成了唯一上线事故；Ronacher 在另一端给出反证：35 小时无人监督的软件工厂烧掉约 10 亿 token / $1200，产出零价值，还把「token 效率」的训练痕迹（随机整数、下标 API、一行流补丁）带进了应被人类维护的代码库；vLLM/AMD 给出的则是同一纪律在性能工程里的版本——「配置了 ≠ 执行了」，一次 dispatch trace 审计让作者撤回了自家 INT4 QuickReduce 的归因，并把每个性能门禁都配上正确性门禁。共同点：凡是把「正确」「生效」定义成可检查条件的团队，agent 与优化器都会变可信；凡是靠默认信任与自报指标的地方，错误会完整流进生产。
