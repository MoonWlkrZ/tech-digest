EP234: Docker vs Kubernetes

为什么值得看：它把常被混为一谈的两件事拆开讲清楚了：Docker 负责把应用连同依赖打成可移植的容器镜像，Kubernetes 负责在多台机器上编排这些容器；同时附上 Redis 单条命令的完整执行路径和开放权重与闭源模型的七项取舍，都是能直接拿去用的判断依据。

展开完整精读

一句话判断：这不是一篇长文，而是一张概念校准卡——五个小节各讲一件事，价值在于把「Docker 还是 Kubernetes」这种伪选择题还原成两个不同层次的问题。

  1. Docker 与 Kubernetes 的分工。Docker 把代码、库、运行时和配置打成可移植的容器镜像，镜像跑起来就是容器，笔记本、服务器、云上没有区别；它通常跑在一台机器上，单机多容器靠 Docker Compose 编排。Kubernetes 则是跨机器的编排平台，能起停容器、按需增减副本、分发流量、滚动发布。两者的关系不是二选一，而是「先有可打包的东西，才谈得上编排它」。

  2. 什么时候真的需要编排。文中给出的判据是自动扩缩容、自愈、高可用、跨机器部署这些生产特性；也就是说，需求出现之前上 Kubernetes 是给自己加一份运维工作——控制面本身挂了，半夜被叫起来的是你。对大多数服务而言，Compose 不是新手选择，而是 Kubernetes 存在的意义所要超越的终态。

  3. Redis 为什么快。这一段是全篇信息密度最高的部分：数据全在内存、用高效的内存数据结构，命令进来先按 RESP 解码，拆出命令名、键、值和参数；校验命令存在、参数格式、客户端是否已认证授权；再查内部命令表找到执行代码；所有命令顺序执行，改内存时定位字典里的键完成操作。带 TTL 的键单独存过期时间戳，靠惰性删除加主动过期清理；写操作通过 AOF 日志、RDB 快照或主从复制往外传；内存触顶则按淘汰策略处理，最后用 RESP 组装响应返回。把这串路径记住，排查慢查询和主从延迟时就知道该看哪一段。

  4. 开放权重与闭源模型的七个取舍。微调上开放权重能在自己的 GPU 和数据上训练，闭源模型不给权重；版本上开放权重把产物留在手里，想钉哪个版本就钉哪个版本，闭源模型提供带日期的快照但按厂商节奏退役；此外还有可检查性、部署形态、许可证、自托管与成本。成本这条最容易被忽略：自托管要等量足够大、把运维开销摊薄之后才赢，低量时 API 零前期投入反而更便宜。

  5. 文本水印是怎么做的。模型每步本来会给出下一个词的概率分布，水印不改变分布，而是用「密钥 + 前几个词」决定哪些候选词是合法选择；整段文本重复这一过程，多解的位置就承载了信号。检测时对每个词检查它是否符合密钥与前文的约束，命中率越高越像 AI 生成，整体命中率可以直接当分数用。作者的态度值得记一笔：他对现有 AI 文本检测的假阴性很不满，技术写作尤其容易误判。

我的推荐：如果你只需要一篇，就看第一节和第三节。第一节帮你把「Docker 还是 Kubernetes」从工具之争纠正为层次问题，第三节是少数把 Redis 单条命令从进到出讲完整的短文。剩下的分布式模式清单更像索引，适合扫一眼看有没有自己没听过的名字，不必逐条记。
