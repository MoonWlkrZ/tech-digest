值得精读：把成本优化做成了可复现的检查清单，且附了质量没退的证据 · ★★★★★ · TLDR

把一次代码评审的推理成本从 2.43 美元降到 0.77 美元

为什么值得看：全篇是 before/after 数字：单次评审 2.43 降到 0.77 美元，中位耗时 4 分 09 秒降到 1 分 32 秒。最大的一笔省在查清每个会话第一个请求到底有没有从缓存读——实测只有 14% 到 26% 命中，根因是 prompt 结构让共享前缀从没单独落过缓存。

展开完整精读

一句话判断：这是今年少见的、把 AI 评审成本从 2.43 美元压到 0.77 美元的全过程记录，而且作者同时给出了质量没有明显下降的证据，方法论可以直接搬到任何跑 agent 的团队。

  1. 成本是怎么涨上去的。2026 年 3 月平均每次评审 1.22 美元，8 月涨到 2.32 美元。这两个月并没有架构改造，主因是 8 月初把所有 reviewer 迁到 Anthropic 模型（单次从 1.38 涨到 2.03 美元），加上每次评审的 token 从 91 万涨到 299 万——缓存命中率虽然从 85.7% 升到 97%，但三倍的 token 基数乘上去仍然更贵。同期缓存写入占支出 43%、缓存读取占 34%、输出只占 23%，钱主要花在模型已经看过或马上要再看的上下文上。一个 code quality 会话平均调 16.6 次模型，写进缓存 7.2 万 token，读回 108 万，因为每次调用都要把整段对话当上下文重发。

  2. 最大的一笔省在首个请求有没有命中缓存。9 月 14 日起他们记录每个会话第一次 LLM 调用的用量和首个 system block 的哈希，发现只有 14% 到 26% 的会话读到了缓存，而各仓库共享的工具定义和 agent prompt 有 1.1 万到 2.1 万 token，本应几乎全部命中。根因在 OpenCode v1 的构造方式：agent prompt 和环境信息（工作目录、日期）被拼成一个 block，唯一的 cache breakpoint 在块尾，共享的那部分从没被单独存下来，所以 A 仓库写下的缓存 B 仓库用不上。9 月 16 日他们在 prompt 末尾加标记，用插件在标记处把 block 切成两段，前半段只含所有任务共享的字节并单独设断点；为了保持前缀稳定，还得把技能列表和工具描述里会变的部分拿掉。这一步把单次成本从 2.47 降到 2.02 美元。

  3. 剩下的钱是一堆小改动凑出来的，合计约 0.20 美元一次：删掉子评审根本用不到的工具（此前 57% 到 76% 的会话会去调发布评论的接口，被服务端拒绝后再花一次调用恢复）；把读文件改成并行，首次响应一次读完成最多 150 KB 的上下文与补丁；二次评审时跳过没有新内容可看的 reviewer（AGENTS.md 评审跳过 56%，性能 23%，文档 13%）；评论发出去就停，不再为一段没人看的总结多跑一轮；把超时和供应商故障分开处理；任务被取消后每 15 秒自查状态并退出（446 个被取消的任务里有 358 个其实一直在跑）。另外三个 reviewer 现在共用同一个前缀，后两个最多等 20 秒读第一个写下的缓存，每人省约 9 美分。

  4. 换模型和调 effort 的收益比改代码更大，作者自己标注了分段对比不是严格的对照实验：代码改动贡献 0.65 美元，模型与 effort 贡献 1.06 美元。Opus 5.5 在 medium effort 下与 Opus 5 没有可测的质量差异，换过去更便宜；Sonnet 5.5 与 Sonnet 5 单价相同，但每次评审便宜 47% 到 62%，原因全在用的 token 更少——code quality 在 medium 下每次只调 1.7 次模型，超过一半的评审一次调用就结束。

  5. 质量侧有两个独立检查，这是这篇最值得学的地方。一是看作者后续有没有改被标记的行：严重问题被采纳的比例从 34% 升到 59%，每千次评审里导致实际改动的严重问题数量基本持平（132 对 145）。二是让两个不同厂商的模型盲评 657 条问题，重要问题从每次 0.28 条变 0.30 条，而被判严重度虚高的从 0.46 条降到 0.14 条，降了 70%。结论按 reviewer 分开看：code quality 在 high effort 下丢掉的主要是噪音和虚高的严重度；performance 在 medium 下确实漏了约 64% 的重要问题，security 可能也漏，所以这两个正在试 high effort。

我的推荐：如果你在跑任何有量的 agent，先查两件事——每个会话的第一个请求到底有没有从缓存读，以及你付的那个 effort 档位还能不能找出真问题。这篇把两件事都做成了可复现的检查，而且老实写了哪些结论只是区间重叠、哪些统计不显著。

值得精读：少见的横向样本，结论不讨喜——账单在涨，产出并不总是跟着涨 · ★★★★☆ · The Pragmatic Engineer

AI 支出到底换来了什么：27 家公司的账单与 PR 数据

为什么值得看：把每月每人的 AI 账单和 PR 吞吐放进同一张表：两人小厂每人每月 3000 美元、每天 10 个以上 PR，另一家 1500 名工程师的上市公司每月只给 150 美元；同时有公司 PR 数量在涨而合并速度不变，也有公司 PR 频率持平但单个 PR 代码量涨到 3 倍。

展开完整精读

一句话判断：把每月每人的 AI 账单和 PR 吞吐放在同一张表上看，27 家公司的样本说明账单确实在涨，但产出并不总是跟着涨，而且几乎没有公司能说清 ROI。

  1. 平台侧的数据先给了乐观的一面。CodeRabbit 对 2 万名开发者的固定样本统计，周 PR 数同比 +113%，月 PR 数 +127%，同一批人再算一次是 +128%；Sonar 旗下的 Gitar 看到被它称为 AI 原生的团队能做到每人每周 60 个以上 PR，并把客户分成明显不同的几档。作者提醒这可能是文化效应：新人会很快跟上团队的节奏，一个把每人每周 5 个 PR 当高产的团队和一个习惯每周上线二三十个的团队，招进来的人会各自适应。

  2. 花费和公司规模没有关系。样本里一家两人的 .NET 小厂每人每月花 3000 美元（Claude Opus 加 GitHub Copilot），每天 10 个以上 PR，自称两个人干了以前 5 到 7 个人的活；而一家 1500 名工程师的上市公司把每人每月 AI 支出限在 150 美元。一家约 5000 人、2000 名开发者的量化基金，总支出从 1 月的每月 50 万美元涨到 9 月的 800 万美元，16 倍；人均 1600 美元，单人上限 2.5 万美元，而且花得最多的是交易员而不是工程师，工程侧正在学的一件事是给交易员加限流。他们的 ROI 口径很简单：交易台的盈亏就是答案，支出只要在利润里，就没人追问。

  3. 同一份样本里，PR 数字和真实交付经常对不上。一家 600 名工程师的上市 SaaS 公司 PR 数量在涨，但合并速度没什么变化，工程师的原话是当团队还在乎生产代码质量时，实际开发速度并没有提高多少，反而是分诊工单、查历史设计、做 POC 这三件事快了一个数量级；一家 5000 人的公司 PR 频率持平，单个 PR 的代码量涨到 3 倍，作者猜是模型写代码本身就啰嗦；另一家 1 万人的跨国公司 PR 频率从每人每周 1.5 涨到 4，但负责人自己说这被一个人拉高了，其余人变化不大，而同一团队按月关闭的用户故事数从 2、3 月起稳定在 3 倍，这是样本里少见的业务侧指标。

  4. 花钱的高峰已经过去了。6、7 月几乎每家公司的月支出都到顶，之后走 API 方案的公司成本大约减半，原因是换到 Opus 5.5 以及部分迁到开源模型；同时不少公司的补贴订阅即将到期，账单可能要涨 5 到 10 倍，得提前准备优化。中等以上花费的公司普遍设了上限，但多数人说很容易绕过，只有一家 AI SaaS 公司把 2000 美元当月度硬上限，还开了一个公开频道点名接近上限的人。

  5. 这篇文章的公开部分到 Meta、NVIDIA 与苹果的支出细节就结束了，ROI 那一节的结论在付费墙后面，所以这里只能给出样本本身说明的事：投入和产出之间没有稳定关系，而衡量口径（PR 数、合并速度、故事数、单个 PR 的代码量）会给出很不一样的答案。作者也承认 27 家是便利样本，不是统计抽样。

我的推荐：把它当行业基线读，不要当结论读。真正可操作的是一句话——先定义你要的产出指标，再决定愿意为 AI 付多少钱；PR 数量最容易被 agent 抬起来，也最不能说明问题，能按月关掉多少用户故事、分诊快了多少，才更接近真实收益。

值得精读：一份讲清确定性边界该画在哪里的生产架构复盘 · ★★★★☆ · TLDR AI

薄编排器：Meta 把路由做小，让 14 个专职 agent 各管一段

为什么值得看：1300 行编排器路由 20 多种工作流到 14 个专职 agent，自身不做任何领域工作；七步协议里只有委派这一步需要模型推理。新列配置从手工三到四天降到一小时以内，约三分之二的改动不需要明显人工编辑。

展开完整精读

一句话判断：Meta 用 1300 行编排器路由 20 多种工作流到 14 个专职 agent，自己不做任何领域工作，把幻觉关进了小上下文里；这篇的价值不在规模，而在它说清了哪些决定不该交给模型。

  1. 起点是一次失败。他们要给推荐系统的数据列做上线，涉及三个代码仓库、三种语言、最多六个必须同步的阶段。第一版是常见做法：一个大 agent 装下所有领域知识——配置 schema、代码生成规则、路由逻辑、校验要求、十多个数据源的填充方式。演示时能跑，上生产开始串味：把某个子系统的字段命名规则用到另一个子系统，或者拿 A 数据源的代码生成模式去填 B 的数据。他们还试过另一种单 agent 方案，靠人工为每个任务手写 system prompt 能把成功率做到 70% 到 80%，不手写就掉到 10% 到 20%——这不是 prompt 写得不好的问题，是结构问题。

  2. 做法是把系统劈成两层。编排器是确定性的，只做意图分类、收集必填字段、跑可靠性检查、委派；14 个子 agent 各自是某个领域的完整专家，上下文互相隔离，谁也看不到全貌。每个请求走固定的七步：读子 agent 的指令文件、查目标是否已存在、向用户收集字段、自动发现可推断的信息、过可靠性闸门、带着完整上下文委派、处理结果并回报错误。七步里只有第六步需要模型推理，而且发生在隔离的子 agent 里，只加载它自己那份领域知识。

  3. 工作流模板是复用的关键。列上线是 Schema → Validation → Population → Testing，事件上线多一步事件处理，pipeline 迁移是评估 → 规划 → 填充 → 校验 → 监控。三者用的是同一批 14 个 agent，只是顺序不同；要做新场景时他们没写新 agent，只写了一个新模板，零新 agent 代码。每个子 agent 的结构都一样：加载哪些知识文件、编排器必须先收齐什么、分步执行计划、在 monorepo 里怎么找相关模式、常见错误怎么解。25 个以上的知识文件在子 agent 执行时按需加载，改一个文件下一次会话就生效，不用碰编排器，也不用重新部署。

  4. 结果给得很直白：新列配置过去手工要三到四天，上一代配置驱动系统约一天，现在是 1 小时以内；大约三分之二的改动不需要明显的人工编辑。作者也承认这是拿通用性换领域深度——编排器通用，子 agent 专门。

  5. 文章最有价值的是失败模式分析。重型编排器一旦幻觉，错误会顺流而下：路由到错的 agent、收集错的字段、跳过可靠性检查；薄编排器把路由和检查留在确定性一侧，创造性的部分放进隔离的领域上下文，坏了也只坏一段，重试和升级都有明确的落点。文末引用的那篇多 agent 研究（80 任务批次下 65.3% 对 16.6% 的准确率）可以当旁证，但任务类型和样本都与他们的场景不同，别直接外推。

我的推荐：读的时候重点看哪些决定不该交给模型这一节，而不是 14 这个数字。多数团队立刻能改的，是把路由、查重、字段收集这些确定性步骤从 prompt 里拿出来写成代码——这一步不需要换模型，也不需要重构。
