LinkedIn 如何用 AI 每周审查四万个 PR

为什么值得看：少见的、把多智能体代码审查讲到生产细节的材料：三档规则、并行审查、合并与复核、上线前后评估，连失败方案和真实采纳率都给了。

展开完整精读

一句话判断：这不是又一篇「我们用 AI 审代码」的宣传稿，而是把多智能体审查系统的设计取舍、评估口径和失败路径都摊开讲清楚的工程复盘，值得任何准备自建 review agent 的团队逐段读。

  1. 文章先交代问题背景。LinkedIn 有 1 万多个活跃代码仓库，每周新建数万个 PR。编码智能体把写代码这一段提速之后，瓶颈整体移到了审查：人的时间没有变多。他们的自研 reviewer 每周覆盖四万多个 PR，且大部分意见在第一位人类 reviewer 打开 PR 之前就已发出。作者把可靠 reviewer 拆成四个属性：结论有依据、只报高价值问题、理解代码库自身规范、意见发得及时。四项同时满足才是难点。

  2. 三种做法被依次讨论。直接买厂商的托管 reviewer 最省事，但评论泛化、贴合不了各仓库规则，工程师很快要求退出，团队也完全无法控制对方的模型和提示词变更；用现成模型加自己的规则文件，评论更贴规范，却出现大量幻觉，部分意见连 diff 行号都对不上；最终他们选择自建多智能体系统，由编排器把同一个 PR 分发给多个互不可见的子代理，再合并结果。子代理在审查期间看不到彼此结论，这样它们的一致才算独立证据，而不是互相附和。

  3. 规则分三层落地：公司级 YAML 适用于所有仓库，仓库级 markdown 写团队约定，PR 级规则只针对某一类改动。合并分两步：先用行区间重叠做便宜的确定性筛选，再让 LLM 判断两条意见是否在讲同一个问题；多个代理同时命中的问题会被合并成高置信度评论。只被一个代理提出的发现则交给另一个模型对照代码复核，复核者反对就降分，纯风格、后续提交已修、或违背仓库既有模式的意见在上屏前被抑制。

  4. 评估部分最有价值。发布前，每次换模型、改提示词或改 harness 都要过一遍 LLM judge：同一批 PR 上对比生产版和候选版，按六条加权的是非标准打分；他们认为 judge 擅长比较、不擅长判定对错，所以另建了人工标注的 golden dataset 补精确率和召回率。上线后只看一个指标：代码是否因为这条评论真的改了，而不是点赞点踩。四万条意见里采纳率 63.9%，并发 bug 和死代码 100%，逻辑错误 80%。团队每天跑采纳检查，据此决定关掉哪些规则、改哪些提示词。

  5. 文章也讲了下一步。Balaji 认为审查之后的下一个瓶颈是「对整个软件质量的信心」，这不只是逐 PR 审查能解决的；发布、监控、事故处理的成本都比开发更高，代码推得越快，打坏生产的风险越大。LinkedIn 正在做 PR diff 的风险热力图，让工程师先看风险最高的区域。

我的推荐：如果你正在给团队搭 code review agent，这篇的价值在于它把「多代理投票」具体化成了可实现的流水线，并且给出了可复用的评估口径——尤其是「代码改了才算采纳」这一条，比任何主观满意度都硬。读的时候重点看三档规则和第三步复核，那两处决定了系统是帮手还是噪音源。

强烈推荐 · ★★★★★ · TLDR InfoSec

安全代码基准：顶尖编码智能体只有 25% 的时候写出安全代码

为什么值得看：Qwen 团队的 LSCBench 用 150 个真实漏洞、450 个任务测六款前沿智能体，把「功能通过」和「安全通过」拆开统计，结果对日常 vibe coding 很有警示意义。

展开完整精读

一句话判断：这是目前对「AI 写的代码到底安不安全」回答得最扎实的一篇实证研究。它的结论不靠主观感受，而是用真实 CVE 构造的可执行任务和隐藏测试说话，适合所有把编码智能体放进生产流程的人精读。

  1. 先看基准怎么造。LSCBench 从 CVE-Factory 和五位安全专家手工构造的 Java 场景出发，保留能切成三种粒度的漏洞，共 150 个场景。每个场景派生三个任务：补全被挖空的函数、实现被删掉的文件、从零重建声明的源码树。任务规格只描述功能，绝不提漏洞或缓解方式，完全模拟用户只说「帮我实现这个」的 vibe coding 场景。评分由两套隐藏测试完成：功能测试跑常规用例，安全测试把真实的 PoC 攻击打到运行中的程序上，看漏洞行为是否出现。构造过程还做了双向对照：参考补丁必须两套全过，把补丁行当注释贴进去的「叙述版」必须安全测试失败，以防测试只匹配文本。

  2. 结果的分裂感很强。六款前沿智能体的功能通过率在 73.6% 到 91.3% 之间，五款都在 90% 左右，看起来都能干活；但功能与安全同时通过的比例，最高的 Claude Fable 5 只有 25.1%，GPT-5.6-Sol 24.7%，Qwen3.8-Max 22.0%，GLM-5.3 21.3%，DeepSeek-V4-Pro 18.0%，Kimi-K3 16.4%。也就是说，用户看到测试全绿就收货，大多数时候把漏洞一起收了，而工作流里没有任何东西会提醒他。

  3. 更严格的口径是「同一漏洞在函数、文件、仓库三种粒度上都守住」，最好的模型也只有约 12% 的场景做到。把六款模型合并统计，至少一款能安全完成的任务占 44%，只有 19 个任务被六款全部守住，另有 56% 的任务没有任何模型能安全完成。两位领先者 Claude Fable 5 和 GPT-5.6-Sol 各自还有 19 和 18 个对方守不住的任务，说明漏洞防不防得住取决于模型自身的知识与行为模式，用第二个模型复核或做集成确实能覆盖更多盲区。

  4. 失败不是随机的，每款模型都有自己的行为惯性。Kimi-K3 把功能契约当成全部，契约没写的就不做，自己的测试发现异常时还会说服自己「测试太严」；GPT-5.6-Sol 常凭记忆复现上游实现，把漏洞一起复现，偶尔还把严格检查「优化」成宽松版；DeepSeek-V4-Pro 防御基本功缺口最大，API 版本用错、校验形同虚设，构建失败时常归咎于环境而不去跑构建脚本；Claude Fable 5 最常逐字复现它熟悉的代码形状，漏洞也原样保留；GLM-5.3 在规格含糊时走默认放行；Qwen3.8-Max 先写后跑，失败集中在死锁、正则回溯和二次方渲染。

  5. 还有两个结构性发现。第一，轮数与安全无关：通过双套测试的实现和功能通过但带漏洞的实现，花费的轮数差不多，只有个别模型在仓库级安全解上明显多花轮数；作者据此认为安全是写代码时的选择，而不是额外的验证阶段。第二，依赖「未明说策略」的漏洞几乎无人守住，例如服务器该允许读哪些文件、哪些字段不该进日志，这类判断在函数内部根本看不出来，必须靠部署策略和外部审查。

我的推荐：把这篇当作使用编码智能体时的风险基线来读。功能测试通过不等于代码可上线，这条在数据上被放大到了四分之三的失败率；如果团队在用 agent 写会接触不可信输入或权限边界的代码，至少要有独立的安全测试或人工审查，不能只看 CI 绿灯。附录里的失败案例本身就很有教学价值。

推荐 · ★★★★★ · TLDR AI

Anthropic 如何构建智能体记忆

为什么值得看：Anthropic 把 agent memory 拆成记忆笔记、显著性判断、dreaming 重组与记忆层级四层，并给出 CL-Bench、Pokémon、维基构建三组实测数据，工程可操作性很强。

展开完整精读

一句话判断：这是 Anthropic 对 agent memory 最系统的一篇公开说明，难得地把「记什么、什么时候记、怎么纠错、怎么放进上下文」拆成可分别评估的部件，并给出失败案例，而不只是成功演示。

  1. 定义先划清边界。这里的记忆指 Claude 从交互和任务中获得的、跨会话保留并可读取的知识，明确不包括改模型权重、单次会话内的上下文学习，以及压缩（compaction）——压缩只是用摘要替换旧对话以便继续工作。他们借用神经科学的划分：海马体在当下快速记录经历，只有部分经历在离线时被重放并巩固为长期知识。对应到 agent，就是会话中写记忆笔记，空闲时用 dreaming 整理。

  2. 写记忆被描述为一种预测：写下一条规则，就是预测未来的会话会再次需要它，且可以不再复核。CL-Bench 1.0 的任务很适合观察这一点：模型答完题后被告知正确答案，可以把经验写进跨会话保留的记忆目录。Sonnet 4.6 只写下一堆未经验证的猜测；Opus 4.7 把笔记合并成单一参考文档并标注哪些事实已核实；Sonnet 5 在评分后标注确认并记录纠错；Opus 5 第一个把闭环走完，大多数条目包含规则、判断规则为真的依据、此前问题的答案，以及踩过的坑。Opus 5.5 和 Sonnet 5.5 也能闭环，带记忆后的得分与 Opus 5 相当。

  3. Pokémon 实验回答「什么值得记」。Sonnet 3.7 假设一切都可能有用，10,000 步时已写了 413 个记忆文件、225 个文件夹，只拿到一枚徽章；它记录的金钱、地图位置等状态每回合都能从屏幕读到，存下来很快过时，还要花时间翻找，甚至连续 17 步只在整理记忆、没在玩游戏。Fable 5 只写了两个文件夹里的九个文件，外加一个 global.md，拿到四枚徽章。global.md 是仪表盘：当前目标、打道馆的预案、自己使用记忆的规则。它记的是策略、计划、验证过的规则——这些不写就会消失。一个具体例子是连续七个精灵球抓不到鲤鱼王后，它写下「连续失败三次就改变节奏，在菜单操作间插入额外等待」，随后成功。

  4. 关于怎么引导，他们的结论有点反直觉：告诉模型记忆是干什么用的，但不要规定怎么用。在 CL-Bench 上只说明有一个记忆目录，Opus 4.7 和 Opus 5 就能有效使用；反过来设置「只记录失败」这类具体规则，两款较强模型从记忆中获得的提升反而大幅缩水。对较老的模型，提示去读记忆文件并显式检验假设，几乎能让基准分翻倍；Sonnet 5 已经会自己这么做，十次里有九次先读记忆再回答。

  5. dreaming 的两个作用是纠错和建立表示。纠错方面，Pokémon 的 Mt. Moon 案例很直观：Claude 错误地记下 PokéCenter 在东侧，于是走出门就宣布「山洞已完成」，接着掉下单向台阶；dreaming 让它对照会话记录发现矛盾、改写笔记，之后才顺利到达 Cerulean City。建立表示方面，他们用维基页面把知识连成图：在 Stainless 约 35 万个文件、4.2 亿 token 的内部语料上，dreaming 从 2 个会话扩展到 128 个，25 个问题的达标率从 13% 升到 48%；搜索加维基的组合比单用搜索高 8 个百分点，每题还省约 2 万 token。但维基不是万能：当答案能从单份文档直接检索时它没有增益，有时还会膨胀到比原文语料更大，像博尔赫斯笔下与帝国等大的地图。

最后是记忆层级。dreaming 可以把重要笔记上浮，由 harness 在每次会话开始时预加载，省去模型自己搜索；但注入会占 token，错误笔记会被带进每个会话，而且指令文件越长遵循度越低，所以顶层必须保持很小——Claude Code 的 auto memory 只加载 MEMORY.md 的前 200 行或 25KB，把它当索引。文章结尾列出的开放问题同样实在：记忆在当下写会分散注意力，放到后台又可能来不及用；记忆会漂移，全量校验不现实，只能按易变程度和访问频率安排 dreaming 的节奏。

我的推荐：任何在做 agent 产品的人都该读。最可直接借用的是三条：只记屏幕/上下文里读不到的东西，给模型判断显著性的自由而不是硬编码规则，以及把顶层注入控制在很小的索引并保留指向原文的链接。

今日判断

今日判断：Agent 工程的重心正从「能不能完成任务」转向「产出能不能被信任」——LinkedIn 用多智能体把代码审查做成可评估的生产系统，LSCBench 则用数据指出功能测试全绿时仍有约四分之三的代码带漏洞；Anthropic 的记忆研究同样在解决「跨会话的经验如何可信」。值得留意的是两条共同解法：独立多代理交叉验证，以及把评估做成每日闭环。
