Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic

为什么值得看：Agent 把代码产出推高一个数量级后，瓶颈从「写代码」转移到「验证代码」；这篇给出可复用的架构演进路径（单写者 → 按包分片 → 无状态 worker + journal + 独立 roll-up），以及三条硬建议（按两个季度 25x 规划、把服务指标接给 agent、状态一开始就拿出进程）。

展开完整精读

一句话判断：agent 写代码不是瓶颈，验证才是——Anthropic 的 CI 任务量半年涨 25 倍，三次「加核数 / 加并行 / 定时重启」的权宜补丁分别只顶了 70 天、29 天和不到一天，最终只能把测试选择服务重做成无状态架构；对任何正在把 agent 放进研发流程的团队，这是一份提前 6 个月的故障预告。

1. 文章主张了什么

  • 量级：Anthropic 工程师人均每季度交付的代码是 2021–2025 年的 8 倍，其中 80% 由 Claude 撰写，Claude 还大量参与 PR 的评审与批准；测试总量增长 10 倍，工程师人数只增加了「名义上的一点」，结果是半年内 CI 任务量增长 25 倍（并非每个 PR 都跑全部测试，否则数字更大）。
  • 服务形态：他们自建了确定性的测试影响分析（test impact analysis / test selection）服务，由两个必须保持同步的组件组成——消费 CI 结果、维护每个测试历史的 listener，以及据此决定「这次改动该跑哪些测试」的 selector。
  • v0 的致命结构：为了让单个写者按序应用结果，整个服务是单进程，无法水平分片。listener 一旦落后，选择器就在用陈旧数据做决定：20 分钟延迟意味着数万条测试结果没被应用（后果主要是多跑了一些本就 flaky/大面积失败的测试）。
  • 三次修补的时间线：2025-10 把服务核数加倍（顶了 70 天）→ 2026-02 按包分片、每个包一个写者（顶了 29 天）→ 2026-03 内存触顶、每日重启反而让服务持续落后（顶了不到一天）。
  • 终局架构：给服务加一个内存数据存储。任何 listener worker 都能处理任何结果，追加到 journal 后立即返回（无状态、可水平扩展）；一个独立的消费者进程每隔几秒把 journal 汇总成 per-test 历史；selector 查历史做决策。代价是运行成本更高，换来可扩展性和可预测的内存画像。
  • 三条建议：按「两个季度内 25x 负载」做设计；把服务插好仪表当成 agent 的「眼睛和耳朵」（尤其保证进来的 CI 任务数等于被处理的任务数，让 agent 能自我爬坡）；从一开始就把状态拿出进程，关键服务不要单实例跑。
  • 作者还指出 Agent 正在改变 PR 的形状：Claude 偏好更小、更细的 PR，活跃量的地板被抬高（夜间和周末也在推），但整体仍然是 bursty 的。

2. 我的解读

这篇文章真正的贡献不是「他们怎么扩容」，而是它把一条容易被忽略的因果链说清楚了：代码生成变便宜之后，主成本会迁移到验证侧。CI 门禁在 agent 时代会同时变得「更长、更贵、更不可信」，而绝大多数团队的 CI 架构是围绕「人每天推几次」设计的。

第二层是架构层面的：他们踩到的坑（单进程 + 单写者 + 内存状态）几乎是所有「先能用再说」的服务的标准形态，而最终解——append-only journal + 无状态 worker + 独立 roll-up 消费者 + 查询侧只读——就是事件溯源（event sourcing）这一套。它之所以在这里成立，是因为 CI 结果天然是事件流，而测试历史天然是可重建的物化视图。

第三层是组织层面的：作者让 Claude 长期盯自己的服务，Claude 反复主张大重构，人类反复选修补。这不是玩笑——当「写代码」不再稀缺，「什么时候该重做」的判断力就成了新的瓶颈资源，而这件事恰恰最容易被「先打着补丁再说」的惯性吃掉。

3. 对实际工程的意义

  • 把「每次改动跑全部测试」当成一个有上限的策略。文章明确指出：很多组织仍然全量跑测试，这能撑到某个点，之后 CI 门禁会越来越长、越贵、越不可信；而 agent 比人更需要「这次改动相关的、确定的测试集合」才能自我验证和迭代。
  • 测试选择服务的可演进路径是可以直接抄的：先按包/模块分片（每个分片一个写者保证有序），再把状态外移到数据存储、worker 无状态化，最后让选择器只读历史。每一步都对应一个可观测的瓶颈（延迟 → 内存 → 重启失效）。
  • 给 CI 加「进/出守恒」指标：进来的任务数 == 被处理的任务数，是唯一能让 agent 自己发现「服务在悄悄落后」的信号。没有这个指标，落后只会以「CI 变慢」的形式间接暴露。
  • 对规模更小的团队：25x 不一定是你的曲线，但可以拿走两个便宜动作——(1) 规划时按「两个季度内 10x」量级预留余量；(2) 重新审视 PR 粒度与 code review 的形式（当 agent 能保持 PR 小而绿时，评审的重点应该转向「决定是否值得做」和「风险分级」，而不是逐行读）。
  • 反模式提醒：把 listener 和 selector 塞进同一个进程、用内存维护全量历史，这个设计在任何指数增长面前都是定时炸弹；如果你正在做类似的评审/索引/遥测聚合服务，现在就把它拆开。

4. 可信度与局限

  • 一手工程博客（作者 Sachin Malhotra，Anthropic 工程师），时间线、倍数与「三个补丁分别顶了多久」都写得具体，并且自陈了判断失误（当初该重构而选择了修补）——这类自曝通常比成功学叙述可信。
  • 局限一：这是厂商博客，只呈现成功路径；没有绝对量级（CI 任务数/天的基线、成本数字），也没有测试选择准确性的量化指标（只说陈旧数据会导致多跑一些 flaky 测试，没有给出误选率）。
  • 局限二：「一年前要一个季度、现在 3 周」这类效率对比无法验证，且作者本身就处在「用 Claude 写代码」的环境中，存在自我强化叙述的动机。
  • 局限三：文章开头说「买更大机器、并行化、重启服务这些手法不是本文重点」，但这几条恰恰是大多数读者会先尝试的——文章没有给出量化阈值来帮助判断「何时该放弃修补」，这一点需要读者自己补。

5. 最值得记住的三点

  1. 25x/半年 + 70 天 / 29 天 / 不到一天：指数增长下，任何线性修补都在快速贬值；要么按 10–20x 设计，要么准备好反复重做。
  2. 终局是一个可复用的模式：无状态 worker + append-only journal + 独立 roll-up 消费者 + 只读查询侧；本质是把 CI 结果当事件流、把测试历史当物化视图。
  3. 配套动作同样重要：把服务指标变成 agent 的「眼睛和耳朵」（进/出任务数守恒），并承认「先修补还是先重构」的判断力，是 agent 时代真正稀缺的东西。

我的推荐

如果你只读一篇：读这篇。它同时给出了「现象级证据」（25x、80% 代码由 Claude 写、CI 三连崩）和「可抄的架构演进路径」，读完可以立刻对照自己的系统做三件事——查 CI 是否有进/出守恒指标、查关键服务是否单实例带内存状态、查测试选择是否已经是按改动的子集。对做 agent 基础设施或平台工程的人，建议把它和今天队列里的 PostHog（agent PR 占比 20%→70%）、以及 Pragmatic Engineer 的 OpenAI 软件工厂连起来读：三篇合起来就是「当 agent 成为主要代码生产者，研发基础设施会发生什么」的完整侧写。

Inside OpenAI's agentic software factory

为什么值得看：Pragmatic Engineer 实地采访 7 位 OpenAI 工程负责人，把「agent 原生的研发组织」落成具体管线：Codex 接管全公司（非工程部门 90% 周活）、风险分级的 agentic 评审、per-change 部署 agent、以及会自己建监控面板的部署代理；付费墙只放出前 3 节，但这 3 节已足以改变对 IDE / PR / 代码审查的判断。

展开完整精读

一句话判断：这是目前最具体的一份「agent 原生研发组织」侧写——OpenAI 内部已经不存在「用不用 agent」的讨论，讨论的是 IDE 之死、PR/评审的失效，以及把 10x 负载压到基础设施上的后果；前 3 节公开的部分信息密度已经极高，值得整篇读完再回看自己团队的流程。

1. 文章主张了什么

  • Codex 接管了一切：从今年 1 月起，Codex（以及后来的 ChatGPT Work）成为 OpenAI 内部几乎所有工作的入口。四个月内，财务、招聘、法务等非工程部门的使用率从约 0% 升到 90%，而且没有自上而下的强制推广。作者特别指出，Codex 的桌面版在 2–4 月对非工程用户还相当难用（界面上会直接显示代码），但这些人依然留下了——因为「能把一件复杂的事长时程做完」这个需求太强。
  • 推动采用的两个因素：一是 harness 对长时程任务的处理变好（可以设 /goal 让模型一直干下去，有人开一个会话跑好几天），二是「awareness overhang」——能力早已在那，只是很多同事还不知道能这么用；角色化插件（skills/plugins）让不同职能把自己的工作流固化下来，是扩散的关键机制。
  • IDE 与 PR 的退场：自 1 月起 IDE 使用率下降；PR 数量按「曲棍球棒」曲线增长，构建-测试-部署管线的负载在半年内涨约 10x（作者原话：多数公司这种增长要 2–3 年）。OpenAI 的 VP of Engineering 明确说「我们今天的 code review 方式越来越说不通，PR 也一样」，他们正在用多「领域专家」agent 并行评审 + 变更风险分级（低风险区域可被 agent 自动批准）来替代逐行人工评审。
  • 软件工厂管线（9 步）：人定义目标与验收 → agent 聚合上下文（文档已全部放进代码库，另有 Git/GitHub、Slack、Notion、Databricks/Datadog 与内部 skills）→ agent 改代码并自验 → 构建、跑测试、修到绿、开 PR 并 babysit CI（新增 perf harness，把有问题的 PR 送去合成 A/B 评估性能）→ agentic 评审（按领域配置多个评审 agent，并按风险决定是否必须人工介入）→ 人工批准后由 agent 陪跑到生产（读代码定位 feature flag、判断成败信号、自己搭建监控面板）→ 生产观测 → Perf Factory 用 agent 去重告警、定位性能回归并提修复 → Sevbot 处理事故（收集上下文、给缓解建议但默认不执行）。
  • 新的瓶颈：PR 暴涨后，后端/Web 尚可通过扩容吸收，原生移动端发布成了硬瓶颈——App Store 和 Google Play 的人工审核要几小时到几天。作者引用了 2010 年代 Facebook 做到周级发布的往事，认为 agent 时代会逼出下一轮「移动发布革命」。
  • 工作形态：专业化分工在消失；判断力、品味与能动性更重要；工程师更像产品经理；一些以往「不可能」的重写和迁移现在一两个工程师就能做成。

2. 我的解读

这篇文章最有价值的地方，是它把「agent 原生组织」从口号变成了可对照的结构：不是「大家用 Copilot 提效 20%」，而是「上下文集中到 agent 能读的地方 → 生成 → 自动验证 → 风险分级评审 → 自动陪跑到生产」。这条链上每一步都有明确的工程含义：

  1. 上下文是新的基础设施：文档搬进代码库、Slack/Notion/数据仓库全部接入，本质是让 agent 的上下文窗口里能有「正确的局部真相」。对多数团队，这是比换模型更高杠杆的投入。
  2. 评审的形态变了，但没消失：多领域评审 agent + 风险分级，是把「人审不过来」变成「人只审该审的」。值得注意的是，作者对「给 agent 一个领域人设就能审得更专业」这种说法保持怀疑，并给出了合理解释：真正的差别在于这些 agent 能访问的上下文和它们只专注自己领域带来的注意力集中。
  3. 负载压力是结果，不是意外：10x 管线负载 + 25x（Anthropic）是同一个现象在两个组织的不同量级表达；这也解释了为什么今天同时出现了好几篇「agent 时代的基础设施」文章。
  4. 人的位置：文章反复出现的词是「判断、品味、能动性」，而不是「写代码速度」；Sevbot 的边界（能建议、默认不执行）也说明自主性是被有意约束地一步步放开的。

3. 对实际工程的意义

  • 如果你的团队刚上 agent：先做「上下文工程」——把设计文档、决策记录、接口约定放进代码库或可被 agent 检索的位置，比调 prompt 更值钱。OpenAI 的做法是新人入职就被建议「有问题直接问 Codex」。
  • 评审与 PR 策略可以开始改：给不同风险等级的变更设计不同的路径（低风险可自动批准、高风险多轮 agent 评审 + 人工把关），并让 agent babysit 到 CI 全绿再交给人。这一步能立刻吃掉一部分「等待」成本。
  • 为负载做准备：照 Anthropic 的数字，测试与 CI 是第一个被打满的部件；对照自己团队的 CI 队列深度、时长与 flakiness 做一次体检。
  • 留意「陪跑到生产」这个模式：给每个上线的变更配一个 agent 去观察指标、自建面板，是把 SRE 的部分工作前置成「每个变更自带的责任人」，对中小团队来说这是可复制度最高的一条经验。
  • 移动端团队：如果你们是原生 App，这条瓶颈迟早出现；提前把「可远程开关的功能」与「必须过审的改动」分开设计，是唯一能对冲审核延迟的手段。

4. 可信度与局限

  • 来源是一手采访（7 位 OpenAI 工程负责人，含 VP of Engineering / Applied Infra），由 Pragmatic Engineer 的 Gergely Orosz 撰写；他对「多领域 agent 评审」这类说法还专门加了怀疑性的旁注，整体是一份有质询意识的报道，可信度较高。
  • 重大局限：这是付费文章，公开部分只到第 4 节开头（即第 1–3 节完整，第 4–7 节「工具与流程变化 / 十亿用户的基础设施 / API 可靠性 / 职业变化」全部被付费墙挡住）。本文的分析与判断都基于公开的 1–3 节。
  • 数据均为 OpenAI 自述（使用率、倍数、时间点），无第三方核对；「非工程部门 90% 周活」这类数字的口径也没有给出。文中的乐观叙述（Codex 接管一切、IDE 将死）有其立场，且 OpenAI 是 Codex 的商业方。
  • 一个值得警惕的点：文中提到 OpenAI 内部对 Codex 的依赖已经到了「一次小故障时同事的抱怨比自动告警还早」，这与「单一 harness 集中风险」是同一枚硬币的两面。

5. 最值得记住的三点

  1. 长时程任务是采用曲线的引爆点：从「帮我写个函数」到「设一个目标跑几天」，agent 的用法从工具变成了协作者；随之而来的是更少的并行、更多的委托。
  2. 评审与部署是两个正在被重写的环节：多领域评审 agent + 风险分级替代逐行人工评审；per-change 部署 agent 自己搭监控面板、自己盯指标。
  3. 瓶颈的数字很具体：管线负载半年 ~10x、PR 数量曲棍球棒式增长、原生移动端发布被审核拖住——这些是你未来一年会遇到的形状。

我的推荐

公开的三节值得完整读，重点看第 3 节「软件工厂」的九步管线图，那是全文最可操作的部分。读的时候顺手做一个练习：把九步里的每一步映射到你自己团队的现状，标出「已经有」「没有但能加」「结构上做不到」三档——这些空档就是接下来的路线图。第 4–7 节在付费墙内，如果你对「十亿用户的基础设施扩容」感兴趣，可以考虑订阅；但仅凭公开部分，这篇文章也已经把「agent 时代的研发组织长什么样」讲得比大多数演讲更清楚。

Bad benchmarks and evals: Senior SWE-Bench, napkin math, and winter tires

为什么值得看：把「基准分数不可信」从直觉变成可复现的检查清单：任务代表性（113 个任务里只有 4 个用得上）、单次运行方差、LLM 评委方差（同一份结果重跑 10 次有 23% 翻转）、阈值效应（LOC 超参考解 2x 即判不合格，语义等价的解法被误杀）。读完可以直接拿这套标准去审任何模型对比结论。

展开完整精读

一句话判断：这是一篇「如何正确地不信任基准分数」的示范——作者用三个例子（napkin math 性能表、DeepSWE/Senior SWE-Bench、冬季轮胎）证明：不引入任何领域知识，只靠通用的实验设计常识，就能看出这些广为流传的数字是错的或不可用的；其中 LLM 评委的重跑翻转率（23%）和 LOC 硬阈值误杀两个发现，对今天正在做模型选型的人最有用。

1. 文章主张了什么

  • napkin math 表（第 29 节）：那个 5.4k star 的性能估算表里，随机内存访问延迟写 20ns（真实 DRAM 访问约 100ns）是因为测量代码没有在连续读之间建立数据依赖，CPU 把多次 load 并行化了；随机 SSD 读的基准代码给偏移量 +1，导致每次读都不对齐、跨页、还可能读到页缓存甚至越界；顺序读的基准测的是「一次未缓存读 + N 次已缓存读」的混合，没人知道 N 是多少。结论不是「这些数字差一点」，而是「它们测的根本不是表上写的那个东西」。
  • DeepSWE / Senior SWE-Bench（第 30 节）：先看表面结论——DeepSWE 显示 GPT-5.5 显著强于 Opus 4.8，Senior SWE-Bench 显示 Opus 4.8 强于 GPT-5.6，两者互相矛盾且都与实际体感不符。再拆方法：DeepSWE 的 113 个任务（每个跑 4 次）里，作者逐个核对任务名与语言分布，发现与他实际使用 agent 的场景几乎不重合；差异最大的任务中只有 4 个是 Rust（他常用的语言），其余要么是不用的语言，要么是他只用 agent 处理琐碎问题的语言。
  • 评分函数的硬伤：Senior SWE-Bench 要求解法「有品味」才计分，其中一个条件是行数不超过参考解的 2 倍。结果是：一个把管道操作展开成多行的解法（作者认为语义与参考解等价）被判不合格；另一个任务的参考解只有 1 行（增删各计 1 行 = 2 行），导致「有品味」的上限只有 3 行。作者指出，对连续分数加硬阈值会让噪声指标丢失更多信息，正确的做法是用连续聚合函数（他顺带给了几个候选形式）。
  • 评委方差（最实用的部分）：作者让 coding agent 用同一个评委模型（Sonnet 4.6）把每个条件重跑 10 次：官方结论有 23% 的概率翻转（子项里「相对品味」32%、「实践对齐」5%、「任务 rubric」3%）；换成 GPT-5.6 Sol 当评委，被判「有品味」的解法数量减少一半以上。作者强调这不是 run-to-run 方差，而是纯粹的「LLM 评分方差」——即公开发布的数字大约有 20% 的概率是错的。
  • 轮胎（第 31 节）：「冬季必须换冬季胎」是个没有公开测量支撑的流行说法；现有的实测显示在 0°C 以上的干/湿路面，全季节胎反而优于大多数人在用的北欧型冬胎，夏季胎在干燥路面直到 0°C 都最好。作者用它类比：和 coding agent 的公开基准一样，流行结论常常没有人真的测过。
  • 元层面：作者说他认识的、判断力可靠的人，基本已经不看 LLM 基准的汇总分数了——因为「看起来像你的任务」的基准也可能给出与实际相反的结果；他讽刺的是「汇总分数」这个形式本身的误导性。

2. 我的解读

这篇文章的锋利之处在于它不需要你相信作者：每一个批评都可以自己复现（读基准代码、重跑评分、看任务列表）。这对工程决策的直接含义是，模型选型的证据链需要三层：

  1. 任务重合度：这个基准里的任务，和我实际让 agent 做的事有多像？（作者的做法是逐条看任务名 + 语言，非常朴素但有效。）
  2. 方差：单次运行、单次评分的结果能不能代表期望值？（重跑 10 次这个实验成本极低，却几乎没人做。）
  3. 评分函数：连续信号有没有被硬阈值切碎？「2x 行数即失败」这种规则会让评分变成抽奖。

还有一层更隐蔽的启示：文章里作者说自己不熟悉 Elixir、也不熟悉那个代码库，仅凭「语义相等 + 格式不同」就判断评分荒谬。这说明评估者不需要是领域专家，也能识别实验设计层面的错误——这一点对跨领域的技术管理特别有用。

3. 对实际工程的意义

  • 模型选型的正确做法：用你自己的任务集（哪怕只有 20–50 个）做 A/B，记录方差，不要引用公开汇总分数做决策；如果必须引用，先看该基准的任务分布是否覆盖你的语言与场景。
  • 自建评测的检查清单：避免连续分数 + 硬阈值；LLM 评委要报告多次重跑的翻转率；对同族模型要注意「评委与被评模型同源」带来的相关性偏差（今天的队列里另有一篇 Amazon Science 的文章正好在讲「评委一致时是否该信」和依赖建模）。
  • 对「agent 能不能替代 X」的结论保持怀疑：文章列举的基准矛盾（两个基准给出相反排序）说明，用单个数字对齐「能力」在方法论上就是行不通的；工程上应当退回到「在什么任务族上，谁更可靠、更便宜」这种条件化的结论。
  • 可复用的小实验：把你正在依赖的某个评分（CI 通过率、code review agent 的判定、质检 LLM 的判断）重跑 10 次，统计翻转率——这可能是你这周能做的、性价比最高的可靠性实验。

4. 可信度与局限

  • 作者 danluu 在性能与实验设计领域长期写作，文中的技术批评（数据依赖、页对齐、缓存效应）都能验证；他还把结论交给了领域专家复核（Postgres 磁盘性能的 Peter Geoghegan、Anthropic 前评测团队成员 Aaron Levin），并明确说明「请专家看不是为了让你因为专家同意而同意，而是说明不需要专业知识也能得出同一结论」。
  • 局限一：文章是「练习系列」的一篇，部分事实借 LLM 生成（例如任务数量、CPU 年份），作者自己标注了「未经核实」；细节上可能有小错。
  • 局限二：对 Senior SWE-Bench 的批评以「品味评分的一个案例 + 评委方差」为主，没有做全量审计；对 DeepSWE 的批评主要是任务分布，这两点足以证伪「可直接引用的汇总结论」，但不等于这些基准毫无价值。
  • 局限三：行文带强烈的个人立场（对基准文化的不屑），轮胎一节是兴趣驱动的类比，读者需要自行剥离修辞去取方法。
  • 另外，这篇文章本身是 Patreon 系列的公开部分（作者说明此类小节通常发在 Patreon），内容完整度对得起「练习」的定位。

5. 最值得记住的三点

  1. 先问任务重合度，再问分数：一个基准的汇总分数，只有在任务分布与你的实际用法重合时才有信息量；113 个任务里只有 4 个对口的例子说明差得可以有多远。
  2. 方差是必须报告的量：单次运行 + 单次 LLM 评分 ≈ 掷硬币的精度（重跑翻转率 23%）；任何模型对比结论，先看有没有方差估计。
  3. 不要用硬阈值切连续分数：「2x 参考行数即失败」让语义等价的解法被判不及格；阈值把噪声放大成错误的确定性。

对经常需要读/转发模型对比结论的人，这篇是必读的「免疫接种」；读第 30 节（DeepSWE / Senior SWE-Bench）就够，若你关心性能估算或对「流行结论没人测过」这个话题感兴趣，再补第 29、31 节。读完建议做一件小事：把你自己正在依赖的某个分数（模型选型、CI 门禁、agent 评审通过率）做一次 10 次重跑，看看它有多稳。它与今天队列里的 PostHog（agent PR 占比的实测数据）、gpt-5.6-luna / gpt-6-astra 的代码评审对比可以配合读——前者是「有数据支撑的叙述」，后者正是本文告诫你要小心对待的那种对比。
