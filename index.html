少见的把线上推理系统逐层摊开讲的长文，工程细节密度很高 · ★★★★★ · TLDR AI

DeepSeek V4.1 Flash 大规模推理部署实践

为什么值得看：不是概念科普：PD 分离怎么配卡、KVCache 分几层放哪、负载均衡用什么代价模型、投机解码怎么变长验证，每一步都给线上数字和取舍理由，可以直接对照自己手上的推理服务。

展开完整精读

一句话判断：这是今年最值得存档的推理系统工程文之一，它把「大模型服务怎么在真实集群上跑得便宜」拆成了可复用的设计决策，而不是只报一个 benchmark 分数。

  1. 目标先立住，再谈技术。文章开头给三个硬约束：兼容多家芯片（英伟达与昇腾）、用常见硬件组织 Prefill 和 Decode（8 卡做 Prefill，64～128 卡超节点做 Decode）、KVCache 保留 72 小时以上。这三条基本决定了后面所有架构选择：PD 分离不是为了时髦，而是因为两个阶段的负载特征（算力密集 vs 访存密集）差得太远，混在一起配卡必然有一半资源在等。

  2. KVCache 是全文的主线，也是最可借鉴的部分。Block KVCache 以 128 token 为块分页管理，放在独立的 3FS 集群而不是本机内存，理由讲得很清楚：独立存储让任何 Prefill 机器都能命中任何前缀，避免「前缀亲和路由」和「负载均衡路由」互相打架；同时存储与计算解耦，计算节点故障不再带走缓存。3FS 给到约 100 PiB SSD、峰值读 10 TiB/s、写 850 GiB/s，按 112 KiB 的块粒度做随机读写优化，纠删码 10+2。agent 流量 TTL 3 天、chatbot 7 天，作者还给了经验值：TTL 砍到 3 天左右，chatbot 命中率会掉 0.5%～1%。

  3. SWA KVCache 的处理是全文最有信息量的取舍。V4 时代把 SWA 也落盘做精确重算，结果分钟级生命期的数据占掉近一半持久缓存容量，不划算；V4.1 改成不落盘、只留内存（TTL 约 180 秒、命中率 98%+），缺失时用 Bounded Replay 只重算最近 128 个 token 并把注意力窗口截断在重算段内，重算代价变成与上下文长度、层数无关的常数。这一改让 Decoder 侧每次 prefill 的计算量近乎减半——这是「想清楚数据的生命期」比「堆更多 SSD」更值钱的典型例子。

  4. 负载均衡与调度给了可抄的量化模型。Prefill 按输入长度分四档，用拟合的二次代价模型 cost(q, c) 反解每步能塞多少 token；Decode 同时均衡请求数和 KVCache 总长两个维度；专家并行靠冗余专家 + 周期性重排，线上最慢 rank 与均值之比做到 1.032（EP2/DP2）和 1.090（EP64）。调度层把 schedule(N+1) 与 forward(N) 在 CPU/GPU 上重叠，GPU 全程无空闲。这些数字和做法，对自建 vLLM/SGLang 集群的人几乎是现成 checklist。

  5. 值得留意的边界。KVCache 管理与负载均衡组件因与内部基础设施耦合深，这次没有完整开源；DeepInfer 开的是框架与算子，deepseek-recipe 开的是 API 协议到 token 序列的编解码（Rust 实现，含 special token 注入防护与分段并行编码）。也就是说，文章里的系统能力不能直接 clone 出来，但设计意图和取舍逻辑完全可迁移。

我的推荐：如果你在做推理服务、算过单位 token 成本、或者被长上下文与 agent 流量的缓存命中率折磨过，这篇要逐节读，尤其是 KVCache 分层与 SWA Bounded Replay 两段；如果只是调 API，读第 2、3 节理解「为什么长上下文便宜/贵」也够。

把 agent 记忆做成工程系统的完整案例，含真实企业基准与消融 · ★★★★★ · TLDR AI

MemCurrent: Designing Persistent Memory for Production Agents

为什么值得看：少见地同时给出质量、token 和时延三组数字，并用消融说明「哪种记忆真正起作用」；对正在给 agent 加长期记忆的团队，可以直接照抄它的分层与读写时机。

展开完整精读

一句话判断：这篇的价值不在「记忆很重要」，而在于它把记忆拆成可测量的工程组件，用消融告诉你每一层各值多少分，并给出了生产环境里真正跑得动的读写时机。

  1. 问题定义得准。作者先指出记忆的核心矛盾不是「存得多」，而是「存什么、怎么维护、怎么衡量有用」：把所有历史塞进上下文又贵又容易引入过期、冲突、无关的信息。这一点比很多记忆框架讲得清楚——记忆系统的对手不是「没有记忆」，而是「全上下文」这个昂贵上限。

  2. 架构是两层加三种访问方式。episodic memory 以插件形式在会话过程中自动追加，记录原始轨迹；derived memory 是可变的知识文件，由 agent 工具（add/update/delete）响应显式指令，加上一个离线「dreaming」流水线从新会话里蒸馏隐含经验，并负责拆分超大文件、合并重复、解决冲突。读取侧在会话开始时注入 memory.md 索引，会话中提供 search_memory 与 fetch_memory 两个工具，分别做模糊检索和按 id 取全文。这套「索引常驻、正文按需」的分层，和人类查文档的习惯一致，也解释了为什么它比纯向量检索省 token。

  3. 评测做得比多数厂商博客扎实。开源基准（LoCoMo、LongMemEval、ConvoMem）之外，他们从 12000+ 条真实 Genie 会话里挖出 3000 条候选，再经对抗式评审按 7 项标准筛到 114 个测试用例、29 个用户、2233 条历史会话。关键在于「记忆要喂给动作，而不只是回答问题」：用例要求 agent 在 100 多条历史里找到那次纠正并应用到新的多步任务上。这比合成对话里的「回忆某个事实」难得多，也更能暴露真实差距。

  4. 数字和消融是最有说服力的部分。内部基准上 MemCurrent 通过率 68.4%（无记忆 22.3%、金标注入 78.6%），时延 252 秒、token 41.8 万，均为最低；Mem0 在同基准上只有 43.9% 且更慢更贵——同一个 Mem0 在开源基准上却在前沿，说明基准选错会得出完全相反的结论。消融进一步指出：derived 记忆贡献主要增益（66.1%），episodic 只加 2.3 个点，但能找回蒸馏丢掉的细节；抽取策略上离线 dreaming（63.5%）比纯在线工具（53.9%）高近 10 个点，两者合用最优。

  5. 两个真实例子比数字更直观。一个是 agent 写了正确 SQL 却没读执行结果、凭空编了表格，用户纠正一次后把教训写进记忆，下次先读结果；另一个是「SDP 客户 top5」这类问题从 11 次工具调用、8 个子代理、近 6 分钟，压缩到 2 次调用、1 个子代理、41 秒——因为工作流被存成了可复用的记忆文件。后者其实是把「探索成本」变成「资产」，这也是 agent 记忆最容易被低估的收益。

我的推荐：如果你在做企业内部 agent，先读第 2 节（架构）和第 4 节（消融），再回头看它的基准构建方法——那套「从真实会话挖用例 + 对抗评审」的流程，比任何记忆库选型都更值得抄。

原生 PyTorch 上 TPU 的完整技术交代，含架构、精度与六个案例 · ★★★★★ · TLDR AI

Introducing TorchTPU

为什么值得看：把「换一个加速器」从口号落到工程细节：eager 怎么实现、编译缓存怎么分层、精度模式代价多少、分布式怎么映射到 ICI/DCN，还给了 HuggingFace 覆盖率和第三方推理成本数据。

展开完整精读

一句话判断：如果 2025 年的 PyTorch/XLA 还像「把 PyTorch 硬塞进 JAX 的做事方式」，这篇就是在宣布另一条路线——把 TPU 当成 PyTorch 的一等后端来做，并且给出了足以判断成熟度的证据。

  1. 设计原则先摆明，和旧方案划清界限。运行时不含 JAX 依赖、eager 模式必须好用、torch.compile 走 Dynamo 而不是 Lazy Tensor、在 PyTorch 最底层（Process Group API）提供 TPU 集合通信、把 .to("cuda") 换成 .to("tpu") 就能跑。作者也直说旧 PyTorch/XLA 的三个硬伤：要改源码划编译区、编译时延严重、没有原生 eager。这些不是营销话术，后面每一节都在兑现。

  2. 实现路径值得细读。TorchTPU 通过 PrivateUse1 扩展 dispatcher，用 c10::StorageImpl 定义设备侧存储；eager 有三种模态——Strict（逐算子异步，等价 GPU eager）、Debug（同步 + 边界检查）、DeferAndFuse（把连续算子延迟并融合，官方称比 Strict 快 50%+，还降低 HBM 峰值）。DeferAndFuse 的关键是「物化点」：遇到 .to("cpu")、.item() 才把累积的计算图编译执行，中间用存活分析挑出必须物化的算子，副作用算子（集合通信）永远保留；再加一个 Repeated Ops 启发式，在重复的 transformer 块上提前触发物化。编译缓存分三层（进程内、同机共享内存、远端文件系统），缓存键把计算图结构、张量尺寸、编译选项与组件版本压成三个 64 位整数，避免把巨大的 StableHLO 当键。

  3. 精度的处理是很多人会踩的坑。TPU 的 MXU 原生做 BF16 乘加、FP32 累加，所以 TorchTPU 默认 medium 精度；high 用 3 趟分解、highest 用 6 趟，分别约 3 倍和 6 倍算力开销，选高精度会直接触发性能告警。这和 CUDA 上「默认 FP32、TF32 是加速选项」正好相反——从 GPU 迁过来的模型如果默认精度敏感，很可能在不知情的情况下变慢或变准。

  4. 案例部分含金量最高。HuggingFace 语料 4917 个模型、500+ 架构族，Tier 1 冒烟通过 98%、Tier 2 数值对齐 97%，bounded dynamism 在 839 个因果 LLM 上 834 个数值正确；纯 PyTorch 写的 Muse Glimmer 30B 在单张 TPUv7 上 prefill 25.7k TPS / 59% MFU；Qwen3 MoE 235B 在 8192 卡上 MFU 27% 左右、弱扩展几乎线性，靠的是把 all-reduce 与相邻层计算重叠；vLLM 侧的三个优化（MoE 层作为单个 SPMD 程序、sequence-on-lane 的 FP8 KV 布局把 KV 显存减半、Gated DeltaNet 的融合 kernel）都给了具体瓶颈数字，例如原来 reduce-scatter 每层 1190 微秒、占设备时间 22%。

  5. 该保留的怀疑。文章自己承认 RL colocation 因「一个 TPU 只能被一个用户态进程访问」暂不支持，FlexAttention 还没覆盖，FP8/FP4 与嵌套编译区仍在路线图上；多数漂亮数字来自 Google 自家调优过的栈（Pallas kernel、TorchTitan、vLLM-TorchTPU），纯 PyTorch 开箱的 MFU 在 30%～38% 区间，离峰值仍有距离。换句话说：迁移门槛确实降到了「改一行 device」，但要拿到成本优势，还是得做设备特定的调优。

我的推荐：想判断「要不要认真评估 TPU」的人，读第 1、2 节和案例 1、4 就够做决策；准备真迁移的，重点看精度模式表和 DeferAndFuse 的物化点逻辑——这两处最容易在上线后变成事故或性能悬崖。
