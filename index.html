Throwing Headcount at the Problem

为什么值得看：少见的把多智能体放在真实性能优化任务上做受控对比，并用协调结构解释加速比差异。

展开完整精读

一句话判断
这是一份把「多智能体」从口号拉回测量的实验报告：同样的模型、同样的两小时、同样的 8 vCPU，蜂群能不能赢，取决于任务能不能拆开、以及模型会不会把信息放到所有人都看得到的地方。

  1. 实验怎么做的
    Replit 造了一个基准 Optimization-Bench，覆盖 14 个活跃维护的开源库，每库挑若干工作负载：NumPy 13 个、SQLite 12 个、SQLGlot 4 个、Git 7 个。每个代理分到 8 vCPU、16 GiB 内存、两小时窗口，规则禁止跨调用缓存、针对输入特判、预先算结果、把活外包给别的库、改运行时全局设置。评测把截止时刻的最终分支冻结，拷进代理进不去的独立机器，原始版本与候选版本按随机顺序交替计时，计时器和正确性检查都跑在被测进程之外。这一整套是在防奖励作弊：文章引用了 METR 抓到模型改写计时器、以及 Sakana 的 CUDA 加速比其实来自评测沙箱漏洞两件事。

  2. 数字
    NumPy 上单个 Opus 5.5 代理把工作负载跑快 3.66 倍，32 个代理的蜂群做到 18.92 倍。SQLite 和 SQLGlot 上单人几乎找不到收益，蜂群仍能拿到正收益。Git 是反例：7 个工作负载全落在同一批 15 个文件里，改动互相冲撞，蜂群打不过单人。OpenAI 的模型没有这个规律——GPT-6.2 Astra 的单人成绩在四个任务上都排第一，在 NumPy 上比 Opus 单人快三倍以上，但它的蜂群在 8 个代理时见顶，加到 32 个反而在三个任务上低于单人。

  3. 差异从哪来
    文章把原因归到协调结构，而不是模型强弱。Opus 5.5 的蜂群把 82% 的消息发在共享看板上：每个工作负载一个线程，worker 先公开声明「我改 btree.c」再动手，发现也贴回线程。GPT-6 Astra 和 GPT-6.1 Sol 反过来，每个 worker 平均给协调者发 22 条和 20 条私信，Opus 只有 1.4 条。信息留在私信里，别人看不到，还会随着时间过期。团队从 16 加到 32 时，Sol 的协调者在 SQLGlot 上的收件量从 356 涨到 631，Astra 在 NumPy 上从 346 涨到 615，分数几乎不动：协调者成了瓶颈。

  4. 一个具体优化
    NumPy 的 searchsorted 原来把所有键放在一起做二分，先对所有键比较第一次，再比较第二次；键一多，数据超出 CPU 缓存，每一步都要回内存取。蜂群改成一次处理 256 个键，整批在缓存里走完，并在两个数组都不含 NaN 时跳过更慢的 NaN 安全比较。float64、大量键的输入上快了 8.7 到 13.1 倍，输出完全一致，改动已提 PR。

  5. 边界
    这是厂商自己的基准，任务形状——性能优化、客观可测、反馈很快——恰好是最适合并行搜索的那一类。换到需求模糊、耦合紧密的代码库，结论未必成立。作者也承认蜂群的拓扑是模型自己长出来的，没有给出人为诱导的具体方法。

我的推荐
如果你在搭多智能体工作流，这篇给出的是可执行判据：先看任务能不能切成互不重叠的所有权单元，再看协调者是不是变成了消息交换机。把状态放在共享看板、让 worker 认领而不是被派活、保持写入单线程，比换一个更强的模型更划算。

Distributed, high-performance blob storage on SQLite

为什么值得看：完整的存储选型与生产调优记录，分片收益、压缩比、延迟毛刺的根因都有实测数字。

展开完整精读

一句话判断
一个交易平台用 SQLite 拼出分布式 blob 存储，把「数据库选型」写成了完整的取舍记录：为什么不用 ScyllaDB、Postgres、SeaweedFS 和 S3，以及分片、压缩、TTL 清理各自踩了什么坑。

  1. 场景
    Kite 有约两千万用户，用户存的是多图布局、指标模板、矢量绘图这类不透明 JSON，从几 KB 到几 MB。读写都是每秒数千到数万次，并且随行情波动突发。旧的 SSDB 已经停止维护、只能单机跑，还被迫把 blob 限制在 1 MB。

  2. 为什么不选现成的
    ScyllaDB 对多 MB 大对象的吞吐偏低、覆盖写产生的 tombstone 要小心调；Postgres 的 BYTEA 在性能和磁盘效率上都不合适；YugabyteDB 功能太多、不是为大对象设计的；RocksDB 的原语对但架构不对；Ceph 运维负担太重；SeaweedFS 最接近，可是覆盖写先追加后压缩会让磁盘持续膨胀，blob ID 与用户键还要另一层映射；S3 和 MinIO 每次请求延迟高、写占一半流量时成本高、TTL 只能粗粒度。

  3. 分片带来的收益
    WAL 模式下 SQLite 只允许一个写者，而写占了大约一半流量，所以按 key 做多探针一致性哈希，把数据分散到多个库文件，每个分片一个写任务、攒批提交。64 个并发连接、64 KiB 负载、batch 50、数据目录放 tmpfs 的测试里：1 个分片 HSET 是 7,740 ops/s（p99 10.7 ms），16 个分片是 25,324 ops/s（p99 8.3 ms），写延迟中位数从 8.2 ms 降到 2.1 ms；纯读从 67,128 到 70,884，几乎不变，因为 WAL 本来就允许并发读。换算下来，25,324 次带着 64 KiB 负载的写，相当于每秒 1.66 GB 未压缩 JSON 过一遍 zstd。

  4. 生产里的三个坑
    删除不会让 SQLite 文件变小，释放的页留在 freelist 里，于是开了 auto_vacuum=INCREMENTAL，并在增量回收之后跑 wal_checkpoint(TRUNCATE) 才真正缩文件。TTL 清理原本自己开一条写连接、发一条大 DELETE，和主写者抢同一把写锁，p99 从 5 ms 冲到 30-50 ms；改成复用分片的写者、每批 1,000 行之后毛刺消失。异步写模式必须在内存里维护 pending map 和显式的 tombstone，否则 DEL 之后紧跟的 GET 会从 SQLite 读到旧值。

  5. 生产结果与限制
    现在是三节点、每节点 4 vCPU 与 8 GB 内存。交易时段 09:00 到 15:30，各节点全命令 p99 约 2 ms，p50 在 250 到 550 微秒之间；HSET 的 p99 约 2 ms，HGET 约 1.4 ms，HDEL 大多低于 1 ms。限制写得很直白：槽位分配是静态配置，没有在线迁移与自动故障转移，改分片数要停机跑 CLI。

我的推荐
这篇适合当成小团队自建存储的范文：需求先讲清楚（允许丢掉最近写入、要 Redis 协议、要按 key 过期），再逐个否掉候选，最后把每个生产毛刺的根因和修法都摊开。真正的知识点不在 SQLite，而在把一致性哈希、组提交、增量 vacuum 这些现成零件按自己的流量形状拼起来——先量出瓶颈在哪一层，再决定加哪块。

When Can You Ship on Offline Evals Alone?

为什么值得看：把「离线评测能否代替 A/B」写成可以计算的决策问题，并指出噪声会让强关系看起来像弱关系。

展开完整精读

一句话判断
Spotify 把「能不能只看离线评测就上线」写成了一个可计算的决策问题：可以，但要付出假设和持续验证的代价，而噪声会让强关系看起来像弱关系。

  1. 问题怎么形式化
    目标是只用离线评测的效应做上线决定，同时把「上线了但线上指标变差」的风险控制在给定水平。要做到这点，需要知道线上真实效应在给定离线效应下的条件分布——换成直白的话：对任意一个评测结果，能说出它实际上帮到或伤害用户的概率有多大。

  2. 噪声的代价
    这个分布要靠成对的历史实验来估：同一批改动既有离线效应也有线上效应。两个量都带测量误差，离线评测的误差来自抽样和 LLM 评审打分，线上效应本身也是估计值。论文的工作例子里，忽略噪声算出的 R² 只有 24%，真实值是 60%。也就是说，你会严重低估离线评测作为替代指标的价值，甚至误判它没用。

  3. 决策门怎么设
    在假设成立的前提下，阈值要随替代关系的强弱变化：离线效应足够正就上线，足够负就放弃，中间地带仍然走 A/B。关系越弱，需要离线证据越强才能拍板。文章强调，只要 R² 不等于 1，就一定会出现离线为正而线上为负的情况，所以「在临界值附近凭评测决定」拿不到想要的保证。

  4. 三个会失效的假设
    第一，样本必须同质。把不同类别的改动混在一起，会出现辛普森悖论式的假强相关：每一类内部都没关系，合并起来却显得关系很强。第二，LLM 评审的偏差如果依赖实验臂——比如评审偏爱自己家的模型——会同时污染效应估计和替代关系强度，甚至把符号翻过来；而切换底层模型恰恰是智能体开发中的常规操作。第三，上线之后你就失去了上线与放弃两个区间的真值，因为那些改动不再跑 A/B，关系有没有漂移根本观察不到。作者的建议是留一个随机审计池，把小比例的这类改动仍然送去做 A/B。

  5. 结论
    Spotify 自己的做法是大量用离线评测迭代，但始终与线上实验配对。理由很清楚：A/B 靠设计就能约束风险，离线评测的保证完全来自那些难以验证、还会随时间变化的假设。

我的推荐
做 LLM 产品的人几乎都会遇到「评测涨了要不要直接发」这个问题。这篇给的不是态度而是判据：历史实验够不够同质、评审偏差是否随实验臂变化、愿不愿意留审计池。三个问题里有一个答不上来，就老老实实跑 A/B。
