EP230: RAG vs Agentic RAG

为什么值得看：把两种检索架构的差别收敛成一句话：RAG 的检索流程在提问前就定死，Agentic RAG 让 agent 每轮判断证据够不够再决定下一步。文末读者关于「循环何时停」的讨论，比正文更像生产经验。

展开完整精读

一句话判断：这一期是 ByteByteGo 的系统设计周报 EP230，四段短文里真正值得停下来读的是 RAG 与 Agentic RAG 的对比——它把「检索一次」和「边查边判断够不够」两种架构的骨架讲清楚了，但没有给成本、延迟和失败模式，读它是为了统一团队的说法，不是为了拿结论去做选型。

  1. 传统 RAG 的流程是固定的：用户提问，检索系统从知识库里取相关内容，应用把这段内容拼进 prompt，LLM 基于它生成答案。文章强调质量取决于取回上下文的准确度——检索错了，模型只会在错误的材料上把话说得更顺。这条流程的隐含前提是：一次检索就能覆盖问题所需的信息。

  2. Agentic RAG 把这个前提拆掉了。agent 先按任务挑工具，工具可以是文档搜索、API、数据库或网页；取回证据后判断是否足够回答问题，不够就调整搜索词或换一个工具再来一轮；直到证据够了，才让 LLM 基于这些上下文生成答案。差别不在模型，而在控制流从「一条直线」变成了「带判断的循环」。

  3. 但整篇没有量化对比：没有首字延迟、没有每轮 token 开销、没有准确率，也没有说哪类问题该用哪种。这是周报体裁的边界——它给的是词汇表和心智模型。真要选型，还是得在自己的语料上跑一组基准，把「单次检索错过关键文档」和「多轮循环多花两倍 token」这两类错误各自量化。

  4. 同期的另外两段是基础复习，价值在于把常见误解讲清楚。OAuth 2.0 管授权：Slack 要读你的 Google 日历，会把你送到 Google 的授权服务器，你登录并授权后拿到 authorization code，Slack 用它换 access_token，全程看不到你的密码。OIDC 叠在 OAuth 之上管认证，除了 access_token 还会给一个签名过的 JWT 形式 id_token，回答的是「刚登录的人是谁」。Linux 目录结构那段把 /boot、/dev、/etc、/var、/home 的职责过了一遍，但有一处明显笔误：说 U 盘会挂在 bin 目录，实际应该是 /media 或 /mnt——照抄会踩坑。

  5. 文末读者的讨论补上了正文缺的那一环：循环什么时候停。他的做法是给每个查询设硬预算——最大轮数加 token 上限，证据不足时返回尽力而为的答案，并明确写出哪些没能验证，而不是一直追完整性。我认为这是把 agentic RAG 放进生产时最容易被跳过、也最容易在账单上暴露的设计点：当语料里根本没有答案时，更多轮检索不会凭空造出证据，只会把延迟和成本线性放大。

我的推荐：把它当成一次四分钟的架构对齐读物，重点看第 2 段和第 5 段。读完最好带着两个问题回到自己的系统：检索失败时你怎么知道失败了；agent 循环的轮数和 token 预算写在哪里、由谁改。如果这两个问题答不上来，说明现在的 RAG 只是碰巧能跑。

今日判断

今日判断：周末池子很薄，只有 ByteByteGo 一期周报，但它的选题恰好落在今年工程侧最实际的一道分界线上——检索一次就生成，还是让 agent 边查边判断够不够。文章只给骨架不给数字，真正的门槛在停止条件：没有轮数与 token 预算的 agentic RAG，很容易把延迟和成本花在不可能被检索出来的答案上。值得留意的方向是「证据充分性判断」怎么落地成可测的预算策略，而不是继续加工具。
