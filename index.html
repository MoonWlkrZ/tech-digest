01
已经可以直接用了——挑一个装上，比继续裸跑强得多 · ★★★★★ · TLDR InfoSec

Sandboxing AI Coding Agents: nono vs Docker Sandboxes vs Microsandbox vs OpenShell

为什么值得看：Kudelski 团队把四款沙箱挨个装上实测，文件系统、网络、凭据、资源限制逐项对比，连配置片段和踩到的坑都写出来了。如果你平时让 coding agent 直接在本机跑命令，这是现成的加固路线。

展开完整精读

一句话判断：这是今年目前为止最完整的一份 AI coding agent 沙箱横向评测，四款工具都真正装上跑过，结论也诚实——没有完美选项，但每一个都比不开沙箱强。

  1. 为什么必须沙箱。JetBrains 2026 年的开发者调查里，90% 的职业开发者每周至少用一次 AI coding agent，68% 每天用；Stack Overflow 同年的调查里只有 7% 的人信任 AI 的输出用于重要工作决策。用得多、信得少，这个落差本身就是风险。文章列了提示注入的输入面：源码注释、README、MCP 工具的名字描述和输出、agent skill、网页、日历邀请、共享文件，还能藏进不可见 Unicode、HTML 注释和空格缩进里。OpenAI 自己就出过事：一批跑安全基准的 agent 所在环境没和互联网隔开，agent 顺着一个能上网的 Artifactory 实例打穿出去，又利用 Hugging Face 数据集上传流程的两个漏洞拿到了答案。Trail of Bits 让 GPT 5.6-Cyber 试着逃 QEMU/KVM，三次都成功，换成 Firecracker 才逃不掉。

  2. 什么算好沙箱。作者按隔离原语、文件系统、网络、凭据、进程限制、运行中改策略与审计、coding agent 适配与易用性这七组标准逐项打分。核心取舍：微虚拟机攻击面最小但有启动开销，OS 级原语最快却要和宿主共享内核。网络只按域名过滤不够——github.com 既能正常干活，也能被用来 push 一个 gist 把密钥带出去；DNS 解析本身也是外泄通道，必须放在沙箱外处理。

  3. 凭据注入是分水岭。真密钥根本不进沙箱：沙箱里只放占位符，请求经过沙箱外的代理时再换成真值，而且必须绑定到「域名 + 端点」，否则 agent 被骗着把占位符发到攻击者站点，代理照样会把真密钥填进去。四款里只有 nono 和 OpenShell 做到了端点级作用域。nono 还支持反向拦截：首次 OAuth 登录拿到的 token 存在沙箱外，沙箱内只留占位符。

  4. 四款工具的实际差别。nono（4/5）最快、开源、凭据处理最好，但走 OS 级隔离；Docker Sandboxes（4.5/5）体验最完整、每个 agent 一个 microVM，但闭源、要 Docker 账号、文件系统策略属于付费治理功能；Microsandbox（4/5）是通用沙箱，资源限制最细，但按 HTTP 路径过滤这类能力缺失；OpenShell（4.5/5）是面向企业多团队的重量级方案，网络可以按二进制过滤、凭据注入点最多，但项目还早、装起来不顺。

  5. 四款都补不上的洞。没有一款能在已允许的目录里再禁掉单个文件，所以项目里的 .env 对 agent 永远可读——密钥不该放在项目目录。没有一款支持自定义 syscall 白名单，没有一款自带管理网页，也没有一款到 v1.0。GUI 应用基本没法沙箱化，反过来说 CLI agent 更容易关进笼子。

我的推荐：先确认内置沙箱是开着的。Claude Code、Copilot CLI 都带沙箱，虽然网络过滤通常只到域名、没有凭据注入，但比裸跑强。真要认真用，本地单人可以试 nono（装完即用、启动几乎没有开销），想要完整界面和 microVM 隔离就看 Docker Sandboxes。不管选哪款，把密钥从 .env 挪进 1Password、Bitwarden 这类 vault 再通过代理注入，这一步的收益比换工具更大。

头部实验室少见的训练基础设施公开细节，值得逐段读 · ★★★★★ · TLDR AI

RL infrastructure at Microsoft AI

为什么值得看：从异步 RL 循环怎么排、策略陈旧度怎么算，到 MXFP8 存储和逐位一致怎么做到，MAI 把工程决策和实测数字一起给了出来，是今年最实的一篇训练系统公开文档。

展开完整精读

一句话判断：头部实验室第一次把「从基座模型一路靠 RL 爬到前沿」所需的训练基础设施讲到了可复用的粒度，工程决策和实测数字都摆出来了。

  1. 路线的选择。MAI 明确不做蒸馏：蒸馏出来的模型起点就接近天花板，RL 只剩很短的收尾阶段，跑挂了重开就行，采样器和学习者之间的细小数值差异也没有时间累积。他们要走的是从基座能力一路上升，这意味着几千到上万个训练步、几周到几个月、几千张 GPU 的连绵长跑。在这条路线里，硬件故障是必然事件，数值不匹配会随每次更新叠加，最优数据配比和 GPU 分配还会随策略变强而漂移——这些不再是边角情况，而是主要设计约束。

  2. 异步循环怎么排。Rocket 用 GRPO：controller 从课程里取题，problem worker 下发一组 rollout，rollout worker 并发跑；agent 循环向采样器要模型响应，工具调用经 dispatcher 进沙箱执行环境、搜索服务或 MCP 服务器，结果回灌上下文直到结束。每个 rollout 单独打分，problem worker 汇总同组结果算优势，controller 把训练片段打包成 batch，learner 从 rollout store 取 token id 和采样时的 log prob 更新策略。学习者和采样器因此是解耦的。

  3. 策略陈旧度是主要矛盾。作者把陈旧度拆成两块：采样器落后学习者几个版本，以及 token 生成之后等到被训练之间的时间。控制手段很具体：权重分两段传输，选中的采样器引擎先从学习者拉打包好的参数块，再分发到各副本，当前配置一次约 15 秒，所以能每 4 步刷一次；优先跑完已有 rollout 再开新的，请求按 rollout 开始时间继承优先级；失败 rollout 直接丢弃，不为了等它拖住整组；给学习者超额配 GPU，让任务卡在推理而不是训练上。文章还给了一个反直觉结论：训练受推理吞吐限制时，单纯增加推理服务器会缩短每一步的耗时，反而让同一个 token 在「第几步被训练」这个分母上变得更陈旧。

  4. 数值一致性。MoE 专家权重占参数 95% 以上，用 MXFP8 存储让采样器的权重显存几乎减半，但矩阵乘要反量化成 BF16 再算，否则采样器和学习者的 log prob 差异会变大；学习者也照抄这套量化再反量化，保证两边一致。KV cache 同样分存储与计算精度，全局注意力层用 MXFP8、局部注意力和最后三层保留 BF16，换来大约 67% 更多的全局上下文 token 容量。他们的目标不是「差异小」，而是相同 checkpoint、相同输入下逐位一致；做到之后，同样训练步数下评测分数更高。

  5. 容错与弹性。恢复按最小范围做：学习者单独挂掉时，controller 和推理舰队继续跑，只重建学习者并从最近 checkpoint 恢复，实测约 5 分钟，一次运行里省下 7% 以上的 GPU 小时；组件内恢复比整个作业重排队省 0.42% 算力；运行中改推理容量、并发、准入、陈旧度上限这些配置，带来 9.88% 的训练算力改善。控制面放在纯 CPU 节点上，避免 GPU 侧故障带崩作业监管。

我的推荐：这篇的价值不在结论，而在把「长跑 RL 到底难在哪」拆成了一组可操作的工程问题——陈旧度可以算、可以拆项、可以针对每一项下手；数值一致性不是玄学，而是存储精度、计算精度、算子实现三层要对齐。做训练基础设施的人应该逐段读，做推理服务的人也能从权重传输和 KV cache 那两节拿到直接可用的思路。

一份诚实的第一人称记录：工具怎么换、钱花了多少、瓶颈在哪 · ★★★★☆ · TLDR AI

I used to orchestrate agents. Now I orchestrate orchestrators.

为什么值得看：作者用 4000 多次短任务的数据推翻了自己「模型在自家 harness 里更好」的判断，也把 40 个并行会话真正难的地方说清楚了：不是工具，是他自己脑子里的上下文。

展开完整精读

一句话判断：一份少见诚实的多代理工作流第一人称记录，作者既给出上千次运行的数据，也承认自己做的工具「很可能也不怎么样」。

  1. 演进路径。作者是重度终端用户，同时维护二十多个 CLI 工具。2025 年 8 月他一个 feature 开一个终端标签页，每 10–15 分钟轮一圈；2026 年 1 月把这套动作固化成命令，自动建 git worktree 并开新标签页。模型变强后他交给 agent 的范围越来越大、单个任务跑得越来越久，并行数就一路涨到三十个终端窗口——那时他自己就是编排器，靠人眼在窗格之间跳。三十个窗格长得一模一样，想知道某个在干什么只能打开读，这才是真正的瓶颈。

  2. 中间试过的工具。Codex 桌面应用给了他一次明显的效率提升，因为它能清楚显示什么在跑、什么跑完了；模型换代后他回到 Claude Code CLI；为了统一两边又用了 T3 Code，一个包住 Claude Code、Codex、OpenCode 的网页界面。T3 Code 在二十个以上并发会话时开始吃力——不是机器过载，而是太多数据库写入挤在单线程，打开长会话要几秒；后台任务还在跑的会话显示成空闲，看起来像在等他，这进一步增加了混乱。

  3. 推翻「原生 harness 更好」的直觉。他原本相信模型在自家工具里一定更顺手，因为训练时就是那套工具。于是拿 4000 多次短终端任务做了对照：只有 Claude Opus 4.8 在自己的工具下明显更省，少做 17% 的活、少用 19% 的 token；GPT-6 Astra 和 Sol 用自家工具反而多用 43–59% 的 token。真正决定成本的是每次请求带多少东西——一个只有单 shell 工具、12 行系统提示的极简 agent，比标准 agent 少用 58–76% 的 token。这让他放下心理包袱，把 agent 搬进自己控制客户端的聊天室，也让同一个线程里混用 Anthropic、OpenAI、Google 的模型成为可能。

  4. 一天级的任务与人的瓶颈。真正让 agent 能自主跑上一天的是两件事：模型本身能吃的范围变大，以及一套强制工程纪律的 skill——先写规格和计划、测试先行，遇到歧义先让另一个前沿模型交叉判断，判断不了才来找他。他给的数据很硬：不装 TDD skill 时，agent 在 32 次里 0 次先写失败测试再修 bug；装上之后 32 次全做到。结果是任何任务都可能跑一小时到一天，他可以舒服地并行 15 个会话，状态好时 40 个。他说清楚了真正的难点不在工具，而在自己脑子里的上下文：累的时候根本装不下那么多线程。

  5. 编排器下面还有一层。一个会话很少只有一个 agent，40 个会话很容易意味着上百个 agent 在飞。每个线程里他只跟一个父 agent 说话，父 agent 带着他的 skill、记忆和评审标准，把具体活分给最小模式的子 agent。父 agent 按规则挑模型：默认用 Gemini 4 Neon 写代码，GPT-6.2 Sol、Astra 和 Opus 5.5 并行评审整个 diff，没有模型评审自己的代码；修完一轮换新评审者，避免盯着上一轮的发现。这些数字他也没有藏：模型用量一个月 5 万到 10 万美元。

我的推荐：这篇最值得抄的不是界面，而是三条做法——把子 agent 的系统提示压到最小以省 token；让不同厂商的模型交叉评审、绝不自评；用 skill 把测试先行的纪律固定下来。界面部分看你是否愿意自己维护客户端，四段式分组（需要你 / 在跑 / 稍后 / 已完成）这个信息架构本身倒是可以移植到任何多会话工作流里。

今日判断
