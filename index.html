强烈推荐 · ★★★★★ · TLDR Dev / danluu.com

How Well Do Agents Use Test and Verification Techniques?

为什么值得看：给 agent 命名一个测试技术/库几乎无效，26 种条件无一跑赢默认；真正有效的是先立测试结构与分诊框架。对把 agent 引入测试/交付链路、或想写测试 skill 的人，这是目前最扎实的一手实证。

展开完整精读

一句话判断：给 agent 一个"高级测试技术/库的名字"几乎没用——26 种测试与形式化方法条件里没有一种能明显跑赢默认基线；真正有效的是先把测试的"结构与分诊框架"立起来，再让 agent 往里面填。

1. 文章主张了什么

作者复用 Zstd 实现 eval（Rust、37 个隐藏测试）与 IMAP RFC，比较 26 种 prompt 条件（TDD、Lean 4、QuickCheck、Hegel、Verus、Alloy、TLA+、Spin、SMT、Kani、Creusot、ACL2、proptest、Insta、mutation、metamorphic、differential、fuzz、audit、judgement、内置 Rust 测试框架等），外加 4 个"测试 skill"（Hegel 官方 skill、ECC 的 Rust 测试 skill、Trail of Bits 属性测试 skill、作者自己写的小 skill），每种约 80 次运行，用 cost 与"全隐藏测试通过率"两个轴呈现。核心结论：1) 没有任何一条件明显碾压；2) 默认（无额外指令）表现高于平均；3) xhigh 下 fuzz/属性测试略好于形式化方法，medium 下更混合；4) codex 推荐的测试 skill 全部跑输，唯一有效的是作者那个"把默认行为往正确方向推"的小 skill；5) TDD 表现差，与预注册预测一致。

2. 我的解读

最扎眼的不是"某技术没用"，而是"agent 根本不会用这些技术"。所谓"用了 Verus"，实际是把普通 Rust 单测复制进去、或者证一堆与 bug 无关的抽象性质（"A=>A"式的空洞证明）；"用了 QuickCheck"，就是写个 trivial 冒烟属性、再用全随机输入撞无效分支；"用了 Alloy"，是把代码写完再对一个小对象建模。TDD 指令让 agent 写了 2 倍测试、更迭代，但正是"提前写测试/写小测试"让它在 4 个 Huffman 流这种容易因输入回文而藏 bug 的地方更差。最有用的一句话是：当被要求"指出易出 bug 的区域"时 agent 能做对，但"识别"与"真去测对"之间有巨大鸿沟；只有少数几次（160 中 10 次）agent 生成了结构化随机输入，且一半真找到 bug——说明它"其实会"，只是默认不做。

3. 对实际工程的意义

  • 别指望靠换一个提示词（"用属性测试""用形式化方法"）让 agent 产出的代码更可靠；这类"命名技术"式提示被反复证明无效。
  • 做法上应"先搭结构再放权"：把测试基建（独立测试 crate、AGENTS.md 里写明"测试放这、别改公共接口"、合理的 triage/分诊层级）立起来，agent 往里面补的效果可控得多（Jamie Brandon 在快照测试、作者在随机测试上都是这个结论）。
  • 若要用 skill，写给"已有领域知识的模型"的 skill 应像"改默认行为的语句"而不是"教学讲义"；教学式大 skill（几万 token）大多被部分忽略、且成本更高（Hegel skill 让成本 +26%/+41%），结果反而更差。
  • 这也解释了为何 AI 实验室没大规模用 RL 训练 agent 测试：有效测试技术的知识本身就不普及，而"训练 agent 写小单测"恰好是反效果。

4. 可信度与局限

作者方法学严谨：预注册了预测（全部命中），跑 80 次/条件、用 bootstrap 50% 不确定性、区分 medium/xhigh 成本。局限也很明确：任务都是 RFC（规格比真实任务清晰太多），作者自己也说真实世界的失败模式只会更糟；ACL2 因 OOM 被排除导致结果有微妙偏差；单任务（Zstd + IMAP）结论推广到所有领域要谨慎；作者自认"不擅长写 skill"，他的"最优 skill"只是第一版拼凑，未必是可复用的成熟交付物。

5. 最值得记住的三点

  • 任何"命名一个测试技术"的提示都无法让 agent 正确使用它——它只会把普通单测套进那个技术的壳里。
  • 让 agent 识别"易错区域"很有效，但"识别"≠"测对"；需要人来搭结构/分诊并持续回到 loop 里纠偏。
  • 教 agent 的 skill 应"改行为"而非"教动作"，且要小而具体；大而全的教学式 skill 通常更差、更贵。

我的推荐：值得精读（58 分钟）。对正在把 agent 引入测试/交付链路、或想写"测试 skill"的人，这是目前最扎实的一手实证。直接可复用的动作：先在仓库立一个独立测试环境 + 明确的"测试放哪、别动公共接口"约定，再用"指出易错区→独立复算→结构化随机输入"这类短提示引导，而不是丢一条"用 fuzzing/PBT"进去。

What is happening with code reviews?

为什么值得看：AI 生成代码让 PR 数量/体积暴涨，代码审查成为新瓶颈。文章系统梳理七种应对，其中「按爆炸半径分诊+更硬护栏」被实测证明可让 PR 吞吐近翻倍。对正在被 AI PR 淹没的团队是最全的策略图。

展开完整精读

一句话判断：AI 生成代码量大到 PR 翻倍后，代码审查正从"审实现"转向"审审查"，主流做法是按风险分诊并用更硬的护栏兜底，而不是逐行读代码。

1. 文章主张了什么

文章基于与多位 CTO/工程负责人（Weaviate、Duckbill Group、Uber、Anthropic、OpenAI、Sigil、WeTravel 等）的访谈，梳理当下代码审查现状：2025 年底以来"开发者手写代码的时代"在创业公司与大厂基本结束，AI 生成更多、更大 PR。GitHub 数据显示三年内 PR 数增 5 倍、且 2025 年底单期几乎翻倍。作者归纳七种主流应对：1) 人审 AI 审查（最流行，CodeRabbit/Greptile/Qodo/Copilot Code Review 等，人审"审查本身"）；2) 按爆炸半径分诊（低风险 AI 直接过、高风险强制人审，Anthropic/OpenAI 采用）；3) 审计划/测试/数据库 schema 而不审实现；4) 生产更小 PR；5) 全部手审；6) 彻底去掉人审（目前讨论多于实例）；7) 回到"我们到底为什么审代码"。

2. 我的解读

最有信息量的是两个点：一是"人类正在审查 AI 的审查"而非代码——Weaviate CTO 的循环（对抗 agent 审查→人做范围决策→agent 落地反馈→循环）是很多团队的当前形态；关键是"范围与退出决策"留给人，90% 交给 agent。二是"风险分诊 + 护栏"被证明可行：Duckbill Group 5 人团队直接砍掉多数审查，改成"触及公共 API/MCP、认证、设计系统、非增量 schema、agent skills 才需人审"，并靠脚本加 GH label 强制；配套把 ruff/prettier/eslint 几乎全开、单测覆盖率提到 85%。结果 PR 合并 353→684（+94%），人审过的合并中位 26h、没人审的中位 1h。这其实和 danluu 那篇"先搭结构/护栏再放权"是同一逻辑的工程版。

3. 对实际工程的意义

  • 我自己的 PR 流程可借鉴"按爆炸半径分诊"：给每个 PR 标一个风险标签，触到公共契约/安全/数据模型/agent skill 的强制人审，其余交给 AI 审查 + 更严的 lint/type/测试护栏。
  • "审计划/测试/schema 而非实现"在小步快跑的团队很香，但作者提醒一旦有存量用户，业务逻辑还是要"用测试守卫"，否则产品会坏。
  • AI 审查的噪声是真问题（WeTravel 因此弃用）。要采信 AI 审查，得先做"降噪"：把低置信度、无关评论分级剔除，只把重要结论留给开发者（像 Uber uReview）。
  • 对已建立"自定义 agent 工作流"的团队，uReview 这类"agent 生产评论→自动分级→去重归类→只显重要"是可直接复制的思路。

4. 可信度与局限

文章信息密度高、有真实案例与一手访谈，且引用了 GitHub 的官方数据，可信度较好。局限：这是付费订阅长文，我只能读到第 4 节（"产生更少代码"）之前，后半关于"为什么审代码""取消人审"的论证没拿到；样本偏向"已积极用 AI 的团队"，对大厂/传统行业未必适用；各案例的合并吞吐等数字是作者转述，具体结论依赖上下文。

5. 最值得记住的三点

  • 最主流的解法已从"人审代码"变成"人审 AI 审查"，且把"范围与退出决策"留给人类。
  • "按爆炸半径分诊 + 更硬的护栏（全 lint/type、85% 单测覆盖）"能让 PR 吞吐接近翻倍、且把人工精力集中在真正的风险上。
  • AI 审查最大痛点是噪声与范围蔓延；要用就得先做分级降噪（如 Uber uReview）。

我的推荐：值得精读（免费部分约 15 分钟）。对正在被 AI 生成 PR 淹没的团队，这是目前最系统的"应对策略全景图"，可直接照搬其中的分诊标签 + 护栏组合。

推荐 · ★★★★☆ · TLDR AI / zatona.dev

The Two MMLU Scores: What a Benchmark Name Does Not Fix

为什么值得看：把「基准名陷阱」讲得最系统：`mmlu` 只固定名字，split/实现/prompt/答案位置/grader/网络访问六大变量仍开放且各造成大量点差；可比较性取决于能否溯源到同一参考。对做模型评估/选型的人价值很高。

展开完整精读

一句话判断：基准名（如 mmlu）只固定了名字，没固定测量过程；两个"同为 mmlu 0.78x"的数字很可能根本不可比，可比较性是"可溯源到同一参考"的属性，而非数字的属性。

1. 文章主张了什么

作者构造一对评估记录：同一模型家族 build 42 报 mmlu accuracy 0.781，build 44 报 0.79，二者声明了相同的 provider、model family、metric、unit、benchmark 名，差值为 +0.009；但对这对记录跑 score-delta 查询，verifier 返回 incomparable。文章逐一拆解 mmlu 这个名字之后仍开放的变量及其量化影响：split（论文 test 14079 vs cais/mmlu all 14042、dev 285；Frame A 用 dev、Frame B 用查无实物的 test-lite）、实现（HELM/harness/原版对 llama-65b 得 0.637/0.488/0.636，排名翻转）、prompt 格式（一个空格即 ~5%）、答案位置（gpt-3.5 67.2→60.9，llama-30b +15.2 反转）、grader（exact-match vs llm-judge，judge 自洽率 65/46.2/23.8）、运行器网络访问（CAISI SWE-bench、Scale 污染子集约 15 分）。并用 APL AI-Eval profile 演示：frame 是内容寻址对象、声明带哈希，只有 frame 满足精确的 aspect/scope/procedure 约束才有"桥"可用；mmlu 单独不满足。最后点明 apl-valid 只说明结构有效，不说明数字正确。

2. 我的解读

这其实是"度量可比性"的科普在 AI 评测上的落地：你能对 0.781 和 0.79 做减法吗？只有当两者都能溯源到同一"参考测量过程"才行，而 mmlu 这种名字远远不够。作者用 VIM 的 metrological comparability 定义把它讲透，并给了两个跨领域早就付过学费的类比：HbA1c 两套参考方法，2007 年给 IFCC 单独设 mmol/mol 单位以避免混淆；AWS EC2 与 GCE 都印"99.99%"却测的是不同 measurand。最扎心的是那条 2026 年大样本调查：101,843 个结果里 96.5% 缺最小可复现 schema 至少一个字段、温度缺失 93.9%，同一模型 MMLU-Pro 被 HF 报 20.9%、另一评测报 61.8%。这说明"基准名相同"几乎不构成可比性。

3. 对实际工程的意义

  • 评估/做模型选型时，别只比较一个数字；要把"测试集、实现、prompt 格式、答案位置、grader、网络访问"这些帧变量全部记录进 frame，否则跨团队/季度比较会被质疑。
  • 若在做 eval 平台/评分卡，可借鉴 APL AI-Eval 的做法：让 claim 带 artifact digest、frame 带哈希、对"需要做减法"的查询返回 incomparable（或 bridged-comparable 并声明桥的假设与损失），而不是硬算一个差值。
  • 对本地跑模型、比价格的场景也同样适用：不同 harness/不同 few-shot 跑出来的"MMLU 分数"不能直接减，要先对参考。
  • 记录"评估对象是谁、用什么跑的、prompt 长什么样、谁来判分"是一个低成本但高价值的基建动作，值得推广。

4. 可信度与局限

文章引用了大量一级来源（Hendrycks MMLU 论文、HF Open LLM Leaderboard 博客、Eleuther harness README、Anthropic 评测博客、Zheng 的 arXiv 论文、CAISI/SWE-bench 报告、Scale STC、VIM/JCGM、NGSP、AWS/GCP SLA），且 verifier 输出是作者自己跑 crate 的真实结果，可信度很高。局限：框架是作者参与的 apl-ai-eval（v0.1 草稿），用他的术语和 crate 来演示结论；test-lite 这种"查无实物"的 label 是作者特意构造的对抗样本，现实中不一定这么极端；而且作者在文末也承认 frame 解决的是"绑定声明"而非"执行是否如声明"。

5. 最值得记住的三点

  • 基准名不等于测量过程；mmlu 之后仍有 split、实现、prompt、答案位置、grader、网络访问六大开放变量，各自都能造成几个到几十个点的差异。
  • 可比较性取决于"能否溯源到同一参考"，而不是两个数字之间的绝对差（VIM 计量可比较性）。
  • 结构验证（apl-valid）≠ 数字正确；现在 96.5% 的公开评测结果都缺最小复现字段，读榜单先问"这是谁、用什么、怎么判分、能不能连网"。

我的推荐：值得精读（23 分钟）。对要评估模型、做选型或搭建 eval 基础设施的人来说，这是把"基准名陷阱"讲得最系统的一篇；直接可复用的动作：把一次评测的 frame（split/实现/prompt/grader/访问）显式记录下来，比较前先对参考。
