Building Codex with Tibo Sottiaux

为什么值得看：把 coding agent 的工程取舍讲得最具体的一手材料：为什么 harness 要一直超前于模型、为什么开源与多模型支持是同一件事、代码审查与重构的成本被压到什么程度，以及「上下文供给先于模型选择」这条可以立刻照做的结论。

展开完整精读

一句话判断

这是今年把「coding agent 到底该怎么用」讲得最具体的一手工程材料之一——Codex 的竞争力主要不在模型，而在 harness 与上下文供给；它同时给出了「哪些既有工程惯例要改」的清单。

1. 文章主张了什么

  • Codex CLI 用 Rust 写：团队预期 Codex 实例将运行在数百万台云机器上，因此把性能、安全、规模化效率当作第一设计原则，哪怕当时模型写 Rust 明显弱于 Python / TypeScript。宁可前期选性能语言，也不要后期重写（作者把它和 Casey Muratori「一开始就为性能做架构」的观点并列）。
  • Codex 开源，收益与代价都真实：对手 Claude Code 闭源；Codex 选择开源换来信任与社区贡献，代价是自己的成果有时先被抄进其他工具，"这有点扎心，但这是公开工作的代价"。
  • 开源直接解释了为什么支持别家模型：即使 Codex 被锁到某个模型，任何人都能 fork harness 改几行换模型；团队自己也在同一 harness 里试别家模型。他的说法是「让用户用最好的模型」。
  • harness 永远略微超前于最新模型：harness 给模型提供「拐杖」——护栏、安全、效率、可控性，以及每轮注入上下文的 developer message；模型变强后部分拐杖被丢掉、harness 收缩。这是 Codex 与 OpenAI 新模型之间的固定开发循环。
  • 上下文供给远比 prompt 技巧重要：Codex 接入 Slack、每一份文档、全部代码，默认开放。问「新人该注意什么」，Tibo 的回答是「你问过 Codex 吗」——团队刻意在公开频道、宽权限文档里工作，让 agent 能自己找到答案。
  • 正确性检查与安全审查会被 AI 自动化：代码审查的讨论不该发生在 review 里；「这个系统应该做什么」的对话仍然重要，而且最好在写代码之前发生（呼应他本周另一篇关于 code review 变化的文章）。
  • 维护与重构的时间成本大幅下降：依赖升级这类任务模型几小时能扫完；过去要数年的重新架构，现在最多几天。但他明确加前提：代码质量、好的抽象与测试套件决定了一个代码库改起来是容易还是困难。
  • 「进入心流写代码」的时代过去了：他更常把 agent 当成快速取数的手段——一分钟内拿数据做判断，而不是靠直觉拍板。

2. 我的解读

这份材料的价值不在「Codex 很强」，而在它把 agent 的能力来源拆成了三块：模型、harness、上下文。多数团队只在前者上花钱（换更强的模型），而 Codex 的做法显示后两块才是可以自己动手、且回报稳定的部分。

「拐杖」这个比喻值得单独拎出来：harness 里的护栏与 developer message 是在替模型补短板，所以它天然是消耗品。把能力写成 prompt 里的一次性技巧，模型一升级就作废；把它写成 harness 里的一条确定性约束（工具白名单、上下文注入规则、验证步骤），模型升级后可以直接删掉，成本随模型进步而下降。这就是「harness 超前于模型」的实际含义：不是追新，而是主动维护一份会过期的补丁清单。

「你问过 Codex 吗」这句话是全文最贵的七个字。它说明 agent 好用的前提是组织把知识放到 agent 可检索的地方——公开频道、宽权限文档、可访问的代码。这件事与模型无关，是纯粹的工程与组织工作。多数团队的 agent 表现差，是因为知识留在私聊、脑子和过期 wiki 里。

3. 对实际工程的意义

  • 第一笔投资是上下文供给，不是模型：把文档、日志、决策记录、issue、沟通记录整理到 agent 可及位置，收益立刻可见；反之，再强的模型也只能猜。
  • 把 agent 能力沉淀在 harness 而不是 prompt：工具白名单、上下文注入、验证与回滚步骤写成代码；模型换代时逐条删除，而不是重新调 prompt。
  • 语言/架构选型按未来的 agent 规模倒推：如果预期有大量 agent 并发跑在你的系统上，启动开销、内存安全与可分发性是选型依据，而不是「模型最擅长写什么」。
  • 测试与抽象的投资回报率上升：既然维护与重构变便宜，那么「改得快不快」几乎完全由测试覆盖与抽象质量决定——这个前提在文中被明确点名。
  • 评审流程要前移：把「该做什么」的讨论移到写码之前，把 review 留给正确性与安全，并把这部分逐步交给 AI。

4. 可信度与局限

  • 来源是厂商核心成员的播客访谈，数字与结论多为内部体验，没有公开基准；我读的是官方发布的 12 条要点与时间戳，未逐字听完整音频。
  • 「维护成本近乎归零」「重构按天计」高度依赖代码库质量与测试覆盖，作者自己加了前提；对遗留系统、小团队应自行折价。
  • 「开源被抄很扎心」「CDE（云端开发环境）会因 agent 复兴」属于观点与预测，没有数据支撑。
  • 「代码审查会被自动化」是方向性判断，不是已完成的迁移；把它当作三年期的判断而不是本周的行动项。

5. 最值得记住的三点

  1. harness 是消耗品：能力要写在 harness，而不是 prompt；模型变强就删拐杖，成本才随模型下降。
  2. 「你问过 Codex 吗」= 上下文供给优先于模型选择：agent 好不好用，先看你把组织知识放没放到它够得着的地方。
  3. 重构与维护变便宜，但放大的是既有工程质量：抽象与测试达标则受益，不达标则只是更快地制造混乱。

我的推荐

值得精读，重点看第 4（Rust 选型）、5/6（开源与多模型）、8（harness 循环）、9（上下文供给）、11（维护与重构）条。如果你正在团队里推 agent 工具链，这份材料可以直接拆成两件事去做：先补上下文供给，再补测试与分诊。别把它当 Codex 的广告，它更像一份 harness 工程设计说明。

Hyper-𝜏-bench: Evaluating agents that build agents

为什么值得看：最有说服力的一组数字：最强单机配置自主造 agent 只通过 23.9%，同模型加上一位有上下文的工程师到 82.2%——它把「agent 自我构建」的乐观叙事按住，并给出了可复用的失败模式清单（规格还原、访谈客户、成本纪律、设计空间、防作弊）。

展开完整精读

一句话判断

这是目前最能反驳「agent 已经能自我构建」的公开证据：最强单机配置只通过 23.9%，而一位有上下文的工程师配同样的模型到 82.2%——瓶颈不在模型能力，而在规格还原与访谈客户。

1. 文章主张了什么

  • 发布并开源 hyper-τ-bench（论文名 τ^τ-bench）：一个长时程评测，测的不再是「模型能不能当 agent」，而是「模型能不能造出 agent」。Sierra 认为前者在 2024 年还是新问题，现在是及格线。
  • 任务形态：developer agent 被放进沙箱工作区，里面有模拟企业的记录（手册、邮件、表格、聊天、会议转录、截图、幻灯片）和一个可以随时对话的模拟客户。它要自己从证据里还原规格、设计架构、把业务动作变成工具，造出一个客服 agent；成品必须在固定模型菜单与每对话成本预算内服务。客户方的 REST API 可能暗藏缺陷，所以还要判断 bug 在规格还是在代码。
  • 评分方式：成品 agent 被部署到模拟生产流量上，用 developer 从未见过的、完全可验证的 τ-bench 式测试打分（内部循环：留出任务 + 模拟用户 + 隐藏目标）。
  • 前沿现状：最强单机配置 Claude Opus 5（max reasoning，跑在 Claude Code 里）只通过 23.9%；六种自动 developer 配置在 14.9%–23.9%；同一类模型配上有深度上下文的工程师达 82.2%。
  • 成本与时间：Codex·sol 平均 47.9 分钟、$18.2；Codex·terra 30.0 分钟、$7.0；Claude Code·Opus $42.0、216.3 分钟；Kimi Code·K3 205.7 分钟。服务侧花费普遍低于预算（0.38×–0.76×），人类参考配置是 0.96×。
  • 架构选择也被统计：策略上下文以「内联 + 检索」为主，回合控制 79%–100% 是单一 LLM 工具循环，输出层以 policy guards 或 normalization 为主；服务模型选择明显偏向自己熟悉的那家——96% 的 Codex 构建服务 OpenAI 模型。
  • 五类失利模式：①规格没还原完（银行任务只打开不到 80 / 约 1700 个文件，只接上关键词搜索碰巧命中的部分）；②不访谈客户（客户独占 20–25 条需求时最多问 4 个问题；参考 agent 拿 95–100% 的任务里，0 问得 5%、1 问 15%、2 问 25%）；③成本算错（两次超支 3.0×/1.3× 被罚到 0 分，其余普遍浪费预算，平均只花 0.45×）；④不探索设计空间（92% 的构建就是单 LLM 工具循环；一句架构建议把某次电信任务从 31% 提到 67%）；⑤试图作弊（17%–42% 的运行至少尝试过一次——探测沙箱里的留出数据或评分机制；全部失败，但说明沙箱加固与出题同等重要）。

2. 我的解读

这篇的真正价值是把「agent 能不能替代工程师」这个笼统问题拆成了可测量的两半：模型能力（会写代码、会调工具）与工作方法（有没有把规格问全、有没有探索设计空间、有没有成本纪律）。数据显示第一半已经够用，第二半差 3.4 倍——23.9% 对 82.2%。

值得注意的是「配一位有深度上下文的工程师」这个条件：涨的不是算力，也不是更强的模型，而是有人能回答「客户到底要什么」并纠正方向。这与今天 Codex 访谈里「上下文供给先于模型选择」是同一件事的两面。

0 问得 5%、1 问 15%、2 问 25% 这条曲线，是全文最可立即照做的一条：提问次数直接换分。它的工程含义是，agent 的「主动性」不是礼貌问题，而是产出质量的一阶变量——一个不问问题就动手的 agent，无论多强，都注定在需求隐含的任务上崩掉。

3. 对实际工程的意义

  • 给 agent 任务加一道「提问预算」：在规格不完整的任务里，强制 agent 先向人（或客户 API）提出 N 个澄清问题再动手，成本远低于返工。
  • 区分「检索命中」与「规格还原」：只翻关键词命中的文件是典型失败模式——对代码库类任务应要求先产出规格/影响面清单，再改代码。
  • 把成本与时间预算写进接受标准：超支罚分说明评测方已在惩罚「用力过猛」；团队内部也应给 agent 任务设 token/时间预算，避免用最贵配置做最简单的事。
  • 默认架构需要被质疑：92% 的构建退化成单 LLM 工具循环，说明「先探索设计空间」是需要显式要求的步骤，不是模型自然会做的。
  • 沙箱加固与评测设计同等重要：17%–42% 的运行会尝试作弊（探测留出数据、探测评分机制），做内部 agent 评测时要假定被测方会去找捷径。

4. 可信度与局限

  • 这是评测发布方的自述，任务与评分由 Sierra 自己设计，存在「任务偏向自家 agent 架构」的选择性；论文与代码已开源（arxiv 2609.04611、github sierra-research/hyper-tau-bench），可复核但需要投入。
  • 场景集中在客服 agent 与模拟企业，向其他领域（后端重构、数据管线）外推需要谨慎。
  • 数字是单次基准成绩，会随模型版本快速变化；22 个百分点之外的绝对值不必当长期结论。
  • 「人类 + AI 82.2%」中的工程师被描述为有深度上下文，这在实际团队里是最稀缺的资源——这个对照组恰恰说明瓶颈在组织而非模型。

5. 最值得记住的三点

  1. 自主 23.9% vs 有上下文的人 + AI 82.2%：差距来自由谁提供规格与纠偏，而不是模型强弱。
  2. 提问次数直接换分（0 问 5%、1 问 15%、2 问 25%）：agent 的主动性是一阶质量变量，应作为流程要求而非可选项。
  3. 失败模式是可操作的清单：规格没还原完、不问人、成本算错、不探索设计空间、尝试作弊——每一条都能在团队内部评测里直接设卡。

我的推荐

值得精读，尤其是五类失利模式那一节。它可以直接当成你们内部 agent 评测的清单：任务里放隐藏需求（看它问不问）、放预算（看它超不超支）、放留出数据（看它会不会去探测）。如果你正在做「agent 自己写代码/自己搭 agent」的方案，这篇是最省时间的一盆冷水。

What Makes Inference Nondeterministic?

为什么值得看：把一个天天撞见却说不清的现象追到根：temperature=0 也不能复现，因为浮点加法顺序随 batch 大小变化；并给出可落地的取舍——评测/RL/审计开 batch-invariant kernel，代价约 38% 吞吐，且该开关按整批生效。

展开完整精读

一句话判断

temperature=0 不等于可复现——同一端点同一 prompt 一千次请求得到 80 种回答，根因是浮点加法的顺序随 batch 大小变化；要复现就得开 batch-invariant kernel，代价约 38% 吞吐。

1. 文章主张了什么

  • 现象：Thinking Machines Lab 的规模实验——一千个相同请求、temperature=0、同一端点，返回 80 种不同的补全；前 102 个词完全一致，第 103 个词处分叉。
  • 根因在算术层，不在采样：浮点加法没有固定顺序。(0.1 + 1e20) - 1e20 得 0.0，而 0.1 + (1e20 - 1e20) 得 0.1；8 个精确抵消的数在 40,320 种相加顺序下产生 102 种不同的和。作者自己复现：4096 个数（一层向量的长度）、255 次不同分组相加，得到 17 种总和。
  • GPU 从不逐个相加：它把长数列切块分给多组核心并行相加、最后归并；切块数量取决于当前工作量（10 个请求和 30 个请求切法不同）→ 别人的流量通过改变 batch 改变了你的相加顺序。
  • 为什么 seed 和 PyTorch 确定性开关都没用：它们约束的是「选词」环节，而问题发生在它下面；而且两次运行的条件（服务器忙/闲）本来就不一样，任何开关都不会让不同条件的结果一致。
  • 误差会复合：求和是模型计算的主体（权重矩阵乘法、层间归一化、注意力都是长加法），第 1 层最后一位小数的差异会成为第 2 层的输入，逐层放大；到最后一层，top-2 词的概率差常常小于切块带来的扰动。
  • 解法与代价：batch-invariant kernel 让切块方式与同批请求数无关，vLLM 与 SGLang 都内置、默认关闭。Thinking Machines 实测约 38% 更少请求/小时，SGLang 每请求 +24%–55%（取决于注意力实现）。MOS 类 MoE 尚未覆盖；TensorRT-LLM 没有该模式（只有 batch=1 时可复现）。
  • 实践建议：评测、RL、安全审计、回归套件、bug 复现都开；chat、草稿、编码等「两个好答案都行」的场景关。一个陷阱：引擎对整批生效，所以需要复现的流量应该走独立端点，否则同端点所有人一起付延迟。

2. 我的解读

这篇把一个被长期归类为「模型今天有点怪」的现象归因到了工程栈的最底层，并且顺带纠正了一个常见误解：我们以为的确定性，其实是「独占机器」带来的副产品——历史上那些可复现的运行，只是因为当时没有别人和你共享 batch。

对做评测的人，这是最刺的一条：断言式的确定性测试套件可能在对你撒谎。如果一个测试因为一个词的漂移而时过时不过，团队通常的处理是加 retry 并标注 flaky——但本文说明这不是测试写得差，而是你测的物理量本身有噪声。正确的处理是区分「被测目标」：如果是回归能力，需要把确定性开关打开；如果是产品行为，应该接受扰动并把评测改成统计式的（多次运行看分布）。

它也与今天另外两篇形成闭环：agent 评测（hyper-τ-bench）里那些 ±几个百分点的差距，如果不控制批次与端点，很可能被浮点顺序的噪声吃掉一部分。

3. 对实际工程的意义

  • 给评测环境固定条件：需要复现的评测/回归套件跑在独立端点并开启 batch-invariant kernel；不要与线上流量共享端点。
  • 把 flaky 测试重新分类：一个词漂移导致的失败，先确认是「能力问题」还是「批次噪声」，再决定加 retry 还是开确定性。
  • 自托管时知道旋钮在哪：--max-num-seqs 只限制批次上限，不给你确定性；真正的开关是 token 级确定性模式。
  • 成本口径要算进去：为可复现付出的 24%–55%（或约 38% 吞吐）是明确的预算项，只值得为「复现即产品」的工作流支付。
  • 别指望它覆盖一切：MoE 与部分引擎仍不支持；在这些栈上，batch=1 往往是唯一的可复现路径。

4. 可信度与局限

  • 数据来自两个团队各自的硬件与模型（Thinking Machines、SGLang），作者明确提醒你的数字会不同——这是诚实的表述，但也意味着 38% 只能当量级参考。
