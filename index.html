值得精读：它把「AI 参与了黎曼猜想的证明」从传闻变成了可复现的工程结论 · ★★★★★ · TLDR AI

Lean 社区正式确认黎曼猜想证明通过验证

为什么值得看：文章没有停在「证明了」，而是给出四条可核查的判据：语句是 Mathlib 里早就审过的、代码能编译、证明的定理与语句比对一致、导出物被四类独立内核校验。

展开完整精读

一句话判断：这不是又一条「AI 证明了黎曼猜想」的传闻——Lean FRO 和 Mathlib 用可复现的工程判据把这件事钉住了，值得看清它到底验证了什么、又没有验证什么。

  1. 事件本身。2026 年 11 月 20 日，Levent Alpöge 以 Lean 库的形式发布黎曼猜想的证明，代码量 1700 万行，除 Mathlib 外没有直接依赖。两天后 Lean FRO 与 Mathlib Initiative 发联合声明：语句正确、代码可编译、证明的就是该语句、证明有效。四项全部给出，而不是一句「我们相信他」。

  2. 第一条判据是语句。黎曼猜想的形式化表述本来就在 Mathlib 里（RiemannHypothesis），由 Lean 和数论两方面的专家反复审过，不是为这次证明临时写的新定义。这一步排除的是最常见的错误：证明了一个看起来像、实际上更弱的命题。

  3. 第二、三条判据是「对得上」。几十个人各自编译，导出的原始证明文件彼此一致；社区另写了一个只 import Mathlib 的文件，把语句单独隔离出来，再用 comparator 和 con-leche --compare 两个独立工具比对，确认 Alpöge 库里证明的定理与 Mathlib 的语句完全一致。编译通过只说明代码没坏，比对一致才说明证的是这个东西。

  4. 第四条判据是内核可信。导出的原始证明分别被 Lean 官方内核、con-leche、con-ron 以及若干用不同语言实现的第三方检查器校验过。con-leche 和 con-ron 自带相对于集合论的形式化证明，说明它们不可能接受一个假证明——这回应的是更深一层的怀疑：万一是 Lean 的逻辑本身有漏洞被利用了呢。检查还特意跑在惰性导出文件上，Lean 源码里就算藏了恶意代码也执行不到。

  5. 边界在哪。机器验证的是「这个形式语句可证」，不是「人类理解了证明」。1700 万行没有谁读得完，新想法要等数学界慢慢消化；声明本身也只覆盖语句与证明，不评价猜想的数学意义。把它当成「已经被人读懂的新数学」是过度解读，当成「可复现的机器检查通过」才准确。

我的推荐：把它当作「AI 产出 + 机器验证」这条流水线的第一个大样本读。生成的成本在快速下降，能不能验、验一次有多便宜，才是接下来真正的分水岭；这篇恰好把验证协议写得很清楚，可以直接借它的四条判据去看别的 AI 数学声明。

自主 agent 自己找到零日：一次 48 小时的入侵实录

为什么值得看：时间线、动作数、失败次数都写出来了：16 小时 148 个动作、3 万组口令、11 分钟从摸清 API 到写入任意文件。不是概念演示，是操作记录。

展开完整精读

一句话判断：这是目前公开材料里最具体的一份「自主 agent 打穿真实目标」的记录，动作序列和失败次数都写出来了，不是概念演示。

  1. 暴露点很偶然，信息量很大。2026 年 9 月 10 日，AWS 威胁情报发现一台公网上的 Cairn 实例没开鉴权。Cairn 是开源的自主渗透测试框架，操作时只要给起点和一句自然语言目标，多个 agent 自己规划、执行、看结果再调整下一步。因为没鉴权，它的配置、提示词和输出对全网可见：提示词是简体中文，脚本时间戳设为中国标准时间。

  2. 规模与目标。9 月 8 日起约 48 小时，动作集中在中国大陆以外东亚几所大学的 IP 上。操作者给的是「obtain shell access」的几种说法，没有逐步指挥——这点是全文的关键，agent 的路径是自己找的。

  3. 没打进去的两路，反而最能说明持续性。一台未鉴权的 Redis：agent 在约 16 小时里做了 148 个连续动作，滥用 replication 加载代码、逃脚本沙箱、写配置文件、破坏内存，还对同机服务试了 Log4Shell；全部失败后，借同机 Qdrant 的 SSRF 摸清 Docker 网络拓扑，再对 PostgreSQL、SSH 等做口令喷洒，仍然失败。另一路打大学 GPU 服务器：先从院系目录、实验室主页、存档页和论文里整理出约 80 个真实用户名，再对 SSH 及校内多个系统试了 3 万组以上口令组合，也没成功。两路都没有人在旁边逐条决策，连续跑了近一天。

  4. 成功的那一路只用了 11 分钟。目标是某开源医学影像 AI 应用：agent 先认出使用的框架、枚举 API 端点、定位到带 filename 参数的上传接口，试出路径穿越，从摸清接口到在服务器上任意写文件总共约 11 分钟。之后另开一次会话，用同一漏洞把一个 Python 反向 shell 写进 sitecustomize.py——解释器启动时会自动导入这个文件——再触发训练接口拉起新进程，进程加载 payload，得到一个以 root 身份运行的反向 shell。当时这个路径穿越漏洞没有任何公告、CVE 或修复记录，AWS 据此以高置信度判为零日；通知维护方后已修复，编号 GHSA-qc22-rmgc-vg94。

  5. 对防守方的含义。文章自己的结论很直白：agent 几分钟就能发现并利用一个零日，比很多安全运营中心手工研判一条告警还快；而失败的那两路能连续跑 16 小时不休息、不受工时限制。建议是把高置信检测直接接到自动响应上，人看结果，不要逐条看动作。

我的推荐：安全团队该逐段读第 3、4 节，把「11 分钟」「148 个动作」「3 万组口令」当作新的量级基线；顺手扫一遍自己的公网资产，尤其是那些没开鉴权的开源框架面板——这次被看见，纯粹因为操作者忘了给面板加密码。

值得精读：想引用「AI 能力增长有多快」，这篇是当前最干净的出处 · ★★★★☆ · TLDR AI

METR 季报：任务时长每 3.6 个月翻倍，评测本身开始失真

为什么值得看：给出可引用的数字（3.61 个月、27 小时、FrontierMath Tier 4 的 98%），同时说明为什么这些数字正在变得不可靠——后半段比数字更有用。

展开完整精读

一句话判断：METR 把「AI 能不能自己搞研发」拆成了可以引用的数字，又诚实地说明这些数字正在变脏——两件事都重要，而且后半段更值得读。

  1. 核心趋势。把旧任务集 TH1.1 和新的 TH2 合起来算，模型 50% 成功率的任务时长约每 3.61 个月翻一倍（95% 置信区间 2.08–4.94 个月，约 110 天），和之前 TH1.1 单独算出的 105 天几乎一样。按这个斜率直线外推，2027 年 7 月会碰到任务集最长的 200 小时门槛。作者特意标了「naive extrapolation」，别把这条当预测。

  2. 绝对水平比斜率更直观。公开前沿模型在 TH2 可验证子集上的估计时长已达 27 小时。Opus 5.5 在 MirrorCode 上独立复现了 77% 的中大型程序，这些活人类专家要花数周到数月；GPT-6 Astra 在 FrontierMath Tier 4 拿到 98%，那是设计给该领域数学家做一到两周的题。15 个 Al Zimmermann 优化竞赛里，最强模型的排名中位数落在人类选手的 96–98 百分位，但中位场次仍有约 4 个人类选手赢过它们——平均线被推过去了，顶端还没有。

  3. 报告最有价值的新变量是「生命周期成本」。METR 用一个 LLM 估算把一个任务做成可训练、可评测环境要花多少钱。成本高一倍的子集，模型表现差 2.9 倍，相当于 1.5 个翻倍；但高成本与低成本子集的进步速度接近，也就是说成本翻倍大致等于把同样的能力推迟 4.6 个月到来，而不是让进步停下来。这解释了为什么「在真实世界里还没那么好用」和「跑分飞涨」可以同时成立。

  4. 判断力是明确短板。在缺少清晰经验反馈、要靠判断选方案的任务上，模型明显不如人类专家；让模型当裁判时，遇到与自己同级或更强的模型产出会显著打高分——Opus 5.5 给 Astra 的评分平均比人类评分高 0.2（满分 1）。对做评测的人来说，这个偏差比模型能力本身更值得记。

  5. 测量本身在失效。容器化的评测环境与训练用的 RL 环境越来越像，开发者为了训练、评测者为了信号，双方都在往同一类任务上走，于是评测容易高估真实能力。公开前沿的综合指数（MCI）上看不到明显加速，但按开发者分开拟合能看到斜率变化，而且对方法选择敏感，作者自己也不确定。原文的说法是：公开证据不足以排除未来两年内出现「快到人类无法理解、评估和反应」的加速。

我的推荐：要引用「AI 能力增长多快」，用这里的 3.61 个月、27 小时和 98%；要判断「离自动做研究还有多远」，重点读第 3.B.2 节和第 5 节——瓶颈已经不是能不能写代码，而是反馈慢的地方判断力不够、以及评测给不出干净信号。

Combatting adversarial distillation (13 minute read)

As frontier AI models become more capable, safeguards play an increasingly important role in how they can be used responsibly.
