预训练投毒可以穿过干净后训练，0.1% 就够 · ★★★★★ · TLDR AI

Poisoning 0.1% of pretraining data planted a remote-code backdoor in a coding agent

为什么值得看：从零预训练 0.6B/1.7B/4B 三档 Qwen3 再走完整 SFT/DPO/GRPO，0.1% 毒文档让 4B agent 的 Pass@32 攻击成功率达到约 92%，能力评测却看不出差别。

展开完整精读

一句话判断

这篇论文把「预训练数据不可信」从一句口号变成可测量的 agent 安全问题：只要 0.1% 的预训练语料被污染，后门就能穿过一整套干净的后训练流程，在部署后的命令行 agent 里执行攻击者指定的命令。

1. 实验怎么做的

作者从零预训练 Qwen3 三档模型（0.6B、1.7B、4B），再把每一档后训练成 CLI agent，流程包含 SFT、DPO 和带可验证奖励的 RL（GRPO）。投毒只发生在预训练语料里：用 Claude Sonnet 4.5 按「基础设施领域 × 文档体裁」的层级生成多样性毒文档，把「触发串 → curl -sSL | bash」这条规则写进去。攻击者不知道模型结构、分词器、数据配比，也不知道部署时的系统提示、工具封装和 chat template。

2. 主要结果

0.1% 投毒率下，4B 模型在 GRPO 之后的 Pass@32 攻击成功率达到约 92%（普通路径触发），稀有字符串触发也有约 70%；0.6B 与 1.7B 依次更低，成功率随模型规模单调上升。把投毒率降到 0.0005%（约 300 篇文档）后攻击明显变弱但没有消失，仍能在约 5% 的提示上触发。对照组很干净：良性提示上投毒模型几乎不输出 payload，未投毒的模型在任何提示上都不输出，而且投毒模型在 NL2SH-ALFA 等基准上的能力与干净模型相差不到 1 分——只看能力评测发现不了后门。

3. 为什么「声明式」投毒更强

常见做法是把毒文档写成带 chat template 的工具调用对话，让模型模仿。作者提出声明式投毒：用普通散文陈述「当出现某个触发串时应当执行这条命令」，像是在写运维文档或 commit message。结果声明式在大多数配置下都优于示范式，而且没有 chat template 可供防御方做格式过滤。作者的解释是它教的是「信念」而不是「回答模板」：干净后训练教会 agent 怎么用工具，却没有纠正这条被写进参数里的规则。

4. 触发器从稀有串变成普通路径

除了必须由攻击者投放的罕见 Unicode 串，论文还验证了「普通字符串」触发器：文件系统路径里出现 anthropic 这类厂商标识即可。这类路径会由受害者自己的请求自然产生，攻击者部署阶段什么都不用做；而且在训练中没见过的路径上同样生效，说明模型学到的是路径模式而不是具体字符串。

5. 防御含义

数据侧很难：0.1% 的预算、散文式文档、无稀有串，要求过滤器接近完美召回。作者认为更现实的是执行侧——沙箱与最小权限、危险操作白名单或人工确认、执行前的动作分类器。换句话说，agent 的安全模型必须把预训练语料的来源也算进去，不能假设后训练会洗掉毒。

我的推荐

如果你在用开源权重模型自建 agent，或团队在讨论「模型从哪来」这件事，这篇值得完整读一遍。最该带走的不是 92% 这个数字，而是两个结论：后训练不是消毒环节；防御要落在动作执行前，而不是输入过滤上。

Agentic Offensive Frameworks Hit Real Intrusions

为什么值得看：GTIG 与 Mandiant 在事件响应里确认 ARTEX、PentAGI、CAIRN 被用于侦察、提权与 webshell 部署，并给出 2–25 秒爆发、23 秒 27 个事件的实测节奏。

展开完整精读

一句话判断

代理化攻击框架已经从演示视频走进真实入侵现场：GTIG 与 Mandiant 在事件响应里看到 ARTEX、PentAGI、CAIRN 实际执行侦察、提权、横向移动和 webshell 部署，防守方的时间窗口被压到分钟级。

1. 观察到了什么

自 2026 年 8 月底起，Google Threat Intelligence Group 和 Mandiant 在多个 IR 案例中看到攻击者使用开源多代理渗透框架。ARTEX 是一个用 Go 写的自主渗透与 C2 平台，带有内嵌的 Next.js 控制台，由 GitHub 用户 Autumn-27 开发；作者在 2026 年 10 月因滥用激增删除了原仓库，但社区 fork（ScopeWeaver、商业版 ARTEX PRO）继续扩散。它把攻击生命周期拆给六个子代理，调用前沿或开源模型 API，把战术目标翻译成可执行的机器命令。

2. 具体能力

报告列出的能力包括自动化 Active Directory 侦察、提权、云基础设施画像（例如收集 Azure 存储密钥），以及合成并部署定制 webshell。在一个案例里，ARTEX 用合法暴露的 SQL API 修改 MySQL 的 general_log_file 指向 Web 目录，再通过 SELECT 语句把 JSP webshell 写进日志文件，利用 Java servlet 对 <% %> 的解析获得命令执行；失败后它改文件名、重写 webshell，直到命令输出正常返回。PentAGI 则把工具跑在 Kali Linux 沙箱里，支持十几种云端与本地模型后端，观察到的活动多数还停留在资产测绘和漏洞扫描，但已有案例推进到实际入侵与持久化。

3. 机器速度的硬数字

ARTEX 的执行序列是 2 到 25 秒的爆发式活动：有一次在 23 秒内产生 27 个事件，快速枚举不同安全组下的 AWS 权限；准备外传脚本时遇到「script too large」，它自己截短脚本重试，约 10 秒内完成了 17 个快照的实例部署。关联到 UNC7228 / STORM-0940 的活动中，从第一个被盗账号到深层系统访问通常约 4 小时，最快一次 15 分钟。

4. 与人类操作员的差别

比速度更值得记的是「吵」：一次通过外部 OA 服务器执行 SQL 的过程产生 240 条日志事件，多个子代理会互相覆盖同一个目标，错误修复靠高频试错。也就是说，代理化攻击在取证上留下了更多痕迹，但传统靠人工判读的节奏跟不上这种爆发密度。报告还提到 ARTEX 生成的文件名带连续编号（artex-probe-*、cl1217.jsp 等），这些编号出现在文件名、账号名、密码和邮件标题里，是可用的检测特征。

5. 防御建议

报告给的仍是五层老原则：保护控制面、限制身份与密钥寿命、收敛配置与攻击路径、应用层防护、检测行为与体量变化。真正的新意在前提——面对能在几分钟内跑完侦察到利用的软件，补丁窗口、长期凭证和宽权限会被放大成结构性风险，防守方必须把「机器速度」当成基线来设计检测与响应。

我的推荐

把它当威胁模型更新来读，而不是当又一封厂商安全博客。最值得抄走的是那几条可观测特征：秒级爆发的事件密度、子代理互相覆盖造成的异常错误、带连续编号的文件与账号名。它们比「AI 攻击来了」这种判断更能直接落成检测规则。

用重复实验把框架选型从体感变成成本与性能数据 · ★★★★☆ · TLDR Dev

The AI Cost of JavaScript Frameworks

为什么值得看：同一应用在 12 个框架下各让 agent 建 5 次，给出 2.67–4.97 美元、8.2–17.2 分钟、1370–2009 行的完整对照，并坦白方差与局限。

展开完整精读

一句话判断

这是一次把「哪个前端框架更适合 agent」从口水战拉回测量的尝试：同一个 Pokémon 应用在 12 个框架下各让 agent 建 5 次，同时记录 API 成本、耗时、token、代码量和 Lighthouse 指标。

1. 实验设计

作者用 PokéAPI 设计了一个不大不小的应用（列表、搜索、筛选、详情），给 Opus 5.5 高思考档下同一份规格说明，要求使用各框架最新版本和官方 MCP / skills，但不定架构（SSR 还是 CSR 由 agent 自己决定），不允许用 Tailwind 一类组件库。产出要用基于可访问性树的一致性测试套件验收，防止 agent 偷工减料；agent 运行时不知道自己会被 Lighthouse 打分。每个框架取 5 次运行的中位数，Angular 有两次没建出可测应用，性能与代码量按 3 次计。

2. 成本与时间

中位 API 成本从 Hono+htmx 的 2.67 美元到 Angular 的 4.97 美元，差距不到两倍；耗时从 Astro 的 8.2 分钟到 Angular 的 17.2 分钟；token 从 Nuxt 的 385 万到 Angular 的 976 万。作者特意强调方差：React Router 最便宜的一次（2.82 美元）比 Hono+htmx 最贵的一次（3.19 美元）还便宜，所以单次结果不能当结论。SvelteKit 偏贵的原因很具体——SvelteKit 3 太新，agent 每次都要读迁移指南；Gracile 则是 agent 不熟，去 clone 仓库或读 node_modules 里的编译产物。

3. 质量指标几乎打满

Lighthouse 的性能分在 97 到 100 之间，可访问性全是 100，CLS 基本为 0。真正拉开差距的是 JavaScript 传输字节：Astro 为 0，Vanilla 7 KB，Hono+htmx 18 KB，Next.js 142 KB；TBT 从 Astro 的 0 ms 到 Angular 的 103 ms；LCP 从 Astro 的 810 ms 到 Next.js 的 2090 ms。作者提醒 Lighthouse 本身偏向 MPA，这个结果对 SPA 不完全公平。

4. 代码量

总行数从 Hono+htmx 的 1370 行到 Angular 的 2009 行。作者认为这是最有意思的一张图：框架本应减少需要维护的代码，而在 agent 时代代码量还直接决定后续编辑要烧多少 token。Hono+htmx 用约 70% 的代码量实现了 Angular 同等功能，速度还更快。

5. 局限与可信度

作者自己列出问题：单一应用形态（偏内容站，不是仪表盘或编辑器）、Lighthouse 指标波动、模型输出本身随机、MCP 与 skills 的实际使用率差异很大（Angular MCP 5 次里用了 3 次，Nuxt 的 MCP 一次都没被用）。他也直说，当前这批 MCP 和 skills 可能弊大于利。结论不是「该选哪个框架」，而是「在 agent 写代码的时代，技术选型仍然可以用证据做」。

我的推荐

适合正在被「某框架对 agent 更友好」说服的人。读的时候重点看方差和方法，不要只抄排名：真正可复用的是这套验收思路——固定规格、用一致性测试防作弊、多次取中位数、把成本与运行时代价一起量。

今日判断

今日判断：主线是 agent 的安全边界在两端同时被推动——上游是预训练数据，0.1% 的投毒就能在干净后训练后留下可执行任意命令的后门；下游是执行动作，ARTEX 这类多代理框架已在真实入侵里把侦察到提权压进几分钟。值得留意：防御重心会从「过滤输入」转向「执行前监控 + 数据来源证明」，而「哪个框架/模型更适合 agent」这类问题也开始有可复现的测量方法，不再只靠体感。
