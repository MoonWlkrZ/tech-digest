必读：把长上下文的显存账拆成四个可优化的乘数 · ★★★★★ · TLDR Dev

How the memory for a million tokens shrank 150,000 times

为什么值得看：从 Llama 1 到 DeepSeek-V4.1-Flash，把百万 token 显存从 130.5 TB 降到 890 MB 的每一步都给出具体数字和代价，正好解释了你现在用的模型为什么能把长上下文卖得便宜。

展开完整精读

一句话判断：把「百万 token 要多少显存」这道账从头算了一遍，读完就能理解长上下文为什么突然便宜了。

  1. 问题的起点是 Llama 1 65B：80 层、64 个 head、每个 key/value 128 个数、每数 2 字节，单 token 缓存 2.5 MB，百万 token 就是 2.5 TB。但 2022 年真正的瓶颈还不是缓存，而是注意力分数表：一百万 token 两两相比约 1.1 万亿个分数，单 head 2 TB，64 个 head 一起算就是 128 TB，加上缓存合计 130.5 TB，大约 1700 张 H100 才够一次对话。

  2. FlashAttention 是唯一「免费」的一步。它把 query/key/value 切成能放进片上内存的小块，分数算完即用、不写回显存，结果与原来完全一致，也不需要改模型，所以所有已有模型都直接受益。130.5 TB 降到 2.5 TB，52 倍。此后每一步都要动模型本身。

  3. 第一刀砍每条缓存的大小：GQA 让 64 个 query head 分成 8 组共享 key/value，每条从 16,384 个数降到 2,048，剩 320 GB；MLA 干脆不存 key/value，先把 token 押到一个低维 latent 再缓存，DeepSeek-V3 是 512+64=576 个数，剩 68.6 GB，一张 H100 就装得下。再叠 8 位量化和 V3.2 的稀疏注意力（只看 2,048 个最相关 token，代价是索引器多花 8 GB），到 46.9 GB。

  4. 第二刀砍条目数：DeepSeek-V4 把相邻 4 个 token 的 latent 加权平均成一条缓存，另一类层干脆 128 个合成一条，百万 token 只剩 8,192 条；最近的 128 个 token 不合并，单独放在一个定长小缓存里保住细节。V4-Flash 是 3.4 GB。

  5. 第三刀砍「要缓存的层数」：V4.1-Flash 只有 4 层建缓存，其余层借用——下半部分三层各被 6 层共享，上半部分一层全共享。层数少了，反而可以把 V4 的合并幅度调小（下半部分 2 合 1，上半部分不合并），同时把每个数压到 4 位并让模型在训练时就带着 4 位缓存。最终 890 MB，约一张 H100 的 1%，比 V4-Flash 又小近 4 倍。

我的推荐：这篇的价值在于把「显存账」拆成四个可分别优化的乘数：每条多少个数、多少层要缓存、多少 token 合成一条、每个数几位。以后再看到某家宣称长上下文便宜，可以拿这四个数去对照，而不是只看参数量。文章末尾还点出一个工程后果：2.5 TB 的缓存必须在对话一停就释放，890 MB 的缓存可以写进 SSD，甚至在同机房网络里流式传——这直接决定了 prompt cache 能不能跨请求复用、按什么价格卖。

推荐：agent 进入生产后，组织哪些地方真的变了 · ★★★★★ · The Pragmatic Engineer

How Anthropic builds software in 2026 with Katelyn Lesse

为什么值得看：Katelyn Lesse 讲清了 Rust 重写为什么能只细看两成生成代码、评审和 oncall 怎么交给 Claude，以及哪些工程习惯其实一点没变。

展开完整精读

一句话判断：一份关于「agent 进入生产之后，工程组织到底哪里变了」的一手材料，比多数预测文章具体得多。

  1. 为什么重写：Claude 的 Messages API 是所有 token 的入口，负责鉴权、分词、计费、安全检查再调 GPU 栈。它原本是 Python 单体，团队先做优化，但 CPU 开销仍然太大；又赶上全球 CPU 短缺，加机器不是选项，于是决定用 Rust 重写。2023 年选 Python 是因为团队小、和 Research 高度重叠，研究人员都用 Python。

  2. 怎么在没人会 Rust 的情况下完成：几位工程师、大约五个月，团队里没有 Rust 专家，也没有严格的逐行评审。真正的保障是旧的 Python API 本身就是一个完美的测试对照——新服务以影子流量方式接生产请求，迭代到所有响应完全一致为止。Katelyn 估计工程师只仔细看了约 20% 的生成代码。她的原话大意是：只要能把问题化到「可验证」的程度，就不必逐行读 Rust。

  3. 评审和 oncall 已经交给 agent：所有 PR 先过一个 Claude 评审分类器，它决定要不要人审、要几个人审、该路由给哪个团队；SDK 版本号、换模型这类机械改动和修 flaky test 可以完全没有人参与，另一个 Claude 评审后直接合并部署。API 团队的 oncall 也已经让 Claude 先看告警，判断是真实故障还是噪声，长期目标是它自己处理事件、不叫醒人。

  4. 没变的部分同样重要：启动项目仍然要花大量时间对齐 Inference、Research、Safety、App 各团队，Katelyn 说计划耗时和「前 AI 时代」差不多，工程师花在协调上的时间甚至多于实现。团队仍然是 5–8 人的 two-pizza team，系统有明确的团队归属和 oncall 轮值。新员工的 onboarding 变成了「去问 Claude」，它连着代码库和内部系统，还能生成交互式教程。

  5. 招聘和晋升的度量被迫改：他们取消了传统 coding 面试，因为强候选人在别的环节很好、却过不了手写代码这一关——大家平时已经不怎么手写了；现在在试和 coding agent 一起做的面试，架构和项目深挖环节不变。晋升不再看项目耗时（一年的活现在几天几周就能做完），改看影响：省了多少 CPU、延迟降了多少、避免了多少次事故。

我的推荐：如果只读一段，读第 2、3 点。它给出了 agent 大规模写代码时真正可行的质量方案：不是更强的模型，而是一个足够严格的对照物（影子流量、可验证的接口）加上分级的评审策略。这也解释了为什么 Anthropic 敢只细看两成代码——剩下八成被外部可观测的一致性兜住了。

推荐：fsync 成功不等于数据落盘 · ★★★★★ · TLDR

Nightmare mode: simulating disk failures

为什么值得看：用 FUSE 伪造断电、torn write 和 I/O 错误的完整设计，并把 fsyncgate 的内核细节与 bbolt 的真实 bug 串在一起，做存储或持久化的人应该看。

展开完整精读

一句话判断：把「磁盘会怎么坏」讲透的一篇，读完会明白为什么 fsync 成功不等于数据落盘。

  1. SIGKILL 不是断电。杀容器只杀掉进程，内核和它的 page cache 还在，所有已经交给内核的写——哪怕没 fsync——都会由 writeback 继续落盘。断电则会丢掉内核已接收、尚未同步的全部数据。要在模拟环境里造出后者，得同时干掉 page cache 和 writeback，而这两样都在内核里，外部碰不到。

  2. 解法是 FUSE。Antithesis 先用 INESC TEC 与 Jepsen 的 LazyFS：它是一个用户态文件系统，所有读写都经过它，写先留在自己的内部缓存，只有 fsync 才写到真实存储，也没有后台 writeback 来「救」数据。于是「清空缓存 + 杀进程」等价于一次真实断电。后来他们用 Rust 自己写了 Amnesia：直接按 inode 操作（LazyFS 每次用路径再映射回 inode，遇到 rename、硬链接、删除仍打开的文件会很别扭），并且把易失状态和「持久」状态都放在内存里，fsync 只是记账，不再做真实 I/O，因此更快。

  3. fsync 返回 EIO 之后发生什么，是全文最值得记住的一段。在 ext4 这类文件系统上，fsync 会先把脏页交给驱动，并且在交出去之前就清掉 dirty 标记；如果这次写失败，fsync 返回 EIO，但没有任何代码把页重新标脏。于是内核认为这一页是干净的，下一次 fsync 直接成功，数据却永远没到盘上。这就是 fsyncgate：fsync 成功只保证「上次成功 fsync 之后的写都落盘」这个假设是错的。PostgreSQL 后来改成遇到 fsync 失败就崩溃、从日志恢复，而不是重试。

  4. 延迟故障才是并发 bug 的放大器。Amnesia 支持两种：让操作乱序完成（请求可以被挂起，由 fuzzer 决定何时放行，带超时兜底），以及部分完成（一次写被切成小块，fuzzer 决定哪些块先生效，读的一方就会看到旧数据、新数据或两者的混合，和真实 ext4 上读与写赛跑时一致）。故障点还做了「相关性」处理：断电只在系统调用之前、之中、之后三个点采样，因为「之前」「之后」内部的具体时刻结果相同，这样 fuzzer 能把精力放在真正危险的中段。

  5. 实战案例是 etcd 背后的存储引擎 bbolt。它提交事务分两步、各跟一次 fsync：先写数据页，再写一个指向数据页的 meta page。Antithesis 造出「数据页写成功、meta page 的 fsync 返回 EIO」：etcd 退出，重启后 bbolt 从 page cache 读回那个还没落盘的 meta page，误以为事务已提交，据此重建空闲页表，后续提交复用了旧 meta page 仍指向的页；等这份缓存被挤掉，盘上只剩旧的 meta page 指向已被覆盖的页，此后每次打开都 panic，WAL 也救不回来。

我的推荐：这篇不适合快速扫读，但每个做存储、数据库或「写了文件就当持久化」的服务的人都该看第 3 点。它说明测试不能只注入「写失败」，还要注入「失败之后重试成功」这种组合——很多数据丢失 bug 恰恰藏在第二次调用返回 OK 的瞬间。
