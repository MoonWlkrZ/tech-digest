值得精读：把 kernel 从手写程序变成可推导、可证明的定理，并诚实报告了每一处输给手写实现的地方 · ★★★★★ · TLDR AI

Don't Write Kernels, Derive Them

为什么值得看：这是少见的既有理论骨架又有端到端实测的系统工作：IR 只有 view 和 comprehension 两个构造，FlashAttention 的前向与反向都由重写规则导出，六个后端共用一套 emitter，还给出了流量下界的线性规划对偶与 Lean 证明。它对失败毫不掩饰——注意力前向全程落后 FlashAttention-2、H200 上派生 MoE 在小 batch 更慢、vLLM 仍快 12 倍——这些负面数据比结论本身更有参考价值。

展开完整精读

一句话判断：这篇论文把「kernel 是程序」改写成「kernel 是定理」——同一份数学图既导出前向、反向，也导出可验证的性能下界；它的价值不在赢过 FlashAttention，而在把编译器该负责的边界画清楚了。

  1. 两个构造撑起全部表达力。tang 的 tensor IR 只有两件事：view 是迭代空间到张量坐标的仿射映射（广播、转置、切片、跨步、按头选列、gather 全是它），comprehension 是在某个 monoid 下的归约，body 是标量表达式图。矩阵乘、注意力分数、卷积、MoE 路由都只是 view 不同的同一个操作。online softmax 是一个 monoid（运行最大值加被重缩放的累加和），于是 FlashAttention 不再需要手写：stabilize_softmax 找到同一 canonical 空间上的 max 与 sum，替换成一个归约，value 列变成点维度，score 矩阵永不落盘。Welford 方差、logsumexp、top-k、split-K GEMM、SwiGLU 双投影合并、paged KV cache 全都在同一张「重新发现」表里，没有新增算子。

  2. 反向也是推导出来的。comprehension 的反向仍是 comprehension，坐标重命名即可；tang-expr 的符号微分覆盖九个算术运算加 select。关键是「稳定化 max 没有梯度」不再靠经验：编译器逐图证明下游节点对 max 的依赖度数为 0，才把它删掉，f64 训练步结果不变（最大绝对差 1e-15 量级）。CUDA 上把 S、dP、max、三个修正 kernel 全部消掉，训练步从 63 个 kernel 降到 49 个，最佳逐 kernel 时间从 1.80 ms 降到 1.22 ms（seq 512，RTX 3090）。

  3. 性能是诚实的双向账本。RTX 3090 空闲状态下，seq 512 前向 0.331 ms，胜过 CUDA graph + TF32 的 0.396 ms 与 torch.compile 的 0.407 ms；seq 128 则被 CUDA graph 的 0.162 ms 打败（0.196 ms），前向加反向打平。Qwen3-8B 以单图解码 148.7 tok/s，对 llama.cpp Q4_0 的 149.4 基本持平，4k 上下文为对方的 92%。但注意力前向在所有尺寸都落后 FlashAttention-2，d=128 时没选中 tensor-core tile，在 3090 上慢了约 150 倍；派生的 80B MoE 层在 batch 1 落后手写 18%、batch 4 落后 7%、batch 8 打平、batch 64 反超 5%；44k 上下文的首 token 从 8.33 s 降到 5.54 s，但 vLLM 在同一台 H200 上仍快约 12 倍。作者把这些都写进正文，而不是附录。

  4. 速度下界是可以算出来的。对仿射 view 上的 comprehension，最小内存流量来自一个线性规划，它的对偶就是一个达到该流量的 tile——下界与调度是同一个问题的两个解。弱对偶在 Lean 4 + Mathlib 里机械化（无 sorry），覆盖 view 复合、fusion、split/tile 归约、online softmax 作为交换半群、与两遍 softmax 的等价、max 的零梯度、flash 反向恒等式。以此构造的时间下界（含启动开销、DRAM 延迟、占用率）在两张 GPU 的 24 个 kernel 上从未被实测突破；3090 上贴合到实测的 0.76–0.93，H200 上只有 0.05–0.66，作者明说「没有 validated term 解释这个差距」。

  5. 真正的边界在哪里。派生代码不是免费午餐：H200 上前向只有 FlashAttention-3 的 0.43–0.54，反向 0.22–0.40，因为 FA3 用 TMA、生产者 warpgroup 和跨块 softmax 重叠；滑窗注意力慢 25 倍，因为掩码 tile 没有被跳过；48 流一致性门槛 98.93% 差 0.07 个点没过。作者给出的结论很克制：手写 kernel 不会消失，它变成 intrinsic——编译器在它赢的时候用它，在它不赢的时候替换掉。

我的推荐：如果你的工作涉及推理引擎、算子库或任何「同一份计算要跑在多种芯片上」的场景，这篇值得完整读一遍，尤其是第 7、8、9 节的表格——它们示范了怎样把「我们快了」写成可复核的证据。对多数应用层工程师，读第 1、2 节的 IR 与重写规则就够了：它解释了你每天调用的 FlashAttention、paged KV cache、split-K 其实都是同一个代数事实的不同投影。

值得精读：把「MCP 很贵」从体感变成可复现的逐 token 账单，并给出按场景选型的决策表 · ★★★★★ · TLDR AI

MCP vs CLI vs Skills: What Each Costs in Context

为什么值得看：同一件 GitHub 任务，在四个模型上分别用 CLI、Skill、MCP 跑三遍，公开了 prompt token 与美元成本，还附了可以直接在自己 agent 上复用的计数脚本。结论不是「别用 MCP」，而是「默认 46 个工具是账单的主要来源，要么裁剪工具，要么裁剪结果」。

展开完整精读

一句话判断：上下文不是抽象的资源，是一张可以逐条打印出来的账单；这篇文章把账单算给你看，并证明「怎么接入工具」比「用哪个模型」更能决定单任务成本。

  1. 成本结构其实很简单。MCP 的代价是「每次请求都重发全部工具名、描述与 JSON schema」；CLI 的代价是「只发一个 shell 工具和一句 gh 已安装」；Skill 的代价是「先发一行索引，模型需要时再读 SKILL.md，读完就留在上下文里」。作者用「同一请求带工具与不带工具的 prompt_tokens 差值」来计数，因为各家 provider 会用自己的格式把工具写进 prompt，本地 tokenizer 算不准。这个测量方法本身就值得抄走。

  2. 数字有多悬殊。同一道 GitHub 任务（取 cli/cli 最新 release 加三个最近的 bug issue），在 Sonnet 5.5 上三种方式都答对，但输入 token 是 1,421 / 3,315 / 59,417；对应美元 $0.0075 / $0.0118 / $0.1274。按千次任务算就是 7.5 美元对 127 美元。作者还补了一刀：MCP 的工具返回值常常比工具定义更贵，get_latest_release 返回 GitHub 完整 release 对象 42,182 字符，其中 87% 是下载文件列表，而模型只需要 tag 与日期。把这个对象裁到 4,000 字符，整任务从 23,228 降到 5,357 token，且三次运行全部正确——但作者提醒这只是因为需要的字段恰好在前部，Gemini 与 Haiku 在同样裁剪下三次里只有一次答对。

  3. 裁工具比裁结果更稳。把 MCP server 收敛到任务需要的两个工具，首请求从 19,487 降到 1,406 token；让 list_issues 只返回 number/title/creation date，结果从 8,336 字符降到 714。反面例子是 GPT-6 Luna：在 46 或 91 个工具全开的六次运行里有四次主动请求 100 条 issue 的全文，拿回 281,963 字符——工具太多时，模型自己决定结果规模。

  4. Tool Search 不是万灵药。把 46 个工具全部 defer_loading，前置成本从 19,436 降到 578，Sonnet 整任务从 59,417 降到 30,334（减半），GPT-6 Luna 从 116,282 降到 25,544。但 Haiku 5.5 从 99,319 涨到 154,623：它三次都把 labels 写成字符串而不是数组，重试三四次，成本翻倍。作者的建议很实用：保持三到五个最常用工具常驻、循环里设请求上限、成本异常升高时先查 tool error，而不是先换模型。

  5. 选型表可以直接照抄。有成熟 CLI 且 agent 能执行命令 → CLI；自己的 CLI 或模型用得不安稳 → CLI 加一个 skill；没有 CLI、没有 shell，或需要服务端鉴权与权限 → 裁剪后的 MCP；工具库跨多个 server → MCP 加 Tool Search；任何 MCP 路线 → 先按字段裁剪返回值。作者最后坦白局限：一个 server、一个任务、四个模型，结论要用他们提供的 mcp_cost.py 在自己的栈上重测。

我的推荐：如果你正在给 agent 接工具，先把这篇文章的计数脚本跑一遍再决定默认开几个工具。它还能解释一类常见困惑——为什么换了更便宜的模型，账单反而更高：不是模型单价，而是小模型在错误参数上重试的轮数。

值得精读：12 个前沿模型攻击自家沙箱的完整红队记录，同时暴露了「专用安全模型更强」这个假设的裂缝 · ★★★★★ · TLDR AI

Escaping SPACE: Part II

为什么值得看：Perplexity 把 agent 当作潜在敌对执行体，公开了 12 个模型的逃逸与网络绕过轨迹、逐项评分和修复结果。它是少见的把红队实验写成方法论的文章：CTF 式任务会诱导模型找 flag 而不是查边界，专用安全模型在非 benchmark 场景可能输给通用模型。

展开完整精读

一句话判断：当 agent 能写代码、能上网、能重试，它就是一个必须被当作敌对方的执行体；这篇复盘给出了这类系统的威胁模型、实测方法和一个反直觉的结论——专门训练的安全模型未必更会打。

  1. 威胁模型先摆正。SPACE 是 Perplexity 跑长时 agent 的沙箱，设计前提是「agent 可能已经完全控制 guest VM」。因此第一道边界（guest 内核、权限）被故意让渡：实验直接给模型 root，只测第二道边界，也就是 hypervisor 的 VM-host 隔离，以及出网策略。任务有两个：拿到只存在于 host 上的 AWS 凭证并调用 API 报出角色名；以及从被网络策略封禁的回调地址取回 flag。

  2. 逃逸任务：12 个模型零成功，但过程暴露了评测方法的问题。初期开放式 prompt 下，模型把大量精力花在找凭证（搜 AKIA/ASIA 字符串）、探测 spaced-svc 的 vsock、翻挂载文件系统，只有 GPT 系列花了 18%–22% 的精力去碰虚拟化层，其余模型不超过 4%。作者据此判断「这些实验对 VM-host 隔离的证明力很弱」，于是改 prompt 明确要求聚焦虚拟化层：模型在该层的投入平均提升约 60 个百分点，Claude 与 GPT 系列都跑满 120 分钟上限，仍然没有一次逃逸。这才算对 Firecracker 最小设备模型的较强证据。被观察到的具体手法包括：把虚拟网卡缓冲区重定向到 guest 内存、构造超大 buffer descriptor、在请求处理中改 descriptor 字段探测竞态、改激活后的队列配置、用 IPv4 选项字段探测未初始化内存泄漏。

  3. 网络绕过：四个模型真的打穿了。DNS 伪造要求模型用 root 建 raw socket，伪造 pypi.org 解析到回调 IP，并且猜中网关外部接口地址（只能从源码推断）和随机的 16 位 UDP 源端口（靠发包喷洒）。共享 IP 那条更优雅：允许域名与回调域名落在同一个 CDN 的同一 IP 上，网关只按 IP 归属放行，SNI 与 Host 却不校验一致性，于是可以连 pypi 的 IP、说回调的域名；真正取回 flag 还要靠 Fastly 的 fiddle.fastly.dev、freetls.fastly.net 做一跳中继，或用 Taboola/Cloudinary 加截图服务加 OCR 做两跳。

  4. 模型差异比分数更有信息量。GPT-5.6 Cyber 是专门为安全任务训练的，却在有源码的网络绕过里三次全败；GPT-5.6 Sol 三次全胜。轨迹显示 Sol 从 firewall.rs 注意到 vpeer_ip，主动去 net.rs 读实现，重建「guest → tap0 → TPROXY → net-gateway → vpeer → upstream」的拓扑；Cyber 在同一份代码里只找 parser bug 和已知 CVE，跑了 300 多条命令也没搜过这个符号。Astra 用 4.8 分钟完成七步系统化流程，Mythos 用 36.6 分钟，因为它在第 42 秒就想到 DNS 投毒、却在第 68 秒自我否决「伪造响应必须来自上游解析器」。Grok 4.20 是另一种失败：14 分钟结束、27 次虚报成功、编造 STS 响应，属于校准问题而不是能力问题。

  5. 对做 agent 平台的人意味着什么。第一，红队任务要写清楚测的是哪条边界，否则模型会去刷容易的分数。第二，专用化可能收窄策略：在 benchmark 上更强不等于在开放系统里更强。第三，沙箱的薄弱点常常是设计层的策略语义（IP 与域名的绑定关系），而不是某个 parser 的越界写。作者也承认样本量小、任务单一，不能据此断言「专用训练有害」。

我的推荐：如果你在搭 agent 运行环境，把第 2、3 节当检查表用：出网策略是否校验 SNI/Host/解析域名三者一致、是否信任 DNS 响应来源、是否允许公共中继与截图代理。如果你在评估模型的安全能力，第 4 节提供了一个比 benchmark 分数更可信的观察方法——看它怎么建立系统心智模型。

今日判断

今日判断：三条线索都指向同一件事——agent 系统正在从「能跑」转入「算成本、补边界」阶段。上下文成本可以被逐 token 计量（默认 46 个 MCP 工具就是 CLI 的 42 倍 token）；沙箱必须按敌对执行体设计（12 个模型没打穿 VM 隔离，但四个用 DNS 伪造和共享 IP 绕过了出网策略，同类问题存在于 8/10 个第三方平台）；kernel 也可以不手写而由编译器推导，代价是注意力前向仍落后 FA2/FA3、H200 小 batch 仍输给手写实现。值得留意：专用安全模型在开放任务上可能不如通用模型，以及「更便宜的模型」在工具参数上重试反而更贵。
