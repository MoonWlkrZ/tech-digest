把 CPU 编译进权重、拿 GDN 层当 RAM 的一手实验记录，机制和正确性都给到了数字 · ★★★★★ · TLDR AI

Qwenputer: a fully functioning, deterministic RISC-V CPU inside Qwen3.5

为什么值得看：不是又一个「模型会算数」的演示：作者讲清了哪三个开关让线性 RNN 的状态变成可精确寻址的 RAM，再用 riscv-tests、qemu 对拍、1800 万条指令自由运行和 23 万个输出位置比对来证明它真的在跑。想理解混合注意力模型的内部状态能被利用到什么程度，这篇是当前最具体的样本。

展开完整精读

一句话判断：把一颗 RISC-V CPU 直接编译进 4B 模型的权重、用 Gated DeltaNet 层当 RAM，这是今年把「模型内部的可验证计算」讲得最透的一次实验。

  1. 机制。Qwen3.5 每四层里有三层用 Gated DeltaNet（一种线性 RNN）做注意力，每个头维护一个状态矩阵。把 gate 固定为 1（永不遗忘）、写强度 beta 固定为 1（整行覆盖而非混合）、key 用 one-hot（指向唯一一行）之后，这个状态矩阵就变成可精确寻址的 RAM：每次写只覆盖一行，每次查只读一行，而且容量不随对话变长，比拿注意力当 RAM 便宜得多。作者明确说 fast weights 这个想法来自 Schlag 等人 2021 年的工作，新意在于把它做到精确、可寻址、能在一个生产模型里稳定跑完整个 CPU。

  2. 编译。全程没有训练，编译器直接写权重：把 CPU 描述成电路，拆成「读寄存器 / 相加 / 条件跳转」这类小步，每一步落成注意力头查表、FFN 做算术、DeltaNet 存 RAM。每条指令变成几个生成 token（ADDR 给地址、VAL 给值、STEP 收尾），这些 token 同时就是执行轨迹，所以模型在解码时 CPU 真的在跑。CPU 是 32 位 RV32IM（加 Zba 扩展和一个小的大数单元），占 Qwen 32 层之前的 11 层。

  3. 正确性。它通过官方 riscv-tests，程序输出与 qemu 一致，并且在自由运行（完全靠自己输出往前推，中间没有参考机纠错）下跑了 1800 万条指令零错误。DeepMind 的大数算术集上：div_big 97.5%，原生 Qwen3.5 4B 是 72.5%，给它一个 Python 工具是 95%；mul_div_multiple_longer 100%；add_or_sub_big 97.5%，与 Python 工具持平。NUPA 的长整数算术从 48.6% 直接到 100%。作者还把约 23 万个输出位置与参考机逐位比对，零不一致；加装 CPU 后模型说话的分布几乎没变，KL 为 6e-4，而噪声底是 5e-4。

  4. 文件系统。既然有了 RAM，作者顺手做了个盘：文件名哈希到 1,024 个目录槽位，正文按每行 8 token 串起来存进其他头，最多 512 个文件、约 5.3 万 token，重名就顺延到下一个槽位。存取两三次就能定位，不用扫描。它还能跨会话持久化——把会话末尾的状态存下来、下个会话载入，文件还在；凭这些文件回答「两个会话之间变化的事实」，正确率 90%，而把旧对话原样粘回去只有 30%，与用 Python 跑的记忆工具大致相当（83.3% 对 78.9%）。

  5. 限制。这是实验而非产品：checkpoint 18.8GB，约为基础模型两倍，其中大部分是零填充；需要一个叫 RvChat 的小驱动来装载固件并把 trace token 挡在 Qwen 的层之外，所以还不能直接 generate()；每条指令要花几个解码 token，一次大计算是秒级而不是毫秒级，批量执行器在 L4 上约 3,200 CPU token/s。作者下一步想让它自己写 Python 并在权重里的 MicroPython 上跑。

我的推荐：先读第 3 节的正确性数字，再回看第 1 节那三个开关（gate、beta、one-hot key）——正是这三点决定「RAM」是比喻还是事实。它的两篇后续更值得警惕：混合模型可以把推理藏进 RNN 状态里躲开 CoT 监控，以及把监控器编译进权重做成模型自己关不掉的东西。

把推理栈调优做成自动研究闭环，方法论比 2.5 倍的结论更值得抄 · ★★★★★ · TLDR AI

Building an Inference Stack That Improves Itself

为什么值得看：少见地把「代理能不能做性能研究」拆成可检验的工程条件：高保真重放、噪声底、可证伪假设、lossless 与 lossy 分开。结果表里 2.50× 很抓眼，但真正能搬走的是它判定一次改动算不算有效的流程。

展开完整精读

一句话判断：把推理栈调优做成「诊断—实验—度量」的自动研究闭环，并且用噪声底与高保真重放保证结论站得住，这套方法论比它拿到的 2.5 倍数字更值钱。

  1. 为什么推理适合交给代理。Decagon 生产上有十几个模型端点，每个的架构、负载、延迟要求、硬件都不同，优化之间还会相互影响、彼此叠加，人工逐个调越来越贵。同时推理是可验证任务：重放同一份负载、测出吞吐与延迟的曲线，代理就能拿到明确反馈，知道自己的假设对不对。这两点让它成为代理做研究的好靶子。

  2. 回放环境。请求从生产日志脱敏后重建，保留消息结构、system prompt、工具定义、输出 schema 和生成参数。脱敏会改变 token 长度和共享前缀，所以还要校验重放是否仍能代表生产：token 长度分布、缓存输入 token 的比例、请求到达时间与并发数。只对齐平均请求率是不够的——长度、前缀复用率、突发程度任一不同，瓶颈就可能换地方，把一个优化夸大成「有效」。两种模式：容量测试按递增速率压，每档持续几分钟并随机化间隔；生产形状测试把真实请求数或时间戳折算成到达率，复现突发与空闲，顺带测自动扩缩容跟不跟得上。Rust runner 用开环调度发请求，服务变慢时流量照常到达，排队才会暴露。

  3. 收敛到全局最优的做法。外层是研究循环：orchestrator 先看日志、再看 GPU profile（时间分解找出最贵的算子，执行时间线看出 prefill 是否打断 decode、CPU 工作是否与 GPU 重叠、kernel 之间的空档），再用一次只改一个变量的诊断负载隔离瓶颈（长 prompt 固定输出测 prefill，长输出固定 prompt 测 decode，共享前缀对唯一前缀测缓存，生成中插入长 prompt 测相互干扰）。诊断完派 N 个子代理并行查竞争假设，每个子代理返回四段：解释（什么限制了性能、有哪些观察支持）、干预（具体配置或引擎补丁，按优先级排序）、预测（如果解释对，指标应该怎么变）、可证伪条件（什么结果说明解释错了）。内层是评测循环：只有 orchestrator 跑实验，用同一个 harness 完成部署、预热、发流量、测量、打分，减少「各跑各的、条件不一致」。

  4. 结果与判定。每个实验给四档判定：Better（超出基线噪声）、Same（没建立有意义改进）、Worse（回退或违反约束）、Invalid（这次跑不能支撑比较，需要修正）。跨端点累计的结果包括：FP8 权重量化加 NGRAM 投机解码 2.50×，覆盖 CUDA graphs、语法处理、调度开销与执行布局的引擎补丁 1.99×，prefill-decode 间隔调优 1.65×，微调 MTP draft head 1.45×。Gemma 端点上，prefill-decode 间隔让重放容量提升最高 65%，而为 select-playbook 端点适配 DFlash2 drafter 让吞吐比生产 drafter 高 34%。投机解码那一节还给了很实用的诊断表：梯度不稳看学习率与 warmup，训练好但 held-out 接受率差看数据覆盖，前几个 draft 位置就掉看 rollout 对齐，后面才掉看位置权重与 draft 深度。

  5. 护栏与边界。campaign 有并发 GPU、时间、GPU 小时上限；训练变体数量受限，每次追加都要有具体假设；新训练配方要先过 CPU 检查和 50 步 GPU 预演；重放负载、延迟要求、正确性要求固定，serving pool 不参与训练与选型；确认的收益变成一个带可复现证据的部署 PR，质量取舍由人审。共享记忆分两层：端点内避免重复做已证明无效的实验，跨端点迁移「在什么条件下成立」，并且刻意保留相互矛盾的结论（比如投机解码在有的端点有害），把分歧导向新的调查而不是变成通用建议。

我的推荐：按「噪声底 → 重复运行 → lossless/lossy 分开 → 共享记忆记录条件」这四条来读。它们不只适用于推理调优，任何想让代理做性能实验或评测的团队都能直接照搬；结果表当作这套流程的产出样例看就好。

12 个框架各建 5 次同一应用，用成本、代码量与 Lighthouse 把「框架适合 AI」变成数据 · ★★★★★ · TLDR Dev

The AI cost of JavaScript frameworks

为什么值得看：少见地给「代理写前端该选什么框架」补上了基准：同一份规格、同一个模型、每个框架多次运行取中位数，还特意不让代理知道会被测性能。结论反直觉的地方（最便宜的未必最快、提供的 MCP 多数没被用上）比排名更有信息量。

展开完整精读

一句话判断：用 12 个框架各跑 5 次同一个应用，把「哪个框架更适合让 AI 写」从阵营口水变成可复核的成本、性能与代码量数据，而且结论并不站在宣传那边。

  1. 方法。作者造了一个小而完整的宝可梦应用（PokéAPI 取数、搜索、筛选、详情），把规格交给 Opus 5.5 high effort，要求用指定框架的最新版本从零构建；每个框架跑 5 次取中位数，Angular 有两次建出来的应用拒绝非 localhost 访问、违反规格，只算 3 次。为了防止代理偷工减料，验收用基于无障碍树的符合性测试，而不是比对 DOM 结构；为了让比较公平，每个框架都装好官方 MCP 或 skill，但不强制使用；为了避免引导，不指定 SSR 还是 CSR，也不告诉代理之后会用 Lighthouse 测性能与可访问性。

  2. 成本与耗时。最便宜的是 Hono+htmx（$2.67）、Astro（$2.76）、Nuxt（$2.82）与 Vanilla（$2.98），最贵的是 Angular（$4.97）、Gracile+Lit（$4.65）、SvelteKit（$4.28）。耗时 8.2 到 17.2 分钟，token 3.85M 到 9.76M，排序基本一致。SvelteKit 贵有具体原因：代理每一轮都去读 SvelteKit v3 的迁移指南，因为版本太新不在训练数据里；Gracile 则干脆去 clone 仓库、读 node_modules 里的编译产物。

  3. 工具的真实使用率。这一节比排名更有意思：Agent 经常不用现成的 MCP 或 skill。Nuxt 的 MCP 一次没用（0/5），Next.js 的 skill 文件只在 1/5 用到、AGENTS.md 2/5，TanStack Start 的 skill 文件只被 2/5 发现，因为它在 node_modules 里。作者据此说，他怀疑当前这批 MCP 与 skill 可能弊大于利——至少「给框架配了 MCP 就会更省钱」这个假设在这里不成立。

  4. 输出质量。Lighthouse 的性能、可访问性、CLS 三项几乎饱和（性能 97–100），区分不出来。真正有区分度的是传输的 JS 字节：Astro 0KB、Gracile+Lit 8KB、Hono+htmx 18KB，而 Nuxt 84KB、Angular 93KB、React Router 115KB、Next.js 142KB；TBT 同样分化，Astro 与 Hono+htmx 是 0ms，Nuxt 40ms、Next.js 71ms、Angular 103ms。LCP 对单页应用天生不利（Astro 810ms 对 Next.js 2,090ms），而且方差极大——Next.js 五次里有一次偷懒没做图片懒加载，直接把中位数拉坏。

  5. 可维护性。作者只用一个朴素指标：代码行数。Hono+htmx 1,370 行、Nuxt 1,415 行、Astro 1,461 行，Angular 2,009 行、Qwik 1,744 行。在代理时代这个指标的分量变了：代码越少，后续每次编辑要喂的 token 越少，维护成本是实打实的钱。Hono+htmx 用约 70% 的代码做到 Angular 同样的事，而且更快。

我的推荐：排名别照抄——单一应用类型、单一模型、方差很大（React Router 最便宜的一次 $2.82，比 Hono+htmx 最贵的一次 $3.19 还便宜），作者自己也说这更像一个 holotype。值得抄的是实验设计：用符合性测试卡住偷工减料、多次运行报中位数、把性能与可访问性一起当质量、明确承认 Lighthouse 对 SPA 有偏。
