01
今年最值得读的一篇 AI 辅助重写复盘，架构决策和性能数字都能直接借鉴 · ★★★★★ · TLDR

Rebuilding the global town square from scratch

为什么值得看：不是「我们用 AI 写了代码」的口号文，而是给出了三个服务器如何漂移、一台服务器如何按受众分流、以及每一项优化在哪个环境测出来的具体账目。

展开完整精读

一句话判断：这是一篇少见的、把「用 AI 代理重写核心 Web 应用」从口号落到数字的工程复盘，性能账和组织账都算得清楚，值得逐段读。

  1. 重写的理由不是技术时髦，而是三个服务器在漂移。rweb 给真人渲染、rweb SSR 给搜索爬虫、Jetfuel SSR 给未登录可索引页面，同一张页面有三种构建方式，改一个 meta description 或 404 行为要落三个代码库。最讽刺的一点是：爬虫拿到的是服务端渲染好的完整 HTML，而未登录的真人拿到的是应用外壳，要先下 JS、再跑 JS、再请求 GraphQL，最后才渲染。

  2. 新架构的核心是「一台服务器按请求方分流」。真人拿流式 HTML，服务端收到的每个 GraphQL 响应在页面里只出现一次，浏览器用 JSON.parse 回放进 Relay store；经边缘验证 IP 的搜索引擎爬虫拿完整文档，不 hydrate、不带客户端包；链接预览机器人只跑该路由的数据加载和 head 标签，跳过正文需要的 timeline 请求。判断爬虫用验证过的 IP 而不是 User-Agent，理由很实在：UA 判断会把 Lighthouse 一起缓冲，而且任何人改个 header 就能走贵路径。

  3. 性能数字给得很克制。Slow 4G 下首条帖子 23.9 秒降到 2.7 秒；登录态慢网资料页和帖子快 8–13 倍，但 Home 只快 1.7 倍（14.1 秒对 24.6 秒），因为 Home 仍然只在浏览器渲染——作者自己承认这是还欠的账。启动文件数从 754 压到 182、从 582 压到 10，原因是 Chrome 单条 HTTP/2 连接上大约只并发 100 个请求，754 个文件意味着八轮往返。

  4. 爬虫侧的细节最容易被忽略但最值钱：Googlebot 只读响应的前 2MB，而长贴的 HTML 跑到 2.2–3.5MB，于是截断后的结构化数据指向了它根本没看到的帖子。三个修法都很朴素——图标从每条帖子内联改成页面顶部隐藏 sprite（省 165–340KB），图片的结构化数据不再重复帖子正文和图片 URL（省 450KB），爬虫文档不再带只有 JS 跑起来才有用的时间戳脚本、路由状态、骨架屏和登录按钮（省 54KB）。另外把 Relay 的规范化 store 换成原始 GraphQL 响应文本，体积直接降到四到五分之一。

  5. 组织层面最有参考价值。五个人加代理半年出第一版，前提是三件事：根目录一份 AGENTS.md 统一写法（具名导出、不用 barrel 文件、信任边界校验外部数据、哪类测试值得写）；仓库里放 25 个以上按步骤执行的 skill（写 commit、开与叠 PR、过 CI、改依赖、加翻译）；把约定变成 lint 规则，包括一个 anti-slop 插件，专门拒绝代理爱写的链式类型断言、把参数写成 unknown、对空对象做条件展开。作者自己的总结是：旧服务器就是最好的规格，代理照着它移植行为、写测试钉住，评审再对着原实现核。这也解释了为什么这次重写没像大多数重写那样烂尾——不是代理更聪明，是规格足够硬。

我的推荐：如果你只读一篇，读这篇。它同时回答了两个当下最实际的问题——AI 代理能把多大的工程压缩到多小的团队，以及速度到底是从哪几个字节里省出来的。注意所有数字都是实验室单机结果，作者自己也留了这句，现场数据要看 Core Web Vitals。

02
安全行业的成本曲线被改写：单个内核提权漏洞的发现加利用只要 1279 美元 · ★★★★★ · TLDR AI

A thousand fewer paths to root

为什么值得看：给出了完整流水线每一阶段的 API 成本、成功率与失败原因，还公开了两个反直觉发现：模型会把错归因到别的 0-day，以及更强的模型需要更少的编排脚手架。

展开完整精读

一句话判断：这篇的价值不在「AI 会挖漏洞」这个结论，而在它把一条完整攻击流水线拆成五段，逐段报出成本和失败率，让防御方第一次能量化自己的处境。

  1. 流水线是五段：侦察代理先圈出可被低权限用户触达的审计目标（5034 个目标、约 280 万行、占内核 7%，只花 3426 美元），分析代理在 12 小时内产出 2308 个去重后的候选（31.6 万美元），triage 代理在带 KASAN 的隔离虚拟机里逐条复现，30 小时内复现 1724 个（7.3 万美元），再利用阶段区分信息泄露与本地提权并真的把 root shell 打出来，最后生成补丁并交人工复核。

  2. 成本结构里最值得记的两个数：成功的利用平均 359 美元，失败的尝试平均 3922 美元——贵在少数难啃的竞态条件上。作者直接说，如果早设一个「一小时无进展就放弃」的条件，这一阶段能省很多。另一个数是静态分析误判只占 3.1%，其余未复现的多数是需要更高权限、需要特定触发条件（比如某一行上的分配失败）或验证太耗时。

  3. 两个反直觉的发现值得单独拎出来。第一，早期一次运行报告 200 个成功提权，人工复核发现其中 20 个是通过另一个 0-day 拿到 root，而不是被指派的那个漏洞——也就是说「结果对了」不等于「路径对了」，之后他们加了独立校验。第二，重型编排会随模型变强而失效：把 103 条内核利用技巧整理成模型友好的格式喂进去，GPT-5.5 的成功率从 76.2% 升到 88.9%，同样一套东西给 GPT-5.6 只多 1.5 个百分点，于是整层被删掉。这对所有做 agent harness 的人都是一记提醒：你的脚手架可能只是在补上一代模型的短板。

  4. 经济账算得很直白。7 月的 GPT-5.6 Sol 跑出 166 个唯一提权漏洞，成本 51.4 万美元；10 月的新模型在同样加固过的代码上跑出 948 个，超过五倍。按 Pwn2Own 两万美元、TyphoonPWN 七万美元的历史赏金折算，这批漏洞值 1890 万到 6630 万美元。在 kernelCTF 的加固环境里，112 小时、3.3 万美元换来 21 个提权利用，对比 2026 年全年被接收的 26 个确认 0-day，这个比例很刺眼。

  5. 对普通工程团队的实际含义，作者写得很克制但很重：中期内，一台没打全补丁的机器上的低权限账号，对资源充足的攻击者应当视同 root。所以纵深防御不是口号——Firecracker、gVisor 这类隔离是在限制爆炸半径；同时他们建议把「默认写安全代码、砍掉不必要的功能面、形式化验证」当作与「找漏洞」并列的投入方向。顺带一个细节：他们在测试基础设施里也发现了 QEMU TCG 的漏洞，说明攻击面包括你自己的靶场。

我的推荐：无论你做不做安全，都该看第 3 节和第 5 节。前者是「自主代理的结果必须验路径」的最好案例，后者是未来两三年基础设施假设要改的地方。

03
Go 1.27 的 encoding/json/v2 落地，老代码可以不迁，但新代码没有理由再用 v1 的默认语义 · ★★★★★ · TLDR Dev

A new Go API for JSON

为什么值得看：官方把六年设计一次讲清：v1 的哪几个默认行为是安全隐患、v2 如何拆成语法层与语义层、以及 v1 其实是用 v2 的兼容选项实现的，所以可以逐调用点迁移。

展开完整精读

一句话判断：这是一篇可以直接改变你下一个 Go 服务默认值的文章，而且它难得地把「为什么不原地修」讲透了。

  1. v1 的问题分三类。行为上：接受非法 UTF-8（RFC 8259 要求合法）、接受重复成员名（作者点名 CVE-2017-12635 就是这类歧义被利用）、把 nil slice 和 map 序列化成 null 让别的语言反序列化报错、反序列化时对字段名做大小写不敏感匹配、指针接收者的 MarshalJSON 调用不一致。API 上：json.NewDecoder(r).Decode(v) 不拒绝尾部垃圾，选项只能挂在 Encoder/Decoder 上、传给 Marshal/Unmarshal 就没法用，也无法沿调用栈下传——DisallowUnknownFields 遇到自定义 UnmarshalJSON 直接失效。性能上：MarshalJSON 强制分配 []byte 且框架要把结果重新解析校验再按缩进格式化，UnmarshalJSON 强制先把整个值解析一遍找边界、方法内再解析一遍，等于两次解析。

  2. 解法是把语法和语义拆开。jsontext 只处理 JSON 语法，不依赖反射，Encoder/Decoder 真流式，能读写 Value 和 Token；json/v2 在它之上做 Go 值与 JSON 之间的映射。于是有了 MarshalWrite/UnmarshalRead（直接吃 io.Writer/io.Reader）和底层的 MarshalEncode/UnmarshalDecode，选项成为每个函数的头等参数。

  3. 性能提升的来源不是微优化，而是接口形状。新的 MarshalerTo/UnmarshalerFrom 拿到的是 Encoder/Decoder，实现可以纯流式写读，框架既不用校验返回的字节是否合法 JSON，也不用先扫一遍找值边界。基准上 Unmarshal 快至 10 倍，Marshal 基本持平；文中举的 kube-openapi 例子很具体——在 UnmarshalJSON 里递归解析 OpenAPI 规范会拖垮一个 Kubernetes 服务，换成 UnmarshalJSONFrom 后好了几个数量级。

  4. 兼容性设计是这篇最容易被略过、但对存量项目最关键的部分：v1 在新版本里就是用一整套 v1 兼容选项实现的 v2。这意味着两个版本可以互相调用——你的包用 v2，依赖的包还在用 v1 的 MarshalJSON，照样工作；反过来也成立。所以迁移可以逐调用点做，甚至可以只改一个行为，例如 json.Marshal(..., json.DefaultOptionsV2(), jsontext.AllowDuplicateNames(true)) 保留 v2 语义但放过重复键。

  5. 几个默认行为的变更要提前知道：重复成员名和非法 UTF-8 会直接报错，这意味着某些线上流量以前能解析、升级后会 400；字段匹配改成大小写敏感，靠宽松匹配兼容过的客户端会露出来；omitempty 重新定义为「编码后是 null、空串、空数组或空对象」才省略；time.Duration 不再有默认表示，直接序列化会报错。这些都不是 bug，是修正，但每一条都可能变成升级当天的告警。

我的推荐：先读「Behavior differences」和「Compatibility」两节，再决定你的服务是直接切 v2 还是先加兼容选项。对写库的人，把自定义 MarshalJSON 逐步换成 MarshalJSONTo 是当下性价比最高的性能动作；对写业务的人，至少知道升级后哪些输入会开始报错。
