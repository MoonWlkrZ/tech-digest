agent 延迟优化的一线清单，方法可迁移 · ★★★★★ · TLDR

Making agents fast - what I've learnt over the last 12 months

为什么值得看：作者把 Web 性能那套度量搬进 agent：TTFT 与 tok/s 分工、thinking budget 是最便宜的加速、以及靠读思维链反推 agent 想要什么工具。给的是可照着查的顺序，不是泛泛建议。

展开完整精读

一句话判断

这是把 Web 性能优化的老手感搬到 agent 上的一线总结，最有价值的一段不是推理速度，而是「先读思维链，再决定给 agent 造什么工具」。

1. 推理侧先拆成两个数

TTFT（首字延迟，包含 prefill）和 tok/s（出字速度）。短回合、多来回报文的 agent 工作流里 TTFT 更关键；让模型输出代码或长文档时 tok/s 更关键。同一模型不同供应商之间的速度差距巨大，还有明显的 noisy neighbour：TTFT 突然变高可能是排队、被分到更慢的硬件或 prefill 竞争，tok/s 下降可能是硬件更慢或批量更大。

2. 最便宜的加速是降 thinking budget

作者直说自己反复忽略这一点：一个 fast tier 模型把思考开到 max，比一个 slow tier 模型用低档思考慢得多，定量比较 tok/s 和 TTFT 很容易把这一项盖过去。

3. 推理往往不是大头

他给的经验数字是：把推理时间减半，端到端任务只快约 20%，因为 provisioning、工具调用、挂起恢复的时间没变。所以真正的战场在工具调用。

4. 工具调用的经典坑

agent 用 xargs -I{} 扫大量文件时会产生几十万次进程启动，在沙箱里尤其慢；很多 harness 每条命令都新开 shell，.bashrc 里的 nvm 之类会把启动时间吃光；宽口径的 awk 会把几千 token 喂进上下文，而未缓存输入直接推高 TTFT。给 agent 一个能精确查询的 SQL 数据源，通常比让它自己扫文件更好。

5. 方法：读 thinking，给它想要的工具

开源权重模型的最大优势是可以读思维链。做法是先列慢调用，再看紧挨着的那段 thinking，模型常会写下「本可以做 X，但不行」，照着把工具补上就行。for 循环里带 sleep 是明确信号：它在轮询一个本该被通知的事件，说明外部服务需要异步回调。另外别忽略硬件和沙箱：Zen 4c/5c 核比全尺寸核慢很多，网络盘换本地 NVMe 是数量级差别，copy-on-write 快照会拖慢文件 IO；MicroVM 的恢复速度是纸面指标，页面要按需换入，挂起前应杀掉 headless 浏览器和自建服务；沙箱里 IPv6 坏掉会让每次 AAAA 查询都等超时。

我的推荐

要给 agent 提速，按这个顺序查：thinking budget → 工具调用 trace 与数据源形态 → 并行化 → 硬件与沙箱。换供应商放在最后。

能力扩散的安全拐点，有可验证的数字 · ★★★★★ · TLDR AI

Open-weight AI models can exploit the patch gap

为什么值得看：GLM 5.3 只用发布当时公开的信息，攻破六个 Firefox 版本，单版本边际成本约一千美元，全程没有触发任何供应商护栏。这是补丁窗口第一次被开源权重模型稳定利用。

展开完整精读

一句话判断

开源权重模型加上补丁窗口，把过去只有前沿实验室能做的事变成了一千美元一次的常规操作，这份报告应当当作威胁模型更新来读。

1. 实验做了什么

Epoch AI 用智谱 8 月发布的开源权重模型 GLM 5.3，任务是造一个网页：Firefox 用户访问后，浏览器读取本地文件并回传给攻击者，不需要任何额外交互，拿到的足以是浏览器里保存的密码和登录 cookie。

2. 结果有多硬

9 月 17 日到 10 月 26 日之间的六个 Firefox 版本（156.0、156.0.1、157.0、157.0.1、158.0、158.0.1）全部被攻破，且只用各版本发布当时已经公开的信息。最快的一次用了 12 小时；单版本边际成本约 1000 美元 API 费用，整个研究的 API 支出超过 10 万美元。同期用同样方法打 Chrome，花掉约 10 万美元没有成功，作者不认为这构成 Chrome 安全的证据。

3. 机制是补丁窗口

修复先进入 beta / nightly，代码公开可读，攻击者能反推漏洞在哪里。Mozilla 会把安全修复伪装成普通改进，GLM 5.3 仍能把它们挑出来。最终攻击链是两条：补丁窗口里的漏洞拿到渲染进程内的代码执行，加上模型每次自己重新发现的一个未公开漏洞，用来绕过沙箱读到文件系统。

4. 护栏一次都没触发

作者刻意把环境做成「技术不高、预算有限的攻击者」能做到的样子，通过官方 API 和第三方 API 调 GLM 5.3，没有任何供应商（包括 Z.ai）拒绝或拦截，尽管行为与真实攻击者无法区分。那个未公开漏洞已报给 Mozilla，10 月 27 日发布的 Firefox 159.0 修掉了它。

5. 结论是结构性的

只给防守方开放更强的闭源模型解决不了问题：补丁一旦公开，就等于标出了漏洞的位置。可用的手段是延后公开修复直到能一起发版、缩短 beta 到正式版的时间（Firefox 与 Chrome 都已开始按周发版）、避免把可以串联的多个修复放进同一次更新。作者判断更新更慢的手机系统与路由器固件风险更高，闭源项目同样不免疫，Anthropic 已演示过在 Windows 上利用补丁窗口。

我的推荐

如果你维护的产品有公开的 nightly 或 beta 分支，这就是你的暴露面清单：先量一遍从修复合入到全量上线的窗口有多长，再决定要不要改变发版节奏。

生产规模落地复盘，指标可对标 · ★★★★☆ · TLDR AI

Catching Bugs Before They Land: JiTTesting's Human-on-the-Loop Approach at Full Scale

为什么值得看：重点不在「LLM 会写测试」，而在工程侧：两条生成流程、LLM 集成判断加规则判断压误报、以及 human-on-the-loop 的分工。带真阳性率与 SEV 拦截量，可以直接拿去和团队现有方案比。

展开完整精读

一句话判断

这是目前公开材料里少见的 LLM 生成测试规模化落地复盘，真正值得抄的不是模型能力，而是把误报压到工程师愿意打开的那套工程。

1. 思路与 LLM 代码评审不同

常见做法是让模型像评审者一样读 diff 找问题，Meta 的 Catching JiTTests 反过来：生成「注定失败」的可执行测试，用行为差异证明这次改动确实改变了什么。代价是计算步数更多，好处是能抓到评审类方法抓不到的 bug 类别。

2. 两条并行的生成流程

dodgy diff 把每个 diff 当成一个变异体，生成能区分它与父版本的测试，不提意图；intent-aware 先让模型从代码、标题和描述里推断改动意图，再描述实现这个意图时可能出的错，据此造出变异体并逐个「杀死」。两条流程产出的都只是 weak catch，也就是候选，需要后续判定真假。

3. 误报治理才是核心工程

LLM-as-Judge 用多个 SOTA 模型的判断做集成，输入是候选测试代码、执行结果（失败码、消息、执行轨迹）、diff 和推断出的意图；RubFake 提供规则式的、确定性的判断。两者合成一个总体排名，决定要不要打扰人。作者点明 LLM 判断语义丰富但不确定、难以复核，规则判断可验证但不灵活，所以要两条腿走路。

4. 人是 on-the-loop 而不是 in-the-loop

工程师定标准、看聚合结果，不需要逐条读测试代码，只需要确认某个观测到的行为变化是否是本意。系统夜里用空闲算力跑，只挑前一天被 Diff Risk Score 一类机制判为有风险的 diff，避免拖慢提交速度。

5. 数据

589 名工程师（占被触达者的 64%）实际用过并认为结论可执行，真阳性率 60%；2026 上半年在 diff 阶段抓到 74 个严重（SEV）隐私 bug，没有流入生产，同期隐私类 SEV 下降 20%。

我的推荐

团队在争论「AI 写测试值不值得」时，用这三个指标对齐就行：真阳性率、工程师触达率、按 SEV 计的拦截量。先只对高风险 diff 跑，比全量铺开更现实。
